## 1. CAN バスとフレーム

### CAN バス名は udev で個体固定する

`can0`/`can1`/`can2` は USB 列挙順で入れ替わり、番号が入れ替わると C620 に EDULITE 用の
コマンドが飛んでモータを壊す。バス名は `can_m3508` / `can_edulite` / `can_generic` /
`can_dm3520` で、STM32 UID 由来の serial に紐付ける。

### Damiao DM3520 は専用バス（`can_dm3520`）に載せる

相乗りできる既存バスが無い。本機は 11bit 標準 ID を帯で使い、受信 ID の**下位 8bit だけ**を
見て自分宛かを判定する（`0x000+ID`=特殊コマンド / `0x100+ID`=位置速度指令 /
`0x200+ID`=速度指令）。`can_generic` は `E_STOP` / `SET_TARGET` / `SET_PARAM` の 3 帯が
そのまま重なり、`can_m3508` は C620 のフィードバック `0x201`〜`0x204` が本機から見て
**速度指令**になる（発生源がモータ自身なので PC を止めても流れ続ける）。`can_edulite` だけは
ID 空間が分かれる（29bit 拡張専用 vs 11bit 標準専用）が、それは「本機のファームが拡張
フレームを確実に無視する」というマニュアルに無い前提に寄りかかるので採らない。

### CAN ID はバス単位でロボット横断に一意

メインハンドとサブハンドは物理的に同じ `can_edulite` / `can_generic` を共有する。重複すると
受信ループが最初にマッチした 1 台で打ち切るため、もう一方は永久にフィードバックを得られない
（`tests/test_robot_sequences.py` が固定）。

`generic` の `can_id` は `0x01`〜`0xFE`（仕様書 §2.2）で、`lib/config_schema.py` の
`CAN_ID_RANGES` と `lib/drivers/generic.py` の両方が弾く。`0xFF` を許すと
`activation_steps()` の緊急停止**解除**フレームが `0x0FF` ブロードキャストになり、共有バス上の
全基板のラッチが外れる。**これは「モータ 1 台の `can_id` に `0xFF` を書いてはならない」という
話**で、サーバーが解除時に全バスへ流す意図的なブロードキャスト解除とは別物である —— 前者は
1 台への指令のつもりが全基板へ効く事故、後者は全基板へ効かせることが目的。

### DM3520 の ESC_ID は `0x01`〜`0x0F` に限り、MST_ID は下位 8bit を衝突させない

フィードバックには CAN ID の**下位 4bit しか載らない**（`D0` = エラー<<4 | ID下位4bit）ので、
下位 4bit が重なる 2 台は原理的に区別できず、2 台目のフィードバックが 1 台目の状態を上書き
する。範囲を下位ニブルへ閉じれば「ID が違う = 下位 4bit も違う」が構造的に成立する。

副次的に、パラメータ応答との取り違えも無励磁時だけに閉じ込められる —— 両者の `D0` が
一致するには `エラー == ESC_ID>>4` が要るので、`0x0F` 以下なら「エラー == 0 = 無励磁」に
限られる（出荷値の `0x010` 台を許すと**通常運転中に成立する**）。

MST_ID はどの ESC_ID とも下位 8bit が一致しない値にする（本機は受信 ID の下位 8bit だけを
見るので、一致するとフィードバックが指令として解釈される）。実機は `0x01`/`0x02` +
MST_ID `0x11`/`0x12` に書き換え済み。検査は `lib/config_schema.py` の
`_check_dm3520_master_id_collisions` が起動時に行う。DM3520 の出荷値は 2 台とも
ESC_ID == MST_ID なので、ESC_ID だけ書き換えて MST_ID を書き換え忘れた個体もここで弾かれる。

**1 ロボットの config ファイル内で閉じた検査**にしてあるのは、`can_id` の重複検査
（`lib/can_manager.py` の `add_motor`）と違い `can_dm3520` が現状 1 ロボットの config でしか
使われないため（ロボット横断の `can_id` 重複は 1 つの `CANManager` からは検出できず
`tests/test_robot_sequences.py` の静的テストが担うのと対称的な制約）。

### EDULITE 05 の出荷時 ID は 2 台とも `0x7F`。バスへ載せる前に 1 台ずつ書き換える

書き換えは `scripts/edulite_set_id.py`（走査 → 書き込み → 照合）で、ID の組み立ては
`Edulite05Driver.encode_set_id()` にしか無い。**同じ ID の個体が 2 台ぶら下がった状態で
書き換えてはならない** —— 1 通の書き換えフレームを両方が受け取り、**両方とも同じ新 ID に
なる**（走査で複数応答を見つけたらツールが拒否する）。

書き換えは起動・励磁・動作確認のどの手順にも混ぜない（混ざると電源を入れ直すたびに ID が
書き換わる）。走査は `disable` フレームで行う —— 無励磁を保ったまま応答を返させられる唯一の
フレームで、障害フラグも握り潰さない。

**書き換えフレームの宛先は「現在の ID」のままにする。新 ID を宛先にしてはならない** —— まだその
ID を名乗っていないモータへ宛てることになり、1 台も受け取らない。新 ID はデータエリア 2 の上位
バイトへ、`host_id` は下位バイトへ載せる。症状は「書き換えツールを走らせたのに ID が変わらない」
だけで、出荷値が 2 台とも `0x7F` である以上、書き換えられないまま同一バスへ載せる事故に直結する。

### 受信は 1 通ごとにエグゼキュータへ往復してはならない

`run_in_executor(bus.recv)` はスレッドの起床とイベントループへの復帰を伴い、実測 168us/通。
C620 は 1 台 1kHz を流すので M3508 2 台 + `can_generic` で 4200 通/秒になり、**受信だけで
1 コアが埋まる**（実測 83.5%）。追いつかない分はカーネルがソケットバッファ溢れとして捨て、
実機では `can_m3508` の受信 369 万通に対し **77 万通（17%）が `rx_dropped`** に積まれていた。
捨てられた窓は M3508 の累積角に化ける。

`fileno()` を持つバスは fd を `loop.add_reader` に載せて起こしてもらい、起きたら滞留を
`recv(0)` で出し切る（`_ReadableFd`。1 通 47.5us / CPU 34.8%）。`fileno()` を持たないバス
（`--dry-run` の virtual バス）だけが従来のエグゼキュータ経由へ落ちる。

**復帰待ちのあいだは `remove_reader` で監視を外す** —— down した socket は「読める」と報告され
続けるので、載せたまま待つとイベントループが毎周期起こされ、素の `continue` と同じく位置制御
ループの周期を巻き添えにする。**取り込み中に失敗しても、既に引き取った分は捨てない**
（カーネルのバッファから出したフレームはもうどこにも残っておらず、捨てればその窓は永久に
失われる）。

### 受信フレーム 1 通の失敗を、そのバス全体の失敗にしない

バス上に解釈できないフレームが流れるのは構成上の正常である（`can_edulite` / `can_generic` は
2 台のロボットで物理共有している）。`_dispatch_frame` は宛先判定とデコードを**モータ 1 台
単位**で囲い、落ちるドライバがいても他モータ宛のフレームは配り続ける。ここを素通しにすると
受信タスクが死に、しかも `_tasks` を誰も await しないので例外は消え、**そのバスの全モータが
永久に STALE・UI は「接続中」のまま**という最も復旧しにくい壊れ方になる。3 つの約束:

- **`_last_rx_at` はデコード成功後にのみ更新する。** 解釈できていないフレームを「受信できて
  いる」と記録すると、途絶検出そのものが効かなくなる
- **握り潰した件数は `rx_error_count` に積むが、`BusHealth` の判定は動かさない。** 解釈できない
  フレームで DEGRADED を出すと、本物の送信障害の警告まで信用されなくなる。実害はそのモータの
  `MotorHealth.STALE` として別に現れる
- **`bus.recv` 自体の失敗でも降りない。待って呼び直し、そのあいだ `rx_down` を立てる。**

### `bus.recv` の失敗で受信ループを降ろしてはならない

かつては「回り続けても無意味」として伝播させていたが、その前提は実測で覆った ——
SocketCAN の socket は `ip link` の down/up を跨いで生き残り、up 後は同じ socket のまま受信を
再開する。`bus.recv` を失敗させる事象 —— `cbc-can-watchdog.service` による bus-off 復旧の
down/up / `ip link set down` / CANable の抜き差し / `setup_can.sh` の再実行 / udev 経由の
`cbc-can.service` 再起動 —— はどれも 1 秒以内に戻る一過性のものなので、同じ `Bus` のまま
recv を呼び直すだけで復帰する。

降りる実装だと**送信側だけが次の周期で自動復帰し、受信は二度と戻らない** —— 症状は「指令は
効くのにフィードバックだけ永久に無い」で、UI は接続中のまま全モータが STALE のまま試合を
終える（実機で発生済み。`ip link` 再設定の 0.6 秒後に受信ループが死に、以後 3 分間 1 通も
取り込まないまま手動操縦だけが効き続けた）。**送信側（`PeriodicTask._run`）は tick ごとに
例外を握って回り続けるので、受信側だけが片道だった。**

`cbc-can-watchdog.service` を入れた以上この再試行は必須で、降りる実装のままだと「ウォッチ
ドッグがバスを直したそのときに受信が永久停止する」という、直すほど壊れる関係になる。

素の `continue` にしないのは、戻らないインタフェース相手に全速で失敗を繰り返すと 1 コアを
食い潰し、**同居する位置制御ループ（200Hz）と偏差監視（50Hz）の周期まで巻き添えにする**ため。
ログは `LogThrottle` を通す。ただし黙って回り続けてもならない —— 読めていない間は
`BusHealth.DOWN` として必ず見えるようにする（`bus_off` とは原因も手当ても別なので相乗りさせ
ない）。**復帰を確定してよいのは実際に 1 通読めたときだけ** —— python-can の socketcan は
select がタイムアウトすると socket に触れずに `None` を返すので、down 中も `None` は返り続ける。
これを復帰扱いにすると `rx_down` が数十 ms で勝手に外れ、画面は「読めていない」ことを一度も
出さない。

### SocketCAN のエラーフレームはモータへ配らない。鮮度も動かさない

`_handle_error_frame` が bus-off / 復帰の判定だけに使い、`_dispatch_frame` へは流さない。流すと
エラー種別のビット列がそのまま `arbitration_id` として宛先判定に掛かる。DM3520 の MST_ID は
`0x11` / `0x12` で、**`CAN_ERR_TRX|CAN_ERR_TX_TIMEOUT` の `0x11`、`CAN_ERR_TRX|CAN_ERR_LOSTARB`
の `0x12` と衝突しうる** —— つまり**バスのエラーがモータの実測角として取り込まれる**（起動時の
`CTRL_MODE` 書き込みの応答を取り込むのと同型の事故で、励磁した瞬間に機構が飛ぶ）。鮮度
（`_last_rx_at`）を動かすと、エラーフレームは「モータからの応答」ではないので**本物の途絶が
見えなくなる**。

### 宛先判定は CAN ID だけでなく DLC も見る

`GenericDriver.matches_feedback` / `matches_info` は長さの足りないフレームを「自分宛ではない」
として無視し、例外を投げない。`FEEDBACK` の DLC は可変（状態フラグ 1 バイト + 位置を持つ基板
だけ 2 バイト）なので `== N` では書けないが、**状態フラグすら無いフレームを claim すると
`update_state` が `d[0]` で `IndexError` を投げる**（`INFO` 側も 3 バイト未満だと `decode_info`
が `d[2]` で落ちる）。`_dispatch_frame` がそれを握って `rx_error_count` を積むので、「解釈でき
ないフレームは自分宛ではないとして無視する」というこのメソッド自身の宣言に反する。リモート
フレーム・ノイズ・他プロトコルの相乗りで実際に流れうる。`Edulite05Driver` / `Dm3520Driver` が
`len(msg.data) != 8` を見ているのと同じ理由。

### `CANManager` は `can.Bus` そのものを外へ渡さない

外へ出すのは `bus_names`（バス名のタプル）だけで、送信は必ず `send_to_bus` を通す。生のバスを
掴むと `send_to_bus` を経由しない送信ができてしまい、**送信失敗が `tx_error_count` / 送信エラー
スコアに載らない** —— つまり**ヘルスが「正常」と言い続ける経路**ができる。同じ理由で `motors` /
`sensors` も `MappingProxyType` で返す（書き換え可能な dict を渡すと `add_motor` 以外の登録経路が
生まれ、名前・can_id の重複検査を素通りしたモータが混ざる）。

### CAN ID のコマンド種別は調停順に合わせる

CAN は ID が小さいほど優先なので、`E_STOP` を最小（`0b000`）に置く。かつては `0b111` で、
ブロードキャスト停止の `0x7FF` は Standard ID 全 2048 個のうち**最も優先度が低かった**。
止めるフレームが目標値やフィードバックに追い越される設計は、デバイスを増やすほど悪化する。

### デバイス ID は固定ビット分割（種別 2bit / 基板番号 3bit / スロット番号 3bit）

サーボ基板は `0x40`〜`0x7F`、DC 基板は `0x80`〜`0xBF`。**帯も刻み幅も連続ブロック性も要らない**
（かつては 4 つの規則が重なり、しかもサーボの DIP 4bit に対して帯が 3 枚分しか無いという
噛み合わない状態だった）。範囲外は未設定へ倒す — 黙って丸めると DIP を回しすぎた基板が別の
基板の ID を名乗る。`candump` の ID からどの基板のどのスロットかが直接読めるのも利点。

### CAN 上を流れる数値はすべて int16 の固定小数点。float は 1 バイトも流れない

float32 をやめたのは NaN の防御をプロトコル全体から消すため。NaN は比較がすべて false になる
のでクランプも範囲チェックも素通しし、一度内部へ入ると「無言で止まったモータ」になる
（診断ビットも到達フラグも立たない）。かつては 5 箇所で防いでいたものが、「シリアルデバッグの
float を変換する 1 箇所」（`motorcan::toRaw`）だけになった。

### フレームは頭から詰め、空きは末尾へ寄せる

`FEEDBACK` は状態フラグ 1 バイトが先頭で、位置を持つ基板だけが 2 バイト足す（DLC 可変）。
全基板が必ず持つものを先頭に置かないと、位置を持たない基板まで同じ長さを送ることになる。
速度・電流・温度はプロトコルから外した（どちらの基板も測る手段が無く、常に 0 を運ぶと UI にも
ヘルス判定にも「測ったように見える 0」が流れ込む）。

## 2. 制御ループと軸

### M3508 の累積角は「フィードバックが途切れていない」ことに立っている

単回転角のアンラップは「半周を超える差分は 0 を跨いだ折り返し」という推定で、1kHz で届き
続けている間しか成り立たない。途切れた窓でモータ軸が半周以上回ると方向を取り違え、累積角に
360deg が乗る —— `y_axis` の scale では **6.54mm** で、`sync_tolerance` は現在 10.0mm。
1 回転の注入はこの内側に収まるので**注入 1 発では止まらない**（検出経路は再アンカーの
WARNING だけになる）。窓は CAN 受信の中断で実際に開く。

`M3508Driver` は窓を跨いだ推定を拒み、差分を積まずに再アンカーする（1 回転を捏造するより、
誤差を窓の中の実移動量に留めるほうが小さい）。**再アンカーしたことは必ず報告する** ——
`health_detail()` が `MotorHealth` を WARNING へ倒して `MotorHealthInfo.detail` に理由を載せる。
黙って再アンカーすると、位置がずれたまま平常どおりに見える機体ができる。信頼を戻す経路は
原点の確定だけで、受信の復帰では戻らない（ずれは復帰しても消えない）。

**到達判定も累積角で行う。単回転角（`MotorState.position`）と比較してはならない。** 位置制御
ループは累積角を目標値として扱うので、単回転角と比べると**次元が食い違う** —— 何回転もする軸で
ラップ角がたまたま目標と一致した瞬間に**誤到達**し、シーケンスは機構がまるで違う場所にいるまま
次のステップへ進む。位置フィードバックの定義は `feedback_position()` の 1 箇所に置く（到達判定と
偏差監視で別々の定義を持つと、片方だけ直したときに気付けない）。

### 窓の長さはフレーム自身のタイムスタンプで測る。処理時刻で測ってはならない

カーネルがフレームを捨てているとき、残りは滞留から詰めて処理されるので**処理間隔は 1ms 程度
にしか見えない** —— つまり両者が食い違うのは、この判定が要る場面だけである。処理時刻
（`time.monotonic()`）で測っていた頃は、巡航 200mm/s（モータ軸 1834rpm）でわずか **16ms 分**が
捨てられるだけで折り返しを逆向きに読み、**累積角へ 360deg = 6.54mm が入りながら再アンカーの
記録も残らなかった**（実機で発生。症状は「何回か動かすと走行中に軸が荒れて同期ずれで緊急
停止」だけ）。時刻を持たないフレーム（virtual バス）と時刻が逆走した場合（NTP 補正）だけ
処理時刻へ落とす。

### EDULITE 05 の生角度は連続化する。読み側だけ直すと軸が 1 回転する

**EDULITE 05 は 1 回転を超える範囲の位置を電源断を跨いで保てない。** 零点そのもの
（`SET_ZERO`）は残るが、**電源投入時に位置の報告値が [0, 360) へ畳み直される**（2026-09-09 実測。
`docs/history/incidents.md`）。`rotate` は `scale` が逆の 2 台の対で、片側は論理角が正であるかぎり
生値が常に負になるため、電源が落ちるたびに構造的に +360deg される。もう片方は範囲内なので動かず、
**左右に 1 回転の差が生まれて `SyncMonitor` が解除のたびに全体緊急停止を掛け直す**（実測の偏差
360.2853deg に対し `sync_tolerance` は 5deg）。

`Edulite05Driver` は前回の**電文値**との差が ±π を超えたら回転数（`_wrap_turns`）を ±1 補正し、
`feedback_position()` = `電文値 + 回転数 × 2π − 原点オフセット` を返す。**原点オフセットも
連続化した座標で控える**（電文座標で控えると、控えた瞬間に回転数ぶんの論理位置が生える）。

**同じ回転数を書き側でも引く。** `encode_target(POSITION)` が書く電文座標は
`(論理値 + 原点オフセット) − 回転数 × 2π` で、**その後で `POS_MIN`/`POS_MAX` のクランプ**を掛ける
（クランプは電文座標で行う。論理値で掛けるとオフセットを足した生値がレンジ外へ出て折り返す）。
読み側だけ直すと `feedback_position()` は正しいまま、指令が**モータの居場所から 360deg 離れた
値**になり、軸が 1 回転する。テストは事故シナリオそのものを置くこと。

**`MotorState.position` は電文の値のまま返す。** 連続化した値で上書きしてはならない —— 診断の
生値カラムはここを読み、畳みが起きたことを人が読み取れる唯一の材料になる。

M3508 と同じく「2 つの電文のあいだに軸が半回転以上動かない」ことに立っている。通常は 20Hz 以上で
受けるので満たし、**電源断を跨ぐ窓は `rotate` が無励磁で自重で回らないこと**（指差喚呼
`rotate_holds`）が人の手で担保している。ここが崩れると、連続化は静かに 1 回転を捏造する。

### M3508 は電流指令しか受け付けない

位置制御は PC 側の PID ループが担う。C620 の電流指令フレーム（`0x200`）は 1 通に 4 モータ分の
スロットを持つため、**同一バス上の M3508 は必ず 1 つの `M3508PositionLoop` が束ねる**
（個別送信すると他モータのスロットを 0 で潰す）。

### DM3520 は位置ループをドライバが内蔵している。PC 側 PID を足してはならない

二重ループになって必ず干渉する。config の `pid: null` が「ドライバ側で制御していて PC 側 PID を
持たない」の単一の表現で、実際に位置制御ループへ載せるかどうかは `main._build_position_loops`
がドライバ種別（M3508 だけ）で決める。

`p_max` / `v_max` / `t_max` は**フィードバックの固定小数点レンジ**で、実機のレジスタ
（`0x15`/`0x16`/`0x17`）とずれると値が比例倍で読める。指令は float なので効かず、症状は
「指令どおり動いたのに到達判定を通らない」だけ。**`p_max` は「動ける範囲」ではなく
「読める範囲」である** —— 位置速度モードの指令は生の float なので `p_max` を通らず、16bit の
フィードバックだけが `[-p_max, +p_max]` へ線形マップされる。ストロークが `p_max` を超える軸は
指令どおり動いた先で位置が読めなくなる（サブハンド前後は 510mm = 545rad なので、出荷値 12.5 では
±11.7mm しか読めなかった。2026-09-09 に 2 台とも 1000.0 へ）。

### DM3520 の位置はロータ角（減速前）。速度だけが出力軸 rad/s である

DM-S3519 のマニュアル §Note 2 は「位置は減速後の出力軸の rad」と書いているが、**実機が正**である
——2 回転ぶんを指令してロータが 2 回転し、出力軸は 2/19.2 回転しかしなかった（2026-09-09）。
したがって減速比 `Gr` = 19.203211（レジスタ `0x14`、読み取り専用）は位置定数の `scale` に
**現れる**（`scale = Gr * 2/(m*z)`）。**一方 `limit_speed`（`v_des`）は出力軸 rad/s** で、
こちらはマニュアルどおり——同じフレームの中で位置と速度の単位系が違う（`mm/s = limit_speed *
(m*z/2)`。ピニオン KHK SS1-36 では ×18.0）。掛け忘れの症状は「指令 113mm でラックが 6mm しか
動かない」だけで、19.2 倍という比が見えるまで機械的な滑りと区別が付かない。

### DM3520 は固定小数点レンジを読み返せるまで励磁しない

`p_max` / `v_max` / `t_max` も `CTRL_MODE` もフラッシュへ保存されず、**電源断で出荷値へ戻る**。
守る形は 4 つ:

- **静的な初期化列（`initialization_steps()`）で書き直してはならない。** 一度そうして実機を
  壊しかけた —— 書き終わるまでの窓でドライバが 12.5 で送ったフィードバックを config の 1000 で
  復号すると位置が **80 倍**に読め、直後の `activation_steps` がその値を「現在角」として保持目標に
  書き、**機構がリミットスイッチを踏み越えて端まで走った**（2026-09-09）。現在角を書いてから
  励磁するのは飛び出しを塞ぐ仕掛けなのに、レンジが食い違う窓ではそれ自体が飛ばす原因になる。
  静的な list は「読み返せたらやめる」を表現できないので、書き直しはここに置けない
- **読み返して食い違いを検出し、書き直し、もう一度読み返す。** 応答が 1 通落ちたときも
  「通す」へ倒さず、`configuration_probe_messages()`（まだ確認できていないぶんだけを返す）を
  `CANManager._confirm_configuration` が空になるまで送り直す。**書いた事実を「一致した」と数えては
  ならない** —— レンジ外の値を書くと実機は元の値をそのまま返すので、成否は読み返しでしか
  分からない（書いた register を控えから外して問い合わせ直す）。**未確認のまま締切を過ぎたら
  拒否する** —— 既定を緩めて解くと、事故の経路が 1 通の取りこぼしで丸ごと復活する。レジスタごとに
  重さを変えないのは、現実の壊れ方が「電源断で 3 つ同時に戻る」だからである（`t_max` は
  `guard.stall_torque` の実効値を比例倍でずらす）
- **書き直してもフラッシュへ保存しない（`0xAA` を送らない）。** 寿命は約 1 万回で、電源が入る
  たびに焼けば確実に潰れる（そもそも保存コマンド `0x7FF` へ `[id_l, id_h, 0xAA, 0x01]` は応答を
  返さず、電源を入れ直すと 12.5 に戻っていた＝焼けていない。2026-09-09）。揮発は承知のうえで**電源が入るたびに書き直す**のが正解。書いたときは
  前後の値を INFO でログに残す —— 無言で直すと、電源が落ちたこと自体が誰にも見えなくなる。
  **ゲートは残す**：書いても読み返しが変わらなければ励磁しない
- **再励磁でも初期化を送り直す。** 物理非常停止は本機の電源を数秒落とすので、`reenergize_motors` /
  緊急停止解除の経路は「電源が落ちたかもしれないところからの復帰」である。送り直さないと
  MIT モードのまま「励磁を名乗るのにトルクが出ない」（`is_energized()` は True、`is_fault()` も
  掛からない）か、80 倍の保持目標に落ちる。**控えてある読み返し結果と書き直しの回数もそこで
  捨てる** —— 起動時の値が残っていると「一致している」と答えてしまい、諦めた回数を持ち越すと
  2 回目の物理非常停止で書き直しが 1 通も出ない。何が揮発するかを知るのはドライバだけなので、
  捨てる判断を `CANManager` 側へ書き写さない。**操縦者が押せるボタンは再励磁だけ**なので、
  書き直しがこの経路で効かないと「人が別ツールでレジスタを書いて起動し直す」まで機体が動かない

拒否の理由は `health_detail()` で `MotorHealth.WARNING` として画面に出す（`is_fault()` には
入れない）。ログにしか出さないと、操縦者からは配線不良と区別が付かない。

### 可動端のインターロックは判断を 1 つにし、指令の瞬間と移動中の両方で効かせる

判断は `MotionGuard.check_limit` だけが持つ。呼ぶのは `AxisHandle.set_target_value`（指令を出す
瞬間）と `LimitMonitor`（移動中の周期監視）の 2 箇所で、**判断を層ごとに書き写すと片方だけ
緩んだ状態が作れる**（左右ペアの偏差判定を `SyncGroup.violation()` へ
一本化しているのと同じ理由）。宣言は位置定数 yaml の `axes.<軸>.guard`（`limits.plus` /
`limits.minus` / `max_step` / `stall_torque`）で、**書かなかった軸は今までどおり素通り**
（既定値で埋めない）。守るのは 2026-09-09 に実機で踏んだ 4 つ —— 押されている端へ進む指令の拒否 /
**離れる向きは必ず通す**（塞ぐと端に張り付いた軸を手動でも戻せず、零点確定の離脱段も成立しない）/
桁の違う目標の拒否 / トルクの立ち上がり。

**1 つの向きには何本でも宣言でき、1 本でも押されていればその向きを塞ぐ。** 左右直結ペアは同じ端に
1 本ずつスイッチを持つ（`y_axis` の左右の原点スイッチ）ので、片方だけ宣言すると守りが半分になり、
しかもどちらが落ちているかは機構が壊れるまで分からない（軸は 1 つなので、片側が端に着いた時点で
その向きへ進める余地はもう無い）。書式は 1 本なら文字列・複数なら並びで、**既存の
`plus: <センサ名>` を書き換えさせない**（書き換える理由の無い差分に紛れて向きを取り違える）。
三値の扱いも変えない —— **複数本のうち 1 本でも `None`（読めていない）ならその向きは塞ぎ、
そのとき文面は読めていない側を先に言う**（端に着いていることは機構の姿勢から読めるが、死んだ 1 本は
画面にしか出ない。「端に着いているのだから当然」で片付けられると、押された 1 本の陰に隠れる）。
**止めたセンサ名は必ず文面に出す** —— 出さないと操縦者は 2 本を順に触って探すことになる。

**零点確定で当てに行くスイッチは、同じ向きの可動端として宣言されていなければならない**
（`AxisSpec` が起動時に突き合わせ、食い違えば**その位置定数ファイルが丸ごと読めなくなる**。起動
そのものは止まらない —— `main._load_position_table_file` が読み込み失敗を「定数なしで起動」へ倒す）。
両者はセンサ名の文字列でしか繋がっていないので、載せ忘れは「探索で当てた後、誰も守らない端」として、
逆側へ載せたのは「守りが反転して押されている端へ進む指令だけが通る」として残り、どちらも機構を
壊すまで出ない。`guard.limits` を書かない軸（歯止めそのものが無い）は対象外。

**`None`（読めていない）を `False`（押されていない）へ丸めてはならない** —— 丸めると配線が抜けた
センサが「進んでよい」に化ける。センサ状態は `MotorGroup.sensor_active`（三値）として
`main._make_sensor_reader` が注入し、未登録・途絶はどちらも `None` を返す。**トルクは「動く指令」に
しか掛けない** —— 実測位置と同じ値を送り直す指令（接触を検出した瞬間の「その場で止まれ」）まで
塞ぐと、押し込む向きの古い目標が生き残る。

**指令の瞬間だけでは足りない。** 小刻みなジョグは 1 歩ごとに判定を通るので端で止まるが、遠い
目標を 1 回書くと、その後スイッチが立っても誰も見ていない —— ドライバは書かれた目標へサーボし
続ける（`sub_y_axis` へ `-450` を 1 回指令し、後端の作動点 `-447.0` を 3mm 越えた）。そこで
`LimitMonitor`（`lib/control/limit_monitor.py`、50Hz）が「**今の実測位置から今書かれている目標へ
向かう向き**」の端センサを見て、押されている／読めていないなら**その場の実測位置を目標へ書き直す**。
目標そのものを書き換えないと、`TargetRefresher` が古い目標を送り直して押し込み続ける
（`HomingRunner` が接触を検出したときと同じ作法）。

**周期監視が見るのは可動端だけ。** `max_step` は「1 指令で実測位置から離れてよい量」の判定なので、
移動中の実測位置に当てると長距離移動の途中で必ず誤発火する。トルクも誤発火が怖いので入れない。
**発火した軸は目標が書き直されるまで記録して撃ち直さない** —— 50Hz で `set_target_value` を
撃ち続けるとバスが埋まる。離れる向きは `sensor_for` が反対端を返すので素通りし、零点確定の
離脱段を邪魔しない。

**周期監視も現在値だけでは足りない。** 20ms ごとに `sensor_active` を読むだけでは、それより狭い
ON 区間を丸ごと落とす（`rotate` はスイッチの 2deg を約 18ms で通過する）—— 零点確定が探索の
到達判定で踏んだのと同じ穴が、走行中の保護側に残っていた。`LimitMonitor` は判定へ渡すセンサ状態を
「今 `sensor_active` が True」**または**「前の周期から `sensor_contact_count` が増えた」で作る
（`main._make_sensor_contact_reader`。零点確定と同じ読み口で、カウンタは読んでも減らないので
基準値は読み手ごとに控える）。**変えたのは入力の作り方だけで、判定は `MotionGuard.check_limit` の
まま**である。三値は潰さない —— `None`（読めていない）は接触の有無に依らず `None` のまま渡し、
**カウンタを提供しないドライバのセンサは従来どおり現在値だけで判断する**（`None` へ倒すと、
カウンタの無い基板に付いたスイッチの軸が 1 歩も動けなくなる）。基準値は 1 周期に 1 度だけ進めるので
同じ接触を二重に数えず、**監視を始める前に数えたぶんは基準値を置くだけで捨てる**（前回の零点確定や
手動操縦のぶんまで見ると、最初の移動でいきなり止まる）。

**保護が介入した移動は `move_to` を失敗させる。** 目標を実測へ書き直すと `is_reached` は必ず
成立するので、放置すると**軸は途中に居るのにシーケンスだけが先へ進む**（黙って別の位置で成功する
機体になる）。`LimitMonitor` は軸ごとに「移動を止めた回数」を単調に数え（`intervention()`。回数と
**直近の理由（センサ名を含む文言）を 1 組**で運ぶ。バラすと理由だけ後から取り直す形が書け、その間に
別の軸で発火すると理由が入れ替わる）、`move_to` が指令の前に控えて到達待ちの後で比べ、増えていれば
`LimitInterventionError` を投げる。**タイムアウトと同じ型で投げてはならない** —— 中身は「待ち時間が
足りなかった」ではなく「機構が端に着いたので保護が目標を書き直した」で、同じ型に混ぜると操縦者は
`timeout_s` を伸ばす側を疑い、配線・向き・スケールの食い違いへ辿り着けない。ただし
**`SequenceTimeoutError` の派生である** —— 移動の失敗を型で拾う既存の経路は保護の介入も同じ扱いで
よく、狭めた型に替えたせいで失敗が握り潰される経路を作らない。**保護の介入と未到達は集めてから
1 つの例外にする** —— どちらかで先に `raise` すると、両方起きた移動でもう片方の軸に何が起きたかが
失敗表示から消える（切り分けは「止められた軸」と「届かなかった軸」の対応で進むので、片側だけでは
辿れない）。**片方しか起きていないときに空の見出しを並べてはならない** —— 単独の失敗が読みにくく
なっては本末転倒で、出るのは起きたぶんだけ。型は保護が 1 件でも絡めば `LimitInterventionError`。
**終了時の状態（`stopped_axes`）を見る方式にしてはならない** ——
接点がバウンドして触れて離れると軸は触れた位置で止まったままなのに状態だけが戻り、逆に前の移動の
ラッチが残っていると次の移動まで巻き添えで落ちる。配線は `main._make_limit_interventions` が
`Sequence.bind_limit_interventions` へ注入する（`bind_homing` と同じ作法。**`lib/sequence/` から
`lib/control/` を import する向きを作らない**ため、`LimitIntervention` は `sequence/engine.py` が
持ち、`LimitMonitor` がそれを import する）。手動操縦は対象外 —— 指令の入口が `GuardViolation` を
拒否として返すので、操縦者には既に見えている。

**書き戻す目標は指令の単位のまま運ぶ。** 実測を値へ換算して指令へ戻すと（`to_commands(to_value(…))`）、
複数モータ軸では平均を挟むぶん往復が丸め誤差を生み、それが非ゼロの `delta` として入口の
`MotionGuard` に届く。誤差が押されている端の向きに転べば**引き戻しの指令そのものが
`GuardViolation` で拒否される** —— 止めるための指令が、止まっていないことを理由に拒否される
逆立ちで、症状は「止めるはずの周期に 1 通も送らず軸が走り続ける」だけ。実測（逆回転ペア・
`scale` 1.0668451）では往復の約 3% で発生する。フィードバックをそのまま書き戻せば `delta` は
厳密に 0 になり、ついでに各モータが**自分の位置**を保持する（平均へ寄せる指令は、止めるべき瞬間に
左右を動かしに行く）。

**「その場で止まれ」を書くのは 3 経路とも同じ形である** —— `LimitMonitor._stop_here` /
`HomingRunner._stop_here`（探索の接触検出・途絶で降りる前・離脱段）/ その口である
`AxisHandle.observed_commands()`。零点確定だけが `to_commands(to_value(…))` のままだと、
`guard:` を書いた複数モータ軸で**接触した瞬間の引き戻しが拒否され、押し込む向きの古い目標が
生き残る**（`y_axis` に `guard:` を書いた時点で踏む）。

**パラメータ読み書きの応答も `MST_ID` で返る**ので、フィードバックとして取り込まないこと
（起動時の `CTRL_MODE` 書き込みの応答が実測角として入り、励磁した瞬間に機構が飛ぶ）。
EDULITE 05 と同じく、**現在角を目標に書いてから励磁する**（モード切替で `p_des` が 0 に落ちて
いるため、書かずに enable するとラックがストローク端まで走る）。

**ここで表現できるのは軸 1 本ずつの条件だけである。** `check_limit` は 1 軸ぶんの引数しか取らず、
「他の軸がどこに居るか」を条件にできない。サブハンドの `sub_y_axis` × `sub_rotate` のような**軸どうしの
干渉**は §4 にあり、守っているのはシーケンスの並びだけである。

### コートで回転と移動の対応が鏡になる軸は `scale` の符号をコート別に持つ

サブハンド昇降 `sub_lift` は同じ回転で青コートでは下へ、赤コートでは上へ動く（リミット
スイッチは重力側に固定）。逆回転を `scale` の符号で表す原則をコートへ広げ、mm の座標系を
両コートで「`+` = 下端スイッチへ向かう」に揃える。**`homing` / `guard` / `positions` / `manual` に
コートの分岐を書かない** —— 変わるのは mm↔rad の換算だけである。書式は
`scale: { blue: x, red: -x }`（`positions` のコート別と同じ）で、変わってよいのは符号だけ
（大きさまで変わると `motion` / `tolerance` の換算もコート別になり、起動時の検証がコートを
知らないまま通る）。

**コートを解決していない `AxisSpec` で換算を呼ぶと `CourtUnresolvedError` になる。** 黙って
片方のコートを採ると、`for_court` を忘れた経路だけが赤コートで鏡になり、config からもログからも
読めない。解決は `AxisHandle` を作る 3 経路（手動 / `move_to` / 零点確定）が `spec.for_court(court)`
で行い、`AxisHandle` 自身も未解決の spec を拒む。`sync_tolerance` との併用は起動拒否
（同期監視は起動時に 1 度だけ組まれ、コートを知らない）。

### DM3520 と EDULITE 05 のフィードバックは問い合わせ駆動。PC が黙ると 1 通も届かない

自分の CAN ID 宛のフレームを受けたときにしか状態を返さないため、`QueryDrivenTargetRefresher`
（20Hz）が送り続ける。**2 種を 1 つのタスクにまとめてある** — 片方だけラッチの規則を直した
状態を作れないようにするため（症状は直し忘れた側にしか出ない）。対象を増やす条件は「自分宛の
フレームを受けたときにしか状態を返さない」ことと `idle_target_value()` を持つことの 2 つで、
`_QUERY_DRIVEN_DRIVERS` が単一情報源。

**EDULITE 05 を対象外にしてはならない** — かつて「ドライバ内蔵の位置ループが目標を保持し、
かつ自発的にフィードバックを返す」として除外していたが後半が誤りで、実機は励磁したまま 13 秒
放置してフィードバック 0 通だった（症状は「手動操縦すると動くのに常に赤い」だけ）。

**目標を持たないモータへも送る**のが `GenericTargetRefresher` との決定的な違いで、あちらは
「目標が無い = 送らない」で正しい（送れば起動直後にコンベアが回り出す）が、こちらで送らないと
操縦していない時間はまるごと `MotorHealth.STALE` になり、症状は「常に赤い」だけで配線不良と
区別が付かない。送る中身は `idle_target_value()` を**ラッチした値**で、毎周期そのときの実測角を
書き直してはならない（負荷で下がったぶんへ目標が追従し、誰も操作していないのに軸がクリープ
する）。緊急停止中も送り続ける（停止中だけ画面から機体の状態が消えるのを避ける。このフレームは
機構を動かせない — 励磁は enable でしか起きず、このタスクは enable を 1 通も送らない）が、
**停止中はラッチを取らず毎回測り直す**（惰走中にラッチすると解除後 1 周期目にその位置へ戻す
動きが出る）。

### `y_axis` は最終目標をステップで PID へ入れてはならない

速度・加速度で制限した中間目標（`lib/control/trajectory.py`）が要る。導入当時の `kp`=32 /
`output_limit`=2000 / `scale`=55.0131 では**偏差 1.14mm で P 項が飽和**し、飽和中の PID は制御
ではなくフル電流の定加速になる。減速に使える距離は移動距離に依らず 1.14mm 固定なのに、そこ
までに乗る速度は移動距離とともに増えるので、**止まりきれるのは移動距離 2.3mm まで**。実運用
ストローク（home 0.0 〜 `work_shared` 650.0mm、シーケンス 1 回の移動は 130〜530mm）はその
外側なので**原理的に行き過ぎる**（最小の移動でも 56 倍）。

`kd` を上げても直らない（飽和中は P+I+D の合計がクランプされ、D 項も出力に現れない）。下げる側も
塞がっていて、当時の想定ストローク L=15mm でも行き過ぎない `kp` は 4.85 まで落ちる一方、実測
では `kp`=16 で左が 1mm も動かなかった —— **単一のゲイン組で短距離と長距離は両立しない。**
制限値は位置定数 yaml の `axes.<軸>.motion` が持ち、書かない軸は従来どおりステップ入力。

**減速の判定に連続時間の `v²/(2a)` をそのまま書かないこと** —— その式は「今の周期に進む分」を
含まないので 1 周期ぶん取りこぼし、実測（200Hz / 60mm/s / 400mm/s²）で最大 0.29mm
（`sync_tolerance` 10.0mm の 2.9%）行き過ぎる。`_stoppable_velocity` は代わりに「この周期に
出してよい速度の上限」を離散時間の停止距離から厳密に解く。

### `motion.velocity_ff` は `pid.kd` と同値に保つ。2 つの config にまたがる対である

`kd` の単位は counts/(deg/s) なので**巡航速度がそのまま制動として出力に乗る** ——
200mm/s = 11003deg/s では D 項だけで −11003counts になり、`output_limit` 5000 を超えて
**逆向きに飽和する**（プロファイルで飽和を消したはずが、速度を上げた途端に別の理由で飽和し
直す）。定常追従では実測速度 ≒ 参照速度なので、参照速度へ同じ係数を掛けて足せばその制動を
ちょうど打ち消せる。

**どちらも実行中に変更できず UI にも配信されない** —— `config` に書いた値がそのまま動いている
値である。対が崩れるのは 2 つの yaml の片方だけを書き換えたときに限られ、症状は「飽和率だけ
上がって速くならない」だけ。突き合わせるときは `config/<robot>_positions.yaml` の
`motion.velocity_ff` と `config/<robot>.yaml` の `pid.kd` を並べて読むこと（起動ログに出るのは
`velocity_ff` の側だけである）。

### 軌道の起点は「前周期に出した中間目標」であって実測位置ではない

毎周期実測から起こし直すと、左右直結ペアの追従誤差の差がそのまま軌道長の差になり、偏差監視が
見ているずれを**能動的に作りに行く**ことになる。実測から張り直してよいのは位置制御へ入る最初の
1 周期だけ（`_anchor_profile`）で、電流 0 に落とすどの経路 —— 緊急停止・フィードバック途絶・
相方の異常・`clear_target`・`pause` からの復帰・開ループ指令 —— でも起点を捨てる。捨て忘れた
経路は「**止まっていた間に進んだはずの中間目標へ復帰 1 周期目に飛ぶ**」という形でしか現れない。

破棄を `profile_anchored` フラグ 1 つに集約してあるのは、`set_target` 側にも再起点を書くと
**層が互いを覆い隠し、片方を外しても検出できなくなる**ため。

**CAN 送信が落ちた周期も同じ扱いで、ここだけは「起点は捨てるが目標は捨てない」。** `_step_locked`
は送信より前に全軸の `profile.advance()` を回し終えているので、機構へ 1 通も届いていない周期でも
中間目標だけが `max_velocity` で先へ進む。据え置くと、送信が戻った最初の 1 周期で PID が「実測と
中間目標の全差分」をステップ入力として受け、**出力レンジいっぱいの電流が 1 発で出る**
（`trajectory` を入れた目的そのものが無効になる）。送信だけが落ちている間は `feedback_timeout_ms`
の途絶判定が立たないので、ここで捨てないと回復する経路がどこにも無い（受信も同時に止まる
down/up では途絶側が捨ててくれるが、qdisc の ENOBUFS はそうならない）。捨てるのは
`_on_tick_error` → `_discard_profile_anchors` で、`pid.reset()` と `profile_anchored` しか触らず
`_reset_axis` は呼ばない —— **目標まで捨てると `wait_reached` が永久に到達せず、送信が 1 周期
落ちるたびにシーケンスが失敗する。**

### 飽和したかは制御周期ごとにその場で記録する

`_Axis.last_output` / `_Axis.saturated` は `_compute_current` が毎周期その場で書き、PID の内部
状態から後で計算し直さない。途絶や緊急停止で PID を reset した後は内部状態が 0 に戻るので、
後から起こすと**「飽和していたのに飽和していないと見える」周期**ができる。同期補正も同じ経路を
通し、**補正込みの出力**で判定する（外して判定すると、実際には上限へ張り付いている周期が飽和して
いないと報告される）。電流 0 に落とす経路（`_reset_axis`）では `saturated` も一緒に落とす
（落とし忘れると「電流 0 に落ちた後も飽和が立ちっぱなし」になる）。

読み手は実機チューニング CLI（`scripts/tune_y_axis.py`）だけで配信にも画面にも出ないので、壊れた
ときの症状は飽和率が実態と食い違うことだけ。調整する人は「`kp` を上げても下げても応答が変わら
ない」という観察から機構の負荷や `output_limit` へ辿り着けなくなる。

### フィードバック鮮度の判定に使う時刻は 1 周期に 1 回だけ取る

`FeedbackFreshness.now()` を 1 度呼び、その値を全モータの `is_stale()` へ配る（呼び出し元は
`M3508PositionLoop._step_locked` / `SyncMonitor.step` / `RobotServer._build_state_message` /
`_sensor_states`）。モータごとに取り直すと、**左右直結ペアの 2 台が別の瞬間で判定され、「片方
だけ途絶扱い」という起きてはならない状態が一瞬生まれる** —— 片側だけ止めると残った側が押し続けて
機構が壊れる、という保護の前提そのものが崩れる。配信側では、同じ 1 通の中に別々の瞬間を基準にした
鮮度が並ぶ。

### 左右ペア軸の保護は 3 種あり、揃うのは `y_axis` だけである

機構的に直結した左右ペアは 4 組（`y_axis` = M3508 ×2 / `rotate` = EDULITE ×2 /
`sub_rotate`・`sub_pitch` = サーボ ×2）で、位置がずれるとその場で壊れる。位置定数 yaml の
`motors:` で 1 論理軸に複数モータを束ね、逆回転は `scale` の符号で表す。保護は①軸単位でしか
指令口が無く左右へ同時に送る ②偏差監視（シーケンス停止 / ループ内 200Hz で電流 0 /
`SyncMonitor` 50Hz で全体緊急停止）③フィードバック途絶をペア単位で判定（片方だけ止めると
残った側が押し続ける）。

**①だけが 4 組すべてに効く。②は `sync_tolerance` を書いた軸（`y_axis` / `rotate`）だけで、
そのうち 200Hz の段は全メンバが同じ位置制御ループに載る組しか登録されない
（`main._attach_sync_groups`）ので `y_axis` のみ。③は `SyncGuard` にしかなく、`SyncGuard` は
`M3508PositionLoop` の中にしかないので `y_axis` のみ。**

サーボ 2 組が `sync_tolerance` を持たないのは意図的で（`FEEDBACK` がクランプ後の指令角の
エコーなので偏差監視が原理的に働かない）、ずれの検出は指差喚呼の目視
（`config/checklist.yaml` の `sub_servo_pair_sync`）だけになる。**サブハンドは
`sync_tolerance` を持つ軸が 1 本も無いので `SyncMonitor` 自体が生成されない。**

**`rotate` は③を持たない。** 片側が途絶すると `SyncMonitor` は比較対象を失い、
`violation()` が `None` を返して連続カウントも捨てる。途絶を見て電流 0 へ落とす経路は
`M3508PositionLoop` にしかないので、**残った側は最後の目標を保持したまま駆動を続ける。**

**`SyncMonitor` の再発回数（`_retrips`）は `reset()` で消してはならない。** 緊急停止の解除は
`RobotServer._reset_sync_latches()` を通ってラッチ（`_violated` / `_counts`）を毎回消すので、
**この数だけが「解除するたび即停止する」状態を跨いで残る唯一の手掛かり**になる。機構が本当に
左右でずれていれば解除 → 即停止は正しい振る舞いだが、操縦者には「解除ボタンが効かない」と
しか見えず、機構のずれと左右の原点の食い違いの区別も画面から付かない。回数は
`SyncMonitor.on_violation` の第 3 引数として `main._make_sync_violation_handler` へ渡り、
2 回目以降だけ理由文（`e_stop_state.reason`）へ「何回目か」と次の一手が足される。
**発報の条件そのものは回数と無関係**で、数えることが境界を動かしてはならない。

**判定と単位換算は `lib/axis_sync.py` に一本化してあり、②の 3 段とも `SyncGroup.violation()`
を呼ぶ。** 段ごとに違うのは頻度と超過後の扱い（debounce・ラッチ・効果）だけで、境界そのものが
ずれてはならない。逆換算を段ごとに書き写すと、符号を 1 箇所落としただけで「ずれていないのに
止まる」か「ずれているのに止まらない」のどちらかになり、しかも片方の段だけが壊れるので
気付けない。`lib/axis_sync.py` は最下位層なので上位モジュールを import してはならない。

### 保護は止めるだけ。駆動中にずれを縮めるのは `sync_kp` だけである

位置制御はモータごとに独立した PID なので、左右で負荷や摩擦が違えば追従差は原理的に残る。
`SyncGroup.corrections()` が「グループ平均へ引き戻す向き」の操作量を各モータの指令単位で返し、
`M3508PositionLoop` が `PIDController.update(feedforward=...)` へ渡す。

**外で足して後からクランプしてはならない** —— PID 側のアンチワインドアップが補正を知らないまま
積分を進め、「補正込みでは飽和していて機構が動けないのに積分だけが育つ」状態になり、拘束が
外れた瞬間に暴走する。

逆回転ペアでは 2 台の補正が同符号・同じ大きさになる（`e_l = -e_r` かつ `scale_l = -scale_r`）ので、
**軸としての運動は動かさず内部のずれだけが縮む** —— この性質が方式の根拠そのものなので `scale`
の符号を落としてはならない（落とすと軸ごと押し動かしながらずれは縮まらない）。

**`sync_kp` を書くなら `sync_limit` は必須**で、書かなければ起動を拒否する（押し合いは機構を
その場で壊すので、`homing.search_distance` と同格の唯一の歯止め）。補正を出さないのは電流 0 の
周期・**全員が位置制御中でない周期**・**左右が同じ軸位置を目標にしていない周期**の 3 つで、
判断はグループ単位（モータ単位にすると、ホーミングの押し当てで片方だけモードが変わった瞬間に
もう 1 台へだけ補正が乗る）。

3 つ目は零点確定の整列段のためで、**左右を意図的にずらす段では補正が整列を打ち消す**（実測で
1mm のずれに対し片側 −440counts・相方 +440counts）。判定は `SyncGroup.targets_share_axis_value()`
（許容幅 1e-6。丸め誤差だけを吸収する値で、`tolerance` を流用してはならない）で、**状態から
毎周期導出する** —— suspend/resume にすると再開の取りこぼしがそのグループの補正を試合中ずっと
殺し、画面にもログにも出ない。**止めるのは補正だけで、保護（偏差ラッチ・途絶判定）は生きたまま
である。**

`y_axis` は 2026-09-04 に実運用ストローク（150mm）で詰めて `sync_kp: 16.0` が入っている
（移動中のずれ最大 0.637mm。**最適値は振幅で変わり**、振幅 1.5mm では 8.0 が最良だったが
150mm では 8.0 が最悪になる）。**150mm で検証済み。短距離（15mm）では取り直していない。**
机上ベンチ（`config/bench/`）は直結していない 2 台なので **0.0 のまま**にする —— 揃うべき前提が
無いまま別々の負荷で回り続けるため。

### ペア軸に片側だけ効く操作を作らない

原点確定（`set_origin_here`）も PID ゲインの差し替え（`scripts/tune_y_axis.py` がプロセス内で
行う上書き）もグループ全員へ展開する。左右を別々の時刻に原点確定すると、その間に片方が動いた
分だけ消えないオフセットが残り、正常な動作でも即座に偏差超過で止まる。「1 台だけに効かせて
よいか」の判断は `M3508PositionLoop._paired_with()` に 1 つだけ置く。

**零点確定の整列段だけが例外に見えるが例外ではない** —— 片側だけを進める段でも指令は
`AxisHandle.set_target_value` の軸単位 1 回で、進めない側にも必ず保持値を載せる
（`AxisSpec.to_commands_each()` がキーの過不足を `KeyError` で拒否するので載せ忘れも塞がる）。
**モータ 1 台だけを指令する API は作らない。**

### 周期タスクは `lib/control/periodic.py` を継承し、作法を揃える

兄弟クラスで作法が違うと片方の知識でもう片方を触ったときに「止めたつもりが止まっていない」が
起きる。二重 `start()` は `RuntimeError`（黙って無視すると起動したつもりのタスクを試合中に
発見できない）、`stop()` は `cancel()` せず停止イベントで降ろす（`_on_run_exit()` で 0 電流
フレームを送るタスクがあり、キャンセルすると止め損なう）。

**周期は次回起床時刻を絶対時刻で管理する。** 後置 `sleep` だと実周期が `interval + 処理時間` に
なり、「50Hz × 2 サンプル = 40ms なら機構破損に間に合う」と置いている偏差監視の時間予算が負荷に
比例して伸びる。

**実周期の乱れも `PeriodicTask` が測る**（超過回数と最悪値だけを O(1) で積む）。集計 1 行を
journal へ出すのは試合終了（`match_finish`）で、`match_start` は前縁リセットだけ —— `match_start`
だけをリセット点にすると窓が「試合 + その後の準備時間」になり、しかもその日の最後の試合が
1 行も残らない。**超過 0 件でも必ず 1 行出す** —— 出さないと、公称の 1.4 倍で常時走っている
（＝停止距離も偏差監視の 40ms 予算も既に崩れている）機体で journal が無音になり、
「警告 0 件 = 乱れていない」と読まれる。**画面にも配信にも出していない** —— しきい値が実機未検証で、
常時点灯すると安全機構のパネルごと読まれなくなるため。

**最悪値（`_worst_jitter_s`）の更新はしきい値超過ブランチの外側に置く。内側へ移してはならない。**
実機の `asyncio.sleep` は必ず数百 us オーバーシュートするので、公称どおりに回っている機体でも
ここには小さな正の値が入る（**超過が 1 件も無くても 0 とは限らない**。`jitter_overrun_count` の 0
とは別物）。しきい値 `JITTER_OVERRUN_MARGIN` が実機未検証である以上、**それを決めるための唯一の
観測値がこの値**なので、内側へ移すと超過が起きるまで 0 のままになり、「しきい値を決めるために
しきい値を超えている必要がある」という循環になる。

**`reset_jitter_stats()` は超過回数と最悪値を必ず両方一緒に 0 へ落とし、`_last_tick_at` は触らない。**
片方だけ残すと「超過 0 回なのに最悪の遅れだけ残る」不整合になり、次の集計 1 行が**前の試合の数字を
混ぜて名乗る**。`_last_tick_at` を `None` に戻すと直後の 1 tick 分の乱れを取りこぼす —— `start()`
が捨てる「停止していた空白」とは違い、ここはタスクが動き続けたままの呼び出しなので空白が無い。

## 3. 安全機構

### 緊急停止は「押した瞬間の状態」に依存させない

`activate_e_stop` は状態を問わず動作確認へ中断を要求する（`is_running` を条件にすると、実行
タスク生成から `run()` 開始までの窓だけ False になり、そこで押された停止をすり抜けた動作確認が
完走してアクチュエータを駆動する）。

**中断要求はシーケンスの外側のフラグ（`MotorCheckController._abort_requested`）に残す** —
`Sequence.run()` は冒頭で停止イベントを `clear()` するので、シーケンス側に預けた 1 通はその窓で
消える。`_run()` は駆動を始める直前にこのフラグを見る。

**停止理由はサーバーが保持し、解除まで再配信のたびに載せる**（定期再配信が理由なしだと、画面の
説明が 50ms 後に消えて正反対の文言へ置き換わる）。**最初に判明した理由を優先する** — 機体の
自動検知で止まった後に操縦者が押しても上書きしない。`e_stop_release` は緊急停止中でなければ
拒否する。

### 停止と解除は対称でなければならない

停止（`_send_e_stop_frames`）はブロードキャスト `0x0FF` を全バスへ流すので、**バス上の全基板・
全チャンネル**がラッチする。解除が `activation_steps()` の個別送信だけだと **yaml に登録された
モータにしか届かず**、PC の管轄外（ベンチ設定で一部だけ動かす / 増設基板が yaml に無い /
片方のロボットだけ起動）は永久にラッチされたまま残る。基板の LED は 1 チャンネルでもラッチが
あれば橙になるので、**全基板が橙のまま戻らず操縦者からは復帰不能に見える**（実機で発生）。

そのため解除は ①全バスへブロードキャスト解除 →②管轄内モータへ個別のラッチ解除 →③励磁 の
3 段で、①と②の重複は意図的である。

**ラッチ解除は中断しない（中断すべきは励磁だけ）** —— ロボットを順に処理するので、
`should_abort` をラッチ解除にも効かせると 1 台目の最中に停止が再発動しただけで 2 台目へ 1 通も
飛ばず、外れないラッチが緊急停止ビットを報告し続けて `_detect_board_e_stop` が停止を再発動する
（解除操作のたびに同じロボットが取り残される）。ラッチ解除で機体が動かないのは、停止時に目標値が
捨てられていること（DC は duty 0 / サーボは現在角保持 / 電磁弁は OFF）と、ファーム側の
`everFed_` ゲートによる。

**`_board_e_stop_ignore_before` は①②を送り終えた後に置く** — 先に置くと、まだ解除の届いて
いない基板の報告を「解除後の報告」と信じて自分で止め直す。

### 解除ハンドラは再励磁を待たずに返す

`_cmd_e_stop_release` / `_cmd_reenergize_motors` は `asyncio.create_task` して即座に返す。
`async for msg in ws` は 1 接続あたり完全に直列なので、ここで待つとそのあいだ次の 1 通が処理
されない。フィードバックの返らないモータは 1 台につき 0.5 秒待つため、CAN が落ちている状況
—— **まさに緊急停止を押した状況** —— では数秒に達し、**E-STOP の押し直しすら効かなくなる**。
進捗は `safety.unenergized_motors` として配信され続けるので、待つ必要がそもそも無い。

### 前の再励磁はキャンセルしてから有界に待ち、待ちきれなくても先へ進む

`_settle_pending_reenergize` / `_settle_pending_reactivation` が畳む。畳み忘れると、並走した
2 本のうち片方のプローブ（EDULITE 05 / DM3520 とも `feedback_probe_message()` = `disable`）が
もう片方の enable 直後のモータへ届き、**`sub_lift` が自重で落ちる**。踏むのは「解除の 2 連打」
ではなく E-STOP → RESET →（同期ずれ検出や再押下で）E-STOP → RESET で、窓が広がるのは応答の
無いモータを 1 台 0.5 秒待っている間 —— つまり CAN が不調なときほど広い。守るのは 5 点:

- **素の `await pending` にしない。** 有界なのは `_wait_fresh_feedback` の deadline だけで
  `CANManager.send_to_bus` は `bus.send` をタイムアウト無しで待つため、SocketCAN の送信キューが
  詰まっている状況 —— つまり `cbc-can-watchdog` が bus-off を疑っている、まさに緊急停止を押した
  状況 —— で「解除の再励磁が無期限に進まない」経路が残る
- **呼び出し位置はハンドラではなく `_reactivate_motors` の冒頭。** ハンドラへ移すと畳み込みが
  最悪 `_PENDING_TASK_CANCEL_TIMEOUT_S` 待つぶんだけ解除の受理が止まり、上の「待たずに返す」を
  自分で破る
- **`asyncio.current_task()` を畳む対象から外す。** 外さないと `_reactivate_tasks` に載っている
  呼び出し元自身をキャンセルし、**1 通も送らずに降りる**
- **`asyncio.wait` を使う**（`await pending` / `asyncio.wait_for` を使わない）。後者はキャンセル
  済みタスクの `CancelledError` をそのまま伝播させ、**この再励磁タスク自身がキャンセルされた
  ことになる**
- **畳んだ後に①ブロードキャスト解除・②個別ラッチ解除を飛ばす経路を作ってはならない。** 畳んで
  よい根拠は「新しい `_reactivate_motors` が①から先頭でやり直す」ことにあり、飛ばすと取り残された
  ロボットが生まれる

### M3508 の緊急停止は `send_stop_frame` が別経路で出す

M3508 は `emergency_stop_message()` を持たず、自作モタドラ向けの `0x7FF` ブロードキャストも解釈
しない。**この経路が無い（またはループの状態でゲートされる）と、左右直結の `y_axis` だけは
「ループが生きていて電流 0 を送り続けてくれること」に停止を委ねることになる。** そのため
`send_stop_frame()` は **`_paused` でも `is_running` でも止めず、`_step_lock` も取らない** ——
`0x200` を別の経路が握っている最中でも全スロット 0 をそのまま上書きしてよい（むしろさせたい）。
lock を取ると、送信が詰まった相手を待つあいだ**停止そのものが止まる**。

### 起動時設定と励磁はモータ単位で交互に送る

1 台目の設定 → 1 台目の励磁 → 2 台目の設定 → … の順（`CANManager._activate_each_motor` に 1 台分の
処理を渡す形）。「全モータの設定 → 全モータの励磁」に組み替えてはならない。EDULITE 05 / DM3520 の
`activation_steps()` は**直前に受信したフィードバックの実測角を保持目標に書いてから enable する**
ので、並び替えるとその実測角が「設定直後」ではなく**他機の設定を挟んだ後**のものになり、「現在角を
書いてから励磁する」保証が崩れる。EDULITE 05 は enable した瞬間に `PARAM_LOC_REF` へ追従を始め、
DM3520 はモード切替で `p_des` が 0 に落ちているので、**励磁の瞬間にアームが原点へ全速で飛ぶ**
（ラックアンドピニオンではストローク端まで走る）。

### 保留中の開始・ジャンプ要求

開始とジャンプは同じ経路（`Sequence._request_index`）を通す。分岐を書き分けると、症状は書き直した
側にしか出ない。守るのは 2 つ:

- **実行中は再開イベント（`_resume_event`）を立てない。** 立てるとその 1 通が次の通常停止まで
  イベントとして残り、`run()` が降りた瞬間に `run_forever` が拾って、**操縦者が何も押していないのに
  先頭から全工程を走り直す**。`match_finish` 経由なら、フェーズは `finished` なのに機体だけが動き
  続ける（`run_forever` はフェーズを見ない）。実行中に届く 2 通目の開始要求は現実に起きる ——
  操縦者 2 名 + 予備タブが同じ画面を開いており、配信周期（50ms）以内の二度押しでも、詰まった
  クライアントが最大 1 秒古い `running:false` を描いていても届く
- **破棄したことの正は `_jump_request is None` に置く。** `asyncio.Event` は `set()` の時点で待機中の
  future を解決するので、その後の `clear()` は**既に起きることが決まった 1 回を止められない**
  （`run_forever` は常にそこで待っているので、本番では必ずこの形になる）。`discard_pending_start()`
  の `clear()` は「まだ待機に入っていない場合に余計な起床を省く」ためだけのもので、破棄の根拠に
  してはならない。`run_forever` は起こされた後に `_jump_request` を見て、無ければ 1 歩も動かさずに
  待ち直す。誤ると、緊急停止の直前に届いた開始要求が残り、停止処理を終えた次の瞬間に発火して
  **操縦者が何も押していないのに機体が動き出す**

### 基板が報告する緊急停止はサーバー全体の緊急停止へ伝播する

拾わないと、機体は止まっているのに UI は平常のままになり、操縦者はシーケンスが進まない理由を
画面から知る手段が無い。判定は**解除フレームを送った時刻より後に届いたフィードバック**に限る
こと（`RobotServer._board_e_stop_ignore_before`）。送信前のフィードバックに残った緊急停止ビットを
信じると、解除した瞬間にサーバーが自分で止め直し、二度と解除できない機体になる。

### 物理非常停止（DC 基板の `REF`）はラッチで受ける。離しても自動復帰させてはならない

PC は 20Hz で目標値を再送し続けるので、レベル追従にすると**スイッチを離した瞬間に機体が動き
出す**。解除は CAN の `E_STOP` 解除フレーム（＝操縦者の明示操作）だけに限る。押している間は
`loop()` が毎周期再ラッチするので、解除フレームの到着順に依らず「押している間は絶対に動かない」が
成立する（判断は `MotorSafety::applyPhysicalStop()`）。**DC 基板が繋がっていない構成では物理停止が
効かない**（電磁弁基板に `REF` 入力は無い）。

### 止める処理が止まる形を作らない

周期タスクの `stop()`・`CANManager.shutdown()`・`main()` の後始末（`_shutdown_step`）は、1 つが
失敗しても残りを続ける。素の for で並べた後始末は途中の 1 例外で以降が丸ごと飛び、2 台目の
ロボットのバスが開いたまま残る。既に異常終了していたタスクの例外をここで再送出しないのも同じ
理由（死因は降りる前にログへ残している）。

### `main()` の後始末はシグナルの扱いに依存する

`systemctl stop` の SIGTERM は既定ではプロセスを即死させ、`finally` に並べた後始末（ループ停止 →
CAN shutdown）が 1 段も走らない。`_install_stop_signal_handler()` が main タスクの cancel へ変換
して既存の経路に載せている。**2 通目のガードに `loop.remove_signal_handler()` を使ってはならない**
（SIGTERM の扱いが SIG_DFL に戻り、2 通目が「無視」ではなく「即死」になる）。

**後始末の順序（位置制御ループ → 目標値再送 → 同期監視 → CAN → サーバー）は不変条件で、段を
入れ替えてはならない** — 位置制御ループは生き残ると電流指令を出し続けるので CAN より先に止める、
同期監視だけが生き残ると停止済みのモータのフィードバックを見て誤発報する、という理由が段ごとに
付いている。**bind の可否（`_ensure_port_available`）は「配線する」より前に見る** — ポートが
埋まっている（会場での二重起動）ときに、CAN を 1 本も開かず・機体を励磁せずに終わるため。

### 零点確定（ホーミング）には止める仕組みが 9 つ要る

電源投入位置をそのまま原点にすると、前の試合の終了姿勢や搬送中に手で動かしたぶんがそのまま
座標のずれになる。位置定数は全て原点からの相対値なので、ずれた原点のまま走らせると全ステップが
同じだけずれた場所へ動く。設定は `*_positions.yaml` の `axes.<軸>.homing`（**軸の機構的性質**で
あって動作確認固有の値ではない）。

「当たるまで動かす」動作なので、止める仕組みが 9 つ要る（数え方は
[`checks_and_health.md`](checks_and_health.md) の「零点確定（ホーミング）」節と揃えてある）:

1. **`search_distance` の上限** — 配線が抜けたセンサは「いつまでも当たらない」形でしか現れない
   ので、**これが唯一の無人の歯止め**。省略できない必須キーにしてある
2. **1 歩ごとの再アンカー** — 指令は毎回そのときの実測位置から組むので、指令だけが先行して
   機構に偏差が積み上がることが構造的に起きない（下の「探索の起点は実測位置であって 0 ではない」）
3. **事前確認**（どれも 1 歩も動かさずに落ちる。5 つの内訳は下の「探索の起点は実測位置であって
   0 ではない」）— そのうち**励磁されているか**は停滞判定でも拾えるが、その文言は「引っかかり・
   探索方向・励磁」の 3 択なので原因を絞れない。`is_energized()` が `False` のときだけ降りる
   （`None` は「励磁を報告しないドライバ」であって無励磁ではない。倒すと M3508 が一切零点確定
   できなくなる）
4. **1 歩ごとの鮮度の再確認** — 事前確認は「始めてよいか」しか見ない。センサの読み口は途絶しても
   **最後に届いたフラグを返し続ける**ので、探索中の基板再起動や CAN の瞬断は「いつまでも
   当たらない」としか見えず、ドライバ内蔵の位置ループが端を押し続けたまま探索距離いっぱいまで
   進む。**降りる前にその場の実測位置を目標へ送り直す**（最後に送った「実測 + `step`」が
   生きたままだと押し続ける）
5. **停滞判定** — 再アンカー方式では「進まない機構」が探索距離を消費しないので、実測が
   `step/2` 未満しか進まない状態が 3 歩続いたら降りる
6. **離脱の距離上限**（`homing.release_distance`）— 接点の固着と極性の取り違えはどちらも
   「いつまでも OFF にならない」形でしか現れない。**`search_distance` を流用してはならない**
   （実ストローク相当まで伸びる値なので反対側の機構端まで走り抜ける）。**既定の `step` 倍数にも
   頼らないこと** —— 本来は ON 区間の広さで決まる値なので、精度のために `step` を詰めると許容も
   一緒に縮み、**精度を上げるほどスイッチから離れられなくなる**（実機で踏んだ）
7. **`align_distance` の上限**（下の整列段を持つ軸のみ）
8. **接触カウンタを提供しないセンサの拒否** — 到達判定は接触の累計
   （`GenericDriver.sensor_contact_count`）で見るので、持たないドライバでは探索を開始しない。
   現在値へ落とす実装は取りこぼす経路そのもので、取りこぼした探索は機構の破損側へ進む
9. **緊急停止**（`AxisHandle` が既に通る）

**センサの読み口は三値**（`True` / `False` / **`None` = 読めていない**）で、可動端インターロックと
同じ `main._make_sensor_reader` を共有する。**`None` を `False` へ丸めてはならない** —— 離脱段では
「途絶したセンサ = 離脱できた」に化け、触れたままの位置で原点を確定する。

**離脱で戻った距離は探索距離を消費しない。** `search_distance` が縛るのは開始位置からの押し込み量で、
離脱は逆向きなので、そのぶんを寄せ直しが再走しても到達しうる最深点は変わらない。数えないと、粗探索が
上限をほぼ使い切った軸で寄せ直しの上限が 0 以下になり、1 歩目から読めない文言で落ちる。

**失敗したら原点を確定せずシーケンスを止める** — 原点がずれたまま走るより、動かないまま止まって
操縦者に知らせるほうが安全。**既にセンサに触れているなら、一度区間の外まで離れてから寄せ直す**
（触れたその場を原点にすると「ON 区間のどこで始めたか」がそのまま原点のばらつきになる。離脱は
探索と逆向きなので、機構端で始まったときに押し込まない性質は保たれる）。

**零点確定を走らせる経路は 1 本しかない**（`lib/sequence/homing.py` の `run_homing`）。
動作確認の通し実行と、軸を指定して走らせる `homing_start` が同じ 1 本を通る —— 手順を
書き写すと、コートの符号やセンサの読み口が片方だけ直された状態が作れる。**単独実行は
`robot` を必ず取り、宛先を省いて全ロボットを回す形を持たない** —— サブハンドを見るつもりで
起動してメインハンドの `y_axis` が動き出したのが 2026-09-09 の事故である。単独実行だけは
1 軸落ちても残りの軸を続ける（軸ごとに独立した確定なので、1 回で全軸の可否を出す）が、
落ちた軸の原点を確定しないことは通し実行と変わらない。

**スイッチの作動点を測る経路も、同じ探索を通る**（`HomingRunner.measure`）。機構が変わるたびに
作動点は動く（2026-09-09 の 1 日で前後 −500〜−520 → −447.0、上下 −189 → −159.0）ので測る手段が
要るが、掃引をもう 1 本書くと片方だけが直された状態が作れる。**違いは原点を書き込まない 1 点だけ
で、`SET_ZERO` は 1 通も出さない。** 向きは指定させる（測りたいのは `homing.direction` が使わない
側の端でもある）。**移動量の上限は `HomingSpec.search_distance` として載せる** —— 測定専用の上限を
別変数で持つと、探索の各段が見る歯止めと二重になる。動作確認・零点合わせとは相互排他で、宛先の
ロボットと軸を必ず取る。

**ストロークが `step` に対して長い軸は二段探索にする**（`homing.coarse_step`）。原点のばらつきは
刻み幅そのものなので、0.1mm の精度を要求する軸では `step` を 0.1mm まで詰めることになるが、その
刻みで 510mm を探すと 5000 歩かかって点検に入らない。**粗い刻みで当てる → 離脱 → `step` で
寄せ直す**の 2 段にすれば、原点の粒度を `step` に保ったまま実用時間で寄せられる。**`coarse_step` は
ON 区間の実測より狭く取ること** —— 広いと粗い 1 歩で区間を跨ぎ切り、離脱も寄せ直しもできない位置で
止まる。**書くなら `release_distance` も必須**（離脱は粗い側の刻みで動くのに、既定の許容は `step`
から作られるので必ず桁が合わない）。原点確定はグループ単位でしか行わない（`set_group_origin_here`）。
`homing` が見るセンサ（`HomingSpec.sensor_names`。単数 `sensor` と複数 `sensors` を吸収する唯一の
口）が `sensors:` に登録されていることは `tests/test_robot_sequences.py` が固定する（居ないと
「センサが応答していません」で必ず失敗し、配線不良と区別が付かない）。

### 左右にスイッチが 1 本ずつ付く軸は「両方が押された姿勢」を原点にする

`homing.sensors`（**モータ名 → センサ名**の対応表。単数の `sensor` とは排他）を書いた軸では、
探索で**いずれか 1 本**が当たった後に**整列段**が走り、まだ押されていない側のモータだけを探索
方向へ進める。片方が当たった瞬間の姿勢を原点にすると**機構の遊びぶんが原点のずれとして焼き付き**、
遊びの向きは前回の移動方向で変わるので再現しない。対応表のキーが軸の `motors:` と過不足なく
一致していることは起動時に強制する（1 つ書き忘れるとそのモータだけが静かに対象外になる）。

**既に当たった側は「検出時点の実測位置」で固定保持し、毎歩実測へ再アンカーしない** —— 遊びが
無い機構では進めた側が保持側を引きずり、再アンカーすると左右のずれが増えないので**歯止めが
1 つも発火しないまま軸ごと機構端まで走る**（固定保持なら停滞判定が拾う）。

**整列段のあいだだけ、その軸の原点センサを可動端の歯止めから外す**（`SensorSuspension`。
`HomingRunner` へ `suspend_sensors` として注入し、`main()` が**両ハンドで 1 つを共有**する）。
軸としては端へ向かう向きなので、既に押された 1 本を見た歯止めが —— 指令の入口でも 50Hz の
常駐監視でも —— この段の指令を拒否し、**整列段は必ず失敗する**（前者は `GuardViolation`、後者は
目標を実測へ書き戻すので停滞判定で落ちる）。進めている側のスイッチはまだ押されていないので、
機構から見れば進んでよい。**外すのは `homing.sensor_names` だけで、軸まるごとではない**
（両端にスイッチがある軸で反対端の守りまで消える）。**探索中は外さない** —— 接触の検出を
取りこぼしたときに次の 1 歩を止める最後の砦がそこにある。**覆いを掛けるのは歯止めが読む口だけで、
零点確定自身は生の読み口を使う**（探索も離脱も「今 ON か」で進むので、覆った値を渡すと自分の目を
塞ぐ）。配線し忘れは安全側に倒れる（その軸だけ零点確定できない）が、症状は config からもログからも
読めないので `tests/test_homing.py::TestAlignsWithTheGuardArmed` が両向きを固定している。

**覆いは歯止めが読む口すべてに掛かる。緩みが露出しないことの根拠は、覆いの側ではなく制御権の側に
ある。** `main()` は 1 つの `SensorSuspension` を両ハンドで共有し、覆った読み口を `MotorGroup` へ
渡すので、整列段のあいだは**手動操縦が通る歯止めも同じだけ緩む**。それでも `y_axis` / `sub_y_axis`
/ `sub_lift` / `rotate` を緩んだ状態で手動操縦できないのは、**その間これらの軸に手動操縦の制御権が
無い**ためで、次の 3 枚が独立に効いている:

1. 零点確定を走らせる 2 つの経路（`homing_start` と動作確認）は、**どのロボットかが手動操縦モードだと
   開始できない**（`RobotServer._environment_deny`）
2. 走り出した後は `_busy_label()` が立つので、**手動操縦モードへの切り替えが拒まれ**
   （`RobotServer._set_operation_mode`）、**`manual_always` の軸すら拒まれる**
   （`RobotServer._allow_manual_in_sequence`）
3. 覆う対象になる軸は到達判定を持つ位置制御軸なので、そもそも `manual_always` を宣言できない
   （`AxisSpec._check_manual_always`。上の `manual_always` の節と対）

**この排他が緩んだら、覆いの適用範囲を歯止めのうち必要な口だけへ絞らなければならない** —— 覆い自体は
口を選ばないので、制御権が開いた瞬間に「原点スイッチの効かない手動操縦」がそのまま生える。1 と 2 の
両向きは `tests/test_server_homing.py::TestDenyGate` が固定している。

**`align_distance` は `search_distance` と同格の無人の歯止め**で、`sensors` を書いた軸には必須・
書いていない軸には書けない。**`sync_tolerance` より真に小さいことを起動時に強制する** —— 届くと
零点確定の最中に偏差監視が発報し、症状は「動作確認の最初のステップでいつも緊急停止する」だけに
なる（零点確定は `move_to` を通らないので、発報しうるのは常駐の 2 段だけ）。`search_distance` を流用してはならない（`y_axis` のそれは 650mm で、片側を 650mm 進めるのは
軸をねじり切ることに等しい）。

### 探索の起点は実測位置であって 0 ではない

`HomingRunner` は毎ステップ `AxisHandle.observed_value()` を読み直して
`commanded = observed + direction*step` を組み、`travelled` も実測位置の差分で数える。起点を
呼び出し側の引数にすると渡し忘れが 0 起点へ黙って戻るので、引数そのものを持たせていない。
**指令の積算で数えると、1 歩目が原点近傍への 1 回のジャンプになり、その移動が `search_distance` を
1mm も消費しない**（手動で軸を動かした後の動作確認で普通に踏む）。再アンカー方式では「進まない
機構」が探索距離を消費しないので、**停滞判定**（`step/2` 未満が 3 歩連続で `HomingError`）が対に
なる。

**「1 歩ぶん進んだ」と見なす移動量は `_progress_threshold`（`step` に対する割合）1 つだけで、追従
待ちの完了判定（`_wait_step`）と停滞判定（`_seek` / `_align`）が同じこれを見る。** 片方に定数を
書き写して基準が分かれると、**待つ側が「まだ動いていない」段階で抜けたぶんを数える側が「待ったのに
進まなかった」と読み、動いている機構が数歩で `HomingError` になる**（症状は「機構は動いているのに
零点確定だけが毎回失敗する」）。

事前確認は 5 つで、どれも 1 歩も動かさずに落ちる —— 位置指令の軸か / 原点を確定する手段があるか /
モータの励磁 / センサの鮮度 / **対象軸モータの鮮度**。最後の 1 つが欠けると、未受信の `0.0` を
現在位置と信じて全ストロークぶんの指令を 1 回で出す。

### 探索の到達判定は接触の累計で見る。「今 ON か」では取りこぼす

リミットスイッチの ON 区間が `homing.step` より狭いと、指令 1 回でその区間を跨いでしまい、
`settle_s`（50ms）後の観測時にはもう抜けている（`rotate` は step 2.0deg を約 18ms で通過する）。
実機で**スイッチに当たっているのに探索が止まらず、可動範囲の端を越えて回り続けた**（その後
`SyncMonitor` の偏差超過で自動緊急停止。再実行では成功したのでタイミング依存として現れる）。

センサの `FEEDBACK` は 100Hz で届いているので、受信のたびに数える
（`GenericDriver.sensor_contact_count`。立ち上がり（OFF→ON）を数える**単調増加のカウンタで、
読んでも減らない**。診断ツリーが描く「今どうなっているか」は `sensor_active` のまま）。
**読み手は 1 つに限らない** —— 走行中の接触を拾う常駐監視が同じセンサを毎周期読むので、
「読むと消える」ラッチだと**先に読んだ側が相手のぶんまで消し、上の壊れ方がそのまま再発する**。
読み手は自分で基準値を控え、その差だけを見る（`_SensorContacts`）。**探索を始める直前に基準値を
取り直す** —— 手動操縦や前回の零点確定で数えたぶんまで見ていると、1 歩目でいきなり到達と読む。

**離脱（センサから離れるまで動かす段）は現在値のまま。対称に見えて非対称である。** 接触の累計を
持ち込むと「一度でも OFF になった」で抜けることになり、接点のチャタリングでまだ ON 区間の中に
いるのに離脱完了と読む。取りこぼしの向きも非対称で、探索の取りこぼしは**機構の破損側**へ進み
続けるのに対し、離脱の取りこぼしは「余計に離れる」だけで次の探索が寄せ直す。**検出したらその場の
実測位置を目標に送り直す** —— 最後に送った「実測 + step」が生きたままだと、原点確定が
効くまでスイッチを越えた先へ向かい続ける。

### 原点を確定する手段はドライバ自身が答える

手段は「PC 側位置制御ループ（M3508）」「ドライバのローカル原点（EDULITE 05）」「ドライバへの
`SET_ZERO`（DM3520）」の 3 つで、可否は `supports_origin_capture()` が答える（`main.py` に
ドライバ種別を書き写さない）。**手段が無い軸は探索を始める前に落ち、起動ログにも `ERROR` で
出る。** 現況は [`checks_and_health.md`](checks_and_health.md) の「零点確定（ホーミング）」節が正。

**`SET_ZERO` の可否だけは「切り直すフレーム」と「無励磁にする手段」の両方を要求する** ——
励磁したまま原点を動かす経路を構造的に塞ぐため。ローカル原点はその条件を**緩めるのではなく
充足条件を 1 つ足した**もので、CAN へ 1 通も出さないので励磁の状態と無関係である。

**`M3508Driver` はローカル原点を名乗らない。** 累積角の原点は `M3508PositionLoop` が持ち
（`set_origin_here` は目標の破棄と PID のリセットまで含む）、ドライバ単体では切り直せない ——
ドライバだけを呼ぶ経路が生えると、目標と積分が旧座標のまま残ったところへ新しい原点が入る。

**有効なのは `rotate`（EDULITE）/ `y_axis`（M3508）/ `sub_y_axis` / `sub_lift`（DM3520）の 4 軸。**
DM3520 の 2 軸は 2026-09-09 に実機で通した（再現性 0.1mm）。`y_axis` は **2026-09-08 に有効化した
だけで実機ではまだ 1 度も走らせておらず**、`direction` / 左右 2 本の極性 / `align_distance` /
`step` はどれも未実測である（**初回は人が付くこと**）。

**「スイッチが付いた」と「零点確定が有効になった」を混同しないこと** —— スイッチは 7 本繋がって
いるが、`homing:` から参照しているのは 5 本（`rotate` に 1 本、`y_axis` に左右 1 本ずつ、
`sub_y_axis` の前端、`sub_lift` の下端）で、残る 2 本は `sensors:` に登録して途絶を見ているだけ
である。

### EDULITE 05 の原点は PC 側が持つ。`SET_ZERO` と併用してはならない

**どちらも「生の座標系そのもの」を動かす操作なので、同時に効かせると原点が二重定義になる。**
症状は「零点確定の直後だけ正しく、次の再励磁でずれる」という最も診断しにくい形で出る。
`Edulite05Driver` は `has_local_origin()` を宣言し、`origin_capture_steps()` を**持たない** ——
`SET_ZERO`（`encode_set_zero()`）は調査ツール（`scripts/edulite_origin_probe.py`）専用に残して
あるだけで、起動・励磁・零点確定のどの自動経路からも 1 通も出さない。

理由は**モータ側の零点が電源断を跨いで残る一方、位置の報告値は [0, 360) へ畳み直される**ため
（§2）。畳みは PC 側の連続化が吸収できるが、`SET_ZERO` は畳まれた電文座標のどこかを新しい 0 に
するので、控えてある回転数と原点オフセットが両方とも意味を失う。

**起動時の暫定原点も PC 側で控える。** `set_zero_on_start` は「起動時に**暫定原点を確立する**」の
意味で、**どう確立するかはドライバが決める**（DM3520 は `SET_ZERO`、EDULITE 05 は生角度の控え）。
config のキー名を変えていないのは、左右で値が食い違うと機械ゼロの差がまるごと偏差として残る
という性質が変わらないため（`tests/test_robot_sequences.py` が同梱 config 全セットで固定）。

**暫定原点を確立するのは 1 度だけである。** `establish_provisional_origin()` は
`CANManager.activate_motor` が**鮮度を確かめた後に**呼び、既に確立していれば何もしない。ここが
毎回効くと、**物理緊急停止からの復帰（再励磁を通る）のたびに原点がその瞬間の姿勢へ書き換わる**。
零点確定でも同じフラグが立つので、スイッチで確定した正確な原点を後の再励磁が上書きすることもない。

**鮮度より先に控えてはならない** —— 未受信の `0.0` を現在位置と信じた原点は、以後の指令を
全部そのぶんずらす。

### ペア軸の原点は全員を同じ処理の中で控える

`CANManager.capture_origin_in_place` は全員の鮮度を確かめてから、**`await` を挟まずに**全員の
原点を控える（`M3508PositionLoop._capture_origin` と同じ形）。別々の時刻に控えると、その間に
片方が動いたぶんが消えないオフセットとして残り、逆回転ペアではそれがそのまま偏差になる。
**1 台でもフィードバックが途絶していれば 1 台も控えない**（未受信の `0.0` を現在位置と信じない）。
**緊急停止が入っていても 1 台も控えない** —— 探索が完遂していない姿勢を原点にすると、
「黙って成功した誤った原点」ができる。

### 原点をモータ側で切り直した直後の励磁は保持目標に 0 を書く

`activation_steps(after_set_zero=True)` は手元の実測角ではなく**新原点そのものである 0** を書く
（DM3520）。`CANManager._wait_fresh_feedback` は「待機開始より後に届いた 1 通」しか待たない
（受信済みの値の再利用も認めない）が、それでも `SET_ZERO` を送った直後に**旧原点で測られた在庫の
フィードバックが届く**余地は残る。それを保持目標に使うと、enable した瞬間に**旧原点と新原点の差
だけ機構が動く**。

**PC 側に原点を持つドライバではこの分岐を持たない。** 生座標は原点を控え直しても動かないので、
控える前に測られた在庫も控えた後と同じ物理位置を指す —— 分岐を残すと「控える前と後で保持目標の
意味が変わる経路」が 1 本増えるだけになる。

### 再励磁は片方向しか塞がない。意図的な例外である

`reenergize_motors` は励磁が落ちたモータを機体を止めずに戻すコマンドで、無励磁のモータ（と直結
ペアの相方）だけ目標ラッチを剥がしてから `activate_motors(only=…)` で絞って励磁する。
100ms〜2 秒かかる別タスクで走り、そのあいだ `safety.reenergizing` が立つ。

**塞ぐのは「在飛中に届くシーケンス系」だけ** — `CommandSpec.blocked_during_reenergize` が
`sequence_start` / `sequence_jump` / `trigger` に付く（在飛中に `move_to` が書いた目標を「フォルト
前の現在角」が上書きし、`wait_reached` が動かない位置を見続けて `SequenceTimeoutError` になる）。

**同じゲートに緊急停止解除の再励磁（`_reactivate_motors`）も掛かる。** 在飛判定が 2 系統に分かれて
いるのは実装の都合にすぎないので、`RobotServer._is_reenergizing` が両方を畳んで答える（解除の
再励磁は全ロボットぶんをまとめて走るので、そちらはロボット名に依らず True）。片方しか見ないと、
窓が開くのは応答の無いモータを 1 台 0.5 秒待っている間 —— つまり CAN が不調なときほど広く、まさに
緊急停止を押した状況 —— なのに、塞いだつもりの経路だけが素通りする。

**逆方向（シーケンス実行中の再励磁）は塞がない** — 励磁が落ちるのはたいていシーケンスを走らせて
いる最中で、そこで使えなければ直したい状況が直せない。

### 再励磁のペア展開は「励磁中のモータへ disable を送らない」に依存している

直結ペアの片側が無励磁なら相方も対象へ含めるので、`only` には**励磁中のモータが混ざる**。
`CANManager.activate_motor` は `requires_fresh_feedback_for_activation()` なモータの鮮度を
`feedback_probe_message()`（EDULITE 05 / DM3520 とも **disable**）で引き出すため、これをそのまま
打つと健全な相方が保持トルクを失い、宣言順（`rotate_r` → `rotate_l`）次第で**軸が両側とも無励磁に
なる窓**（最悪 550ms）が開く。**`reinitialization_steps()` も先頭が `disable` なので同じ窓を開く**
（EDULITE 05 / DM3520 とも宣言している）。

判断は `CANManager._may_probe_for_feedback` と `_is_known_energized` が `is_energized()` の三値で
1 箇所だけ持ち、`True` のモータへは打たない。`after_set_zero` の経路だけは例外で必ず打つ —
直前に `deactivation_steps()` を送っており、無励磁であることを指令として知っているため。
**ドライバ種別をここへ書き写してはならない。**

一方 **`SyncMonitor` は止めない** — 零点確定が止めてよい根拠（「その間モータは無励磁なので押し合いは
原理的に起きない」）は再励磁では片側にしか当てはまらず、止めると保護が本当に要る瞬間に目を塞ぐ
ことになる。再励磁自体は「今いる位置」しか書かないのでずれを増やさない。

### bus-off からの復旧はウォッチドッグが持つ。カーネルには任せられない

`restart-ms` は SocketCAN のドライバが `do_set_mode` を実装している場合しか設定できず、CANable2 の
`gs_usb` は実装していない。さらに実測では、bus-off で送信が完全に止まっている間も `ip link` の
`can state` は `ERROR-ACTIVE` のまま、エラーフレームも 1 通も届かない。**したがって判定を `state` や
エラーフレームに置いた実装は永久に発火しない。** `cbc-can-watchdog.service` は qdisc の backlog が
残っていることと TX packets が進んでいないことの **AND** で判定する（どちらか片方では、動いている
バスを落とすか、平常時を異常と読む）。

**これは電磁弁のウォッチドッグと噛み合う。** bus-off 復旧の `down`/`up` は 1 秒弱 CAN を止めるので、
`command_timeout_ms`（既定 500ms）が満了し、**復旧 1 回で吸着中のワークが落ちうる**。試合中かどうかの
ゲートは意図的に置いていない（「バスが戻らない」ほうが重い）ので、運用で受ける —— **journal に
`[ WD ]` が出たらワーク落下を疑う**。UI にも残る（かつては journal にしか出ず、試合中に journal を
見る人はいなかった）。判定（どのバスの途絶がワーク落下に繋がりうるか）はサーバーだけが持ち、
`BusHealthInfo.may_affect_workpiece` として配信する。

## 4. 運用と操作モード

### 運用の主体は半自動シーケンス制御。手動操縦はその代替ではなく退避路

機体が動くのは操縦者がタブで `sequence_start` / `trigger` を押したときだけで、`match_start` は
フェーズを進めるだけ。`require_trigger` のステップは常にトリガー待ちで止まる（「全自動なら素通り」
のような例外は無い）。試合開始のゲートは指差喚呼の全項目完了。**「全自動」という操作モードは無い**
— 増やしてよいのは制御権の持ち主であって、シーケンスの走り方ではない。

### 手動操縦は制御権をシーケンスから奪う操作であり、同時に 2 つは立たない

`OperationMode`（`sequence` / `manual`）は**ロボットごとに独立**し、正はサーバーが持つ（操縦者
2 名 + Monitor が別ブラウザで繋がるので、片方の画面だけが手動になっていると Monitor から機体の
動きを説明できない）。手動へ入るときは `_stop_sequence` で**破棄が先・停止が後**の順にシーケンスの
制御権を手放させ、動作確認の実行中は切替を拒否する。

**半自動へ戻してもシーケンスは自動再開しない** — 手動で機構を動かした後に先頭から流すと姿勢と
手順が食い違うため、再開ステップは操縦者が `sequence_jump` で選ぶ。**モータの目標値はモード切替で
消さない**（消すと保持トルクを失って昇降軸が落ちる）。消すのはジョグの起点だけで、緊急停止でも
同じく捨てる（停止中に自重で下がっていると解除後 1 回目のジョグが古い起点から飛ぶ）。

### `manual_always` は片方向しか緩めない。軸単位の例外である

位置定数 yaml の `axes.<軸>.manual_always: true` を書いた軸は、`OperationMode.SEQUENCE` のままでも
手動指令を受け付ける（メインハンドの `conveyor` とサブハンドの `valve_1`〜`valve_6`）。コンベアを
止めるだけ・弁を 1 個開けるだけのためにシーケンス全体の制御権を奪う（モード切替は走っている
シーケンスを止める）のを避けるためで、**モードが 2 つ立つわけではない** —— 立っているモードは
今までどおり 1 つ、その軸への指令だけがモードを跨いで通る。

**書けるのは到達判定を持たない単独軸（`duty` / `on_off`）だけ**で、`AxisSpec._check_manual_always` が
起動時に強制する。位置指令の軸で許すと、シーケンスが `move_to` で書いた目標を手動が上書きし、
`wait_reached` が動かない位置を見続けて必ず `SequenceTimeoutError` になる（`blocked_during_reenergize`
が塞いでいる害と同型）。`duty` / `on_off` は `settle_s` の固定待ちへ落ちるのでこの害が無く、単独軸なので
「同一フレームで同時指令」の不変条件にも触れない。通るのは `manual_move` だけ —— 対象軸に `manual:` は
書けないので `manual_set` / `manual_jog` は従来どおり拒否され、「定義した状態以外を送れない」保証が残る。

**緩めたのは `_manual_target` のモード判定 1 枚（`_allow_manual_in_sequence`）だけである。** 緊急停止
ゲート・再励磁ゲート・`CommandSpec`・`_apply_operation_mode` は 1 つも触っていない。**逆方向 ——
シーケンスがその軸へ書きに来ること —— は塞がない**: 手動で止めたコンベアは、次にそれを回すステップが
来れば再び回る。除外もラッチも作らないのは、シーケンスが手順の正であり続けるため（塞ぐと「操縦者が
触った軸だけシーケンスが飛ばす」経路ができ、どの手順が外れているかは画面からもログからも読めない）。

**配信の欠落は「押せるボタンが増える」側へ倒してはならない。** `manual.axes[].manual_always` の受信は
素通しのままで、読む側が `=== true` で厳密に見る（`?? true` のような向きの既定値を置かない）。
扱いの詳細は [`web/data_flow.md`](web/data_flow.md)。

### 制御権の奪い合いは両方向を塞ぐ

手動へ「入る」側は `_stop_sequence` が持つが、逆方向 — **手動に入った後に届く `sequence_start` /
`sequence_jump` / `trigger`** — は別のゲートが要る。手動（`lib/manual.py`）とシーケンス
（`lib/sequence/engine.py`）は同じ `AxisHandle.set_target_value` を通るため、塞がないとジョグ中の軸へ
シーケンスが別の目標値を書きに来る。

正は `CommandSpec.blocked_during_manual` に置く — `_cmd_sequence_start` に `if` を足す形にすると、
次にコマンドを足す人がまた片方向で書く。塞ぐのは対象ロボットの制御権を実際に奪う 3 つだけで、
**塞ぎすぎない**: `sequence_stop` は退避の逃げ道として手動中も通す。`set_operation_mode` /
`manual_move` / `manual_set` / `manual_jog` は対象外（前者は機体を動かさない切替そのもの、後者は
`_manual_target` が別に判定を持つ）。`motor_check_start` も対象外 — 排他は
`_motor_check_environment_deny()` が両ロボット横断で持つ。

### 手動はフェーズでゲートしないが、緊急停止ゲートは別軸で効く

調整は準備中に、シーケンスからの退避は試合中に要るので `set_operation_mode` / `manual_*` はすべて
`PHASES_ANY`。一方、機体を動かさない**モード切替は緊急停止中も通し、目標値を送る `manual_*` は
通さない**（通すと緊急停止が意味を失う）。ここを 1 つにまとめると、「停止中に画面を手動へ寄せられ
ない」か「停止中に機体が動く」のどちらかになる。UI 側も 2 つの理由
（`modeBlockedReason` / `manualBlockedReason`）に分けてある。

### 手動で連続値を送ってよいのは `axes.<軸>.manual` を書いた軸だけ

通常運用の `move_to` は位置名でしか値を引けないため「定義した状態以外を送れない」ことが構造的に
保証されている。手動はその保証を外すので、代わりの境界（`min` / `max` / `steps`）を config に
宣言させる。範囲外は**拒否ではなくクランプ**する（拒否だと端で操作そのものが効かなくなる）。
`positions` に書いた値が範囲の外にあったら**起動を拒否**する（「シーケンスで行ける位置へ手動では
行けない」軸ができ、症状は「手動で戻そうとしても途中で止まる」だけで原因が config から見えない）。
duty 軸に `manual` は書けない。

### 手動でもモータ単位の指令口を作らない

`ManualController` は `AxisHandle` を通してしか送らず、UI にもモータ単位のジョグを出さない。左右
直結ペアが別々の時刻に動くとその場で機構が壊れるため、指令は必ず軸単位で 1 回だけ出す
（`asyncio.gather` で束ねる `AxisHandle.set_target_value` が唯一の経路）。**ジョグの起点は直前の
手動目標値**であってフィードバックではない（毎回フィードバックから取ると、追従が遅れているあいだの
連打が吸われて「押した回数だけ動かない」）。

### 吸着に使うパッドの選択はサーバーが 1 つ持ち、吸着ステップだけが読む

サブハンドの吸着パッドはワークの形で全部が乗らないことがあり、乗らないパッドの弁を開けると
真空が抜けて吸着が外れる。そのため「次の吸着で開ける弁」を操縦者が減らせる（`lib/suction.py`）。

**正はサーバーの `RobotContext.suction` 1 個。** 操縦 UI は 2 台繋がるので、片方の画面だけが
持つと Monitor からもう片方の吸着を説明できない。UI は差分ではなく**使う弁の全集合**を送る
（`suction_pads_set`）—— 差分だと 2 台の押下が交差したとき、どちらの画面とも違う集合になる。

**シーケンスが読むのは「ワーク吸着」ステップの入口だけ**で、選ばれた弁を `open`・残りを
`closed` に 1 回の `move_to` で送る。残りを閉じ直すのは、常時操作で開けたままの弁が 1 つ
あると真空が抜けるため。**選択が空なら吸わずに進まず、ステップを失敗させる**（進むと配置
ステップで落とす）。実行中の吸着には反映しない —— 途中で弁が閉じるとワークが落ちる。

ゲートは掛けない（緊急停止中も手動中も通す）。選択は機体を動かさず、効くのは次の吸着
ステップだからで、停止中の準備を塞ぐ理由が無い。UI の弁ラベルはサーバーが配る（`state.suction`）。
UI が `valve_*` を書き写すと、弁を 1 個増やしたとき片方だけが古い画面になる。

### サブハンドの軸どうしの干渉は、シーケンスの並びでしか守られていない

**`sub_y_axis` が前端スイッチから 150mm 以内に居るあいだ `sub_rotate` を回してはならない**（回した
機構が前端側と干渉する）。回してよいのは `clear`（前端から 150mm 以上）まで後退したときだけで、棚から
受け取る `receive` と箱 4 箇所の `place_1`〜`place_4` はすべて 150mm 未満に取ってある —— **位置定数の
側から「`clear` を経由しない限り回せない」を保証している**（値そのものは仮値だが、この関係だけは
`tests/test_sub_hand_positions_config.py` が固定する）。同じ機構の都合で **前後に動かすのは `sub_lift` が
`top` のときだけ**、**`sub_pitch` と `sub_offset` は同じ指令で動かさない**（閉じるとき オフセット →
ピッチ、開くとき ピッチ → オフセット）。

**守っているのは `sequences/sub_hand.py` のステップの並びだけで、手動操縦では破れる。** `MotionGuard` が
見るのは軸 1 本ずつの可動端・跳躍量・トルクで（§2）、**軸どうしの干渉条件を表現する仕組みを持たない**。
手動で `sub_y_axis` を前端寄りに置いてから `sub_rotate` を回すと、指令の瞬間の判定も周期監視も 1 つも
反応しない。歯止めを足すのは別の作業で、ここに書いてあるのは**今は歯止めが無い**という事実である。

### メインハンドの `y_axis` と `rotate` の干渉も、シーケンスの並びでしか守られていない

**`y_axis` と `rotate` を同じ `move_to` に入れて一息に動かしてはならない**（回した機構がコンベア側と
ワーク側の両方で干渉する）。守っているのは `sequences/main_hand.py` の `_approach()` が
`work_n_via_1`〜`_via_3` を順に踏む並びだけである。位置定数の側には保証が無く、値はどれも等分割の
仮値で、サブハンドの `clear` のような「経由しない限り届かない」不等式にはなっていない。

**同じ `move_to` に両軸を入れても軌跡は同期しない。** `y_axis` は台形プロファイル
（`axes.y_axis.motion`）、`rotate` は `motion` を持たず EDULITE 05 のドライバ内蔵位置ループ
（`limit_speed` 2.0）で回るので、速度も加速度も別物で、段の途中では片方が先に着いて待つ。安全で
なければならないのは各段の終点ではなく **(y_axis の始点〜終点) × (rotate の始点〜終点) の矩形領域
全体**であり、刻むほど矩形は小さくなるが原理的にゼロにはならない。

**守れているのは行きだけである。** 戻り（`TO_CONVEYOR`）は `work_n` → `home` へ下がりながら
`pick` → `place` へ回すので同じ干渉域を逆走するが、経由点は 1 つも無い。`MotionGuard` が見るのは
軸 1 本ずつの可動端・跳躍量・トルクで（§2）、**軸どうしの干渉条件を表現する仕組みを持たない**ため、
手動操縦でもこの順序は破れる。ここに書いてあるのは**今は歯止めが無い**という事実である。

### アクチュエータ動作確認は両ハンド 1 本のシーケンス

かつては機体ごとに独立した確認を持っていたが、2 つを同時に起動できるため両機が同時に動き、可動域の
重なる位置で干渉しうる。順序を 1 本に固定すれば、いつ何が動くかがシーケンスの並びから読める。
設計はこの 8 つ（**項を足したらこの数も直すこと。** 食い違うと、読み手は全部を読んだかを数えられない）:

1. **判定はシーケンスエンジンがそのまま担う。** `move_to` は位置定数の `tolerance` で到達を判定し、
   届かなければ `SequenceTimeoutError`、左右がずれていれば `AxisSyncError` を投げる。到達判定を
   持たない軸（`duty` / `on_off`）は `settle_s` の固定待ちへ落ちる。つまり「フィードバックを持つものは
   自動判定、持たないものは目視」という切り分けが追加実装なしで成立している
2. **確認専用の駆動量を持たない。** 運用で使う位置名へ動かす。専用の値があると、位置定数とずれた
   瞬間に「動作確認で動く位置と運用で使う位置が別物」になり、確認そのものが意味を失う
3. **ペア軸も軸単位で駆動する。** `move_to` は軸名しか受け付けないので、左右が同じフレームで同時に
   動く。モータ単位で駆動していた頃は、単独駆動が構造的に避けられずペア軸を除外するしかなかった
4. **ゲートも排他も全ロボットに掛かる。** どちらかが手動モード / シーケンス実行中なら起動を拒否する。
   **周期タスクは 1 つも止めない**。起動の可否（`_motor_check_environment_deny()`）だけでは
   **既に走っている確認を守れない** —— 確認は `main_conveyor` と `sub_valves` を `manual_always` の
   軸で駆動し、どちらも操縦者が目視・打音で確かめるステップである。守られていたのは「起動には全
   ロボットが sequence モードであることが要る → sequence モードでは手動が全部拒否される」という
   連鎖に乗っていたからで、軸単位で緩めた瞬間にこれが切れる（弁の作動音を聴いている最中に別の弁を
   開けられる）。逆向きの塞ぎは手動側が持つ（`_allow_manual_in_sequence` が実行中を拒否する）
5. **可否の判定は `MotorCheckController.deny_reason()` にしかない。** サーバーが答えるのは環境側の
   条件（フェーズ・緊急停止・各ロボットの制御権）だけで、`environment_deny` として預ける。UI は
   `blocked_reason` を表示するだけで導出し直さない（切断中だけは例外）
6. **進捗も結果も拒否理由も `motor_check_state` 1 通で運ぶ。** 4 種類に分けていた頃は、途中の 1 通を
   落とした画面が古い状態のまま固まり、再送も無いので直らなかった
7. **構成に無い軸のステップは除外するが、除外したことを必ず画面とログに出す。** 黙って落とすと、
   本番構成で 1 軸が config から漏れていてもそのステップごと消えて全ステップ PASSED になる（症状は
   「動作確認は通ったのに試合でその軸だけ動かない」）。必要な軸は `@step(axes={…})` としてステップの
   隣で宣言し、判定は `Sequence.restrict_to_axes()` の 1 箇所だけが持つ。**軸を宣言しないステップ
   （零点確定）は構成に依らず必ず登録し**、一部だけ存在するステップは残して指令先だけを絞る（特に
   最後の `restore_home` を落とすと「必ず初期姿勢で終わる」性質が消える）。除外は `excluded_steps` と
   して**欠けている軸まで**同じ 1 通に載せ、UI は `MALFORMED` へ倒す経路を持つ
8. **周期タスクを 1 つも止めない。** 動作確認は `move_to` でしか軸を動かさず、周期タスクはどれも
   その目標を実現する側なので、止めると仕事ごと消える。**位置制御ループ**を止めると電流が 1 通も
   出ないまま到達待ちがタイムアウトし、復帰した瞬間に残った目標へ機体が走る。**目標値再送**を
   止めると、問い合わせ駆動の EDULITE 05 / DM3520 は `move_to` の 1 通ぶんしか応答を返さず、
   `AxisHandle.wait_reached` は再送しない polling なので**動き出す前の位置を見続けて到達を観測
   できない**（`rotate` の 0→180deg は実際に回りきっても失敗する）。自作モタドラは
   `command_timeout_ms` 500ms で出力が切れるので、`settle_s` 0.5s のコンベア・ポンプは目視・聴音の
   最中に止まる。かつて「C620 の `0x200` を奪い合う」として止めていたのは**モータ単位で直接 CAN を
   送っていた旧実装の理由**で、`move_to` へ移った時点で失効している

### 指差喚呼はロール 1 つ（`pre_match`）に統合し、Monitor の設定面に置く

かつては 2 名が別々に確認していたが、実運用では 2 名が必ず同じ場所で操縦するため独立した 2 回の確認に
ならず、同じ機体を二度読み上げるだけになっていた。**ロールが 1 つでも `checklists` は辞書のまま運ぶ**
— `can_start_match` の判定と WS 契約の形を変えずに済ませるため。ロール名を書いてよいのはサーバーが
`lib/match_state.py` の `ALL_ROLES`、UI が `web/src/lib/protocol.ts` の `CHECKLIST_ROLE` だけ。
**残っている項目名を出すのは `MatchPrep` だけ**（`StartGate` は残り件数しか言わない）。

### 指差喚呼の項目は「操作の隣」に置く。置き場所の正は config だけが持つ

`config/checklist.yaml` の `group`（`preflight` / `court` / `motor_check` / `final`）が唯一の宣言で、
`MatchPrep` はコート選択ボタンの直下に `court` を、動作確認の起動ボタンの直下に `motor_check` を
並べる。1 本の長いリストに戻すと、操作とそれを確認する項目が画面の別の場所へ離れる。

**未指定・未知の `group` は「その他」として必ず描き、決して落とさない** — 落とすと、config に
`group` を書き足した瞬間にその項目が画面から消え、指差喚呼が 1 つ足りないまま試合開始のゲートだけが
開かない（原因はログにも画面にも出ない）。同じ理由でサーバーは `group` の語彙を検証せず素通しする
（既知の名前だけを許すと、UI がまだ知らない group で起動しなくなり、区分を持たないベンチ設定も
通らない）。対応表は `web/src/lib/checklistGroups.ts` ただ 1 つ。**「次」の強調は画面全体で 1 つ**、
**全体の進捗は上端に 1 箇所だけ**置く（ゲートは区分ごとではなく全項目の完了なので、区分ごとの進捗を
操縦者に足し算させてはならない）。

### 試合時間タイマーは「時刻」ではなく「配信瞬間の経過ミリ秒」を配る

操縦者 2 名 + Monitor は別ブラウザ・別 PC で繋がるため、開始時刻（エポック秒）を配って各自が引き算
する方式は使えない — **端末の壁時計が揃っている前提**になり、数秒ずれた 3 つのタイマーが平然と表示
され、ずれていることも画面から分からない。サーバーは `match_state` の `timer` に経過ミリ秒だけを載せ、
各デバイスはそれを起点に自分の単調時計で進める（サーバー `time.monotonic()` / クライアント
`performance.now()`。どちらも壁時計を使うと NTP 補正で試合中に残り時間が増える）。

**残り時間そのものを毎秒配ってはならない** — `match_state` を変化時のみ配信することで抑えている
再描画の前提が崩れ、さらに詰まった 1 台ではタイマーだけが凍って WS は「接続中」のままになる。秒表示の
更新は固定間隔ではなく**秒境界に合わせて**起こす（固定間隔だと端末ごとに起床位相がずれ、同じ値を
持っているのに繰り上がりが食い違って見える）。

**タイマーの状態はフェーズ遷移が成立した後にだけ動かす** — 試合中に届いた `match_start` はゲートで
弾かれるが、その手前で起点を引き直すと機体は動いたままタイマーだけが満了時間へ巻き戻る。**0 到達は
表示が止まるだけ**で、試合終了は操縦者の `match_finish` のまま（公式の計時が正であり、こちらの時計の
ずれで機体が止まる経路を作らない）。

### 開発用コマンドは起動オプションで語彙ごと開閉する

指差喚呼の一括チェック（`checklist_check_all`）は `--dev-tools` / `CBC_DEV_TOOLS=1` で起動したときだけ
受理する。既定を有効にすると「点検していないのに試合を開始できる」経路が常設される。フラグの正は
サーバーが持ち、接続直後の `server_info` で UI へ配る — 表示可否を Vite のビルド時定数にすると、同じ
`web/dist` を配る本番と開発で再ビルドが要り切り替えとして機能しない。ゲートは
`CommandSpec.requires_dev_tools`（サーバー）と `serverInfo.dev_tools`（UI の描画）の 2 重で、UI 側だけに
するとフラグ配信が壊れた瞬間に本番でも押せるボタンが残る。

## 5. 設定と起動

### 起動時に構成の曖昧さを黙って解決しない

シーケンスの登録（`main._load_sequence`）は**そのモジュール自身が定義した** `Sequence` サブクラス
だけを候補にし、**2 つ以上見つかったら起動を拒否する**。かつては `dir()` の並び（アルファベット順）
で最初の 1 つを返しており、`sequences/sub_hand.py` が何かの都合で `MotorCheckSequence` を import
しただけで `"MotorCheckSequence" < "SubHandSequence"` が成立し、サブハンドとして動作確認シーケンスが
登録された。症状は「sub_hand の `sequence_start` でなぜか両ハンドが動く」だけで、config からも
ログからも理由が読めない。

`SEQUENCE_CLASS` のような明示公開にしないのは、3 本すべてに宣言が要るうえ、書き忘れが「今までどおり
動く」形で通るため（軸名の衝突を `PositionTable.merged` が起動ごとに落とすのと同じ方針）。同じ理由で
**`main._DRIVER_MAP` は「種別 → 生成関数」のファクトリ表**で、4 種すべてがそこを通る。if 連鎖に戻すと、
足し忘れが「引数の足りない別物が黙って生成される」形に落ちる。

### 誤記は警告ではなく起動拒否

`health` / `can_buses` / `match` は PC 上に 1 組しか存在し得ないため `config/<robot>.yaml` には書けず、
書いてあったら移動先を示して**起動を拒否**する。ロボットごとの yaml に書けてしまうと読み込み側は片方の
値しか採用できず、もう片方が「書けるのに効かない設定」になるため。

### CAN インタフェースの `operstate` 判定は `== "down"` で書く。`!= "up"` にしてはならない

carrier を管理しないデバイス（`lo` / `tailscale0` など）は up でも `unknown` を返すので、`!= "up"`
にすると**「分からない」まで異常へ倒れる**。拾いたいのは管理上 down だけで、`ip link set <dev> down`
したデバイスは必ず `down` を返す（カーネルの `operstate_show()` が `!netif_running()` を無条件に
`IF_OPER_DOWN` へ上書きするため）。実機の CANable2（gs_usb）4 本は定常状態で `up` を返す
（2026-09-06 実測）。未確認なのは bus-off のときだけで、gs_usb は bus-off 自体を報告しないので
`down` には落ちない公算が高い —— 落ちない場合、この ERROR 1 行が案内する `setup_can.sh` は
bus-off に対しては的外れになる。

### しきい値の既定値は `lib/config_schema.py` にしか置かない

`health` の 4 値は `HealthThresholds` として必ず 1 組で運び、バラの引数に分解しない。分解すると 4 本の
うち 3 本だけ配線した経路が作れてしまい、残る 1 本だけが既定値のまま黙って効く（「途絶は config
どおりに見ているのに温度警告だけ既定の 65℃」が成立し、ログにも UI にも現れない）。同じ理由で、同じ
概念に別名を付けない（動作確認の鮮度判定も `feedback_timeout_ms`）。

### `sequences/*.py` に数値を書いてはならない

シーケンスは `move_to({"軸名": "位置名"})` の形で書き、単位換算・許容差・待ち時間はすべて位置定数
yaml が持つ。機構が変わったら yaml の数値だけを差し替える。

### 離散状態アクチュエータは新ドライバを作らず位置定数で表す

グリッパの開/閉、壁の初期/閉/開、電磁弁の開/閉は `positions` の名前付き状態として書く。`move_to` は
位置名でしか値を引けないため、定義した状態以外を送れないことが構造的に保証される。

### 電磁弁は `control_type: on_off` で、`duty` を流用しない

duty を使うと「duty 0.3 の電磁弁」という意味を持たない指令が config に書けてしまい、しかも基板は 0 か
非 0 かしか見ないので**症状が一切出ないまま**単位が食い違う。専用の制御タイプにしておけば、DC 基板宛の
つもりで書いた値は電磁弁基板が黙って捨てる（逆も同じ）。`on_off` 軸は到達判定を持たない（基板が弁の
開閉を観測できない）ので、`duty` 軸と同じく `settle_s` の固定待ちへ落ち、`manual:` は書けない。

### PID ゲインを実行中に差し替える経路は持たない

ゲインは `config/<robot>.yaml` の `pid:` だけが持ち、起動時に `main._build_position_pid` が読んで以後
動かない。実機で詰め直すのは机上の CLI（`scripts/tune_y_axis.py` + `config/bench/y_axis_tuning/`）で、
そちらはゲインの上書きをプロセス内に閉じるので config は書き換わらない。

この形にしておくと**「config に書いてある値 = 今動いている値」が構造的に保証される** —— 実行中に
差し替える口があると、良い値が決まる前の途中の値のまま試合に入れてしまい、しかもそれを画面から読めない
（かつて 0 で初期化した入力欄がそのまま送られ、`y_axis` の位置制御が無効になった。検証は負値だけを
弾くので `kp=0` は正常値として通る）。

### モータ名はロボット横断に一意

ヘルス表示・アクチュエータ動作確認・指差喚呼はどれもモータ名だけで突き合わせるため、同名が両機に
居ると片方の状態がもう片方の欄に現れる。症状は「値が出ているのに機体と合っていない」だけで、拒否も
ログも出ないので画面から原因が分からない。`can_id` と同じく `tests/test_robot_sequences.py` が固定
している。

**1 つの `CANManager` の中の重複は構成時に弾く**（`_add_device` が `can_id` の重複と同じ扱いで
`ValueError`。センサとモータを同じ名前空間で検査するのも、同じバス上の別デバイスで壊れ方が同じ
だから）。弾かないと `_motors` は**後勝ちで上書き**される一方 `_bus_motors` には**両方残る**ので、
受信ループは孤児になった先勝ちドライバへフィードバックを配り続け、**状態が永久に更新されないモータ**
ができる。ロボット横断の衝突だけは 1 つの `CANManager` からは原理的に検出できないので、上の静的
テストと分担している。

### ログの体裁は `lib/logging_setup.py` が単一情報源

`main.py` が起動時に 1 回だけ呼ぶ（レベルは `--log-level`。既定 info）。`logging.basicConfig` へ戻しては
ならない —— あれは既にハンドラが 1 本でもあると**黙って何もしない**ので、体裁の指定が例外も警告も
無しに無視される。

**HTTP のアクセスログは出さない**（`web.AppRunner(app, access_log=None)` と `aiohttp.access` を WARNING へ
落とす二重の歯止め）—— SPA を配るのでリロード 1 回で数十行出て、読みたい CAN・シーケンスのログを
押し流す一方、HTTP が通ったかどうかは UI の接続表示に出る。

**シーケンスのステップログはエンジンが `[main_hand] 2/22 …` の形で 1 箇所だけ出す。`sequences/*.py` の
各ステップに `logger.info` を書き戻してはならない** —— `@step` のラベルと同じ文字列が 2 箇所に増え、
ラベルを直すとログだけが古くなる（実際に `@step("ハンド閉じる (受け取り)")` の本体が
`[sub_hand] ハンド閉じる` を出していた。ラベルは UI に、写しは journal にしか出ないので食い違いに
気付けない）。

**起動ログから落としてはならない値**は台形プロファイルの 3 値（`velocity_ff` を含むのは、実行中に
変更できず UI にも配信されないので起動ログが唯一の読み口であるため）、動作確認の除外ステップ WARNING、
零点確定の手段が無い軸の ERROR、`後始末完了`。

### `lib/` で `asyncio.get_event_loop()` を使わない（`get_running_loop()` を使う）

前者は実行中のループが無い文脈で新しいループを黙って作る。そこへ渡した CAN 送信や WS 配信は「呼んだ
のに一度も走らない」形で消え、例外も警告も出ない。ブロッキング呼び出しの実行口は `BlockingRunner` と
して注入してあるので、テストのために本番の取得方法を patch する必要も無い。
`tests/test_server_encapsulation.py` が AST で禁止している。

## 6. サーバーと配信

### WS コマンドの語彙は `lib/commands.py` の `CommandSpec` が単一情報源

名前・許可フェーズ・拒否理由・緊急停止中の可否・ハンドラ名・拒否通知経路を同じ 1 行に置く。
`CommandSpec` はどのフィールドにも既定値を持たないので、コマンドを足す人はゲート方針を必ず宣言する
ことになる。語彙が「許可フェーズ表」「拒否文」「if-elif」へ分かれていると、どのゲート表にも載らない
コマンドが生まれ、「意図してゲート対象外にした」のか「書き忘れた」のかコードから読めなくなる。全
フェーズで通すなら `PHASES_ANY` を明示的に書く（＝素通りさせると宣言する）。**`lib/server.py` に語彙を
戻してはならない。**

### テレメトリ配信は 1 クライアントの不調で止めてはならない

配信は全クライアントへ直列に送るため、詰まった 1 台を無期限に待つと他の全員（Monitor 含む）の値が
凍る。しかも WebSocket は開いたままなので UI は「接続中」を出し続け、操縦者は凍った値を最新だと思って
見続ける。守る約束は 4 つ:

1. 送信には `_WS_SEND_TIMEOUT_S` を必ず通す（`WsHub.send_or_drop`）
2. 切り離しの `close()` は別タスクへ逃がす（`close()` も相手の応答を待つので、配信ループ上で await
   すると送信上限を設けた意味がなくなり同じ場所で詰まる）
3. **`WsHub.fanout` の反復は必ずクライアント集合のスナップショットに対して行う**（送信 1 通ごとに
   await が入り、その隙に `_ws_handler` が同じ集合を触る。操縦者のリロード 1 回で起きる。集合をそのまま
   回すと `RuntimeError: Set changed size during iteration` になり、例外ガードの無い `activate_e_stop` の
   経路では E-STOP を押した本人の WS が切れる）
4. `_broadcast_loop` の例外ガードを外さない

**この 4 つはどれも「配信経路が 1 本であること」に依存しているので、集合と送信は `lib/ws_hub.py` の
`WsHub` に閉じてある。** サーバー本体に置いていた頃は、経路を 1 つ足すたびに 4 つを守り直す必要があり、
実際に接続直後の 3 通（`server_info` / `match_state` / `motor_check_state`）が生の `send_str` で送られて
いて①も②も通っていなかった（aiohttp の `send_str` は相手が読まなくなると無期限に待つので、スリープに
入りかけたノート PC が 1 台繋いだだけで接続ハンドラが返らず、`finally` の切り離しも走らない）。
`WsHub` に閉じてあれば**経路を増やすにはここへメソッドを足すしかない**。

### WS メッセージの契約は 1 箇所で定義し、サーバーと UI が同じものを見る

両者がそれぞれ自分のサンプルを持つと、契約が食い違ったまま両方のテストが緑になる。一度これで
`health_change` に `robot` が載っていないのに UI が `typeof msg.robot === "string"` を受信条件にしていて、
ヘルス異常が 100% 捨てられたまま出荷しかけた（TS 側はサンプルを自分で捏造し、Python 側は `target` と
`to` しか見ていなかった）。

`tests/test_ws_contract.py` が実物の `RobotServer` に配信させたメッセージを `web/src/test/ws-contract.json`
へ焼き付け、`web/src/test/wsContract.test.ts` が同じファイルを `useRobotSocket` の**受信経路へ流し込む**
（型が合っていても受信条件が弾けば画面には何も出ないので、型アサーションでは足りない）。契約ファイルは
**手書き禁止**。サーバー側を変えたら `UPDATE_WS_CONTRACT=1 uv run pytest tests/test_ws_contract.py` で
再生成し、web/ 側の型と受信条件も必ず追従させること。

**契約は両方向を見る。** 「UI が読む値が実配信に在るか」だけでは、**サーバーが送っているのに TS が
知らない欄**を取りこぼす（`health.detail` が型にすら無く、サーバーの「判定不能」を画面が「異常なし」と
表示していた）。`wsContract.test.ts` の逆方向は実配信のキーを再帰的に列挙して宣言と突き合わせ、使わない
フィールドは `unused` に理由を書かせる。書かれていない欄が増えたら落ちる。

**サーバーの判定より UI が楽観的になってはならない。** `health.overall` はヘルス計算そのものが失敗した
ときに `down` へ倒れる（内訳は空、理由は `detail`）。内訳だけを見て「異常なし」を出すと、サーバーの
フェイルセーフが画面上で消える。

### 測れない項目は配信の境界で `null` へ倒す。`MotorState` の 4 値は float のままにする

制御経路（位置制御ループ・偏差監視・ホーミング）が float を前提にしているので、そこへ `None` を混ぜては
ならない —— 代わりに測定可否を `lib/drivers/base.py` の `TelemetrySupport`（`position` / `velocity` /
`current` / `temperature` を **必ず 1 組**で持つ。バラすと一部だけ配線した経路が作れるのは
`HealthThresholds` と同じ）が宣言し、倒すのは `lib/server.py` の `_measured_only()` と
`CANManager.health()` の `MotorHealthInfo.temperature` の 2 箇所だけにする。

可否は `control_type` で決め、**受信した状態から推測しない**（`decode_feedback` は DLC>=3 なら位置を
読むので、長いフレームが 1 通流れただけで DC 基板に位置が生える）。温度判定（`has_thermal_warning` /
`has_thermal_fault`）も同じ宣言でゲートする —— しきい値を 0 以下にした構成では「測っていない 0」が
そのまま警告・FAULT に化ける。

**位置を測れないモータの POS 欄にだけ、代わりに PC の指令値（`command`）を出す**（4 値とも `—` では画面が
そのモータについて何も言えない）。**これは実出力ではない** —— ファームの `max_duty` クランプ・
`everFed_` ゲート・ウォッチドッグ満了・緊急停止ラッチのどれでも基板は出していないので、`→` と `title` で
断る。**M3508 位置制御ループの軌道の中間目標をこの欄へ相乗りさせてはならない** —— あちらは配信して
いない値で、畳むと「今どこを狙っているか」と「何を指令したか」が同じ欄の中で入れ替わる。**実測値が
あるモータには出さない** —— M3508 は緊急停止しても `command` が残るため、この規則を外すと停止中の POS に
指令値が出る。

### 機体の健全性判定は 1 箇所だけが持つ

サーバー側は**最悪値への集約を `lib/health.worst_bus_health` だけが持つ**（`compute_overall` も
`/health` もそれを呼ぶ）。かつてランク表とその集約ループが `lib/server.py` に丸写しされており、片方だけ
直せる状態そのものだった。UI 側は `lib/healthVerdict.ts` に一本化する（2 箇所に書くと「Monitor は READY と
言うのに操縦者の画面は異常と言う」状態が生まれる）。

### 試合を開始できるかを決めるのはサーバーの `can_start_match` だけ

UI は理由を説明するだけで、`checklists` から開始可否を導出し直してはならない。一度これを `StartGate` で
やって、サーバーが「開始できる」と配信しているのに画面がボタンを殺す状態を作った（配信ロールが 1 つ
増えただけで試合が始められなくなる）。

## 7. ファームウェア

### ファームと PC 側はプロトコルの対

[`motor_driver_can_protocol.md`](motor_driver_can_protocol.md) を単一情報源とし、片方だけを変更しては
ならない。`firmware/lib/MotorCan/` が `Arduino.h` を include しないのは、native 環境
（`pio test -e native`）でプロトコル層と安全機構をテストできるようにするため。

### 基板は MCU も CAN の持ち方もビルド系も違う。ピン配置を他の基板から類推してはならない

**「サーボ基板」どうしでも類推してはならない。**

- **DC 用** … UNO R4 Minima + 内蔵 CAN（`D4`/`D5` 固定）
- **サーボ用** … 3 枚あり MCU が 2 種類にまたがる。**#0/#1 は Arduino Nano + MCP2515（SPI 外付け）**、
  **#2 は UNO R4 Minima + 内蔵 CAN**（MCP2515 は載っていない）
- **電磁弁用** … **STM32F303K8 + 内蔵 bxCAN**（`PA11`/`PA12` 固定）。出力は GPIO の ON/OFF が 6 本だけ
  （PWM も方向ピンも無い）。**この 1 枚だけ PlatformIO ではなく CubeMX + CMake**

**Nano 固有の制約は #0/#1 にしか当たらない**: `D11`/`D12`/`D13` を SPI が占有する（`D13` は SCK なので
ステータス LED に使えず RGB LED が担う。RGB は #0/#1 が `D9`、**#2 は `D8`** —— #2 では `D9` がサーボ）、
Flash 32KB / SRAM 2KB しかないのでライブラリを足したら使用率を必ず `-e nano` で確認する。スロットのピンは
**#0/#1 が `D4`〜`D8`、#2 は `D9`/`D11`/`D10`/`D6`/`D3`** で、避けるピンが MCU で逆になる。

**ファームは `firmware/servo/` の 1 プロジェクトのまま env を 2 つ持ち**、MCU 差は `src/can_backend.h` に
閉じる。**別プロジェクトにすると `config.h` が 2 つになり、`tests/test_firmware_version_sync.py` の
焼き忘れ検出が片方しか見なくなる。**

各 `main.cpp` / `app.cpp` の `static_assert` が `config.h` のピン衝突をビルド時に検出する。STM32 側は
HAL の `GPIOA` / `GPIOB` が `constexpr` 文脈で使えないため、`config.h` は**自前の `Port` enum でポートを
持つ**（HAL を取り込むと重複検査ごと消える）。**`static_assert` は CAN ピンだけでなく全ピンの重複も
見ること。** かつては CAN との衝突しか見ておらず、`config.h` の想定と実基板の配線がまるごと食い違っても
ビルドが通った（`DIS` として LOW/HIGH を振っていた `D7` が、実機では ch2 の方向ピンだった）。

### 送信バッファの本数は基板ごとに違う。同じ送信コードが基板ごとに違う壊れ方をする

DC（R4 内蔵 CAN）は**標準 ID の mailbox が 1 本だけ**、電磁弁（bxCAN）は 3 本、サーボ #0/#1（MCP2515）は
TX 3 本 + ライブラリが空きを待つ。**サーボ #2 は R4 内蔵 CAN なので DC と同じ 1 本。** 1 反復で全 ch ぶんを
まとめて送るコードは、DC では `INFO` が **1 通も出ず**、電磁弁では **6ch 中 2ch しか出ない**（無症状なのは
MCP2515 の #0/#1 だけ）。しかも `kInfoIntervalMs`(1000) が `feedback_interval_ms`(10) の整数倍なので位相が
固定され、**毎回同じ ch が永久に落ちる**。

**送信コードは全基板で 1 つのまま、下の規則を共通で満たす形にしてある**（`#if` で MCU 分岐させない ——
片方の MCU だけ直した状態が作れ、それこそがこの規則の戒めているものである）:

1. **送信 API の戻り値を捨てない**（唯一の口は各基板の `sendFrame()`。数える規則は
   `motorcan::TxFailCounter` が持ち、`kCanTxFailStreakAlarm`(50) で LED を赤へ倒す）
2. **空きを待たない**（詰まったバスの上で `loop()` が止まると、ウォッチドッグ満了の反映も出力の更新も
   止まる）
3. **`INFO` は 1 反復 1 通に割り、落ちた ch は添字を進めず次の反復で送り直す**（再送キューは持たない）
4. **`FEEDBACK` は落ちたら諦める**（次の周期が 10ms 後に来るので PC 側の STALE 判定 500ms には遠く届かない）

**PC 側は `INFO` の未受信を照合しない**（それが正しい）ので、この壊れ方は FAULT にならない。ただし
§3.4 の焼き忘れ検出（`GenericDriver.info_mismatch`）はその間だけ黙って働かなくなるので、起動から
`_FIRMWARE_INFO_GRACE_S`（3 秒）を過ぎても未受信のモータを `RobotServer._firmware_unconfirmed_motors` が
拾い、`safety.firmware_unconfirmed_motors` として配信する（診断ツリーに青チップ）。**これは「壊れて
いる」の報告ではなく「焼き忘れ検出が働いていない」の報告なので、FAULT にも `evaluateHealth` の異常判定にも
倒さない。** **拾うのは `FEEDBACK` が鮮度内で届いているモータだけ** —— 基板が丸ごと落ちていれば全
チャンネルが STALE になって `evaluateHealth` が既に warning で主張するので、ここでも言えば同じ事実を
2 度描くことになる。加えて**手当てが逆になる** —— 残したいのは「`FEEDBACK` は 10ms で届き続けているのに
`INFO` だけが出ない」ケースで、そこで電源・CAN 配線を疑っても必ず何も見つからない。**native テストでは
守れない層**なので、送信まわりを触ったら実機に書き込んで `candump` で確かめること。

### `PeriodicTimer` は符号なし差分で満了を判定し、満了のたびに起点を `nowMs` へ置く

`millis()` は約 **49.7 日**で 0 に戻る。符号つきの差や「次回満了時刻」を持つ実装だと折り返し直後に
**永久に満了しなくなり**、`FEEDBACK` が止まって PC 側は全モータ STALE、LED も消えたままになる。
起点を「前回 + interval」にするのも駄目で、処理が詰まって遅れたときに取り戻そうとして連続発火し、
送信バーストでバスを埋める。`MotorLoopTimer.h` が `Arduino.h` を include しないのは、native 環境で
折り返しを実時間を待たずに検証できるようにするためなので、その性質も崩さないこと。

**送信位相はチャンネルごとにずらす**（`PeriodicTimer::stagger`。起点を「次回満了が index/count の
位置に来るよう過去へ置く」）。式は 3 枚の `main.cpp` / `app.cpp` が各自で持たず、この 1 箇所に置く
—— 手で書き直した基板が 1 枚だけ同時送信に戻ると、他バスの周期送信と重なったときに調停待ちが伸びて
`FEEDBACK` の間隔が波打つ。

### ファームの版番号は `INFO` フレームで 1Hz 自己申告する

ピン配置やデバイス ID を変えたファームを一部の基板にだけ焼き忘れると、症状は「そのモータが応答しない」か
「違うものが動く」だけで CAN 越しには見えない。**プロトコルかピン配置を変えたら `config.h` の
`kFirmwareVersion` を必ず上げ、`config/**/*.yaml` の `expected_firmware` も同じコミットで揃えること。**
片方だけ動かすと、PC は INFO の申告値と期待値の不一致を FAULT として出すので、症状は**「正しく焼いたのに
全モータ FAULT」**になる。**この対はテストが機械的に守る** — `tests/test_firmware_version_sync.py` が
3 つの `config.h` を実際にパースし、`can_id` の上位 2bit で基板種別を決めて同梱の全 yaml と突き合わせる。
実際に一度、ファームだけを上げて config 側 26 箇所が丸ごと取り残された。

### 状態フラグの組み立ては `motorcan::composeFeedbackFlags()` だけが持つ

3 枚の `main.cpp` / `app.cpp` に書き写してはならない。GPIO も CAN も Arduino.h も HAL も触らない純関数で、
**到達を立てられるのはサーボスロットだけ**という規則を `BoardKind` で持つ（呼び出し側が `reached` に何を
渡しても DC / 電磁弁では立たない）。**センサスロットは緊急停止・ウォッチドッグ・到達を立てない**という
§5.2 の規則も同じ関数が持つ。写しがペリフェラルの翻訳単位にあった頃は native テストが 1 件も届かず、
**DC 基板と電磁弁基板に `flags |= status_flag::kReached;` を 1 行足しても全ケース緑**だった。

### 電流・温度・過電流・過熱は自作モタドラのプロトコルに無い

どの基板も測る手段を持たないので、**組み立てる側も読む側もコードを持たない**。常に 0 の値を運ぶと、UI にも
ヘルス判定にも「測ったように見える 0」が流れ込む。`FEEDBACK` に予約バイトは 1 つも無く（状態フラグ 1 バイト
+ 位置を持つ基板だけが 2 バイト。DLC は 1 か 3）、空きは状態フラグの **bit6-7 だけ**である。センサを積んだ
基板が現れたらそこに定義し直すこと。

### DC 基板はフィードバックを一切持たず、出力禁止ピン（`DIS`）も無い

エンコーダ・電流センス・温度センサとも非搭載で、受理するのは `duty` だけ（位置・速度制御と PID は実装ごと
存在しない）。止める手段は PWM 0% の一重しかないので、出力へ至る経路を `DcChannel::outputDuty()` の 1 本に
絞ってある。**この基板の動作は自動判定できない。** 動作確認シーケンスは `conveyor` を回して止めるところ
までを担い、回ったかどうかは `config/checklist.yaml` の `conveyor_run` で目視確認する。「回ったか」を
`FEEDBACK` の velocity で見る実装は実機では必ず失敗し、しかも原因が配線不良にしか見えない。

**`DcChannel::tick()` を `loop()` から毎周期呼び、出力が許可されていない周期のあいだ目標 duty そのものを
0 へ畳む。** `outputDuty()` は出力禁止中に 0 を返すだけで `duty_` を残すので、これが無いとウォッチドッグ
満了や緊急停止で止まった後に、**受理できない `SET_TARGET`（制御タイプ違い・DLC 不足）が 1 通届いただけで
途絶前の duty が復活する** —— 仕様書 §3.1 / §6 のとおり `handleChannelFrame` は受理できないフレームでも
ウォッチドッグを養う（`feed()` が妥当性検査より先）ので、目標は残ったままゲートだけが開く。症状は
**「操縦者は何も操作していないのにコンベアが回り出す」だけ**。サーボ基板には元からこの穴が無い
（`ServoChannel::tick()` が出力禁止中に毎ティック現在角へ畳む）ので、3 枚で扱いを揃えるためのものでもある。

### 電磁弁基板は「止める = 消磁」の一手しか持たない。停止時は全 ch OFF に倒す

緊急停止・ウォッチドッグ満了・CAN 不通のいずれでも通電を落とすので、**吸着で保持しているワークは落ちる**。
サーボの「現在角を保持」に相当する扱いは持たせていない — 通電したまま復旧不能になった弁は現場で切り分ける
手段が無く、断線でも確実に無通電へ倒れる方を選んでいる。出力へ至る経路は `SolenoidChannel::outputOn()` の
1 本だけで、そこが必ず `MotorSafety::isOutputAllowed()` を通る。**`app.cpp` に GPIO を直に叩く経路を作っては
ならない。**

**弁が開いたかは観測できない。到達フラグを立ててはならない。** 圧力センサもリミットスイッチも無く、分かる
のは「指令どおり GPIO を駆動した」ことだけ。指令の瞬間に到達を立てると、断線したソレノイドも抜けた
コネクタも「到達」と報告される。動作確認シーケンスは 6 個を 1 個ずつ開閉するところまでを担い、鳴ったかは
`config/checklist.yaml` の `valves_actuate` で打音・目視確認する。

**`config.h` のピン割当と CubeMX 生成 `main.h` が食い違ったときは、デバイス ID を
`kDeviceIdUnconfigured`（`0x00`）のまま残して止める。`MotorSafety::stop()`（緊急停止ラッチ）に預けては
ならない。** ラッチは CAN の `E_STOP` 解除フレームで外れ、PC は励磁のたびにそれを送る（`activation_steps()`
の個別解除と `_send_e_stop_clear_broadcast` の全バスブロードキャスト）。つまりラッチに預けると、**PC を
起動して励磁した時点で剥がれ、その後の `SET_TARGET` で間違ったポートの GPIO を叩く** —— 止まっているのは
電源投入から最初の励磁までだけになる。「CAN が上がらなかった場合」に `stop()` が有効なのは**解除フレームが
物理的に届かない**からであって、ポートの食い違いにその前提は無い（CAN は正常に上がる）。ID を未設定のまま
残せば `applyChannelOutput` が入口で return して GPIO へ 1 度も届かず、`FEEDBACK` も `INFO` も 1 通も出ず、
LED は `BoardIndication` が urgent（赤の速い点滅）へ倒す —— 新しいゲートを 1 つも増やさずに「弁を 1 つも
開かせない」が成立する。

### サーボ基板の 5 スロットは、どれもサーボ出力にもデジタル入力にもなる

スロット設定一式（役割 `Servo` / `TouchSensor` / `Unused`・ピン・初期角・可動範囲・パルス仕様・センサ極性）は
`config.h` の `kServoBoards[]` が**基板番号を明示した並び**として持ち、**それぞれ何個でもよい**（センサだけの
基板も成立する）。**基板ごとに分けてあるのは 1 つのバイナリを複数の基板へ焼くため** — 表が 1 つだと基板 #0 の
SV3 をスイッチにした瞬間に基板 #1 の SV3 も道連れになる。

**270 度サーボと 180 度サーボはスロットごと・基板ごとに混在できる** — 型は `pulse` が持ち、`SlotRole` は
「駆動するか、読むか、使わないか」だけを表す軸に保つ（型を `SlotRole` へ入れると `isServoSlot()` が
「どちらかである」に変わり、呼び出し側すべてが型を意識する）。変えるときはその基板の要素を書き換えるだけで、
**デバイス ID は動かさない**（**基板 #2 はピン配置が #0/#1 とまるで違うのに `0x50`〜`0x54` がスロット順に
並ぶ**のがその効き目）。`Unused` にしたスロットも ID を 1 つ予約したままにする。

**「行の添字 = 基板番号」をやめて基板番号を値で持つのは、バイナリが MCU ごとに分かれたため** — 1 つの表に
3 枚ぶんを並べると、R4 ビルドの静的検査が Nano 行の D4/D5 を内蔵 CAN との衝突と誤検出し、Nano ビルドは
R4 行の D9 を RGB との衝突と誤検出する（どちらも実在しない衝突なので、検査を緩めるしか通す方法が無くなる）。

**表に無い基板番号は全スロット `Unused` のまま据え置く** — 黙って基板 #0 の行を使うと、DIP を回しすぎた
基板が別の基板の役割とデバイス ID を名乗り、同じ ID の 2 ノードが違うデータを送ってバスがエラーフレームで
埋まる。据え置けば ID が付かないので、既存の「デバイス ID 未設定 → LED 赤の速い点滅・駆動拒否」へそのまま
乗る。同じ理由で `SlotRole` は **`Unused` を 0** にしてある。**ただしゼロ埋めは `pin = 0` としても現れる** —
役割は安全側へ倒れてもピンは倒れないので、`main.cpp` の `kFixedPins[]` が UART（D0/D1）を
`ENABLE_SERIAL_DEBUG` に依らず常に予約し、書き忘れた 1 行を `static_assert` で捕まえる。

### 1 スロット = 1 CAN デバイス。センサも自分のデバイス ID で `FEEDBACK` を送る

サーボのフレームに相乗りさせてはならない — 相乗り先の無い「センサだけの基板」が成立せず、載せられる個数も
予約ビットの数で頭打ちになる。センサの `FEEDBACK` はデバイス ID 未設定とセンサ入力だけで、**緊急停止と
ウォッチドッグは立てない**（駆動されないので意味を持たず、立てるとヘルス判定が FAULT を出し続ける）。
センサはどのコマンドも受け付けない。

### 基板のセンサ入力は「報告するだけ」。判断は PC 側が持つ

**接触は異常ではない** — ドライバの異常判定は `is_fault()` ただ 1 つなので、そこへ入れてはならない。入れると
原点合わせで触れさせるたびに機体が FAULT になりシーケンスが止まる
（`tests/drivers/test_generic.py::TestSensorInput::test_contact_is_not_an_abnormality` が固定）。**センサは
`motors:` ではなく `sensors:` セクションへ書く** — `motors:` に置くと動作確認・目標値再送・UI のモータ一覧に
「常に 0 のモータ」として並ぶ。**登録し忘れると受信ループがフレームを誰にも配らず、接触が PC まで届かない**
（照合する仕組みは無い）。

**`sensors:` にも `expected_firmware` を書く**（`SensorConfig` が持つ。`expected_angle_range_deg` は
書けない —— センサはサーボの型を持たない）。**駆動するモータが 1 台も無い基板では、これが焼き
忘れを拾う唯一の手段である** —— `motors:` 側の照合は `expected_firmware` を書いた対象としか
突き合わせないので、全スロットがセンサの基板は書かなければ照合対象がゼロになり、旧ファームの
まま焼き忘れても**「スイッチを押してもセンサ入力ビットが立たない」という配線不良と区別の付かない
形**でしか現れない。同じ基板にモータが載っている場合も省かない —— 「隣のモータが見ているから
不要」は「そのモータを消したら照合も消える」という見えない依存になる。

### 基板の再起動は `FEEDBACK` の「起動後未受信」ビットで PC へ知らせる

サーボ基板は `setup()` で `config.h` の初期角へ駆動するので、試合中の瞬断は「機構が勝手に飛ぶ」形で現れる。
PC は 20Hz で再送しているので 50ms 以内に何事もなかったように復帰し、これが無いと再起動そのものがどこにも
現れない（ウォッチドッグのビットは「一度でも受けた後の満了」でしか立たない）。`SET_PARAM` で入れた値も既定へ
戻っている。

### 未設定のチャンネルは `FEEDBACK` も `INFO` も 1 通も送らない

設定ミスの通知は基板の LED（赤の速い点滅）だけが担う。かつては CAN ID `0x300`（デバイス ID `0x00`）で送って
いたが、PC 側の `can_id` は `0x01`〜`0xFE` に限られるので **`0x300` を claim できるドライバは存在し得ず**、
その報告は誰にも届いていなかった。しかも未設定は「DIP を 8 以上へ回した」形で起きて基板 1 枚の全チャンネルが
同時に未設定になるため、2 枚が同時に未設定だと**異なるノードが同じ ID で異なるデータを送ってバスがエラー
フレームで埋まる**。**PC 側から見た症状は「その基板の全チャンネルが STALE」で、配線不良と区別が付かない。**
`GenericDriver.device_id_unconfigured` と `is_fault()` のその項は残してあるが（ビット位置を詰め直すと
bit4/bit5 が動き、PC とファームを同時に差し替えることになる）、**実機からは立たない。ここを設定ミスの防護と
読んではならない。**

### サーボの「安全機構 × 角度補間」の結線は `ServoChannel` だけが持つ

`MotorSafety` と `ServoMotion` を `servo/main.cpp` で直に組み合わせると、その規則がペリフェラルに埋まって
native テストが 1 件も掛からない。規則は 2 つ — 出力が許可されていない間の指令は `setTarget()` が**入口で**
拒否する（受け付けると、ラッチ中の再送のたびに補間が再アンカーされて緊急停止中にサーボが進む）、`tick()` は
補間を進める**前に**現在角で凍結する。駆動ゲートは `MotorSafety::isOutputAllowed()` ただ 1 つで、`everFed_`
（`SET_TARGET` を 1 通も受け取るまで出力しない）は `WATCHDOG_ENABLED 0` でも外れない。

### `constexpr` のループで `continue` を使わないこと

avr-gcc 7.3 は `constexpr` 評価中の `continue` で増分式を飛ばし、無限ループになって
「iteration count exceeds limit」でビルドが落ちる。条件は `if` の入れ子で書く。

なくする 5 つ**だけである —— これらは UI の作法ではなく安全機構の一部なので、他の安全条件と
並べて読めるようにしてある。

### 機体が動いているあいだ画面を覆ってはならない

モーダルにしてよいのは、押す前に出して押した瞬間に閉じる確認だけである。**動作確認の進捗と結果
（`MotorCheckPanel`）はモーダルではなくその場のインライン展開**にする。かつてはモーダルで、しかも
起動と同時に自動で開いていたため、**両ハンドの全アクチュエータが順に駆動されているあいだずっと
ヘッダーの EMG STOP がオーバーレイに覆われて押せなかった**（クリックは背景として吸われ、パネルが
閉じるだけ。`ModalProvider` の `openCount` はホットキーも封じる）。止める手段だけが画面から消える
壊れ方で、操縦者には「押したらパネルが閉じた」としか見えない。**中断は折りたたみの外側に置く。**

**`<dialog>` + `showModal()` は使わない** —— Esc で必ず閉じるため、解除経路を Reset ボタンのみに
限定する緊急停止オーバーレイの安全設計と両立しない。`components/ui/Modal.tsx` は `onClose` を
渡さなければ閉じられない構造になっている。

### 緊急停止オーバーレイを隠せるのは開発時だけで、隠しても解除の口を画面から消さない

解除（`Reset`）を載せる場所は、緊急停止そのものの表示しか無い。**オーバーレイを隠して何も
出さないと、UI から緊急停止を解除する手段が丸ごと消える** —— 再読み込みしても `e_stop_state` を
受け直して同じ状態へ戻るので、開き直しでも戻ってこない。隠したときは全幅の警告帯
（`EStopBanner`）が必ず代わりに出て、停止理由と `Reset` をそこへ載せる。**帯を出さずに隠せる
経路を作ってはならない。**

**隠してよいかは `serverInfo.dev_tools` を描画のたびに見る。** 保持した真偽値をそのまま使うと、
本番サーバーへ繋ぎ直しても隠れたままになる。UI 側の既定は `false` なので、フラグの配信が
欠けた瞬間はオーバーレイが戻る側へ倒れる。

隠すと `ModalProvider` の `openCount` が 0 になり、**緊急停止中もタブ切替のホットキーが効く**。
機体を動かす指令を塞ぐのはサーバーの `CommandSpec.allowed_during_e_stop` なので、隠しても機体が
動く側へは倒れない —— **画面を覆っていること自体を指令の防護として数えてはならない。**

### `RouteErrorBoundary` は `<Outlet />` だけに掛ける

ヘッダー・接続バナー・緊急停止のオーバーレイと警告帯は境界の外に置く。画面全体を包むと、描画が
落ちたときに**止める手段（EMG STOP）ごと消える**。

### EMG STOP の周囲に押下可能な要素を置かない

誤爆の向きは「隣のボタンを押そうとして EMG STOP を踏む」である。EMG STOP は赤地・大面積で常に同じ
位置にあるので、狙って外すのは隣の小さいボタンの側で、外した先が緊急停止になる（試合中に踏むと機体は
止まりシーケンスは降りる）。ヘッダー直下に来る帯の操作ボタンは**帯の先頭**に固定し、右端には押せない
もの（塞がれている理由・時計・状態チップ）だけを置く。**EMG STOP の手前の余白は装飾ではなく緩衝なので
詰めてはならない。** 適用範囲と実測の距離は [`web/design.md`](web/design.md)。

**ヘッダーの EMG STOP は点滅させない** —— 点滅は `EStopOverlay` / `ConnectionBanner` のような
**異常時にだけ画面へ出る要素に限る**。平常時に点滅している要素が 1 つでもあると「平常時に静かで、
異常時に自分から主張する」が成立しない。

### 切断中に楽観的更新をしない

`send()` は送れたかを返す。緊急停止のように送信の成否で画面が変わる操作は必ず戻り値を見ること ——
切断中に赤いオーバーレイを出すと、**機体は動いたままで、矛盾を示す接続バナーもその背後に隠れる**。
ただし黙って捨てるのも危険なので、送れなかったことは通知枠へ流す。


## 9. テスト

### テストを増やすこと自体は目的ではない。増えたテストが本当に噛むかを確かめる

テストを足した／張り替えたら、**本番コードにわざと 1 行の不具合を入れ、狙ったテストが落ちることを確認して
から元に戻す**。落ちなければ、そのテストは「実装が正しいこと」ではなく「実装が存在すること」しか見ていない。
行数もケース数も、噛んでいることの証拠にならない。

**特に「private 依存を公開 API へ張り替える」作業では、張り替えたつもりで守備範囲が狭まっていることがある。**
実例: `driver._state = MotorState(position=1.25)` は**デコード層を丸ごと迂回**しており、`decode_feedback` が
位置レンジを取り違えても（`POS_MIN`/`POS_MAX` を `VEL_MIN`/`VEL_MAX` に取り違える）検出できなかった。公開
経路 `update_state(frame)` へ張り替えて初めて検出できるようになった。「private を触らなくなった」ことは形の
改善であって、網が広がった証拠ではない。

### 多重防護の各層は、1 枚ずつ単独で確かめる

層が複数あると、統合経路のテストでは 1 枚壊しても他が拾ってしまい落ちない。それでは「壊しても落ちない層」が
残り、後で誰かがその層を消しても気付けない。他の層を持たない条件を作って、その層だけが効いていることを見る
テストを層ごとに置くこと。

**安全に直結する不変条件を触ったときは、必ずこの確認を行う。** 左右ペア軸の偏差検出 / フィードバック途絶で
電流 0 / 緊急停止インターロック / フェーズゲート / 動作確認との排他 / ヘルス判定不能は DOWN。

### テストの組み立てはヘルパへ集約し、内部へ手を伸ばす特権は 2 ファイルに閉じる

同じ組み立てが 10 ファイルに書き写されていると、実装を 1 つ変えるだけで全部が機械的に赤くなり、そのたびに
「モックの追従」としてテストを実装へ合わせ直すことになる。`tests/server_fixtures.py`（サーバーの組み立て・
駆動）と `tests/fake_can.py`（CAN 層のモックと受信状態の作成）だけが private へ手を伸ばしてよく、その理由を
各ファイル冒頭に書く。**テストの都合で本番へ注入口を生やさないため**の特権であり（「フィードバックが来た
ことにする」関数が本番に存在してよい理由は無い）、テスト本体は公開 API で書く。

特権も最小に使う — `deliver_frame`（宛先判定とデコードを実際に通す）で足りるなら `mark_feedback_at`
（時刻だけを置く）は使わない。後者だけのテストは途絶検出が壊れても緑になる。本番のモジュール private を
書き換える操作（送信上限の縮小など）もこの 2 ファイルに置く（散らすと、定数が別名へ移ったときに書き換え先
だけが古いまま残り、「上限を縮めたつもりで縮めていない」テストが 1 秒待ちながら緑を返す）。

ヘルパが作る土台そのものにも不変条件がある。**どれも「テストが緑でも本番の経路を 1 度も踏んでいない」
形で壊れる**:

- **実 `CANManager` の受信経路を通すテストは `fileno()` を返す偽バス（`ReadableBus`）を土台にする。**
  `mock_bus`（MagicMock）は `fileno()` が int を返さないので受信ループが**エグゼキュータ経由の
  フォールバックへ落ちる**。実機の SocketCAN が通るのは「fd の可読通知で起きて滞留を出し切る」
  経路（`_ReadableFd`）なので、モックだけで固めると**本番の経路を 1 度も踏まないテスト群**ができる
- **可読性は本物の `socketpair` で作り、1 通ごとに 1 バイト送ってはならない。** イベントループの
  `add_reader` は実 fd しか受け付けないので、偽物では「起こされる」ことそのものを検証できない。
  1 通ごとに送ると **socketpair の受信バッファが埋まって `send` がブロックする**（実際にハングした）
  —— 「残っている間は読めるままにする」を守れば 1 バイトで足りる
- **ドライバのモックは `telemetry` を明示的に宣言する**（`FULL_TELEMETRY`）。`MagicMock` の既定は
  truthy な `MagicMock` になり「4 値とも測れる」と同じ振る舞いを**偶然**するだけなので、配信側
  （`RobotServer._measured_only` / `CANManager.health`）が測定可否の宣言を読まなくなっても誰も
  気付けない。逆に `emergency_stop_message()` は敢えてスタブしない（既定戻り値が None ではないので、
  緊急停止がドライバ固有フレームを送る経路をテストが素通りしない）
- **ドライバのモックの `matches_feedback` は既定を False にする。** True 既定は「**誰宛でも配られる**」
  状態を土台にするので、宛先の振り分けを見るテストが自分で False を書き戻さない限り常に緑になる
- **テスト用のブロッキング実行口（`direct_runner`）は、その場で実行するだけでなく必ず 1 度は
  イベントループへ制御を返す**（`await asyncio.sleep(0)`）。本物の `run_in_executor` はスレッドの
  起床を挟むので必ず戻るが、戻らないスタブだと受信ループが 1 通も取れないまま回る状況で**テスト側の
  タスクが永久に走れず、失敗ではなくハングとして現れる**。差し替えは**コンストラクタ引数として公開
  されている口だけ**を使い、`patch("asyncio.get_event_loop")` のようにループ取得 API へ固着させない
  （正しい `get_running_loop()` へ直した瞬間に**テストが偽陽性で落ちる**）
- **`tests/server_fixtures.py` の `wait_reactivation` / `wait_reenergize` は `asyncio.wait` を使う**
  （`wait_for` / `gather` を使わない）。**これらのタスクはキャンセルされて終わることがある**ので、
  その `CancelledError` がテスト側へ伝播し、**後始末として待っただけのテストが落ちる**。なお「解除
  フレームを送り終えた後」の振る舞いを見るテストは、`_board_e_stop_ignore_before` が確定するのも
  再励磁を終えた後なので、必ずこの完了を待ってから観測すること（待たずに配信を 1 回回すと「解除した
  のに基板の停止が拾われない」ように見える）

**`tests/feedback_frames.py` は特権を持たない 3 つ目のヘルパで、役割が違う** —— 実機と同じフレームを組み立てて
`update_state` へ流し込む唯一の場所であり、**`driver._state = MotorState(...)` を書かないためにある**。
組み立てが各テストに写されていた頃は書式が実際にずれていた（M3508 の単回転角を符号付きで pack しており、
実機の 8192 カウント域を表現できなかった）。

### 層をまたぐ参照は公開 API だけを通す

`web/src/components/` に barrel（`index.ts`）は作らず常に実ファイルまで指す（oxlint の `import/no-cycle` を
効かせたまま依存グラフを読めるようにするため）。**同じ方針を Python にも通す** — `lib/control/` と
`lib/tuning/` の `__init__.py` は再エクスポートを持たない（`__all__` は実体の増減に追従しないので、放置すると
API 一覧として嘘をつく。実際に `control` の barrel は 200Hz の `DEFAULT_INTERVAL_S` だけを再輸出しており、
同名の定数を持つ `sync_monitor`・`limit_monitor`（50Hz）/ `target_refresh`（20Hz）がある以上、「control の既定周期は 200Hz」と
読ませていた）。
