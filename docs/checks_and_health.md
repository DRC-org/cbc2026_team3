# 点検とヘルスの全体像

「機体が正常か」を答える仕組みは 4 系統ある。**目的も頻度も判定者も違う**ので、
どれか 1 つに寄せることはできない。この文書はその 4 つの境界と、どこを触ると
何が壊れるかを 1 箇所にまとめる。

個別の設計判断の理由は `docs/invariants.md` に、実機で観測された事象の記録は `docs/history/` にある。
ここが答えるのは **「今どうなっているか」と「どこを見ればよいか」** だけ。

**試合当日に手が止まったときは `docs/venue_recovery.md`（会場カード）を見る。**
この文書は仕組みを説明するもので、詰まったときに上から読む長さではない。

**⚠ 現在ぶら下がっている穴**（詳細は各節）:

- **`y_axis` の零点確定は有効になったが、実機でまだ 1 度も走らせていない。**
  `direction` と左右 2 本のスイッチの極性（`sensorActiveLow`）が未実測なので、
  **初回は必ず人が付いて EMG STOP を押せる状態で回す**（「零点確定」節）
- **物理非常停止のたびに DM3520 の原点が黙って無効になる。** 電源が数秒落ちて
  モータ内部の原点が作り直され、PC 側に検出手段が無い。当面は「踏んだら零点確定を
  やり直す」で受ける（「零点確定」節の「既知の穴」）
- **CAN 復旧の `down`/`up` で電磁弁が消磁し、吸着ワークが落ちる**
  （「bus-off 復旧ウォッチドッグ」節）

## 4 系統の早見表

| | 答える問い | 頻度 | 判定するのは | 実装 |
|---|---|---|---|---|
| ① 受動ヘルス監視 | 今 CAN とモータは生きているか | 20Hz 配信 | サーバー | `lib/health.py` + `CANManager.health()` |
| ② 統合動作確認 | 指令したら本当に動くか | 準備中に 1 回 | シーケンスエンジン + 人 | `sequences/motor_check.py` |
| ③ 常駐保護 | 壊れる前に力を抜けるか | 200 / 50 / 20Hz | 各周期タスク | `lib/control/` |
| ④ 指差喚呼 | ①②が見られないものを人が見たか | 試合前 | 人 | `config/checklist.yaml` |

**②と④は対になっている。** 動作確認は全アクチュエータを動かすが、自動で合否を
出せるのは到達判定を持つ軸だけ。持たない軸（DC 基板の `duty`、電磁弁の `on_off`）は
「指令を出した」ところまでしか保証できないので、鳴ったか・回ったかは④が受け持つ。

## ① 受動ヘルス監視 — 生きているか

```
CANManager._last_rx_at (デコード成功時だけ更新)
        │
        ▼
CANManager.health(thresholds)      ← しきい値は config/system.yaml の health
        │  FAULT > STALE > WARNING > OK の順で判定
        ▼
RobotServer._compute_health()      ← 例外は必ず DOWN へ倒す
        │
        ├──> 20Hz WS 配信 (state.health)  ──> web: evaluateHealth()
        ├──> _diff_health() ──> health_change (変化時のみ)
        └──> GET /health (200 / 503)
```

**受動**なので、モータを動かさずに分かることしか answer しない。「フィードバックが
来ているか」「ドライバが異常フラグを立てているか」「温度が閾値を超えたか」の 3 つ。
**3 つ目は温度を測れるモータだけが対象**
（「温度を見ているのは温度センサを持つモータだけ」節）。

判定を書いてよい場所は 2 つだけ。**関数ではなくファイル単位の境界**である:

- サーバー側 — `lib/can_manager.py` の `health()`（優先度もここ）
- UI 側 — `web/src/lib/healthVerdict.ts`（`evaluateHealth()` の見出しチップ、
  `summarizeMotors()` のモータ一覧サマリー、`motorTempTone()` の温度色）

**画面の部品側に判定を書き足してはならない。** 一度 `MotorSummary` が自前で
「異常 N 件 / All operational」を出しており、FAULT のモータが行では赤バッジなのに
サマリーだけが緑を出していた（同じ画面に食い違う 3 つの表示が並んだ）。

しきい値の既定値は `lib/config_schema.py` の `HealthThresholds` にしかない。
**4 値は必ず 1 組で運ぶ**（バラすと 3 本だけ配線した経路が作れる）。

**UI が使う温度 2 値（`temp_warning_c` / `temp_critical_c`）は `server_info` で配る。**
接続直後に 1 度だけ届く（`lib/server.py` の `_server_info_dict()`）。UI 側にフォールバック値は
置かない —— 持つと config を変えても画面だけが古い境界で判定する二重管理が戻り、同じモータに
ついてサーバーと UI が違う答えを出す。**届いていない間は `neutral`（色を付けない）に倒す**。
適当な既定値で「正常」とも「警告」とも言わない。UI が使わない値（`feedback_timeout_ms` /
`tx_error_threshold`）は配らない（配ると「配られているのだから使ってよい」という別の写しの
根拠になる）。

**高温を UI が数え直してはならない。** 温度警告はサーバーが `temp_warning_c` を見て
`MotorHealth.state = warning` として既に配信している。`evaluateHealth()` が数えるのは
配信された健全性だけで、UI が別に数えると同じ 1 基が 2 件として計上される。

**UI はサーバーより楽観的な結論を出してはならない。** サーバーは健全性を計算できな
かったとき `overall=down` + 内訳空で「判定不能」を配る。内訳だけを見て「異常なし」を
返すと、そのフェイルセーフが画面上で消える。

### 温度を見ているのは温度センサを持つモータだけ

**「全モータの温度を見ている」と読んではならない。** 温度が判定に効くのは M3508 /
EDULITE 05 / DM3520 の 3 種だけで、**自作モタドラ（DC / サーボ / 電磁弁 / センサ）は
どの基板も温度を測る手段を持たない**（仕様書 §3.2）。

| | `MotorHealthInfo.temperature` | 温度警告 / FAULT | UI の温度欄 |
|---|---|---|---|
| M3508 / EDULITE 05 / DM3520 | 実測値 | `temp_warning_c` / `temp_critical_c` で判定 | 数値 + 温度色 |
| 自作モタドラ（`can_generic`） | `None` | **判定しない** | `—`（色を付けない） |

`MotorState.temperature` は制御経路が float を要求するため測れない基板でも 0.0 が
入っているが、それは詰め物であって測った値ではない。**倒すのは `CANManager.health()`
ただ 1 箇所**で、可否の宣言は `lib/drivers/base.py` の `TelemetrySupport` が単一情報源。
判定側（`MotorDriver.has_thermal_warning` / `has_thermal_fault`）も同じ宣言を見て降りる
—— しきい値を 0 以下にした構成では、素通しだと**「測っていない 0」がそのまま警告・
FAULT に化ける**。

したがって `can_generic` のモータが①に異常として出る経路は **STALE（フィードバック途絶）と
`is_fault()`（状態フラグ）だけ**である。**動いているかどうかは①では分からない** ——
そこは②の動作確認が指令を出すところまでを担い、回ったか・鳴ったかは④の指差喚呼
（`conveyor_run` / `conveyor_stop` / `valves_actuate` など）が人の目と耳で受け持つ。

`state.motors[]` の `pos` / `vel` / `torque` / `temp` も同じ規則で `null` になる
（詳細は `docs/invariants.md` の「測れない項目は配信の境界で `null` へ倒す」）。

**ただし POS 欄に `→0.30` / `→ON` と出ることがある。これは PC が最後に送った指令値で
あって実出力ではない。** ファームの `max_duty` クランプ・`everFed_` ゲート・
コマンドウォッチドッグ満了（`cbc-can-watchdog` の bus-off 復旧でも起きる）・緊急停止
ラッチ・基板の再起動のいずれでも基板は出しておらず、**基板が止まっていても値は載り続ける**
（緊急停止中だけは目標ごと捨てられるので `—` に戻る）。**ここも「動いているかどうか」には
答えない** —— 回ったか・鳴ったかは④の指差喚呼が受け持つ。

### 判定に使う数は「今も壊れているか」に答えられなければならない

`BusHealthInfo.tx_error_count` は**起動からの累計**で、表示専用である。判定は
`CANManager._tx_error_score`（失敗 +8 / 成功 -1 / 上限 255 の TEC 相当）が持つ。

累計で判定していた頃、物理緊急停止で DM3520 の電源が数秒落ちただけで
`tx_error_count` が 6320 まで積み上がり、**CAN が完全に復旧した後も
`dm3520_bus` が永久に DEGRADED のまま残った**（`ip -s link` は ERROR-ACTIVE・
bus-off 0 回・送受信ともエラー 0、フィードバックも 44ms 前まで届いていた）。
単調増加する数は「壊れたことがあるか」にしか答えられない。

### 自作モタドラのデバイス ID 未設定は、PC 側には「その基板の全 ch が STALE」としてしか出ない

**切り分けは基板の LED（赤の速い点滅）で行う。CAN 越しには区別が付かない。**
未設定のチャンネルは `FEEDBACK` も `INFO` も 1 通も送らない（仕様書 §2.2）ので、
報告を運ぶフレーム自体が存在しない。かつては CAN ID `0x300`（デバイス ID `0x00`）で
送っていたが、PC 側の `can_id` は `0x01`〜`0xFE` に限られるため **`0x300` を claim
できるドライバは存在せず**、その頃も PC には届いていなかった。

未設定は「DIP を 8 以上へ回した」形で起きるので**基板 1 枚の全チャンネルが同時に
未設定**になる。2 枚以上が同時に未設定だと、異なるノードが同じ ID `0x300` で
異なるデータを送ってエラーフレームの応酬になり、**バス全体が死ぬ**。送らないことに
した理由がこれで、通知を LED に寄せたのは代替ではなく唯一の手段である。

`GenericDriver.device_id_unconfigured`（状態フラグ bit3）とそれを見る `is_fault()` は
残してあるが、**実機からは立たない**（ビット位置を詰め直すと bit4/bit5 が動き、
PC とファームを同時に差し替えることになるため定義だけ保持している）。
**ここを設定ミスの防護と読んではならない。** 会場での手順は
`docs/venue_recovery.md` §3-2。

### bus-off はエラーフレームでしか観測できない

python-can 4.6 の `SocketcanBus` は `state` を実装していない（基底クラスの既定
`BusState.ACTIVE` が返る）。つまり `health()` の `ERROR` / `PASSIVE` 分岐は
**SocketCAN では永久に成立しない**。実バスの bus-off は
`CANManager._handle_error_frame()` が SocketCAN のエラーフレームから拾う。

ラッチは**実通信（送信成功・フィードバック受信）で外す**。`restart-ms` が 0 の
インタフェースは復帰通知（`CAN_ERR_RESTARTED`）を送らないので、それ以外に
外す経路が無いと一度立った DOWN が永久に残る（上の `tx_error_count` と同じ壊れ方）。

**`restart-ms` は 0 にしてはならない。** 0 は「bus-off から自動復帰しない」で、
カーネル既定でもある。バス上に 1 台しか居ない構成（`can_dm3520`）では相手の電源断
だけで ACK が返らなくなり TEC が 256 に達する。値は `config/can_buses.yaml` の
`restart_ms`（既定 100ms）が持ち、`scripts/setup_can.sh` が `ip link` へ渡す。

### だが現行の CANable2 では `restart-ms` を設定できない

SocketCAN の `restart-ms` は**ドライバが `do_set_mode` を実装している場合しか
受け付けられない**。CANable2 が使う `gs_usb` は実装しておらず、カーネルは
`EOPNOTSUPP`（`Error: Device doesn't support restart from Bus Off.`）を返す。
手動の `ip link set <if> type can restart` も同じ理由で通らない。ドライバ側の
恒久的な制約なので、`config` を変えても回避できない。

`setup_can.sh` は `bitrate` と `restart-ms` を**別のコマンドに分けて**発行し、
非対応を検出したら `restart-ms` 0 のまま続行して警告する。1 コマンドに束ねていた
頃は、非対応環境で**1 本も up できなかった**（しかも `bitrate` は先に適用されるので
「設定に失敗したのに bitrate だけ入っている」形になり、原因が読み取れない）。
起動ログの `restart-ms=` は要求値ではなく**インタフェースから読み戻した実効値**。

したがって bus-off へ落ちたバスを戻す経路は `down`/`up` しかない。カーネルには
任せられないので、**userspace の常駐（`scripts/can_watchdog.sh`）が受け持つ**。
PC 側のラッチは実通信で外れる設計なので、バスさえ戻れば表示も戻る。

### 実測: CANable2 は bus-off を報告しないし、自動復帰もしない

2026-08-30 に `can_edulite`（CANable2 / STM32G431・`clock 170000000` = FDCAN）を
**CAN 側に何も繋がない状態**で up し、`cangen` で ACK の返らないフレームを送って確認した。

- 送信は数通で**完全に停止する**（TX packets が増えず、`tc -s qdisc` の backlog が減らない）
- **30 秒待っても復帰しない。** ABOM 相当の自動復帰は無い。bxCAN 版の candleLight は
  `can_init()` で `CAN_MCR_ABOM` を立てるので自動復帰するが、CANable2 は FDCAN で、
  bus-off では `CCCR.INIT` がセットされたままホストの明示的な復帰要求を待つ。ファーム上流
  （`candle-usb/candleLight_fw` の `src/can/m_can.c`）は `GS_CAN_FEATURE_BUS_OFF_RECOVERY`
  を申告するが、**カーネル 7.0 の `gs_usb` はこの feature を知らない**（実装は
  `GS_CAN_FEATURE_GET_STATE` = BIT(13) まで）
- **`down` → `up`（＝ `scripts/setup_can.sh` の再実行）で確実に復旧する。** 再現性あり
- **PC 側からは状態が一切見えない**:
  - `can state` は落ちている間も **`ERROR-ACTIVE` のまま**。`bus-off` / `error-warn` /
    `error-pass` / `bus-errors` のカウンタも全部 0 のまま
  - エラーフレームが 1 通も届かない
  - `berr-reporting` は `requested control mode BERR-REPORTING not supported` で有効化できず、
    `GET_STATE` も未対応（`ip -details -s link show` に `txerr`/`rxerr` が出ない）

**したがって `_handle_error_frame()` の bus-off 検出は、この実機構成では発火しない。**
`30863fd` は「bus-off を立てる経路が存在しなかった」ことを直したが、アダプタが
エラーフレームを送らない以上、経路は依然として無い。実機で bus-off が現れるのは
**送信の失敗**（`tx_error_count` と送信スコア）と **qdisc の滞留**だけである。
自動復旧を作るなら、検出条件はエラーフレームではなくこの 2 つに置くこと。

### bus-off 復旧ウォッチドッグ（`scripts/can_watchdog.sh`）

`cbc-can-watchdog.service` として常駐し、1 秒周期で全バスを見る。機体を動かさない
（`down`/`up` しかしない）ので `cbc-can.service` と同じく **enable する** ——
制御プログラムだけが「電源投入で機体が待機状態にならない」ために enable されない。

**判定は `ip link` の state ではなく送信の滞留で行う。** 上の実測のとおり、落ちている
間もカーネルから見える状態は正常なままなので、state を見る実装は永久に発火しない。
条件は 2 つの AND:

- `tc -s qdisc` の backlog が 0 でない（＝送るものがキューに残っている）
- `ip -s link` の TX packets が前周期から 1 つも進んでいない

**どちらか片方では足りない。** backlog だけだと正常な連続送信の一瞬を拾って
**動いているバスを落とす**。TX packets だけだと「送るものが無いだけ」の平常時を
異常と読む。3 周期（既定）連続で成立したときにだけ `down`/`up` を出す。

**復旧には最短間隔（既定 5 秒）を置く。** 相手が最初から居ないバス（試合前で機体の
電源が入っていない）では復旧しても滞留は解消しないので、制限しないと `down`/`up` を
回し続ける。害はログ量だけだが、その害が大きい（journal が埋まって本物の異常が
沈む）。同じ理由で、連続復旧のログは 1 回目と 12 回に 1 回だけ出す。

**`bitrate` と `txqueuelen` は入れ直さない。** `down`/`up` をまたいで保たれることを
実測で確認済みで、入れ直すとその途中で失敗したときに元より悪い状態で残る。

判定ロジックは `tests/test_can_watchdog.py` が `ip` / `tc` のスタブで固定している。

#### ⚠ 復旧の `down`/`up` は基板のウォッチドッグを満了させる ——**吸着ワークは落ちる**

**この 2 つの仕組みは互いを知らない。** 復旧は `ip link` を 1 秒弱 down させるが、
そのあいだ PC からのフレームは 1 通も届かない。自作モタドラ 3 枚は
`WATCHDOG_ENABLED 1` で、`command_timeout_ms` の既定は **500ms**
（`docs/motor_driver_can_protocol.md`）なので、**復旧 1 回でウォッチドッグが満了しうる**。

満了したときに各基板がどう倒れるかは設計どおり別々で、うち 1 つだけが不可逆である:

| 基板 | 満了時の振る舞い | 復旧後 |
|---|---|---|
| サーボ | 現在角で凍結 | 20Hz の再送で 50ms 以内に戻る |
| DC | PWM 0%（止める手段はこれ一重） | 同上 |
| **電磁弁** | **全 ch OFF = 消磁** | 弁は開き直せるが、**落ちたワークは戻らない** |

電磁弁が「消磁へ倒す」のは意図した設計である —— 通電したまま復旧不能になった弁は
現場で切り分ける手段が無く、断線でも確実に無通電へ倒れるほうを選んでいる。
サーボの「現在角を保持」に相当する扱いは**持たせていない**。

**復旧に試合中かどうかのゲートは無い。** 誤発火はしにくい（backlog が残っている
**かつ** TX が 3 周期進まない、の AND）が、`can_generic` は両ハンドが物理共有する
バスであり、当然この監視の対象に入る。つまり**試合中に吸着したまま復旧が走りうる**。

ゲートを付けていないのは、試合中こそバスが戻らないと機体が丸ごと止まるためで、
「弁が落ちる」と「バスが戻らない」を比べれば後者のほうが重い。したがって**運用側で
受ける**:

> **試合中に journal へ `[ WD ]` が出たら、まず吸着ワークの落下を疑う。**
> **UI にも残る**（電磁弁基板は弁が開いたかを観測できないので、到達も落下も
> 直接は報告しない。届いた通り「CAN が何回途絶したか」までしか言えない —— 下の
> 「途絶エピソード数と UI 表示」節を参照）。手順は `docs/venue_recovery.md` §3-1。

### 受信ループは断絶で降りない（`rx_down`）

**ウォッチドッグの `down`/`up` で制御プログラムが道連れになっていた。**
`_receive_loop` は `bus.recv` の失敗をそのまま伝播させて降りる実装で、`down` の
1 秒で受信タスクが永久に失われた。`_tasks` は誰も await しないため死はログ 1 行に
しか現れず、症状は **「UI は接続中のまま、そのバスの全モータが STALE」** ——
`docs/invariants.md` が「最も復旧しにくい壊れ方」と呼んでいるものそのものだった。

前提が実測で覆ったのが直した理由:

```
① up      : send OK / recv フレーム受信
② down 中 : send・recv とも CanOperationError "Network is down [Errno 100]"
③ 再び up : 同じ socket のまま send OK / recv フレーム受信
```

**SocketCAN の socket は `ip link` の down/up を跨いで生き残る。** `down`/`up` は
ifindex を変えないので、待って呼び直せば戻る。バスを作り直す必要は無い
（復旧経路を増やすほど「復旧に失敗した中途半端な状態」が増える。ウォッチドッグが
`bitrate` を入れ直さないのと同じ理由）。

そこで受信側を送信側と同じ形にした —— `PeriodicTask._run` は tick ごとに例外を
握って回り続け、復旧すれば自力で戻る。**受信側だけが片道だったのが不具合の本体。**
再試行は 20ms から 200ms までのバックオフで、平常時（`_RECV_TIMEOUT` の
タイムアウトは成功であって失敗ではない）には 1 度も使われない。

**降りないだけでは足りない。黙って回り続けるのが最も危ない。** 読めていない間は
`_rx_down` を立て、`BusHealth.DOWN` として必ず見えるようにする。**`bus_off` へ
相乗りさせない** —— bus-off はコントローラがバスから切り離された状態、`rx_down` は
インタフェースが down している状態で、原因も復旧の手当ても別になる。1 つにまとめると
どちらが起きているのか画面からもログからも区別できない。外せる経路は
**実際にフレームを 1 通読めたときだけ**で、送信の成否でも、`recv` がタイムアウトで
`None` を返しただけでも外さない。

- 送信で外さないのは、インタフェースが戻って送信だけが通り、受信は死んだままという
  形を見逃さないため
- **タイムアウトで外さないのは実測に基づく。** python-can の socketcan は select が
  タイムアウトした時点で socket に触れずに `None` を返すので、**down している間も
  `None` は返り続ける**。最初これを復帰扱いにしていたところ、vcan を down させたまま
  「30ms で受信が再開しました」と誤判定し、`rx_down` は立った直後に外れて
  ヘルスは OK のままだった（実バスへの `ip link down/up` を通した検証で発覚）

**起動時点で既に down だった場合は、起動ログにも 1 行出る。** `main._create_bus()` が
`/sys/class/net/<名前>/operstate` を読み、`down` なら `CAN インタフェース '<名前>' は
down です (起動は続けます)` を ERROR で残す（**起動は拒否しない** ——「揃っているかに
答えるのは人である」の方針どおり、片ハンドだけの練習・机上ベンチ・会場での逃げ道を
潰さない）。実行中に落ちたぶんは上記の `rx_down` が拾うので、**起動時か実行中かが
ログの出どころで分かれる**。手順は `docs/venue_recovery.md` §3-2(a)。

### 途絶エピソード数と UI 表示（`rx_down_episodes` / `may_affect_workpiece`）

**`rx_down` は生の bool なので、1 秒に満たない一過性の途絶は画面に一瞬しか出ず、
機体を見ている操縦者はまず見落とす。** 試合中に journal を見る人はいない。
そこで `CANManager` はバス別に途絶の「立ち上がり」を数えるエピソード数
(`rx_down_episodes`) を持つ。数える場所は `_record_rx_down`（立ち上がりの瞬間）で、
`_clear_rx_down`（復帰の瞬間）ではない —— 復帰しないまま試合が終わったケース
（＝ワーク落下が起きたまさにその場合）を取りこぼさないため。**復帰しても 0 に
戻らない**。リセットは `CANManager.reset_rx_down_episodes()` が持ち、
`lib/server.py` の `_handle_match_start` が試合開始のたびに全ロボットへ呼ぶ
（`match_reset` ではなく `match_start` を選んだ理由は同メソッドのコメントを参照。
準備中に踏んだ途絶を試合開始時点で洗い流し、試合中に見える件数を「この試合で
実際に起きたこと」だけにするため）。

**途絶が全部ワーク落下に繋がるわけではない。** 電磁弁 6 個と両ポンプは
`config/sub_hand.yaml` で `generic_bus`（＝ `can_generic`）に載っているが、
`can_dm3520` や `can_m3508` の途絶ではワークは落ちない。**どのバスかを言わない
表示は意味を持たない。** 判定 (`BusHealthInfo.may_affect_workpiece`) は
「そのバスに `control_type: on_off` のモータが載っているか」を `CANManager.health()`
がドライバ自身 (`MotorDriver.has_on_off_control()`) に聞いて決める —— バス名や
`control_type` の文字列比較にすると、config で弁のバスを変えた瞬間に判定が
古いまま残る。

**`BusHealth`（OK/DEGRADED/DOWN）の判定そのものはここでは動かさない。** エピソード数と
`may_affect_workpiece` は付随情報として足すだけで、バスが復旧すれば従来どおり
`state: ok` に戻る。UI (`SubsystemStatus` の `WorkpieceRiskNotice`) はこの 2 つが
揃った (`may_affect_workpiece && rx_down_episodes > 0`) バスだけをチップで主張し、
0 件なら何も出さない。判定チップ (`evaluateHealth` の tone) はこれによって
変化しない —— バスが復旧すれば見出しは「異常なし」に戻るが、ワーク落下の通知は
リセットされるまで残り続ける（2 つの表示が別の役目を持つ）。

### 投げっぱなしタスクの失敗（`failed_tasks`）

**`asyncio.create_task` して待たないタスクが 3 つある。** 緊急停止解除の再励磁
（`_cmd_e_stop_release` → `_reactivate_motors`）・単発の再励磁
（`_cmd_reenergize_motors` → `_reenergize_motors`）・同期ずれ検出からの全体緊急停止
（`main._make_sync_violation_handler` → `activate_e_stop`）で、どれも
`add_done_callback` が集合から取り除くだけで `t.exception()` を取っていなかった。

かつては CPython の `Task exception was never retrieved` が journal に出るだけで、
**どのロボットのどの経路か・いつ起きたかは読めず、しかも出力は GC のタイミング任せ**
だった。とくに 3 つ目が飛ぶと「全体緊急停止が発火しなかった」ことが汎用メッセージに
しか残らない。`rx_down_episodes` を journal から UI へ出したのと同じ形に寄せてある
（試合中に journal を見る人はいない）。

- 口は `RobotServer.watch_task` ただ 1 つ。`safety.failed_tasks: string[]` として配る
- **平常時は空配列で無音。** `parseSafety` の既存の文字列配列ループにそのまま乗るので、
  パース経路も UI プリミティブも増えない
- **復帰しても消さない。** リセットは `match_start` の前縁リセットだけで、
  `reset_rx_down_episodes()` / `reset_jitter_stats()` と同じループ・同じ理由
- **`t.cancelled()` を先に見る。** `Task.exception()` はキャンセル済みタスクへ
  `CancelledError` を送出するので、見ないと `_on_shutdown` の一斉キャンセルで
  コールバック自身が例外を撒く
- 帰属は**失敗した経路の届く範囲**で決める。全体緊急停止の失敗は全ロボットへ
  （失敗した時点でどの機体も保護されていない）、単発の再励磁は対象 1 台へ

**この欄は tone を動かさず `forcedOpen` にもしない。** `firmware_unconfirmed_motors`
と同じ扱いで、診断ツリーを畳んだままにする。強制展開が要る場面はこの欄が単独で
立つことはなく、別の欄が同時に立って主張するため —— 同期ずれからの緊急停止が
失敗したケースでは `SyncMonitor.violated` がラッチして `safety.sync_violations` が
立ち、`describeSafetyIssues` が tone error へ倒して診断ツリーを開く。再励磁の失敗も、
励磁状態を報告するドライバ（EDULITE 05 / DM3520）なら `_unenergized_motors` の
`is_energized() is False` 側で拾われる。**この依存関係が崩れたら（同時に立つ欄が
無くなったら）、こちらを主張側へ倒し直すこと。**

journal で追うときに探す文字列は `投げっぱなしタスクが失敗しました` である。

### 受信の中断は M3508 の累積角を飛ばす

**受信が戻っても、位置は戻らない。** M3508 の多回転累積は「半周を超える差分は
0 を跨いだ折り返し」という推定に立っており、これは 1kHz で届き続けている間しか
成り立たない。中断した窓でモータ軸が半周以上回ると方向を取り違え、累積角に
1 回転（360deg）が乗る。

`y_axis` の scale 55.0131deg/mm では **6.54mm**。`sync_tolerance` は現在 **10.0mm**
なので 1 回転の注入はこの内側に収まり、**注入 1 発では止まらない**
（検出経路は再アンカーの WARNING（`health_detail()`）だけになる）。

**窓は受信の中断だけでなく、受信の取りこぼしでも開く。しかもそちらは黙って開く。**
カーネルのソケットバッファが溢れると、その分のフレームは PC まで届かない
（実機では `can_m3508` の受信 369 万通に対し **77 万通 = 17%** が `rx_dropped`）。
残ったフレームは滞留から詰めて処理されるので、**処理時刻で測った間隔は 1ms 程度に
しか見えない** —— 窓の長さを `time.monotonic()` で測っていた頃は、この状況でだけ
ガードが素通りし、巡航 200mm/s（モータ軸 1834rpm）ならわずか **16ms 分**の取りこぼしで
360deg が入りながら**再アンカーの記録も残らなかった**。現在は窓の長さを
**フレーム自身のタイムスタンプ**（SocketCAN のカーネル受信時刻）で測る。

取りこぼしそのものはヘルスに載っていないので、**疑ったら
`ip -s link show can_m3508` の `dropped` を見ること**（積み上がっていれば受信が
追いついていない）。受信経路が 1 通ごとにエグゼキュータへ往復しないことは
`lib/can_manager.py` の `_ReadableFd` が担っており、経緯は `docs/history/incidents.md` の
「受信の取りこぼしと累積角への 360deg 注入」にある。

`M3508Driver` は窓を跨いだ推定を拒み、差分を積まずに再アンカーする。判定は 2 つの
OR で、どちらか一方でも引っ掛かれば推定をやめる:

- 窓の間に回りえた回転数が半周に届くか。窓の**前後**で観測した rpm の大きいほうから
  見積もる（昇降軸は窓の間フィードバック途絶で電流 0 に落ちるため重力で加速する ——
  入口の rpm だけでは上限にならない）
- 窓そのものが長すぎるか（既定 100ms）。両端の rpm がたまたま 0 に見える
  「回って戻った」場合の歯止め。`feedback_timeout_ms` を流用しないのは、あちらが
  「途絶とみなす境界」でこちらの「折り返しを推定できる境界」とは別概念のため

再アンカーすると窓の中の実移動量は累積角から失われる。それでも 1 回転を捏造するより
誤差は小さい（推定を続けると実移動量に**加えて**必ず 360deg が乗る）。

**失った量は測れないので、代わりに「原点はもう信用できない」ことを報告する。**
`health_detail()` が `MotorHealth` を WARNING へ倒し、`MotorHealthInfo.detail` に
理由を載せる。**状態を OK に置いたまま detail だけ載せてはならない** ——
`summarizeMotors` が「All operational」を出して `SubsystemStatus` は畳んだままになり、
報告はどの画面にも現れない（「報告した」つもりの黙殺が成立する）。信頼を戻す経路は
原点の確定（`reset_multi_turn_origin`）だけで、受信の復帰では戻らない。

### センサの接触は「異常」ではなく「情報」として配る

自作基板のセンサスロット（原点スイッチ）は `state.sensors` に
`{ "<センサ名>": { "active": bool|null, "stale": bool } }` として載る
（`RobotServer._sensor_states`）。UI は `SubsystemStatus` の配下の `SensorSummary` が
描き、**モータ一覧には混ぜない**（サーバーが `sensors:` を `motors:` と分けているのと
同じ理由 —— モータ一覧に「常に 0 のモータ」が並ぶ）。

- **接触に警告色を使わない。** 原点合わせは「触れさせる」操作なので、接触は平常の
  情報である。ドライバの `is_fault()` に入れてはならないのと同じ判断
  （`tests/drivers/test_generic.py::TestSensorInput::test_contact_is_not_an_abnormality`）
- **異常なのは `stale` の方。** 鮮度の境界は `HealthThresholds.feedback_timeout_ms`
  ただ 1 つで、サーバーにも UI にも別の既定値を置かない。`CANManager.health()` も
  同じ鮮度でセンサを STALE に倒しているので、**件数の集計はそちらが持つ**
  （UI 側で 2 つ目の判定を作らない）
- `active` の `null` は「接触を報告する手段が無いドライバ」で、`false`（触れていない）
  と混ぜない。`—` を描く

**これは①が答えられる範囲を広げただけで、④の `origin_sensor_react` は要る。**
未配線・極性違いのセンサは STALE にならない —— 基板は役割が `TouchSensor` なら配線の
有無に関わらず `FEEDBACK` を送り、`INPUT_PULLUP` の負論理で「接触なし」を報告し続ける。
**触れてみる以外に検出手段が無い。** 変わったのは「触れた結果を画面で読めるように
なった」ことで、それまでは `candump` を打つしかなかった。

### DM3520 は固定小数点レンジを読み返せるまで励磁しない

`p_max` / `v_max` / `t_max`（レジスタ `0x15` / `0x16` / `0x17`）は**フラッシュへ
保存されないので電源断で出荷値へ戻る**。config とずれるとフィードバックが比例倍で
読め、`activation_steps()` はその値を「現在角」として保持目標に書くので、**励磁した
瞬間に機構が飛ぶ**（2026-09-09 に実機で発生。12.5 のドライバを 1000 で復号して 80 倍の
位置を読み、リミットスイッチを踏み越えて機構端まで走った）。

そのため励磁の手前で 3 レジスタとも読み返し、**食い違っていたら config の値を書いて
もう一度読み返す**。それでも一致しなければ、読み返せなかったときと同じく**励磁しない**
（`Dm3520Driver.activation_block_reason`）。読み書きは
`CANManager._confirm_configuration` が確認できるまで（鮮度待ちと同じ 0.5 秒の締切まで）
送り直すので、応答が 1〜2 通落ちただけでは止まらない。

**書き直しはフラッシュへ保存しない（`0xAA` を送らない）。** 寿命が約 1 万回なので、
電源が入るたびに焼けば確実に潰れる。揮発は承知のうえで**電源が入るたびに書き直す**。
書いたときは前後の値が INFO でログに出る（`レンジを書き直します: p_max 12.5 -> 1000`）——
これが「ドライバの電源が落ちた」の唯一の痕跡になる。

画面には `MotorHealthInfo.detail`（`MotorHealth.WARNING`）として出る。**FAULT ではない**
—— ドライバが異常を報告したのではなく、PC 側が安全側へ倒した判断だからである。

| detail | 意味 | 手当て |
|---|---|---|
| 固定小数点レンジ 未確認 | 読み返しの応答が 1 通も届いていない | 電源・CAN 配線（`can_dm3520`）。バスが生きていれば `FEEDBACK` も止まっているはずなので STALE も併発する |
| 固定小数点レンジ 食い違い | **PC が書き直しても**読み返しが変わらない | config の値がその機種で受け付けられる範囲か疑う（レンジ外の値は実機が黙って捨てて元の値を返す）。手で書くなら `config/bench/dm3520/checklist.yaml` |

### 「励磁されていない」はヘルスに現れない

DM3520 は指令フレームを無励磁のまま受理して黙って捨てる。ドライバの通信途絶保護や
電源の瞬断で励磁が外れると、PC は 20Hz で位置指令を送り続け、フィードバックも正常に
届き、`is_fault()`（エラー符号 0x5 以上）にも掛からないのでモータのヘルスは **OK の
まま**になる。操縦者に見えるのは「指令しても動かない」だけで、原因はどこにも出ない。

そこで `MotorDriver.is_energized()`（判定手段が無いドライバは `None`）を
`RobotServer._unenergized_motors()` が読み、`state.safety.unenergized_motors` として
配信する。緊急停止中は無励磁が正しい状態なので報告しない。**この緊急停止ガードが
唯一の抑止で、`activate_e_stop` 側にも同じ判定を置いてはならない**（片方を消しても
症状が出なくなり、後で本物のガードを消しても気付けなくなる）。

`None` を「無励磁」へ倒さないこと。自作モタドラも C620 も励磁の有無を報告しないので、
倒すと常時警告になる（「測ったように見える 0」と同じ罠）。

#### EDULITE 05 でも実際に起きた（2026-09-05）

**UNDERVOLTAGE（低電圧）で fault になって励磁が落ちた後、fault が消えても自動では
励磁に戻らない。** `mode_state` は 0（Reset）のまま、フィードバックは正常に届き続け、
`fault_bits` が 0 に戻っているので `is_fault()` にも掛からない —— **ヘルスは OK のまま
「指令しても動かない」だけが残る**。上の DM3520 と同じ型の異常が、別の原因で成立する。

**復帰には `activate_motors` を通る経路が要る。** 目標値再送
（`QueryDrivenTargetRefresher`）は enable を 1 通も送らないので、いくら待っても戻らない。
経路は 3 つ:

- **操縦者が `reenergize_motors` コマンドを送る（推奨）。** 機体を止めずに使える唯一の
  経路で、試合中でも押せる。可否はサーバーが決め、UI は `state.safety.unenergized_motors`
  が空でない画面（操縦者自身のタブ）にだけボタンを出す。緊急停止中・動作確認の実行中・
  同じロボットへの二重投入は拒否する（`RobotServer._cmd_reenergize_motors`）。**自動では
  呼ばない** —— fault が再発し続けるモータへ無限に励磁し直す経路を作らないため、常に
  操縦者の明示操作を要る
- 緊急停止の解除（`_reactivate_motors`）。試合を止める（緊急停止を経由する）ので、
  上のコマンドが使えないとき（例えば操作モードや UI が使えない状況）の代替
- `main.py` の再起動。同じく試合を止める、最後の手段

**`reenergize_motors` は「現在角を目標に書いてから励磁する」を 1 周期も破らない。**
`activate_motors` 自体は EDULITE 05 / DM3520 とも現在角を書いてから enable するが、
フォルト直前の古い目標（`move_to` の行き先）や `QueryDrivenTargetRefresher` のラッチ
（「今の姿勢を保て」）が生きたままだと、enable した直後の再送（最大 20Hz = 50ms 後）が
その古い値で上書きし、機構が古い目標へ動き出しうる。そのため**無励磁のモータだけに
絞って**目標とラッチを剥がし（`_TargetRefresherBase.clear_target`）、**そのモータだけ**
`activate_motors(only=...)` で励磁する（`CANManager._activate_each_motor`）。対象を
「無励磁のモータだけ」に絞るのは、同じバスの他モータが移動中なら `wait_reached` を
巻き込んで中断させてしまうことと、絞らずに全モータへ渡すと**健全で移動中のモータ**まで
「現在角を書いてから enable」に割り込ませてしまう（一瞬止めて enable し直す形になる）ため。
**手動操縦のジョグ起点も同じタイミングで捨てる**
（`ManualController.reset_axes_for_motors()`）——無励磁のあいだ機構が自重で下がって
いた場合、古い起点のまま再開すると次のジョグがその分だけ飛ぶ。緊急停止解除
（`activate_e_stop` → `on_e_stop()`）と同じ理由だが、**捨てる範囲は違う** ——
あちらは機体が止まっているのでロボット全体でよいが、再励磁は「機体を止めずに」が
売りなので、**対象モータが属する軸だけ**に絞る（落ちたのが `sub_lift` 1 台でも
無関係な `sub_y_axis` の起点まで消えてはならない。ジョグの起点は「直前に手動で
送った目標値」であることに意味がある）。**対象が 1 台も無ければ CAN へ 1 通も
出さずに降りる**（`dropped` は `_inactive_motors` を合併して作るので、空なら
前回の失敗も残っていない）。

**励磁の前に、電源断で失われる設定を送り直す。** 再励磁はどちらの経路も
「物理非常停止でドライバの電源が落ちたかもしれないところからの復帰」なので、
`CANManager.activate_motors` が `reinitialization_steps()` を先に送る（DM3520 の
`CTRL_MODE` 書き直しと固定小数点レンジの読み返しやり直し。戻っていればそのまま
書き直す。1 台あたり +0.1 秒、レンジを書き直すぶんが最大 +0.2 秒）。
**励磁中だと分かっているモータへは送らない** —— 先頭が `disable` なので、
直結ペアの健全な相方へ届けば保持トルクをその場で失う。詳細と落ちる先は
「零点確定（ホーミング）」節の「既知の穴」に続く段。

**在飛中（100ms〜1.5 秒）は `state.safety.reenergizing` が立つ。** UI はその間
ボタンを「処理中…」で無効にする —— `unenergized_motors` はまだ消えない（励磁が
次のフィードバックへ反映されるまで分からない）ので、これが無いと操縦者は
「押しても何も起きない」と読んで 2 回目を押す。**この在飛中は同じロボットの
`sequence_start` / `sequence_jump` / `trigger` を拒否する**
（`CommandSpec.blocked_during_reenergize`）—— シーケンスの `move_to` が書いた目標を
「フォルト前の現在角」が上書きすると、`wait_reached` は動かない位置を見続けて
`SequenceTimeoutError` になる。**逆方向（シーケンス実行中の再励磁）は塞がない**
——励磁が落ちるのはたいていシーケンスを走らせている最中なので、そこで使えなければ
直したい状況が直せない。

**直結ペア（`rotate` = EDULITE 05 ×2）は片側だけが無励磁でも相方ごと対象にする**
（docs/invariants.md「ペア軸に片側だけ効く操作を作らない」）。片側だけを剥がして励磁すると、
相方が移動中なら「無励磁で連れ回されていた片側」を「相方に逆らって現在角を保持する
片側」へ変えるだけになり、直後に `SyncMonitor` の偏差超過で試合が止まる。判定は
`SyncMonitor.groups`（`SyncGroup.members` からモータ名を引く）で行い、無励磁の
モータが属するグループの全モータを対象へ合併する。相方の `wait_reached` が
割り込まれるのは許容する —— そのペアは片側の無励磁で既に破綻していたので、
割り込みは「壊れていた」ことの正しい反映であって新たな害ではない。`y_axis`
（M3508）は `is_energized()` が常に `None` を返すのでこの経路には現れない。

**相方拡張は「励磁中のモータへ `disable` を送らない」に依存している。**
`only` には健全で励磁中のモータが混ざるが、`CANManager.activate_motor` は
鮮度確認に `feedback_probe_message()`（EDULITE 05 / DM3520 とも **disable**）を
使う。そのまま打つと相方が保持トルクを失い、宣言順（`rotate_r` → `rotate_l`）
次第で**軸が両側とも無励磁になる窓**（最悪 550ms）が開く（ワークを掴んだまま
押す操作なので落下しうる）。判断は `CANManager._may_probe_for_feedback` が
`is_energized()` の三値で 1 箇所だけ持ち、`True` のモータへは打たない ——
励磁中なら `QueryDrivenTargetRefresher`（20Hz）への応答で鮮度は満たされ、
届かなければ従来どおり無励磁のまま残す。`after_set_zero`（零点確定）の経路だけは
必ず打つ（直前に `deactivation_steps()` を送っており、無励磁であることを指令として
知っているため）。

**再励磁のあいだ `SyncMonitor` は止めない。** 零点確定
（`capture_origin_via_set_zero`）が `suspend_group` で止めるのは「その間モータは
無励磁なので押し合いは原理的に起きない」からで、再励磁ではそれが落ちた側にしか
当てはまらない（相方は励磁されたまま押しうる）。原点も動かさないので偏差は
そのまま機構の実際のずれを表す。再励磁が書くのは剥がす前も後も「今いる位置」
だけなのでずれを増やさず、既に許容差を超えているなら押さなくても発報する。

**切り分けの順序**: 「指令しても動かない」ときは、静止摩擦や機構の引っかかりを疑う前に
**まず励磁状態（`state.safety.unenergized_motors`）を見る**。CAN のフィードバックは
無励磁でも正常に届くので、鮮度（STALE）からもヘルスからも区別が付かない。

### 「焼き忘れ検出が働いていない」もヘルスに現れない

自作モタドラ（`GenericDriver`）の焼き忘れ検出（`info_mismatch`、§3.4）は `INFO` を
1 通でも受けて初めて働く。ところが `INFO` は送信バッファの都合だけで 1 通も出ないことが
ある（`docs/invariants.md` 「送信バッファの本数は基板ごとに違う」節。DC 基板は mailbox が 1 本しか
無く、1 反復で全 ch ぶんまとめて送るコードでは `INFO` が丸ごと落ちる）。PC 側は `INFO`
の未受信を FAULT にしない（それが正しい —— 未受信を不一致にすると起動のたびに全サーボが
FAULT になる）ので、この壊れ方は上の「励磁されていない」と同じ形で **ヘルスにも
`is_fault()` にも一切現れない**。

そこで `MotorDriver.firmware_confirmed()`（`INFO` を送らないドライバ = M3508 /
EDULITE 05 / DM3520 は `None`）を `RobotServer._firmware_unconfirmed_motors()` が読み、
起動から `_FIRMWARE_INFO_GRACE_S`（3 秒。`INFO` は 1Hz なので数秒で埋まるのが正常）を
過ぎても未受信のモータを `state.safety.firmware_unconfirmed_motors` として配信する。
診断ツリーには青チップ（`FirmwareUnconfirmedNotice`）で出るだけで、`evaluateHealth` の
判定（tone）は動かさない —— **これは「壊れている」ではなく「焼き忘れがあっても
気付けない状態」の報告**であり、機体そのものは正常なことが多い。

**拾うのはフィードバックが鮮度内（`feedback_timeout_ms`）で届いているモータだけ。**
基板が丸ごと落ちていれば `INFO` も当然来ないが、それは全チャンネルの STALE として
`evaluateHealth` が既に `要確認 N 件`（warning）で主張し、診断ツリーを強制展開する。
ここでも言えば同じ事実を 2 度描くことになり、しかも**手当てが逆になる** —— この報告が
残したいのは「`FEEDBACK` は 10ms で届き続けているのに `INFO` だけが 1 通も出ない」
ケースなので、電源・CAN 配線を疑っても必ず何も見つからない（配線が正常だから
`FEEDBACK` が来ている）。直すべきはファーム側の `INFO` 送信経路で、確かめる手段は
`candump`。UI の文面もそう案内する。

**対象にはセンサ（`sensors:`）も含む。** `SensorConfig` にも `expected_firmware` を
書けるので、照合が働いていないセンサは同じ 1 欄（`safety.firmware_unconfirmed_motors`。
配信フィールド名は変えていない）に並ぶ。

**センサ側の照合が要るのは、駆動するモータが 1 台も無い基板があるからである。**
サーボ基板 #1 は 5 スロットとも `TouchSensor` で、この基板には `motors:` の照合対象が
1 つも無い。センサで照合できないと、この基板だけ旧ファームのまま焼き忘れても
**「スイッチを押してもセンサ入力ビットが立たない」という配線不良と区別の付かない形**
でしか現れない。同じ基板にモータが載っている場合（基板 #0）も書く —— 「隣のモータが
見ているから省いてよい」は「そのモータを消したら照合も消える」という見えない依存になる。

## ② 統合動作確認 — 動くか

**両ハンドを 1 本のシーケンスで順に駆動する。** 機体ごとに独立していた頃は 2 つを
同時に起動でき、可動域の重なる位置で干渉しえた。

```
Monitor の設定面 [動作確認]
        │  motor_check_start (WS) / POST /motor_check
        ▼
MotorCheckController.deny_reason()       ← 起動できるかの唯一の判定
        │  ①未登録 ⑥既に実行中          ← コントローラ自身の条件
        │  ②試合中 ③緊急停止中 ④どれかが手動 ⑤どれかがシーケンス実行中
        │                                 ← RobotServer._motor_check_environment_deny()
        ▼
MotorCheckController.start()
        │  全ロボットの target_refresher を pause（position_loop は止めない）
        ▼
MotorCheckSequence.run()          ← sequences/motor_check.py
        │
        ├── 零点確定 (lib/sequence/homing.py)
        ├── メインハンド: y 軸 → 回転 → グリッパ → 壁 → コンベア
        ├── サブハンド: アーム → 補助ハンド → 電磁弁 ×6 → ポンプ ×2
        └── 両ハンドを初期姿勢へ戻す
        │
        ▼
motor_check_state (変化時のみ配信)  ──> web: useMotorCheck()
```

### 実行中も EMG STOP は押せる（進捗をモーダルに入れない）

起動確認のダイアログ（`MotorCheckButton`）だけがモーダルで、**進捗と結果
（`MotorCheckPanel`）は Monitor の設定面にその場で展開する**。ダイアログは押した瞬間に
両ハンドの全アクチュエータが動き出すことを断る場所なので残してあるが、機体が動き出す
前に閉じるため、駆動と重なる時間は無い。

進捗パネルの側はモーダルにしてはならない。`.modal` は全画面の fixed オーバーレイなので、
**駆動しているあいだずっとヘッダーの EMG STOP がクリックできなくなる**（クリックは背景
として吸われ、パネルが閉じるだけ）。`ModalProvider` の `openCount` はホットキーも封じる。
全アクチュエータが順に動いている最中に、止める手段だけが画面から消えることになる。
`MotorCheckPanel.test.tsx` の「画面を覆わない (モーダルではない)」がここを固定している。

パネルは平常時は畳んであり、**実行中と失敗時は操縦者の開閉操作より優先して開く**
（`SubsystemStatus` と同じ方針。畳んだまま機体だけが動く画面を作らない）。中断ボタンは
折りたたみの外側に置く。

### 判定はシーケンスエンジンがそのまま担う

`move_to` が既に 3 つの判定を持っている。動作確認のために足した実装は無い。

| 軸の種類 | 到達判定 | 失敗すると |
|---|---|---|
| `position` / `velocity` | `tolerance` で判定 | `SequenceTimeoutError` |
| 左右直結ペア | 上記 + `sync_tolerance` | `AxisSyncError` |
| `duty`（DC 基板） | **無し**。`settle_s` の固定待ち | 落ちない → ④で目視 |
| `on_off`（電磁弁） | **無し**。`settle_s` の固定待ち | 落ちない → ④で打音 |

### 確認専用の値を持たない

運用で使う位置名（`home` / `open` / `run` …）へ動かす。かつて `motor_check.magnitude`
という専用の駆動量があり、位置定数とずれた瞬間に「動作確認で動く位置と運用で使う位置が
別物」になって確認が意味を失っていた。**その値は config ごと消えている。**

### 構成に無い軸のステップは除外し、除外したことを必ず出す

機構が未装着のハンドを外して実機を動かす構成（`config/bench/main_hand`）では、
サブハンドの軸が 1 本も存在しない。全ステップを登録すると押した瞬間に
`PositionLookupError` で止まり、逆に「軸が 1 本でも欠けたら登録しない」形にすると
残っているハンドの動作確認まで一切できない。

各ステップは `@step(axes={…})` で自分が指令する軸を宣言し、判定は
`Sequence.restrict_to_axes()` の 1 箇所が持つ。**宣言を省いたステップ（零点確定）は
構成に依らず残り**、一部だけ存在するステップは残したまま指令先だけを絞る
（`MotorCheckSequence.move_to`。特に最後の「両ハンドを初期姿勢へ戻す」を落とすと
「必ず初期姿勢で終わる」性質が消える）。指令できる軸が 1 本も残らなければ登録しない。

**除外を黙って行ってはならない。** 存在しない軸のステップが黙って消えると、本番構成で
1 軸が config から漏れていてもそのステップごと消えて全ステップ PASSED になる（症状は
「動作確認は通ったのに試合でその軸だけ動かない」）。除外は `motor_check_state` の
`excluded_steps` として**欠けている軸まで**配り、起動ログにも 1 ステップ 1 行で出す。
UI は動作確認パネルに「この構成に無い軸のステップを N 件除外しています」と内訳を、
Monitor の 1 行サマリーに件数を出す。

### 排他は全ロボットに掛かる

1 本のシーケンスが両機を動かすので、片方だけ見ると確認中にもう一方が手動で動かされる。
起動ゲート（`MotorCheckController.deny_reason()`）も、送信経路の停止（`pause`）も、手動切替の
拒否も、全ロボットが対象。

### 周期タスクは 1 つも止めない

**確認は `move_to` でしか軸を動かさず、その指令はシーケンスと同じ `MotorHandle` を通る。**
周期タスクはどれもその目標を実現する側なので、止めると仕事ごと消える。止める対象は
`RobotServer._motor_check_pausables` が単一情報源で、**今そこは空を返す**。

| 止めたもの | 起きること |
|---|---|
| M3508 位置制御ループ（200Hz） | M3508 は電流指令しか受け付けないので、200Hz のループが C620 へ電流を出さない限り 1 通も機構へ届かない。目標だけが設定されて `SequenceTimeoutError`（実機で発生。目標 520mm・実測 2mm・飽和なし）。しかも**復帰した瞬間に残った目標へ向かって機体が動き出す** |
| 目標値再送（20Hz） | EDULITE 05 / DM3520 はフィードバックが問い合わせ駆動で、`AxisHandle.wait_reached` は再送しない polling なので、そのモータ宛へ飛ぶのは指令 1 通だけになる。返る状態も**動き出す前の位置 1 通**で、`rotate` の 0→180deg は実際に回りきっても到達判定を通らない。自作モタドラは `command_timeout_ms` 500ms で出力が切れ、`settle_s` 0.5s のコンベア・ポンプは目視・聴音の最中に止まる |

0x200 の奪い合いは起きない。確認中は他の指令経路（通常シーケンス実行・手動モード）が
`deny_reason()` の排他で塞がれており、周期タスクは競合相手ではない。再送が確認用の指令を
上書きすることも無い —— 再送が書き直すのは**動作確認自身が設定した目標**で、
`idle_target_value()` のラッチ値が出るのは目標を 1 つも持たないときの
「今の姿勢を保て」に限られる。

### 起動の窓

タスクを作ってから `run()` が駆動を始めるまでに停止が届きうる。`Sequence.run()` は
冒頭で停止イベントを `clear()` するので、**シーケンスの外側のフラグ
（`MotorCheckController._abort_requested`）で覚えておかないとその 1 通が消える**。
消えると「止めたはずなのに全アクチュエータが順に駆動される」。

## 零点確定（ホーミング）

②の最初のステップ。電源投入位置をそのまま原点にすると、前の試合の終了姿勢や搬送中に
手で動かしたぶんがそのまま座標のずれになる。位置定数は全て原点からの相対値なので、
ずれた原点のまま走らせると全ステップが同じだけずれた場所へ動く。

設定は `config/*_positions.yaml` の `axes.<軸>.homing`。**動作確認固有の値ではなく
軸の機構的性質**（どちら向きに、どれだけ動かせば原点に当たるか）なので位置定数と同居する。

```yaml
# config/main_hand_positions.yaml の axes.rotate.homing（現在値）
# スイッチが 1 本の軸。sensor は単数形
homing:
  sensor: rotate_origin_sensor   # config/<robot>.yaml の sensors: に登録した名前
  direction: -1                  # +1 か -1 のみ
  search_distance: 180.0         # [軸の unit] これを超えたら失敗として止める
  step: 1.0                      # 1 回の移動量。下限は静止摩擦、上限は tolerance
  settle_s: 0.05
```

```yaml
# config/main_hand_positions.yaml の axes.y_axis.homing（現在値）
# 左右にスイッチが 1 本ずつ付く軸。sensors は**モータ名 → センサ名の対応表**で、
# align_distance が対になる（下の「左右 2 本のスイッチと整列段」）
homing:
  sensors:                       # sensor（単数）とは排他。どちらか一方が必須
    y_axis_r: y_axis_r_origin_sensor
    y_axis_l: y_axis_l_origin_sensor
  direction: -1
  search_distance: 650.0
  align_distance: 5.0            # [軸の unit] 整列段が片側だけに許す移動量
  step: 0.5
  settle_s: 0.05
```

**`sensors` を書いたら `align_distance` は省略できず、書いていない軸には書けない**
（整列段そのものが存在しないので、書いても効かない設定になる）。キーは軸の `motors:` と
**過不足なく一致**していなければ起動を拒否する —— 1 つ書き忘れるとそのモータだけが
整列段の対象から静かに外れ、片側が押されないまま原点が確定する。

**探索時間は `search_distance / step` × `settle_s` を下回らない。** 上の値では
180.0 / 1.0 = 180 ステップ × 0.05s = **最短 9 秒**で、1 歩の追従待ちに
`_FOLLOW_ATTEMPTS`（5 回）を使い切ると 1 歩 0.25 秒なので**最悪 45 秒**。
**セッティングタイムに毎回これが入る**。縮めてよいのは `step` だけで、
`search_distance` は唯一の無人の歯止めなので速さのために縮めてはならない。
**その `step` も「小さいほど良い」値ではない** —— 下限は静止摩擦が、
上限は原点の分解能（`tolerance`）が決める（下の「実機で確定した値」）。

**「当たるまで動かす」ので、止める仕組みが 9 つ要る。**

1. **`search_distance` の上限** — 配線が抜けたセンサは「いつまでも当たらない」形でしか
   現れない。**これが唯一の無人の歯止め**なので、省略できない必須キーにしてある。
   **数えるのは実測位置の移動量**であって、送った指令の積算ではない。
   **1 歩目も現在値起点**（`AxisHandle.observed_value()`）なので、手動で軸を動かした
   後に動作確認を起動しても、引き戻す距離はそのままここに乗る
2. **1 歩ごとの再アンカー** — 指令は毎回「そのときの実測位置 + `step`」で組む。
   指令が実位置を追い越して先行し続けることが構造的に起こらず、機構が引っかかった
   ときも 1 step ぶんの偏差しか掛からない
3. **事前確認 5 つ**（どれも**1 歩も動かさずに** `HomingError`）— 位置指令の軸か /
   原点を確定する手段があるか / センサのフィードバックが生きているか /
   **対象軸のモータのフィードバックが生きているか** / **励磁されているか**。
   4 つ目が欠けると、未受信の `0.0` を現在位置と信じて全ストロークぶんの指令を
   1 回で出す。5 つ目は停滞判定でも拾えるが、その文言は「引っかかり・探索方向・励磁」の
   3 択なので原因を絞れない —— **`is_energized()` が `False`（無励磁だと分かっている）の
   ときだけ降りる**。`None` は「励磁状態を報告しないドライバ」であって無励磁ではない
   （倒すと常に `None` の M3508 が一切零点確定できなくなる）
4. **1 歩ごとの鮮度の再確認** — 事前確認は「始めてよいか」しか見ない。センサの読み口は
   途絶しても**最後に届いたフラグを返し続ける**ので、探索中にサーボ基板が再起動したり
   `can_generic` が瞬断したりすると、症状は「いつまでも当たらない」だけになり、止めるのは
   探索距離の上限か停滞判定だけになる —— ドライバ内蔵の位置ループが端を押し続けている状態で
   さらに 3 歩ぶん押し込む。**降りる前にその場の実測位置を目標へ送り直す**（最後に送った
   「実測 + `step`」が生きたままだと押し続ける。接触を検出したときと同じ作法で、探索も
   離脱も `_seek` の 1 本を通る）
5. **停滞判定** — 再アンカー方式では「進まない機構」が探索距離を消費しないので、
   実測が `step/2` 未満しか進まない状態が 3 歩続いたら失敗として降りる
6. **離脱の距離上限**（`homing.release_distance`。書かない軸の既定は `step` の 20 倍）—
   下の「触れた状態から始めたら」の離脱にも歯止めが要る。接点が固着したセンサと**極性の
   取り違え**はどちらも「いつまでも OFF にならない」形でしか現れない。
   **`search_distance` を流用してはならない** —— あちらは実ストローク相当まで
   伸びる値なので、離脱に使うと反対側の機構端まで走り抜ける。**既定の `step` 倍数にも
   頼らないこと** —— 精度のために `step` を詰めると許容も一緒に縮み、精度を上げるほど
   スイッチから離れられなくなる（`coarse_step` を書いた軸では必須キー）
7. **`align_distance` の上限**（左右にスイッチが 1 本ずつ付く軸のみ）— 整列段は
   **押されていない側のモータだけ**を進める段なので、極性を取り違えたセンサ・断線した
   スイッチ・ストロークの外に付いたスイッチはどれも「いつまでも押されない」形でしか
   現れない。片側だけを動かす操作にも無人の歯止めが要る。**`search_distance` を流用しては
   ならない** —— 左右のずれは機構の遊びの範囲（数 mm）にしかありえず、探索距離まで
   片側を進めるのは軸をねじり切ることに等しい。**`sync_tolerance` より真に小さいことを
   起動時に強制する**（下の「左右 2 本のスイッチと整列段」）
8. **ラッチを提供しないセンサの拒否** — 到達判定は接触のラッチ
   （`GenericDriver.consume_sensor_latch`）で見るので、それを持たないドライバでは
   探索そのものを開始しない。現在値へ落とす実装は下の「探索はラッチで見る」で
   取りこぼす経路そのもので、取りこぼした探索が向かう先は機構の破損側である
9. **緊急停止** — 目標値を送る `AxisHandle` が既にインターロックを通る

**センサの読み口は三値**（`True` / `False` / **`None` = 読めていない**）で、可動端
インターロックと同じ `main._make_sensor_reader` を共有する。**`None` を `False` へ
丸めてはならない** —— 離脱段では「途絶したセンサ = 離脱できた」に化け、触れたままの
位置で原点を確定する。

**離脱で戻った距離は探索距離を消費しない。** `search_distance` が縛るのは「開始位置から
どれだけ押し込むか」で、離脱は逆向きなので、そのぶんを寄せ直しがもう一度走っても
到達しうる最も深い点は離脱前の位置より深くならない。数えないと、粗探索が上限をほぼ
使い切った軸で寄せ直しの上限が 0 以下になり、1 歩目から「−0.5mm 動かしても到達しません」
という読めない文言で落ちる。なお**上限の判定は指令の前にしかない**ので、最後の 1 歩は
上限を最大 `step` ぶん超えうる（超過は 1 歩に限られるので許容している）。

失敗したら原点を確定せずシーケンスを止める。原点がずれたまま走るより、動かないまま
止まって操縦者に知らせるほうが安全。

### 探索はラッチで見る。離脱は現在値で見る（対称に見えて非対称）

**「今 ON か」を `settle_s` ごとに見る方式では、スイッチの通過を原理的に取りこぼす。**
ON 区間が `step` より狭いと、指令 1 回でその区間を跨いでしまい、50ms 後の観測時には
もう抜けている —— `rotate` の `limit_speed` は 2.0rad/s ≒ 114deg/s なので、**step 2.0deg
だった当時は 2deg を約 18ms で通過**していた（現在の step 1.0deg でも約 9ms で、`settle_s`
50ms より 1 桁速い。**`step` を下げても消えない性質である**）。実機ではこれで
**スイッチに当たっているのに探索が止まらず、
可動範囲の端（0deg）を越えて回り続けた**（その後、左右の同期ずれで `SyncMonitor` が
全体緊急停止。再実行では何もせずに成功したので**タイミング依存**として現れる）。

センサの `FEEDBACK` は 100Hz で届いている（手でゆっくり通過させたときの接触は
1.398 秒 / 139 通）。受信のたびにラッチしておけば区間の通過は 1 通も落ちない。

| 段 | 見るもの | 理由 |
|---|---|---|
| 探索（`want_active=True`） | **ラッチ**（`GenericDriver.consume_sensor_latch`） | 取りこぼしは**機構の破損側**へ進み続ける |
| 離脱（`want_active=False`） | **現在値**（`sensor_active`） | ラッチにすると「一度でも OFF になった」で抜け、接点のチャタリングでまだ ON 区間の中にいるのに離脱完了と読む。取りこぼしても「余計に離れる」だけで、次の探索が寄せ直す |
| 開始時の「既に触れているか」 | **現在値** | ラッチだと、跨いだ痕跡だけで触れてもいない位置から離脱を始める |

**ラッチは読むと消える。読み手が複数いると壊れる**ので、呼んでよいのは `HomingRunner`
だけとする（診断ツリーが描く「今どうなっているか」は `sensor_active` のまま。
両方を 1 つにまとめると、画面を描くたびに探索のぶんが消える）。
**探索を始める直前に 1 度捨てる** —— 手動操縦でスイッチを跨いだ後や、離脱段のあいだに
溜まったぶんが残っていると、1 歩目の観測でいきなり到達と読み、スイッチではなく
**探索開始位置が原点になる**（症状は「原点合わせをしたのに位置がずれる」だけ）。

**検出したらその場の実測位置を目標に送り直す。** 最後に送った「実測 + `step`」の指令は
まだ生きているので、原点確定（EDULITE 05 は `SET_ZERO` の前に `disable` を挟む）が
届くまでモータはスイッチを越えた先へ向かい続ける。

**それでも行き過ぎは残る。** 内訳は 2 つで、送り直しが消せるのは後者だけ:

1. **検出の遅れ** —— ラッチを読むのは `settle_s` ごとなので、スイッチに触れてから
   最大 1 周期ぶん進んだ位置で検出する。1 歩の指令が `step` までしか離れていない以上、
   その 1 周期に進める距離も **`step` 以下**（`rotate` で 1.0deg）
2. **残っている指令** —— 検出位置からさらに `step` 先まで向かう。**送り直しが消すのはここ**

つまり `rotate` の行き過ぎは**最大 2step から最大 1step ≒ 1.0deg へ縮む**。
**スイッチは可動範囲の端（0deg）にあり、1deg 程度の行き過ぎには耐える強度がある**という
機構側の性質が前提で、ここを 0 にする手段は PC 側には無い（`step` を下げれば両方の項が
同じだけ縮むが、下限は静止摩擦が決める。上の「実機で確定した値」）。

### 触れた状態から始めたら、一度離れてから寄せ直す

リミットスイッチの ON 区間には幅がある。触れたその場を原点にすると（以前はそうしていた）、
**「区間のどこで探索を始めたか」がそのまま原点のばらつきになる** —— ばらつきの幅は
`step`（`y_axis` の 0.5mm。`rotate` は deg 単位で 1.0）ではなく**区間幅**（数 mm）で、
症状は「原点合わせをしたのに位置がずれる」だけ。始めた位置は毎回違うので再現もしない。
**原点付近から動作確認を始めるほど踏みやすい。**

そこで、探索の前にセンサが ON なら**探索と逆向き**へ `step` ずつ離脱し、OFF になってから
通常の探索へ渡す。確定位置は探索の `step` 粒度に収まり、区間のどこで始めても同じ場所が
原点になる。離脱が逆向きである以上、機構端で始まったときに押し込まない性質は保たれる。

探索と離脱は `HomingRunner._seek` の 1 本を共有する。歯止め（移動量の上限・停滞判定）を
向きごとに書き分けると片方だけ直せてしまい、症状は「探索は止まるのに離脱は永久に動き
続ける」—— 離脱は普段踏まない経路なので気付けない。

### 左右 2 本のスイッチと整列段（`y_axis`）

`y_axis` は左右直結ペアで、**スイッチが左右に 1 本ずつ**付いている。この軸の零点確定は
探索の後に**整列段**を挟む:

1. 事前確認（**全センサ**の鮮度。1 本でも途絶していたら 1 歩も動かさない）
2. **いずれか 1 本でも ON** なら、全センサが OFF になるまで探索と逆向きへ離脱
3. 軸単位で探索し、**いずれか 1 本**がラッチしたら停止
4. **整列段** —— まだラッチしていないセンサのモータ**だけ**を `direction` へ `step` ずつ
   進め、全センサがラッチしたら終わり
5. グループ単位で原点確定

**なぜ「両方が押された姿勢」を原点にするのか。** 機構には遊びがあるので、左右のわずかな
ずれは物理的に存在する。片方が当たった瞬間の姿勢をそのまま原点にすると、**そのずれが
原点のずれとして焼き付く** —— しかも遊びの向きは前回どちら向きに動かしたかで変わるので、
症状は「原点合わせをしたのに毎回少しずつ違う場所が原点になる」という再現しない形になる。

**既にラッチした側は「検出時点の実測位置」で固定保持し、毎歩実測へ再アンカーしない。**
探索段（1 歩ごとに実測へ再アンカーする）と意図的に非対称で、理由は**遊びが無い機構**
—— つまり片側駆動が物理的に成立しない機構 —— にある。そこでは進めた側が保持側を
引きずる。保持側の目標を毎歩実測へ張り直すと、目標が引きずられた先へ追従するので
**左右のずれは増えない** —— `align_distance` にも停滞判定にも掛からず、**歯止めが
1 つも発火しないまま軸ごと機構端まで走る**。固定保持なら引きずりは「進めた側が
進まない」形で現れ、停滞判定（`_STALL_LIMIT` = 3 歩）が拾う。**これが「この機構では
片側駆動が成立しない」を検出できる唯一の形である。**

**指令は軸単位のまま 1 回。**「ペア軸に片側だけ効く操作を作らない」を破ってはいない ——
整列段の 1 歩も `AxisHandle.set_target_value` の 1 回で、**進めない側にも必ず保持値を
載せる**（`AxisSpec.to_commands_each` がキーの過不足を `KeyError` で拒否するので、
載せ忘れも構造的に塞がる）。モータ 1 台だけを指令する経路はどこにも無い。

**同期補正は整列段のあいだ自動で止まる。** `sync_kp` が意味を持つ前提は 2 つ —— ①全員が
位置制御中 ②**全員が同じ軸位置を目標にしている** —— で、整列段は②を意図的に崩す。
崩れた周期は `SyncGuard.skewed_groups()` が拾い、200Hz の位置制御ループが補正だけを
出さない（`SyncGroup.targets_share_axis_value()` の許容幅 `_TARGET_ALIGN_EPSILON` = 1e-6 は
丸め誤差だけを吸収するもので、`tolerance` を流用してはならない）。止めなければ整列は
成立しない —— `y_axis` の実測値ではずれ 1mm で片側 −440counts・相方 +440counts になり、
**進めたい側は押し戻され、保持側は前へ引きずられる**。
**contextmanager による suspend/resume にはしていない** —— 再開の取りこぼしがその
グループの補正を試合中ずっと殺し、画面にもログにも出ないため。**止めるのは補正だけで、
保護（偏差ラッチ・途絶判定）は生きたままである。**

**`align_distance < sync_tolerance` を起動時に強制する。** 整列段は左右の位置を
意図的にずらす操作なので、そのずれが `sync_tolerance` に届くと、**零点確定の最中に常駐の
偏差監視**（位置制御ループ 200Hz / `SyncMonitor` 50Hz）が発報する。
機体はラッチしたまま止まり、操縦者からは**「動作確認の最初のステップでいつも緊急停止する」**
としか見えない —— 原因が config から読めないので、config 側で先に拒否する。

### 実機で確定した値と、まだ測れていない値（`rotate`・2026-09-05）

**`rotate` の零点確定は実機で通った。** サブハンド不在のメインハンドのみの構成
（`config/bench/main_hand/`）で動作確認シーケンスが完走し、その最初のステップとして
零点確定も成功した。スイッチに触れた状態から始めたので上の離脱経路を実際に踏み、
離脱 → 寄せ直しで **0.70deg 動いて到達**して `SET_ZERO` まで進んでいる。付け替えの
あいだの `SyncMonitor` のグループ単位の一時停止と再開（約 0.9 秒）も設計どおり動いた。

| 値 | 状態 |
|---|---|
| `direction` **−1** | **実機で裏付けられた。** 離脱後に寄せ直した向きが正しかった |
| `step` **1.0deg** | **下限は実機で分かっている。** 0.5deg では `position_kp` 30.0 が生むトルクが減速機の保持力と静止摩擦を超えられず、離脱段で 3 歩連続して進まず `HomingError` になった。手動操縦では 1.0deg で動くが、ホーミングは 1 歩ごとに静止するので**毎歩で静止摩擦を超え直す**必要がある。**現在値は動かなかった 0.5 の 2 倍しかない** —— 停滞判定（`step/2` 未満が 3 歩連続）で落ちるようなら 1.5 前後へ戻す |
| `search_distance` **180.0deg** | **依然として未実測。** 今回は**スイッチに触れた状態から始めた**ので、この歯止めは一度も試されていない —— 実際に何 deg でスイッチに当たるかは、触れていない位置から始めたときに初めて分かる。現在値は `manual` の全幅（0.0〜180.0deg）から置いた暫定値で、実測のスイッチ位置 + わずかな余裕へ詰める |

**`direction` と `search_distance` を混同しないこと。** 前者は同じ 1 回の零点確定で
裏付けられ、後者はその同じ 1 回では一度も試されていない。

**`step` はそのまま原点の分解能である。** スイッチが ON になる瞬間を `step` 刻みでしか
刻めないので、原点誤差の上限が `step` になる。`rotate` の `tolerance` が 2.0deg なので
現在値 1.0deg は**その半分**にあたる。**代償は探索時間**（上の「探索時間は …」）で、
**下限は静止摩擦**なのでこれ以上は下げられない —— 実機で停滞判定に落ちるなら戻す側へ動かす。

### `y_axis` は有効になったが、まだ 1 度も実機で走らせていない（2026-09-08）

スイッチ・ファーム・`sensors:` が揃ったので `axes.y_axis.homing` を有効にした。
**ただし「有効化した」と「実測で埋まった」は別の話で、この軸は 4 値とも未実測である。**

| 値 | 状態 |
|---|---|
| `direction` **−1** | **未実測。**「原点は負方向（`home` = 0.0 より手前にスイッチを置く）」という設計意図から置いた。逆だと反対の機構端まで `search_distance` いっぱい押し込んでから失敗する |
| 左右 2 本の**極性**（ファーム側 `sensorActiveLow`） | **未実測**（`docs/mechanism_handoff.md` §4）。逆だと**離脱段でどこまで動かしても OFF にならず**、`_RELEASE_STEP_LIMIT`（20 歩 = 10.0mm）ぶん探索と逆向きへ動いてから「離せませんでした」で止まる。**初回に最も踏みやすい失敗である** |
| `align_distance` **5.0mm** | **実測値ではない。** `sync_tolerance`（10.0mm）の半分に置いた暫定値で、左右のずれの実測が取れたらそれ + 余裕へ詰める |
| `step` **0.5mm** | **未実測。** `tolerance` 1.0mm の半分にあたるが、**下限を決めるのは静止摩擦**で、`rotate` では 0.5deg で 1 歩も動かなかった実績がある。動かないなら（停滞判定で `HomingError` が出るなら）上げる判断が要る |
| `search_distance` **650.0mm** | `manual` の全幅（0.0〜650.0mm）と一致させてある。**上端から始めても下端までは必ず届き、下端より先へは行かない。** 対は 2 箇所に分かれているので、片方だけ動かされたことを機械的に検出するのは `tests/test_main_positions_config.py` の一致検査だけである |

**探索時間は `rotate` の比ではない。** 650.0 / 0.5 = **1300 ステップ**で、ストローク全長を
走ると**最短 65 秒・最悪 325 秒**。ただし実際に掛かる時間は「そのとき原点からどれだけ
離れているか」で決まる（`search_distance` は上限であって毎回走る距離ではない）ので、
**動作確認の前に手動で原点付近へ寄せておくこと。**

**初回は必ず人が付いて、いつでも EMG STOP を押せる状態で実行すること。**
最初に踏みそうな失敗経路と物理原因の対応:

| メッセージ | 物理原因 |
|---|---|
| `原点センサ '…' が応答していません` | スイッチが載る基板の電源・CAN 配線、`sensors:` への登録漏れ。**1 歩も動かない** |
| `… から離せませんでした（… OFF にならない）` | 極性が逆（`sensorActiveLow`）／接点固着。**最初に踏む可能性が最も高い** |
| `… 動かしても 原点センサ … に到達しませんでした` | `direction` の符号が逆、または両方のスイッチが未接続 |
| `整列段でモータ '…' を 5.0mm 動かしても原点センサ '…' が反応しませんでした` | **片側のスイッチだけ**が極性逆／断線／取付位置がストローク外。もう片方は正常なので探索は成功し、ここまで来て初めて分かる |
| `整列段でモータ '…' が指令しても動きません` | **機構に遊びが無く片側駆動が成立しない**（進めた側が相方を引きずる）／引っかかり／励磁落ち |

埋める作業の棚卸しは `docs/mechanism_handoff.md` §0 / §1 が正。

### 原点を確定する手段は 2 つ。それでも確定できない軸が残っている

零点確定の最後は `main.py` の `_make_origin_resolver` を通る。手段はこの順で探す:

1. **PC 側位置制御ループ（M3508）** —— 累積角の原点を PC が持つので CAN の往復が要らない
2. **ドライバへの `SET_ZERO`** —— 原点をドライバ内部に持つモータ用。可否は
   ドライバ自身の `supports_origin_capture()` が答える（`main.py` にドライバ種別を
   書き写して導出し直さない）。宣言できるのは `deactivation_steps()` と
   `origin_capture_steps()` の**両方**を持つドライバだけで、「切り直すフレームはあるが
   無励磁にする手段が無い」ドライバが能力ありと名乗る形 —— 励磁したまま原点を動かす
   経路 —— が構造的に塞がる

どちらも無ければ `None` を返し、呼び出し側が起動ログと `HomingError` の両方で見せる。

| 軸 | ドライバ | ホーミング | 理由 |
|---|---|---|---|
| `y_axis` | M3508 ×2 | **有効**（2026-09-08〜） | 位置制御ループが累積角の原点を持つ。スイッチは**左右 1 本ずつ**でサーボ基板 #0 の SV4（`0x44`）と #1 の SV0（`0x48`）。整列段を通る唯一の軸で、**実機ではまだ 1 度も走らせていない**（上記） |
| `rotate` | EDULITE 05 ×2 | **有効** | `SET_ZERO` を宣言する。スイッチはサーボ基板 #0 の SV3（`0x43`） |
| `sub_y_axis` | DM3520 | **有効・実機で通した** | `SET_ZERO` を宣言する。原点は**前端**スイッチ（サーボ基板 #1 SV1 = `0x49`）。座標は前端が 0 で収納側が負。実測値は下記 |
| `sub_lift` | DM3520 | **有効・実機で通した** | `SET_ZERO` を宣言する。原点は**下端**スイッチ（サーボ基板 #1 SV4 = `0x4C`）。**+ 方向が下**なので上昇側が負。実測値は下記 |
| `sub_rotate` / `sub_pitch` / `sub_offset` | 自作サーボ ×5 | 無効（`homing:` を書かない） | サーボは指令角がそのまま位置なので、零点確定という概念を持たない |

### `sub_y_axis` の実測値（2026-09-09）

離脱 → 0.1mm 刻みの探索 → `SET_ZERO` → 目標値再送の付け替え、まで実機で通した。
**再現性は 0.11mm**（原点から 3.0mm 離して寄せ直すのを 3 回で 2.92 / 2.95 / 3.03mm）で、
刻み幅 0.1mm の量子化ぶんしかばらついていない。

| 値 | 実測 | 備考 |
|---|---|---|
| `direction` | `1` | + 方向で前端スイッチに当たる |
| `step` | `0.1` | スイッチの移動許容 0.3mm より小さく取る。原点のばらつき = 刻み幅 |
| `release_distance` | `10.0` | 動作点 −2.02mm、**ON 区間は 2mm 以上**。既定（`step`×20 = 2.0mm）では抜けきれない |
| `search_distance` | `560.0` | **スイッチ間の実測 447mm + 余裕。** 機構が動くうちは詰めない。機構側の想定 750mm とは食い違う |
| `coarse_step` | `1.0` | ON 区間の実測 2.2mm より狭く |
| `scale` | `1.0668451 rad/mm` | `Gr`×2/(m·z)。ピニオンは KHK SS1-36 |
| `p_max` | `1000.0` | 出荷値 12.5 では ±11.7mm しか読めない |

**後端へ寄せて測るときは刻みを 0.3mm 以下に落とすこと** —— 20mm 刻みのまま当てて
作動点を最大 20mm 越えて押し込んだ（スイッチの移動許容は 0.3mm。離脱後の再確認では
正常に復帰したが、幅を詰めたければ刻みを落として測り直す）。

**二段探索（`homing.coarse_step`）を入れて実ストロークを賄えるようにした。**
0.1mm 刻みで 800mm を探すと 8000 歩 ≒ 8 分かかって点検に入らないので、粗い刻みで
当ててから離脱し、`step` で寄せ直す。実測では前後 28mm を 1.1 秒、上下 120mm を
19 秒で寄せている。**`coarse_step` は ON 区間の実測より狭く取ること** —— 広いと
粗い 1 歩で区間を跨ぎ切り、離脱も寄せ直しもできない位置で止まる（`HomingRunner` が
粗探索の直後に検出して降りる）。

### `sub_lift` の実測値（2026-09-09）

コートで回転と上下の対応が鏡になるので `scale` の符号だけをコート別に持つ
（`{ blue: +, red: - }`）。**符号は両コートで実機確認済み**（赤でも `direction: 1` のまま
下端スイッチへ寄って原点に入った）。

**再現性 0.12mm**（原点から 30.0mm 離して寄せ直すのを 3 回で 30.44 / 30.38 / 30.32mm）。

| 値 | 実測 | 備考 |
|---|---|---|
| `direction` | `1` | **+ 方向が下。** + へ動かすと下端スイッチが立つ |
| `step` | `0.1` | 前後軸と同じ |
| `coarse_step` | `0.5` | ON 区間 1.0〜1.5mm より狭く。**前後軸 (1.0) より狭いのはこの実測差による** |
| `release_distance` | `10.0` | ON 区間 1.0mm（動作点 0.0 / 離脱 −0.5mm）に対する余裕 |
| `search_distance` | `220.0` | スイッチ間 159mm + 余裕。機構が動くうちは詰めない |

**スイッチ間の実測は 159mm**（2026-09-09 赤コート。下端 0.0mm / 上端 −159.0mm。
−157.98mm では OFF、−158.98mm で ON）。機構側の想定 400mm とは食い違うので、
**どちらが正かは機構担当と突き合わせること**。`manual` と `positions.lifted` は
この 159mm の内側に取ってある。**機構が動くうちは仮の値。**

**`positions.sub_lift.home` は原点そのもの（0.0）ではなく −5.0 に取る。** 下端
スイッチの作動点がまさに 0.0 なので、待機のたびに ON 区間の縁へ座ることになり、
読みが ON と OFF の間で揺れる（ON 区間は 1.0mm しかない）。さらに**可動端
インターロックは押されている端へ進む指令を拒む**ので、0.0 へ寄せる `move_to` 自体が
途中で弾かれうる。

**昇降軸のピニオンがラックから外れて空回りしていた期間の実測を信じてはならない。**
2026-09-09 に「離脱に 30mm 要る」「原点が毎回 27mm ずれる」「無励磁で落ちる」と
読めたのはすべてこれが原因で、エンコーダだけが動いて機構が動かないため、スイッチは
どれだけ動かしても押されたままに見える。**3 つとも配線・スイッチの故障と区別が
付かない。** 見分けるのはトルクで、自重を持ち上げる向きへ動かしているのに軽ければ
（実測 −0.15Nm。保持中は −0.69Nm）機構が繋がっていない。機構を直した後は動作点
0.0mm / 離脱 −0.5mm / 無励磁 10 秒の落下 0.06mm と、当初の実測どおりに戻った。

**同じ理由で `positions.sub_y_axis.extended` も 0.0 から −5.0 へ動かした**（前後軸の
`home: -20.0` は元から離してあった）。あちらは待機位置ではなく動作確認が通り抜ける
中間点だが、**`tolerance` 1.0mm は「動作点を 1mm 越えた場所」も到達として受ける**ので、
移動許容 0.3mm のスイッチへ毎回それだけ押し込む余地を残すことになる。加えて前端の
ON 区間は原点から 2mm 以上あり、**その内側から `extended` を指令すると可動端
インターロックが拒否する** —— 動作確認は `home` から寄せるので今は踏まないが、それは
ステップの並びが偶然そうなっているだけで、運用シーケンスが直動 2 軸を扱い始めれば
順序の保証は無くなる。

**原点を下端に取ったのは、降ろしきるほうが待機姿勢として自然で、探索の向きが重力と
同じになるため。** その結果 `positions` の上昇側は負になる（`lifted: -20.0`）。
`+` が上だと思って正の値を書くと、**降ろす向きへ動いて下端スイッチへ突き当たる**。

**有効なのは `rotate` / `y_axis` / `sub_y_axis` / `sub_lift` の 4 軸である。**
スイッチは合計 7 本繋がっていて、`homing:` から参照しているのは 5 本（`rotate` に 1 本、
`y_axis` に左右 1 本ずつ、`sub_y_axis` の前端、`sub_lift` の下端）。**残る 2 本**
——前後の後端と昇降の上端——**は報告のみ**（`sensors:` に登録して診断ツリーと指差喚呼で
見えるようにしてあるだけ）。**「スイッチが付いた」と「零点確定が有効になった」は
別の話**で、前者だけでは原点は 1mm も正されない。**確定手段そのものを持たないのは
自作サーボの 3 軸だけ**で、あちらは指令角がそのまま位置なので零点確定という概念を
持たない。

**ただし失敗の出方は 2 つとも「早い」形へ寄せてある。**

- **1 歩も動かない。** 確定手段の有無は探索を始める前に問う（`origin_capturable`）。
  かつてはセンサまで押し込んでから最後に落ちており、機構を動かした意味が無いまま
  姿勢だけが変わっていた
- **起動ログに `ERROR` で出る。** `homing:` を書いてあるのに確定手段が無い軸は、
  `_wire_motor_check_sequence` が起動時に軸名を挙げて `logger.error` する。
  押した瞬間に必ず失敗する構成のまま試合当日を迎えないため

**`SET_ZERO` は必ず無励磁にしてから送る。** 励磁中に送るとドライバ内部の位置目標が
旧座標のまま残り、差分だけ軸が飛ぶ。安全な順序は `disable → set_zero → 再励磁` で、
`CANManager.capture_origin_via_set_zero` が段ごとに全モータを回して保証する。
**DM3520 はこの順序と両立しないという理由で長く宣言していなかった** —— `sub_lift` を
disable すると自重で落ちる（保持は減速比 19.2 のギヤ頼みで保持ブレーキが無い）と
見ていたためだが、**2026-09-08 に実機で落ちないことが分かって前提が消えた**。
根拠は指差喚呼 `sub_lift_holds` の実機確認なので、**あれが通らなくなったら宣言ごと
見直すこと。** **同じ理由が `rotate` にも掛かる** —— `SET_ZERO` の数百 ms は無励磁なので、
偏心して自重で回る機構ではその回ったぶんがそのまま原点のずれになる。ソフトでは
解決できないため、指差喚呼の `rotate_holds` が「無励磁でも回らないこと」を人が見る。

**付け替えの最中は偏差監視をグループ単位で止める。** `rotate_r` に `SET_ZERO` が届いて
`rotate_l` にまだ届いていない瞬間、2 台の座標系が違うので偏差という量が定義を失い、
この軸では 175.879deg という値がそのまま全体緊急停止になる。CAN 送信 2 通が debounce
40ms 以内に収まる確率へ安全機構を預けない（`SyncMonitor.suspend_group`）。止めてよい
根拠は 2 つ —— 比較すべき座標系が無いことと、その間モータが無励磁でこの保護が防ぐ
押し合いが原理的に起きないこと。全体 `pause` にしないのは、動作確認中こそ他の軸が動くため。

**既知の穴: 物理緊急停止のたびに DM3520 の原点が黙って無効になる。** 未修正
（2026-09-08 時点）。物理緊急停止で **DM3520 の電源は数秒落ちる**（このページの
`tx_error_count` の節が実機観測として記録している）。本機は**電源投入時に位置が
0.0rad へ固定される**ので、復帰した時点でモータ内部の原点はその瞬間の姿勢へ
作り直されている。**PC 側にこれを検出する手段が無い。**

- 機構は飛ばない —— `activation_steps` は届いた実測角をそのまま保持目標に書く
- しかし PC が信じている「0mm = 前端」とハードの座標系がずれたまま残り、
  **UI にもログにもヘルスにも何も出ない**。以後の `move_to` は前端とは違う場所へ動く
- 症状は「零点確定は成功したのに、緊急停止を挟むと位置が合わない」だけになる

`sub_y_axis` に零点確定を開けるまで、この軸に原点の概念が無かったので穴も無かった。
**当面の運用は「物理緊急停止を踏んだら零点確定をやり直す」**で受ける。
実装で塞ぐなら M3508 の再アンカー報告（`health_detail()` を WARNING へ倒す）と
対称の形が既存の型に合う。実測位置が途絶を跨いで説明のつかない跳躍をしたら報告する。

**同じ電源断で `p_max` と `CTRL_MODE` も出荷値へ戻る。こちらは塞いである。**
どちらも `0xAA` で保存しない限りフラッシュに残らないので、復帰した DM3520 は
**MIT モード / `p_max` 12.5** で立っている。原点と違って PC 側から検出でき、
放置すると落ちる先が 2 つある:

- 戻ったモードで `0x100` の位置指令が効くなら、12.5 で送られたフィードバックを
  config の 1000 で復号した **80 倍の位置**がそのまま保持目標に書かれる
  （2026-09-09 の事故そのもの。機構はリミットスイッチを踏み越える）
- MIT モードのままなら「励磁を名乗るのにトルクが出ない」。`is_energized()` は
  True を返すので `safety.unenergized_motors` は無音、`is_fault()` も掛からず、
  症状は `SequenceTimeoutError` か零点確定の停滞 `HomingError` だけになる

そのため**再励磁は「電源が落ちたかもしれないところからの復帰」として扱う** ——
`CANManager.activate_motors`（緊急停止解除の `_reactivate_motors` と単発の
`_reenergize_motors` の唯一の入口）が、励磁の前に `reinitialization_steps()` を
送り直す。CTRL_MODE を書き直し、控えてある固定小数点レンジを捨てて読み返させるので、
戻っていればそのまま config の値へ書き直し、書いても読み返しが変わらないときだけ
`activation_block_reason()` が励磁を拒否する。所要時間は DM3520 1 台あたり +0.1 秒
（`safety.reenergizing` の窓は sub_hand で最大 +0.2 秒、レンジを書き直すときは +0.2 秒）。

- **`set_zero` はここに含めない。** 原点は励磁が落ちても生き残るので書き直す
  理由が無く、送れば零点確定で合わせた原点をその場の姿勢へ書き換えてしまう。
  起動時だけの手順（`initialization_steps()`）と再励磁のたびの手順
  （`reinitialization_steps()`）を分けてあるのはこのためである
- **励磁中だと分かっているモータへは送らない**（`CANManager._is_known_energized`）。
  先頭が `disable` なので、直結ペアの健全な相方へ届くとその場で保持トルクを失う
  —— 鮮度確認の問い合わせと同じ判断で、電源が落ちた個体は復帰後 `False` を
  報告するので本当に要るモータには届く
- **運用上の意味**: レンジが戻った状態は**再励磁が直す**（読み返して食い違いを
  見てから config の値を書き、もう一度読み返して確かめる）。CTRL_MODE と同じく
  黙って直るので画面には出ないが、**書き直した事実は INFO でログに残る**。それでも
  画面に「固定小数点レンジ 食い違い」が出るのは、書いても実機が受け付けなかった
  ときだけで、そのときは上の表の手当て（config の値がその機種のレンジ内か）を踏む。
  原点は同じ電源断で無効になっているので、**零点確定はやり直す**こと —— つまり
  物理緊急停止を踏んだ後にやることは「レンジの警告が出ていないか見る」と
  「零点確定をやり直す」の 2 つである。

**零点確定の最後の再励磁も緊急停止を見る。** 付け替えの窓（`disable` 0.05 秒 +
`SET_ZERO` 0.2 秒 + 鮮度待ち + 0.15 秒 ≒ 0.5 秒）で停止が入ると、
`_send_e_stop_frames` の `disable` の**後**に enable が届き、**停止中に励磁された
まま残る**（ログにもヘルスにも出ない）。`main._make_origin_resolver` が
`is_estop_active` を `capture_origin_via_set_zero` へ渡し、そこから
`activate_motor` の `should_abort` に載る。**中断するのは励磁だけで、無励磁化と
付け替えは中断しない** —— どちらも機体を動かさない指令で、途中で降りると
「片方だけ付け替えた」状態が残る（`clear_e_stop_latches` が中断口を持たないのと
同じ理由）。

**`y_axis` に欠けているのは実測だけである。** スイッチは左右 2 本とも付いていて
（右がサーボ基板 #0 の SV4 = `0x44`、左が基板 #1 の SV0 = `0x48`）、ファームも
`TouchSensor` として宣言し、`config/main_hand.yaml` の `sensors:` にも登録済み。
残っているのは `config/main_hand_positions.yaml` の `axes.y_axis.homing` を有効に
することだけで、**それを止めているのは極性（`sensorActiveLow`）と
`direction` / `search_distance` / `step` が未実測だから**である。

**左右で 1 本ずつ要る**のは、原点確定がグループ単位にしか効かないため（片側だけ確定
すると、その間に片方が動いたぶんが消えないオフセットとして残る）。

**極性を逆に設定したまま有効化してはならない。** 零点確定は「触れている状態から一度
離れて寄せ直す」段を持つので、逆だとどこまで動かしても OFF にならず、機構端まで
押し込んでから `HomingError` で失敗する。**登録だけを先に済ませてあるのは、途絶が
`STALE` として出るからである** —— 配線が抜けたまま有効化して「いつまでも当たらない」
形で押し込む事故を、先に潰しておける。

逆に、**ファームだけ古いまま `sensors:` へ登録した構成がいちばん踏みやすい**
（旧ファームがそのスロットを `Unused` として宣言していると `FEEDBACK` が 1 通も来ず、
症状は配線不良と区別が付かない）。それを拾うのが `sensors:` の `expected_firmware` に
よる版番号照合で、①の「『焼き忘れ検出が働いていない』もヘルスに現れない」節にある。

**存在しないスロットを登録すると、症状は配線不良と区別が付かない。** かつて
`config/main_hand_positions.yaml` の有効化手順は「サーボ基板 #0 の空きスロット SV5
（`0x45`）へ配線する」と書いていたが、**この基板は SV0〜SV4 の 5 本しか持たない**
（`firmware/servo/include/config.h` の `kServoSlotCount = 5`）。`0x45`〜`0x47` は ID 空間
としては基板 #0 のブロックに入るが対応するピンが無く、**その ID のデバイスは FEEDBACK を
1 通も送らない** —— 登録すると鮮度の事前確認に引っ掛かり、**毎回「センサが応答して
いません」で止まる**。

**現在サーボ基板 3 枚の 15 スロットはすべて埋まっているので、センサもアクチュエータも
増やすには基板を 1 枚足す**（DIP=3 → `0x58`〜`0x5C`）。空いていそうな ID を探して
既存のスロットへ相乗りさせると、そこを使っていた機構が黙って動かなくなる。
どの場合も、**スロット設定一式（役割・ピン・初期角・可動範囲・パルス仕様・センサ極性）を
ファームが基板番号ごと・スロットごとに持つ**ので（`kServoBoards[]`）、配線を差し替える
だけでは足りない。基板ごとに表を分けてあるのはこのためで、表が 1 つしか無いと
基板 #0 の SV3 を変えた瞬間に基板 #1 の SV3 も道連れになる。

原点が確定できない軸は**電源投入位置がそのまま原点**になる。搬送中に手で動かされた
ぶんがそのまま座標のずれになるので、指差喚呼の `sub_dm3520_origin` が
「原点位置にあること」を人の目で埋めている。**`y_axis` もこの状態のまま**で
（スイッチは付いたが `homing:` を有効にしていないため）、指差喚呼の
`main_home_position` が同じ役目を負っている。

**ただし「電源投入位置が原点」は機種の性質ではない。** DM3520 は電源投入時に位置が
0.0rad へ固定されるのでそのまま成り立つが、**EDULITE 05 の原点は放っておくと
フラッシュに保存された機械ゼロで、電源投入位置とは無関係**である。`rotate` は
逆回転ペア（`scale` の符号で向きを表す）なので、2 台の機械ゼロが揃っていないと
物理的に同じ姿勢でも人間の単位へ逆換算した時点で差になる:

```
deviation = pos_r / scale_r - pos_l / scale_l = (pos_r + pos_l) / |scale|
```

実機では起動直後に **175.879deg**（当時の `sync_tolerance` 3.0deg。現在は 5.0deg）
となり、`SyncMonitor` が全体緊急停止を掛けて機体が 1 ステップも動かせなかった。そのため
`config/main_hand.yaml` の `rotate_r` / `rotate_l` を **`set_zero_on_start: true`**
にしてあり、起動のたびに `set_zero`（通信タイプ `0x06`）を送って電源投入時の姿勢を
原点にしている。直結した 2 台は同じ姿勢を取るので差は消える。

**零点確定が有効になっても `false` へ戻してはならない。2 つは競合せず順に効く。**
起動時の `set_zero` は 2 台を 0 に揃えて偏差を消すだけの**暫定原点**で、機体を動かせる
状態にすることが目的。零点確定はスイッチの位置でそれを上書きする**正確な原点**で、
後から効くのでこちらが勝つ。`false` にすると起動直後の偏差が残ったまま `SyncMonitor` が
全体緊急停止を掛け、**機体が 1 ステップも動かせないので動作確認そのものを開始できない**
—— つまり零点確定にたどり着く手前で詰まる。**左右で値が食い違うと揃うどころか機械ゼロの
差がまるごと偏差として残る**ので、`tests/test_robot_sequences.py` の
`test_paired_axis_motors_agree_on_set_zero_on_start` が同梱 config 全セットで固定している。

**それでも「搬送中に手で回されたぶん」は動作確認を回すまで残る。** 起動時の `set_zero` は
そのときの姿勢を 0 と呼ぶだけなので、姿勢がずれていれば座標もずれる。正せるのは
スイッチによる零点確定だけで、セッティングタイムに動作確認を回すことが唯一の手当てになる。

## ③ 常駐保護 — 壊れる前に力を抜く

②とは独立に、待機中も手動操縦中も動作確認中も走り続ける。

| 周期 | 実装 | 何をするか |
|---|---|---|
| 200Hz | `control/position_loop.py` + `control/sync_guard.py` | 偏差超過・途絶で電流 0 にラッチ（**`y_axis` のみ** —— 全メンバが同じ位置制御ループに載る組しか登録されない） |
| 50Hz | `control/sync_monitor.py` | 偏差超過（2 サンプル）で**全体緊急停止**（`y_axis` / `rotate`） |
| 20Hz | `control/target_refresh.py` | 自作モタドラへ目標値を再送（生存通知） |

**偏差の境界そのものは `lib/axis_sync.py` の `SyncGroup.violation()` 1 箇所。**
偏差監視の 3 段（`move_to` 完了時 / 200Hz / 50Hz）とも同じ関数を呼ぶ。段ごとに違うのは
頻度と超過後の扱い（debounce・ラッチ・効果）だけで、境界がずれてはならない。

**この 3 段はいずれも「ずれたら止める」側で、ずれを縮めるものは 1 つも無い。**
位置制御はモータごとに独立した PID なので、左右で負荷や摩擦が違えば追従差は原理的に
残る。縮める経路は 200Hz の位置制御ループに載る**同期補正**（`SyncGroup.corrections()`）
だけで、`axes.<軸>.sync_kp` を書いた軸にしか出ない。**本番の `y_axis` は 2026-09-04 に
実運用ストローク 150mm で詰めた `sync_kp: 16.0` が入っている**（`rotate` は 0.0 のまま）。
**机上ベンチ（`config/bench/m3508/`）は直結していない 2 台なので 0.0** —— 揃うべき前提が
無いまま別々の負荷で回るため。詰め方は `docs/mechanism_handoff.md` §3-1。
補正は電流 0 の周期には出ないので、
上の 3 段の判断を上書きすることはない。

**現在の偏差は手動操縦パネルの軸行に出る**（`state.manual.axes[].deviation`。算出は
同じ `SyncGroup.deviation()`）。ここが無かった頃は「どれだけずれて止まったか」を読む
手段が診断カラムのモータ生単位 `POS` しかなく、逆回転ペアでは符号まで反転して見えるため
暗算では追えなかった。結果として `sync_tolerance` を勘で緩める以外に手が無くなる。
許容差の 6 割を超えると行が自分から主張する（超過した時点では 50Hz の `SyncMonitor` が
既に全体緊急停止を掛けているので、操縦者が手を打てるのはそれより前の区間しかない）。

### 3 層はどれも「公称周期どおりに回っている」ことが前提 — その乱れを測る

`y_axis` の台形速度プロファイルの停止距離（`lib/control/trajectory.py`）も、
`SyncMonitor` の「2 サンプル = 40ms なら機構破損に間に合う」という時間予算も、
200Hz / 50Hz の公称周期が実際に維持されていることに立っている。会場の PC が
USB 負荷やサーマルスロットルで乱れても、かつては何も出ず、症状は「なんか荒れる」
「たまに同期ずれで緊急停止」としてしか現れなかった。

`lib/control/periodic.py` の `PeriodicTask`（3 つの周期タスク全部が継承する基底）が
連続する tick 開始時刻の差 = 実周期を測り、公称周期の 1.5 倍（`JITTER_OVERRUN_MARGIN`
= 0.5。値は「超過分 / 公称周期」なので 0.5 が 1.5 倍にあたる）を超えたら「乱れ」として
超過回数と最悪値だけを O(1) で積む（サンプル列は持たない。起床が遅れた分と tick 自身の
処理が長すぎた分は区別しない — 時間予算にとってはどちらも同じ「次の周期までに
終わらなかった」であるため）。しきい値は `interval_s` からの相対値
（200/50/20Hz の 3 種を跨ぐので `HealthThresholds` には足さず、`config/system.yaml` に
節も増やしていない）。超過は `LogThrottle` 経由で journal へ WARNING。
**停止していた間の空白は乱れとして数えない** —— `start()` が前回 tick の記録を捨てる。

**画面（`SubsystemStatus`）にも WS 配信（`safety.*`）にも出していない。**
しきい値が実機未検証なので、常時点灯すると同期ずれラッチや緊急停止まで載っている
安全機構のパネルごと読まれなくなる。加えて、仮に正しく警告できても**試合中の操縦者に
できる行動が無い**（PC の負荷は下げられない）—— bus-off 復旧ウォッチドッグの節で
触れた CAN の警告が「ワークが落ちたかも → 掴み直す」という行動に繋がるのとは性質が
違う、エンジニアが後から読む情報である。今後の判断は `docs/architecture.md` の未解決課題表
「200Hz が実機で維持できるか未測定」の行が持つ。

**journal に残る 1 行は「試合 N の集計」で、出すのは試合終了（`match_finish`）。**
`PeriodicTask.log_jitter_summary()` が超過回数と最悪の遅れを INFO で 1 行出し、
続けて `reset_jitter_stats()` が 0 に戻す（呼び出しは `lib/server.py` の
`_cmd_match_finish`）。**超過 0 件でも必ず出す** —— 出さないと「公称の 1.4 倍で
常時走っている」機体（＝停止距離も 40ms 予算も既に崩れている状態）で journal が
無音になり、読み手は「警告 0 件 = 乱れていない」と読む。しきい値を決めるための
唯一の観測値が最悪の遅れなので、0 件のときこそその 1 行が要る。文言は超過 0 件と
1 件以上で読み分けられる。1 試合あたり（位置制御 + 同期監視 + 目標値再送）× 2 ロボット
で 6 行程度。

**試合開始（`match_start`）は前縁リセットだけで、ログは出さない**（`_handle_match_start`）。
準備中（配線確認・両ハンドを一巡する動作確認）に踏んだぶんを洗い流し、試合中の数字を
「この試合で起きたこと」だけにするためで、CAN 途絶エピソード数
（`reset_rx_down_episodes()`）と同じ場所・同じ理由である。集計を `match_start` 側に
置くと窓が `[試合N開始, 試合N+1開始)` になって試合後の準備時間が丸ごと混ざり、
しかもその日の最後の試合が 1 行も残らない。

## ④ 指差喚呼 — 人が見る

`config/checklist.yaml` のロールは `pre_match` 1 つで、Monitor の準備の面（`MatchPrep`）に置く。
全項目の完了が試合開始のゲート（`can_start_match`）。

項目は 1 本のリストではなく、**それを確かめる操作の隣**に並ぶ。置き場所は同じ yaml の
`group` が宣言し（`preflight` / `court` / `motor_check` / `final`）、コート選択ボタンの直下に
`court` が、動作確認の起動ボタンの直下に②を埋める `motor_check` の項目が出る。
`group` を書かなかった項目・UI が知らない `group` の項目は「その他」として必ず描かれる
（ベンチ設定 `config/bench/*` は `group` を持たない）。

②が自動判定できないものを、ここが埋める:

| 項目 | なぜ自動判定できないか |
|---|---|
| `can_bus_strict` | `--strict` の点検は人が打つコマンドで、①②のどちらからも呼ばれない（下記） |
| `health_ready` | ①は配信しているが、**誰も見ていなければ何も起きない**（下記） |
| `estop_functional` | 押して止まることは①②のどちらも確かめない（下記） |
| `operation_mode_sequence` | `can_start_match` は指差喚呼の完了しか見ず `OperationMode` を参照しない（下記） |
| `y_axis_sync` / `rotate_sync` | 左右のずれは③が監視するが、機構の目視は人にしかできない |
| `conveyor_run` / `conveyor_stop` | DC 基板はエンコーダも電流センスも持たない |
| `pumps_run` | 同上（ポンプも DC 基板） |
| `valves_closed` / `valves_actuate` | 電磁弁基板は弁が開いたかを観測できない |
| `suction_hold` / `suction_release` | 吸着の成否を測るセンサが無い |
| `origin_sensor_react` | 未配線・極性違いのセンサは STALE にならず「接触なし」を報告し続ける（触れてみる以外に検出手段が無い）。触れた結果は `state.sensors` として画面に出る |
| `rotate_holds` / `sub_lift_holds` | 無励磁で自重に負けるかは機構の性質で、CAN 越しには何も現れない（`rotate` は `SET_ZERO` の数百 ms が無励磁なので、回るぶんがそのまま原点のずれになる） |
| `firmware_match` | 版の不一致は CAN 越しには「応答しない」としか見えない。**照合そのものが働いていない**（`INFO` 未受信）状態も同じチェックで見る —— 診断ツリーの「版番号 未確認」チップが残っていないことを合わせて確かめる（→ ①の「『焼き忘れ検出が働いていない』もヘルスに現れない」節） |

**②から外れたものが④で埋まっていることは `tests/test_robot_sequences.py` が固定する。**
（`test_checklist_covers_what_cannot_be_judged_automatically`）

**項目が黙って消えないことも同じファイルが固定する**（`TestShippedChecklists`。同梱の
checklist.yaml すべて —— 本番と `config/bench/*` —— が対象）。`load_checklist_definitions`
は `id` / `label` を欠くエントリを**意図的に黙って捨てる**（会場で yaml のタイプミス 1 つに
より起動できないほうが重い）ので、`label:` を `labell:` と打つだけで項目が 1 つ消え、
症状は「ゲートは開くのに、その 1 つを誰も読み上げていない」だけになる。id の重複も同じ形で
壊れる —— `MatchState.set_checklist_item` は最初の 1 件しか更新しないので、2 件目は永久に
未チェックのまま `can_start_match` が開かない。どちらも起動ログにも画面にも現れないので、
落とすなら会場ではなくテストで落とす。

### 上の 4 項目は「機械が既に知っているのに、人が見る手順へ結び付いていなかった」ぶん

他の項目と成り立ちが違うので分けて書く。どれも**仕組みは前からあった**。

- **`can_bus_strict`** — `scripts/setup_can.sh --strict` は `docs/operations.md` でも
  「試合前点検」と位置付けられているのに、**操縦者に実行させる
  導線が config にも UI にも 1 つも無かった**。`cbc-can.service` は `--strict` を
  付けずに呼ぶので CAN が 0 本でも `RemainAfterExit=yes` で success になり、
  `cbc-control.service` の `Wants=cbc-can.service` は**何も守っていない**
  （`--strict` を付けない判断とその理由は `scripts/cbc-can.service` のコメント）。
  つまり「揃っているか」に答えるのは、この 1 行の指差喚呼だけである
- **`health_ready`** — ①は `state.safety.unenergized_motors` まで配信しているが、
  無励磁は「指令しても動かない」としてしか現れず、①の色（`MotorHealth`）は **OK の
  まま**である（「励磁されていない」はヘルスに現れない、を参照）。試合が始まってから
  気付くことになるので、始まる前に 1 度だけ人が読む
- **`estop_functional`** — `estop_release`（**解除されていること**の確認）とは別物。
  物理停止は DC 基板の `REF` → `FEEDBACK` の緊急停止ビット → サーバー全体の緊急停止
  → ブロードキャスト `E_STOP` という経路で伝わるので、**配線 1 本・基板 1 枚で機能ごと
  失われる**。失われても画面は平常のままで、**押しても何も起きないことでしか分からない**。
  DC 基板が繋がっていない構成ではそもそも物理停止が効かない。だから解除の確認とは別に、
  試合直前（`final`）に実際に 1 度押す
- **`operation_mode_sequence`** — **手当ては既に 1 つある。** `match_reset`（セッティングへ
  戻す操作）は全ロボットを `OperationMode.SEQUENCE` へ戻し（`RobotServer._cmd_match_reset`。
  コメントもまさにこの失敗モードを述べている）、起動時の既定も `SEQUENCE` である。
  **残る穴は「直近の `match_reset`（または起動）より後に、準備中へ手動で入って戻し忘れた」
  場合だけ。** そしてそれは例外的な操作ではない —— 同じ指差喚呼の `valves_actuate` が
  「手動操縦で valve_1〜6 を個別に開閉」を要求しており、②の動作確認を挟む準備は必ず
  手動を通る。`can_start_match` は指差喚呼の完了しか見ないので、手動のまま全項目が揃い、
  操縦者が `START` を押して「手動操縦中のためシーケンスを開始できません」で拒否される
  まで気付けない。**そのとき計時は既に走っている。**

  **チェックそのものは押した瞬間のラッチなので、「今どうなっているか」には答えない**
  （`final` を全部チェックした後に弁をもう一度確かめて手動のまま戻ると、27/27 のまま
  片ハンドが手動になる）。答えるのは `StartGate` が毎描画で `state.manual.mode` から
  出す「手動操縦中」の警告で、この項目はその 1 行を読み上げさせるためにある。
  警告は機体異常と同じ扱い（**開始は止めない**。可否を決めるのはサーバーの
  `can_start_match` だけ）で、健全性判定（`lib/healthVerdict.ts`）にも混ぜない ——
  手動は機体の健全性ではない。

  **`match_start` 側にゲート（拒否）は足さない。`match_reset` が揃えるのに `match_start`
  が揃えないのは非対称だが、意図的である。** `match_reset` は「既知の状態へ戻す」操作で、
  そこでモードを戻しても操縦者は何も失わない（試合は終わっており機体も動いていない）。
  一方 `match_start` で同じことをすると、**試合中の退避先として手動を選んでいる操縦者から
  開始の瞬間に制御権を奪う**ことになる。手動はシーケンスの代替ではなく退避路であり、
  開始操作がそれを勝手に畳んでよい理由が無い。だから開始は止めず、見えるようにする

### 判定を 2 箇所に書かない

| 判定 | 唯一の持ち主 |
|---|---|
| 機体の健全性（UI 側） | `web/src/lib/healthVerdict.ts` |
| ヘルスの最悪値への集約（サーバー側） | `lib/health.py` の `worst_bus_health()` |
| 動作確認が完了したか（UI 側） | `web/src/lib/motorCheckStatus.ts` |
| ヘルスのしきい値 | `lib/config_schema.py` の `HealthThresholds` |
| 何を測れるか（テレメトリの測定可否） | `lib/drivers/base.py` の `TelemetrySupport`（各ドライバが宣言） |
| 左右ずれの境界 | `lib/axis_sync.py` の `SyncGroup.violation()` |
| 左右ずれを縮める補正量 | `lib/axis_sync.py` の `SyncGroup.corrections()` |
| 動作確認を起動できるか | `MotorCheckController.deny_reason()`（`lib/server_motor_check.py`） |
| 試合を開始できるか | `MatchState.can_start_match` |
| フェーズによる可否 | `lib/commands.py` の `CommandSpec` / UI は `lib/phase.ts` |

UI は理由を説明するだけで、可否を導出し直してはならない。一度これを `StartGate` で
やって、サーバーが「開始できる」と配信しているのに画面がボタンを殺す状態を作った。

### 名前の一意性に依存している

- **モータ名**はロボット横断に一意（サーバーが名前で引く）
- **軸名**もロボット横断に一意（統合動作確認が両機の位置定数を 1 表へ束ねる）
- **CAN ID** はバス単位でロボット横断に一意

3 つとも `tests/test_robot_sequences.py` が固定している。

### 「測ったように見える 0」を作らない

電流・温度・過電流・過熱は自作モタドラのプロトコルに無い。到達フラグも電磁弁基板は
立てない。**測れないものは運ばない** — 常に 0 の値を流すと、UI にもヘルス判定にも
測ったように見える値が入り込む。

測る手段の無い項目は配信の境界で `null` へ倒す（`state.motors[]` の 4 値・
`axes[].value` / `deviation`・`MotorHealthInfo.temperature`）。可否の宣言は
`lib/drivers/base.py` の `TelemetrySupport` が単一情報源で、**UI にドライバ種別を
書き写さない。** 画面は `—` を描くだけで、色も判定も付けない。唯一の例外が POS 欄の
指令値表示（`→0.30`）で、**それも測定値ではなく PC が最後に送った指令値である**
（`docs/invariants.md` の「測れない項目は配信の境界で `null` へ倒す」）。

**`null`（測る手段が無い）と `MALFORMED`（欄の欠落・型違い）を混同しないこと。**
前者を異常へ倒すと DC 基板を 1 枚積んだだけで全画面が異常側になり、後者を `null` へ
丸めると配信の不具合が「測れない」に化けて誰にも見えなくなる。

### テストが噛むか確かめる

安全に直結する不変条件を触ったら、本番コードにわざと 1 行の不具合を入れて、狙った
テストが落ちることを確認してから戻す。層と「1 枚だけを見る条件」の対応は
`docs/invariants.md` §9 にある。
