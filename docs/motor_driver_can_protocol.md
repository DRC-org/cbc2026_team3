# 自作モータドライバ CAN プロトコル仕様

DC モータ用・サーボ用の自作モータドライバ（以下モタドラ）と PC 間の CAN 通信仕様。
**この文書がプロトコルの単一情報源**であり、PC 側 `lib/drivers/generic.py` と
ファームウェア `firmware/` の双方がこれに従う。片方だけを変更してはならない。

`docs/impl_plan.md` の「自作モータドライバ用 CAN プロトコル」節は本書への参照だけを置き、
仕様は書かない。バイト列を 2 箇所に書くと片方が古くなったことに誰も気付けないため、
フレーム定義・状態フラグ・パラメータ ID・制御モードの単位・安全機構は本書のみが持つ。
プロトコルを実装・変更するときは本書だけを見ること。

---

## 1. 物理層

| 項目 | 値 |
|---|---|
| 規格 | CAN 2.0A（Standard Frame, 11bit ID） |
| ビットレート | 1 Mbps |
| バス | `can_generic`（`config/can_buses.yaml` 参照） |

Extended Frame は使わない。同じ PC 上の RobStride EDULITE 05 が Extended Frame を
使うが物理バスが別系統であり、仮に混線しても ID 空間が重ならないようにしてある。

---

## 2. CAN ID レイアウト

```
Bit10..8 (3bit): コマンド種別
Bit7..0  (8bit): デバイス ID
```

### 2.1 コマンド種別

| 種別 | 値 | 方向 | 説明 |
|---|---|---|---|
| `E_STOP` | `0b000` | PC → モタドラ | 緊急停止 / 解除 |
| `SET_TARGET` | `0b001` | PC → モタドラ | 目標値設定 |
| `SET_PARAM` | `0b010` | PC → モタドラ | パラメータ変更 |
| `FEEDBACK` | `0b011` | モタドラ → PC | 状態フィードバック |
| `INFO` | `0b100` | モタドラ → PC | 版番号の自己申告（§3.4） |
| （予約） | `0b101`–`0b111` | — | 将来拡張用。**使用禁止** |

**値は CAN の調停順に合わせてある。** CAN は ID が小さいほど優先されるので、
**止めるためのフレームが目標値やフィードバックに追い越されてはならない。**
かつては `E_STOP` が `0b111` で、ブロードキャスト停止の `0x7FF` は Standard ID
全 2048 個のうち**最も優先度が低い** ID だった。デバイスを増やすほど悪化する形の
設計逆転で、直すコストは定数の値だけだった。

**予約値を勝手に使ってはならない。** PC 側 `GenericDriver.matches_feedback` は
未定義のコマンド種別を「自分宛でないフレーム」として無視するため、予約値を送っても
そのフレームは**どこにも届かないまま捨てられる**。拡張するときは必ず PC 側の
`CommandType` enum を先に更新すること。

なお、以前は `parse_can_id` が未定義値で例外を送出し、それが `CANManager._receive_loop` まで
伝播してバス 1 系統の受信ループごと停止する（＝そのバスの全モータが永久に STALE になる）
状態だった。現在は `matches_feedback` が不正な ID と Extended Frame を握りつぶすため、
想定外のフレームが流れても受信は止まらない。

### 2.2 デバイス ID

| 範囲 | 用途 |
|---|---|
| `0x00` | 予約（未設定）。**この ID のモタドラは駆動してはならない** |
| `0x01`～`0xFE` | 個別デバイス |
| `0xFF` | ブロードキャスト（`E_STOP` のみ） |

**デバイス ID は固定ビット分割で決まる。** 帯も刻み幅も連続ブロック性も要らない。

```
Bit7..6 : 基板種別 (0=予約 / 1=サーボ / 2=DC / 3=電磁弁)
Bit5..3 : 基板番号 (DIP そのもの。0-7)
Bit2..0 : スロット番号 (0-7)
```

| 基板種別 | ID 範囲 | 収容 |
|---|---|---|
| サーボ用 | `0x40`–`0x7F` | 8 枚 × 8 スロット |
| DC 用 | `0x80`–`0xBF` | 8 枚 × 8 スロット |
| 電磁弁用 | `0xC0`–`0xFE` | 8 枚 × 8 スロット（末尾 1 個だけ使えない） |

種別 0 を予約にしてあるので `0x00`（未設定）は自動的に空く。**ID を見れば
どの基板のどのスロットかが直接読める**ので、`candump` を眺めているときに対応表を
引かなくてよい（`0x8A` = DC 基板 1 枚目の ch2、`0xC3` = 電磁弁基板 0 枚目の ch3）。

**`0xFF` は電磁弁基板の「基板番号 7 × スロット 7」と重なるので、この 1 個だけは
未設定（駆動拒否）へ倒す。** ブロードキャスト停止と同じデバイス ID を名乗る基板が
居ると、そのスロット宛の `SET_TARGET`（`0x1FF`）とブロードキャスト解除（`0x0FF`）が
同じ 1 台を指すことになり、「1 つの弁を開ける指令」と「全基板のラッチを外す指令」が
デバイス ID の上では区別できなくなる。潰れるのは 512 個中 1 個、しかも 8 枚目の
基板の 8ch 目という最も使われない場所である。判定は `makeDeviceId()` が持つ。

かつては「スロット表の基準 ID」「DIP のブロックオフセット（刻み幅 = スロット数）」
「基板種別ごとの帯」「帯からのはみ出し判定」の 4 つの規則が重なっており、しかも
サーボ基板の DIP が 4bit なのに帯に収まるのは 3 枚分だけ、という噛み合わない状態だった。
ビット分割にしたことで規則ごと消え、`static_assert` も 3 つ減った。

**範囲外は未設定（駆動拒否）へ倒す。** DIP を回しすぎた基板を黙って丸めると、
別の基板の ID を名乗る。未設定にしておけば LED が赤く速く点滅し、設定ミスが
その場で目に見える（サーボ基板の DIP は 4bit だが基板番号は 3bit なので、
8 以上を設定した基板は全スロットが未設定になる）。

**未設定のチャンネルは `FEEDBACK` も `INFO` も 1 通も送らない。設定ミスの通知は
LED（赤の速い点滅）だけが担う。** かつては「PC 側へ『デバイス ID 未設定』を届ける方を
優先する」として CAN ID `0x300`（デバイス ID `0x00`）で送っていたが、これは 2 つの理由で
成立していなかった。

- **その報告は誰にも届かない。** PC 側の `can_id` は `0x01`〜`0xFE` に限られるので
  （上の表と `lib/config_schema.py` の `CAN_ID_RANGES`）、`0x300` を claim できる
  ドライバは**存在し得ない**。`matches_feedback` で誰にも一致せず捨てられるだけで、
  状態フラグ bit3（デバイス ID 未設定）は**送信側 ID が `0x300` になることと同値**
  だったため、その防護は丸ごと空振りしていた
- **バスを壊す。** 未設定は「DIP を 8 以上へ回した」形で起きるので、**基板 1 枚の
  全チャンネル**が同時に未設定になる。2 枚以上（例: DC 基板と電磁弁基板）が同時に
  未設定だと、**異なるノードが同じ ID `0x300` で異なるデータを送る**。CAN ID フィールドで
  調停が決着しないままデータ部でビットエラーになり、エラーフレームと再送の応酬で
  `can_generic` が埋まる。症状は「その基板が STALE」ではなく「バス全体が死ぬ」

**PC 側から見た症状は「その基板の全チャンネルが STALE」になる。**
配線不良と区別が付かないので、**切り分けは基板の LED で行う**（赤の速い点滅 =
CAN 不通 / デバイス ID 未設定）。状態フラグ bit3 の定義そのものは、観測手段を持つ
基板が将来現れたときのために残してある（ビット位置を詰め直すと bit4/bit5 が動き、
PC 側とファームの両方を同時に差し替えることになる）。

**デバイス ID はバス単位でロボット横断に一意でなければならない**（`config/*.yaml` の
`can_id`）。メインハンドとサブハンドは物理的に同じ `can_generic` を共有しており、
重複すると PC 側の受信ループが最初にマッチした 1 台で打ち切るため、もう一方は
永久にフィードバックを得られない。この一意性は `tests/test_robot_sequences.py` で
検証している。

現在の割り当て（**サーボ基板だけ 2 枚**。DC 基板と電磁弁基板は 1 枚ずつで DIP=0）:

| デバイス ID | 名前 | 種別 | 基板 / スロット | ピン |
|---|---|---|---|---|
| `0x40` | `gripper`（メインハンド） | サーボ | サーボ基板 #0 SV0 | D4 |
| `0x41` | `wall_f`（メインハンド） | サーボ | サーボ基板 #0 SV1 | D5 |
| `0x42` | `wall_r`（メインハンド） | サーボ | サーボ基板 #0 SV2 | D6 |
| `0x43` | `rotate_origin_sensor`（メインハンド） | **センサ** | サーボ基板 #0 SV3 | D7 |
| `0x44` | `origin_sensor`（メインハンド） | **センサ** | サーボ基板 #0 SV4 | D8 |
| `0x48` | `sub_gripper`（サブハンド） | サーボ | サーボ基板 #1 SV0 | D4 |
| `0x80` | `conveyor`（メインハンド） | DC | DC 基板 #0 ch0 | D11 / D12 |
| `0x81` | `pump_vac`（サブハンド） | DC | DC 基板 #0 ch1 | D10 / D3 |

`sub_gripper` は基板 #1（DIP=1）の SV0 に載っている。基板 #1 の残り 4 スロットは
`Unused` なので ID を名乗らず（`0x49`〜`0x4C` は誰も使っていない）、`FEEDBACK` も
`INFO` も 1 通も送らない —— 使うときはファーム側の役割表に足すこと
（**配線を差し替えるだけでは動かない**）。
DC 基板の 2 枚目は DIP=1 で `0x88`〜`0x8F`、電磁弁基板の 2 枚目は `0xC8`〜`0xCF`。

## 3. フレーム定義

**DLC はフレームごとに違う。** かつては全フレーム DLC=8 で、途中に予約バイトを
挟んで末尾まで埋めていた。**バイトもビットも頭から詰め、空きは末尾へ寄せる** ——
途中に空きがあると、報告できる項目が増えたときに「空いている場所があるのに末尾へ
足す」ことになり、対応表が読みにくくなる。

**数値はすべて int16 の固定小数点で、float は 1 バイトも流れない**（§4）。

### 3.1 `SET_TARGET`（PC → モタドラ）

```
Byte 0   : 制御タイプ (0=position, 1=velocity, 2=duty)
Byte 1-2 : 目標値 (int16, little-endian)
DLC = 3
```

制御タイプが Byte 0 に入っているため、送るだけでモードが決まる。現行の 3 枚は
どれもモードが固定なので、**受理できないタイプは黙って捨てる**（§4 / §7.2 / §9.2）。
これは冗長に見えるが、duty 値をサーボへ誤送信したときに弾く関門として効いている。

**この関門はファーム側では `DcChannel` / `ServoChannel` / `SolenoidChannel` の
`applySetTarget()` が持つ。** かつては 3 枚の `main.cpp` / `app.cpp` にしか無く、
そこは native テストの対象外なので**3 行とも消しても全ケース緑**だった
（`composeFeedbackFlags` を切り出した動機とまったく同じ形の穴）。

**受信するたびにコマンドウォッチドッグ（§5.1）がリセットされる。**
制御タイプが受理できないものでも養う（通信自体は生きているため）。

### 3.2 `FEEDBACK`（モタドラ → PC）

```
Byte 0   : 状態フラグ
             bit0 = 目標到達
             bit1 = 緊急停止中
             bit2 = ウォッチドッグ作動中
             bit3 = デバイス ID 未設定
             bit4 = センサ入力
             bit5 = 起動後まだ指令を受けていない
             bit6-7 = 予約
Byte 1-2 : 現在位置 (int16, 0.1deg 単位, 出力軸)  ← 位置を持つ基板のみ

DLC = 1  … DC 基板 / 電磁弁基板 / センサスロット（状態フラグだけ）
DLC = 3  … サーボスロット
```

- 送信周期は **100Hz**（`SET_PARAM` で変更可）。PC 側の `feedback_timeout_ms` 既定 500ms に
  対して十分な余裕がある
- **全基板が必ず持つ状態フラグを先頭に置く。** 逆順にすると、位置を持たない基板も
  位置のバイトを送ることになる
- **速度・電流・温度はプロトコルに無い。** どちらの基板も測る手段を持たず、常に 0 を
  運ぶと UI にもヘルス判定にも「測ったように見える 0」が流れ込む。速度はサーボ基板が
  `slew_rate`（config 定数）を rpm 換算した値を返していたが、PC 側で読むのは UI 表示だけで、
  「動いているか」は到達フラグが既に持っていた
- **位置は「補間中の指令角」であって実測ではない**（サーボ基板。§7.4）。それでも返すのは、
  **`angle_min` / `angle_max` でクランプされた結果が分かる唯一の手段**だから。
  到達フラグはクランプ後の目標に対して立つので、クランプされていても「到達」と報告される
- **位置は ±3276.7deg で飽和する。** 折り返さないのは、+4000deg が負値に化けると
  PC 側が逆方向へ位置制御しかねないため
- **bit5（起動後未受信）は基板の再起動を PC へ知らせる。** サーボ基板は `setup()` で
  config.h の初期角へ駆動するので、試合中の瞬断は「機構が勝手に飛ぶ」形で現れる。
  PC は 20Hz で再送しているので 50ms 以内に何事もなかったように復帰し、これが無いと
  再起動そのものがどこにも現れない。`SET_PARAM` で入れた値も既定へ戻っている
- bit1〜bit5 は PC 側 `GenericDriver.update_state` が保持し、`e_stop_active` /
  `watchdog_active` / `device_id_unconfigured` / `sensor_active` / `never_commanded` で読める。
  緊急停止とウォッチドッグは異常ではないので `is_fault()` には入らない（駆動できない状態は
  サーバー全体の緊急停止として別に現れる）
- **bit3（デバイス ID 未設定）は実機からは届かない。** 未設定のチャンネルは
  `FEEDBACK` を 1 通も送らないので（§2.2）、このビットが立ったフレームを送る基板は
  現状 1 枚も無い。ビット位置だけを予約として残してあり、設定ミスの通知は基板の LED が担う
- **ウォッチドッグのビットは「一度でも `SET_TARGET` を受けたうえで途絶した」ことだけを
  意味する。** 電源投入後まだ 1 通も受けていない基板はこれを立てず、代わりに bit5 を立てる。
  **出力停止の条件とこのビットの条件は別物である**（§5.1）

### 3.3 `SET_PARAM`（PC → モタドラ）

```
Byte 0   : パラメータ ID
Byte 1-2 : 値 (int16, little-endian)
DLC = 3
```

| ID | パラメータ | 単位 | 既定値 | DC 用 | サーボ用 | 電磁弁用 |
|---|---|---|---|---|---|---|
| `0x00` | `max_duty` | 1/10000 | 3000 (0.30) | **有効** | 無視 | 無視 |
| `0x01` | `command_timeout_ms` | ms | 500 | **有効** | **有効** | **有効** |
| `0x02` | `feedback_interval_ms` | ms | 10 | **有効** | **有効** | **有効** |
| `0x03` | `reached_tolerance` | 0.1deg | 0 | 無視 | **有効** | 無視 |
| `0x04` | `slew_rate` | 0.1deg/s | 900 (90deg/s) | 無視 | **有効** | 無視 |
| `0x05` | `angle_min` | 0.1deg | 機体依存 | 無視 | **有効** | 無視 |
| `0x06` | `angle_max` | 0.1deg | 機体依存 | 無視 | **有効** | 無視 |

**ID は穴を空けずに詰める。** かつては `kp` / `ki` / `kd` / `overcurrent_threshold_ma` が
「将来のための予約」として ID を占め、さらにサーボ固有分が `0x10`〜`0x12` に飛んでいた。
飛び飛びの表は、読むたびに使われていない ID を数えることになる。必要になったら末尾へ足せばよい。

**サーボ専用の復号器も廃止した。** かつては `ServoParamId` / `decodeServoSetParam` が
別に存在し、同じフレームに 2 つの enum と 2 つの復号器が並んでいた。ID を 1 つの表へ
詰めたので、各基板は「自分が使わない ID を無視する」だけになった。

**受け付けないパラメータは黙って捨てる。** 内部に保持すると、PC 側からは
「設定できたのに効かない値」に見える。

**パラメータは RAM 上のみで、電源を切ると既定値へ戻る。** EEPROM へ保存しないのは、
壊れた値を保存すると次の電源投入で原因不明の暴走になり、現場で切り分けられなくなるため。
恒久的に変えたい値は `config.h` に書いてビルドし直す。**再起動で既定へ戻ることは
`FEEDBACK` の bit5 で PC から見える**（§3.2）。

**`command_timeout_ms` には上下限が要る。** §5.1 は「`WATCHDOG_ENABLED` に `SET_PARAM` の
ID は無く、最後の砦が 1 フレームで外れる経路を作らない」と定めているが、猶予そのものを
伸ばせば同じ結果になる。上限は既定の 4 倍。下限 50ms は PC 側の再送周期の目安（§5.1）で、
それより短い猶予は契約どおり再送している健全な機体を止めるだけで安全性を上げない。
`feedback_interval_ms` も同様に、0 はバスを埋め、極端に長い周期は PC からは
「基板が死んだ（STALE）」ようにしか見えないので、両端を丸める。

**範囲外は境界値へ丸める**（書いた値に近い側で動かす方が現場で挙動を推測しやすい）。
int16 なので、float32 のときにあった「化けた値を `uint32_t` へキャストすると未定義動作」
という問題そのものが無い。

未知のパラメータ ID は無視する（PC 側の新しいファームと古い基板が混在しても止まらないように）。

### 3.4 `INFO`（モタドラ → PC）

```
Byte 0   : ファームウェア版 (uint8)
Byte 1   : 基板種別 (1=サーボ / 2=DC / 3=電磁弁)
Byte 2   : スロットの役割 (0=アクチュエータ / 1=センサ)
Byte 3-4 : サーボの可動レンジ (int16, 0.1deg 単位)  ← サーボスロットのみ

DLC = 3  … DC 基板 / 電磁弁基板 / センサスロット
DLC = 5  … サーボスロット
```

**焼き忘れた基板をセッティングタイムに見つけるためにある。** ピン配置やデバイス ID を
変えたファームを一部の基板にだけ焼き忘れると、症状は「そのモータが応答しない」か、
悪くすると「違うものが動く」だけで、CAN 越しには何も見えなかった。

送信周期は **1Hz**。起動時 1 回ではなく低頻度で送り続けるのは、PC が基板より後から
起動しても拾えるようにするため。8 デバイスでもバス負荷は無視できる。

**プロトコルかピン配置を変えたら `config.h` の `kFirmwareVersion` を必ず上げること。**
セッティングタイムのチェックリストに「全デバイスの版が一致」を 1 行足せば、
焼き忘れがその場で分かる。

#### サーボの可動レンジ（Byte 3-4）

**180 度サーボと 270 度サーボの取り違えは、これが無いと CAN 越しに一切見えない。**
目標値は出力軸の絶対角 [deg]（§4）で、角度 → パルス幅の変換だけが `config.h` の
`ServoPulseSpec` にある（§7.7）。270 度用の設定のまま 180 度サーボを繋ぐと、
5.0deg の指令で実際には 7.5deg 動く。それでも `FEEDBACK` が返すのはクランプ後の
**指令角**（§7.4）なので PC には 5.0deg と見え、到達フラグも立ち、シーケンスは
何事もなく進む。candump にも UI にも yaml にも症状が出ない。

`ServoPulseSpec::angleRangeDeg` をそのまま自己申告することで、PC 側が
`config/<robot>.yaml` の `expected_angle_range_deg` と突き合わせられる。不一致は
`GenericDriver.is_fault()` を True にする（デバイス ID 未設定と同じ扱いで、
**設定ミスは運用前に必ず気付くべき**）。

- **サーボスロット以外は Byte 3-4 を送らない**（DLC=3 のまま）。測る対象を持たない
  基板に 0 を運ばせると、UI にも照合にも「測ったように見える 0」が流れ込む。
  §3.2 で速度・電流・温度を外したのと同じ理由である
- **DLC=3 の `INFO` をサーボスロットから受けたら、それ自体が古いファームの証拠**である。
  PC 側は「レンジ不明」として扱い、期待値が書かれていれば不一致にする。
  欠けた申告を「一致」へ倒すと、焼き忘れの検出そのものが効かなくなる
- **`INFO` を 1 通も受けていない間は照合しない。** 起動直後は必ず未受信で、1Hz なので
  数秒で埋まる。未受信を不一致にすると起動のたびに全サーボが FAULT になり、
  「いつもの赤」として無視されるようになる
- **`INFO` はフィードバック鮮度（`_last_rx_at`）を更新しない。** 1Hz の `INFO` で
  100Hz の `FEEDBACK` の途絶が隠れると、STALE 判定そのものが効かなくなる

### 3.5 `E_STOP`（PC → モタドラ）

CAN ID = `0b000 << 8 | デバイス ID`。ブロードキャストは **`0x0FF`**（デバイス ID `0xFF`）。
**他のどのフレームよりも優先度が高い**（§2.1）。

```
Byte 0   : 0x00 = 緊急停止 / 0x01 = 解除
Byte 1   : 解除時のみ 0x5A（それ以外の値なら解除しない）
Byte 2   : 解除時のみ 0xA5（それ以外の値なら解除しない）
DLC = 3
```

- **停止**: 出力を即座に停止する。以後 `SET_TARGET` を受け取っても**駆動しない**（ラッチ）。
  DC 用基板にゲートドライバの出力禁止（`DIS`）は無く、止める手段は PWM を 0% に
  することだけである（§5.2）
- **解除**: `Byte1=0x5A` かつ `Byte2=0xA5` のときのみラッチを解除する。
  マジックバイトを要求するのは、1 バイトの値だけで安全装置が解除されるのを避けるため
- 解除直後は**その場から動き出さない目標値**から始める。停止前の目標値を復元すると、
  解除した瞬間にモータが動き出して人を巻き込む
  - DC 用（`duty`）では **0**（＝停止）
  - サーボ用（`position`）では **その時点の現在角**。このモードで 0 は原点への移動指令であり、
    0 に落とすこと自体が「解除した瞬間に動き出す」ことになる（§7.5）

PC 側では `GenericDriver.encode_e_stop()` が停止フレーム、`activation_steps()` が
解除フレームを生成する。解除は `CANManager.activate_motors()` 経由で、
サーバの緊急停止解除（`e_stop_release`）と起動時に送られる。

## 4. 制御モードと単位

| モード | 値 | 目標値の単位 | int16 の刻み | 受理する基板 |
|---|---|---|---|---|
| `position` | 0 | deg（出力軸） | **0.1deg** | **サーボ用のみ**（§7.2） |
| `velocity` | 1 | rpm（出力軸） | 0.1rpm | **どちらも受理しない** |
| `duty` | 2 | **-1.0 ～ +1.0**（符号 = 回転方向） | **1/10000** | **DC 用のみ** |
| `on_off` | 3 | **0 = OFF / 非 0 = ON** | 1（そのまま） | **電磁弁用のみ**（§9.2） |

**DC 用モタドラは `duty` しか受理しない。** エンコーダを持たないので位置・速度を
観測する手段が無く、閉ループ制御そのものが成立しない。`position` / `velocity` の
`SET_TARGET` は黙って捨てる。捨てずに値だけ使うと、位置目標 90.0 [deg] が
duty 90.0（＝ 9000%）の全力指令として解釈される。

### float32 を使わない理由

**CAN 上を流れる数値はすべて int16 の固定小数点で、float は 1 バイトも流れない。**

かつては目標値もパラメータも float32 で運んでいた。やめたのは、**NaN の防御を
プロトコル全体から消すため**である。NaN は比較がすべて false になるので、可動範囲の
クランプも duty の上限も範囲チェックも素通りする。一度内部へ入ると以後の出力が NaN の
ままになり、`max_duty` クランプが 0 へ落とすので「無言で止まったモータ」になる
（診断ビットも到達フラグも立たない）。

float32 のときは復号層・目標値の保持・パラメータの丸め・duty のクランプ・角度補間の
**5 箇所**で NaN を防いでいた。整数にしたことでその失敗クラスごと存在しなくなり、
残る防御は「シリアルデバッグから入る float を固定小数点へ変換する 1 箇所」だけになった
（`motorcan::toRaw`）。8bit MCU のサーボ基板で受信経路がソフトウェア浮動小数点を
踏まなくなる利点もある。

**同じ量が 2 つの表現で往復する状態も解消した。** 以前は `SET_TARGET` の角度が
float の deg、`FEEDBACK` の角度が int16 の 0.1deg で、単位が非対称だった。

すべてのパラメータが int16 に収まることは確認済み（§3.3 の表）。将来 PID ゲインのような
広いレンジの値が要るときは、そのとき別の表現を足す。

duty の絶対値は `max_duty`（既定 0.30）で必ずクランプし、**クランプしてから**
「PWM に出す大きさ」と「方向ピンの向き」に分ける（DC 基板の出力段は PWM 1 本 + 方向 1 本）。
duty 0 は方向を反転させない側に倒すこと。0 を「負」と扱うと、停止指令が届くたびに
方向ピンが反転して機構に衝撃が入る。

## 5. 安全機構

### 5.1 コマンドウォッチドッグ

**`command_timeout_ms`（既定 500ms）の間、自分宛の `SET_TARGET` を 1 通も受信しなければ
出力を停止する。** PC の停止・CAN ケーブル断・コネクタ抜けでモータが回りっぱなしになるのを
防ぐ最後の砦であり、これが無いとコンベアは PC が落ちても回り続ける。

停止後も `FEEDBACK` の送信は継続し、ウォッチドッグのビットを立てる。
新しい `SET_TARGET` を受信したら通常動作へ復帰する（ラッチしない。通信が復旧すれば
操縦者の操作で動かせるべきなので）。

**出力停止の条件とウォッチドッグのビットの条件は別物である。**

| 状態 | 出力 | ウォッチドッグのビット |
|---|---|---|
| 電源投入後まだ `SET_TARGET` を 1 通も受けていない | 停止（§5.4） | **立てない** |
| `SET_TARGET` を受けた後 `command_timeout_ms` 以上途絶 | 停止 | 立てる |
| `SET_TARGET` を受信できている | 通常 | 立てない |

このビットは「CAN 通信が途絶した」ことの報告であって「駆動できない」ことの報告ではない。
未受信の起動直後にまで立てると、PC 側は最初の指令を送る前から「ウォッチドッグ作動中」を
読むことになり、健全な基板の配線を疑わせる。一方で出力は未受信でも許可しない
（通信が始まる前に何かの拍子で駆動されるのを防ぐため）。この 2 条件を 1 つにまとめてはならない。

> **PC 側は最後に指令した目標値を `command_timeout_ms` 以内に再送し続けること。**
> これはプロトコル上の契約であり、目標値が変化したときにしか `SET_TARGET` を送らない実装では
> 満たせない（コンベアに `run` を指令しても既定 500ms 後に止まる）。猶予に対して十分な余裕が
> 要るので、再送周期は `command_timeout_ms` の数分の 1 —— 既定 500ms なら 50ms 周期（20Hz）
> —— を目安とする。

`config.h` の `WATCHDOG_ENABLED` を 0 にすると、DC 用・サーボ用のどちらのファームでも
ウォッチドッグそのものが無効になる（途絶しても駆動ゲートを通し、報告もしない）。
**PC の停止やケーブル断に対する最後の砦を外すことになるので、試合では既定の 1 のまま使う。**

**無効化しても §5.4 の「`SET_TARGET` を 1 通も受け取るまで出力を許可しない」ゲートは外れない。**
この 2 つは別の条件であり、無効化で外れるのは「途絶したら止める」ことだけである。
まとめて 1 つの条件にすると、`WATCHDOG_ENABLED` が 0 の基板は CAN 通信を 1 通も
受けないまま `setup()` でゲートドライバを開く（電源投入と同時に駆動可能になる）。
ベンチ確認の逃げ道は残る——最初の `cansend` でゲートが開く。

**シリアルデバッグの上書き（`ENABLE_SERIAL_DEBUG`）も最後の砦を外す経路である。**
シリアルから 1 行入力している間はウォッチドッグを養い続けないとデバッグにならないが、
その範囲と期限は `SerialOverride` が持つ規則に従う。

- **養うのは打ったチャンネルだけ。** かつては 3 枚とも全チャンネルを養っており、
  電磁弁基板の UART へ `2 1` と 1 行打った後に PC が落ちると、本来 500ms で全 6ch が
  消磁するはずのところ**触っていない 5ch も含めて通電したまま**残った（CAN も PC も
  死んでいるので `E_STOP` も届かない）。DC 基板なら同じ経路でコンベアが回り続ける
- **最後の入力から `kSerialOverrideHoldMs` で自動解除する。** この値は
  `kMaxCommandTimeoutMs`（2000ms）と同じにしてある —— シリアルのデバッグモードが
  CAN 経由で設定できる最大の猶予より長く砦を外せてよい理由は無い
- 明示の解除は `'s'` 入力・CAN の `SET_TARGET` / `E_STOP` ・電源断

**試合用ビルドでは `ENABLE_SERIAL_DEBUG` を 0 にする**（通電前チェックは
`firmware/README.md`）。

有効/無効は `MotorSafety` が持つ実行時フラグで、`setup()` が `config.h` の値を写す
（`MotorSafety::setWatchdogEnabled()`）。ビルド時の `#if` を各 `main.cpp` に置くと同じ分岐を
両ファームが各自で持つことになり、片方に入れ忘れても誰も気付けない。写し忘れた場合は
有効側に倒れる。**`SET_PARAM` にこのフラグの ID は無く、CAN からは変更できない。**
最後の砦が 1 フレームで外れる経路を作らないため。無効化するにはビルドし直すしかない。

駆動の可否は必ず `MotorSafety::isOutputAllowed()` を通す。ウォッチドッグの満了だけを
見る判定（`isExpired()`）を駆動ゲートに直接書くと、この無効化フラグと緊急停止ラッチの
両方を迂回する。

### 5.2 緊急停止

§3.5 のとおりラッチ式。ソフトウェアの緊急停止であり、**ハードウェアの非常停止スイッチの
代替ではない**。

**DC 用基板には出力禁止ピン（`DIS`）が無い。** 止める手段は PWM を 0% にすることだけで、
防壁は一重である。そのぶん、出力へ至る経路を 1 本に絞り、その 1 本が必ず安全機構を
通るようにしてある（`DcChannel::outputDuty()` が出力禁止中に 0 を返す）。

#### 物理非常停止スイッチの検知（`REF`）

DC 用基板は物理非常停止スイッチの状態を `REF` ピン（D2、**LOW = 押されている**）で
読める。ファームはこれを緊急停止ラッチへ落とし、`FEEDBACK` の緊急停止ビットで PC へ報告する。

- **押下でラッチし、離しても自動復帰しない。** レベル追従にすると、PC が §5.1 の契約どおり
  20Hz で目標値を再送し続けている以上、**スイッチを離した瞬間に機体が動き出す**。
  解除は `E_STOP`(0x01) の解除フレーム、すなわち操縦者の明示操作だけに限る
- 押している間は、解除フレームが届いてもファームが次のループで再ラッチする。
  「押している間は絶対に動かない」が、フレームの到着順に依らず成立する
- `INPUT_PULLUP` で読むので、**断線したときも「押されている」側へ倒れる**
- 電源投入時に押されていれば、その状態から始める（緊急停止ビットを立てずに起動すると、
  PC からは「解除済み」に見える）

#### センサ入力（サーボ基板のスロット）

サーボ基板は 5 本の信号線を持ち、**そのうち何本でもデジタル入力として使える**（§7.1）。
「サーボ 2 + センサ 2 + 空き 1」でも「センサだけ」でも成立する。現構成では基板 #0 の
`SV3`（D7）と `SV4`（D8）—— どちらも **LOW = 接触** —— にタッチセンサを繋ぎ、
**原点合わせ**に使う（`SV3` が `rotate`、`SV4` が `y_axis`）。
**零点確定は軸ごとに 1 本のスイッチを要求する**ので、原点を確定したい軸の数だけ
スロットが要る。

- **基板は状態を報告するだけで、判断を一切持たない。** しきい値もリトライも停止判断も
  PC 側のシーケンスが持つ。基板に持たせると、機構の調整のたびにファームを焼き直すことになる
- **センサは 1 個ずつ独立した CAN デバイスとして `FEEDBACK` を送り、センサ入力のビットで
  状態を報告する。** サーボのフレームに相乗りさせてはならない —— 相乗り先の無い
  「センサだけの基板」が成立せず（誰も `FEEDBACK` を送らないので永久に読めない）、
  載せられる個数も予約ビットの数で頭打ちになる。1 スロット = 1 デバイスに揃えれば、
  サーボ・センサ・空きが何個ずつでも同じ規則で動く
- センサの `FEEDBACK` は位置・速度とも 0 で、状態フラグもデバイス ID 未設定と
  センサ入力だけ。**緊急停止とウォッチドッグは立てない** —— 駆動されないので
  緊急停止もウォッチドッグも意味を持たず、立てると PC 側のヘルス判定が
  「駆動できない状態」を出し続ける
- センサはどのコマンドも受け付けない（自分宛の `E_STOP` もブロードキャストも含む）。
  止める出力が無く、ラッチしても意味が無いため
- `INPUT_PULLUP` で読む。極性は `config.h` の `sensorActiveLow` で切り替える
- **接触は異常ではない。** PC 側 `GenericDriver.sensor_active` は、ドライバの唯一の
  異常判定である `is_fault()` に入らない。入れると、原点合わせで触れさせるたびに機体が
  FAULT になりシーケンスが止まる

**PC 側はセンサを `config/<robot>.yaml` の `sensors:` に登録すること**（`motors:` ではない。
`motors:` に置くと、動作確認・目標値再送・UI のモータ一覧に「常に 0 のモータ」として並ぶ）。
登録しないと `CANManager` の受信ループがそのフレームを誰にも配らず、接触が PC まで届かない。
`CANManager.add_sensor` が行うのは受信の振り分けとヘルス監視だけで、`SET_TARGET` は
1 通も送らない。**途絶は STALE として検出される**（センサが死んだまま原点合わせを
続けないために要る）。

**PC 側は緊急停止のビットをサーバー全体の緊急停止へ伝播する。** `RobotServer` は配信ループごとに
`GenericDriver.e_stop_active` を見て、立っていれば `activate_e_stop()` を発動する。
拾わないと、機体は止まっているのに UI は平常のままになり、操縦者はシーケンスが
進まない理由を画面から知る手段が無い。

判定は**解除フレームを送った時刻より後に届いたフィードバック**に限る。解除は
「解除フレーム送信 → 基板がラッチを外す → 次の `FEEDBACK`」の順に伝わるので、
送信前のフィードバックに残った緊急停止ビットを信じると、解除した瞬間にサーバーが自分で
止め直し、二度と解除できない機体になる。

### 5.3 duty 上限

`max_duty` で常にクランプする。ファームの既定値は **0.30**（`SET_PARAM` `0x00` で
チャンネルごとに変更可）。上限はチャンネル単位の値であって、基板単位ではない。

### 5.4 起動時の状態

電源投入直後は必ず以下の状態から始める。

- 出力停止（duty 0）
- 目標値 = 0（DC 用は `duty` 0、サーボ用は `config.h` の初期角、電磁弁用は全 ch OFF）
- 緊急停止ラッチ = **解除済み**（PC からの解除を待たずに動ける必要があるため。
  停止させたいなら PC が明示的に `E_STOP` を送る）
- コマンドウォッチドッグ = **未受信**。`SET_TARGET` を 1 通も受け取るまで出力は許可しないが、
  ウォッチドッグのビットは立てない（§5.1 の表）
- デバイス ID が `0x00` なら駆動拒否

## 6. 状態遷移

```
        電源投入
           |
           v
   [ID 未設定?] --yes--> (駆動拒否・赤点滅・FEEDBACK のデバイス ID 未設定)
           | no
           v
        [待機] --SET_TARGET--> [駆動]
           ^                     |
           |   ウォッチドッグ満了  |
           +---------------------+
           |
           |  E_STOP(0x00)
           v
      [緊急停止ラッチ] --E_STOP(0x01,0x5A,0xA5)--> [待機]
           ^
           |  REF(物理非常停止) 押下  ※ DC 用のみ。押している間は毎ループ再ラッチ
           |
```

図の `[待機]` には「電源投入後まだ指令を受けていない」場合と「指令が途絶えて戻ってきた」場合の
2 つがあり、どちらも駆動しないが、**ウォッチドッグのビットが立つのは後者だけ**である（§5.1）。

緊急停止ラッチ中は `SET_TARGET` を受け取っても駆動しないが、**ウォッチドッグの
タイマはリセットする**（解除直後にウォッチドッグが即満了しないように）。

## 7. サーボ用モタドラ固有の扱い

フレーム形式は DC 用と完全に同じで、違いは「サーボが位置フィードバックを持たない」ことと
「基板が別の MCU に載っている」ことに由来する。ファームは `firmware/servo/`。

**サーボ基板は Arduino Nano（ATmega328P / 8bit / 5V）で、DC 用の UNO R4 Minima とは
ハードウェアが別物である。**

| | DC 用 | サーボ用 |
|---|---|---|
| MCU | UNO R4 Minima（RA4M1 / 32bit） | **Arduino Nano（ATmega328P / 8bit）** |
| CAN | R4 内蔵ペリフェラル（D4/D5 固定） | **MCP2515 を SPI で外付け**（CS=D10 / INT=D3 / 16MHz） |
| PWM | `PwmOut`（R4 専用） | **`Servo` ライブラリ**（`writeMicroseconds`） |
| 空きピン | 多い | **D11/D12/D13 を SPI が占有。D13 は SCK なのでステータス LED に使えない** |
| Flash / RAM | 256KB / 32KB | **32KB / 2KB** |

プロトコルは同じでも、**ピン配置を DC 用から類推してはならない。** 追加のライブラリを
入れるときは Flash と SRAM の使用率を必ず確認すること。

### 7.1 1 基板が 5 スロットを持ち、スロットごとに役割が違う

サーボ基板は 5 本の信号線（`SV0`〜`SV4`）を持ち、**どれもサーボ出力にもデジタル入力にも
なる**。何を繋ぐかは配線で決まるので、ファームは `config.h` に役割を持つ。

| 役割 | 意味 |
|---|---|
| `Servo` | サーボ出力。自分のデバイス ID 宛の `SET_TARGET` で動き、`FEEDBACK` を送る |
| `TouchSensor` | デジタル入力。自分のデバイス ID で `FEEDBACK` を送り、センサ入力のビットで状態を報告するだけ（§5.2） |
| `Unused` | 何も繋がない。`pinMode` すら触らない |

**役割の組み合わせは自由で、それぞれ何個でもよい**（センサだけの基板も成立する）。

**役割は基板番号（DIP）ごとに持つ。** 全基板に**同じファームを焼く**（§3.4 の版番号
照合は 1 種類のバイナリを前提にしている）ので、役割の表が 1 つしか無いと基板 #0 の
SV3 をスイッチへ変えた瞬間に基板 #1 の SV3 も道連れになる。`config.h` の
`kSlotRoleByBoard` が基板番号ごとの行を持ち、`setup()` の DIP 読み取りでその行が
選ばれる。組み合わせを変えるときはその基板の行の `SlotRole` を書き換えるだけでよい
（**デバイス ID は動かさないこと** — スロットに固定しておくと、配線を差し替えても
PC 側 yaml の `can_id` が無変更で済む）。

現構成は 2 枚（`kServoBoardCount = 2`）:

| 基板 | SV0 | SV1 | SV2 | SV3 | SV4 |
|---|---|---|---|---|---|
| **#0**（DIP=0） | `gripper` | `wall_f` | `wall_r` | **`rotate` の原点スイッチ** | **`y_axis` の原点スイッチ** |
| **#1**（DIP=1） | `sub_gripper` | `Unused` | `Unused` | `Unused` | `Unused` |

**表に無い基板番号（現在は 2 以上）では全スロットが `Unused` のまま据え置かれる。**
黙って基板 #0 の行を使うと、DIP を回しすぎた基板が別の基板の役割とデバイス ID を
名乗り、同じ ID の 2 ノードが違うデータを送ってバスがエラーフレームで埋まる。
全 `Unused` なら ID が付かないので、§2.2 の「デバイス ID 未設定 → LED 赤の速い点滅・
駆動拒否」へそのまま乗る（DIP を 8 以上へ回したときと同じ扱い）。

これが成立するのは **`Unused` 以外のスロットをすべて CAN デバイスにしてある**ためで、
センサも自分のデバイス ID で `FEEDBACK` を送る。

- スロットごとに独立したデバイス ID を持ち、**PC からは別々のモータとして見える**
  （`config/main_hand.yaml` の `gripper` / `wall_f` / `wall_r` がそれぞれ別の `can_id` を
  持つのはこのため）
- 基板は自分のスロット表に載っているデバイス ID 宛のフレームだけを処理する
- `FEEDBACK` はスロットごとに個別の CAN ID で送る
- **`Unused` のスロットだけ実効デバイス ID を `0x00` にする。** そのスロット宛の
  フレームで何かが起きる経路を構造的に無くすため
- DIP スイッチの基板番号はデバイス ID の bit5-3、スロットの添字が bit2-0（§2.2）。
  したがって基板 1 枚あたりの刻み幅は**スロット数ではなく 8**で、基板 #1 の SV0 は
  `0x45` ではなく **`0x48`** である。**`Unused` にしたスロットも ID を 1 つ予約したまま
  にする** — 予約をやめると、配線で役割を変えた瞬間にスロットの添字がずれて隣の
  スロットの ID を名乗る
- オフセット適用後のデバイス ID が `0x00` になったスロット、および帯からはみ出した
  スロットは駆動せず、`FEEDBACK` も `INFO` も送らない（§2.2 と同じ規則）

### 7.2 `position` モードのみを受け付ける

`velocity` / `duty` の `SET_TARGET` は**無視する**（モードは `position` 固定）。
サーボは角度指令しか受け付けず、duty 値を角度として解釈すると想定外の位置へ飛ぶため。

目標値の単位は **deg**。チャンネルごとの `angle_min` / `angle_max` で必ずクランプする。
可動範囲外を指令するとサーボがメカストッパに当たったまま停動し、短時間で焼損する。
DC 用の `max_duty` に相当する保護であり、省略してはならない。

### 7.3 到達フラグはファームの推定値

**サーボは位置フィードバックを返さないため、`FEEDBACK` の到達フラグは実測ではなく推定である。**
ファームは指令角と現在角の差をスルーレート（`slew_rate`）で割って所要時間を求め、
補間が完了した時点で到達フラグを立てる。

つまり **脱調・過負荷・メカ干渉で実際には動いていなくても到達と報告する**。
PC 側 `move_to` はこのフラグで次のステップへ進むため、**機構が引っかかっていても
シーケンスは進む**。危険な動作には必ず `require_trigger` を付けて
人間の目視確認を挟むこと（`sequences/main_hand.py` のハンド閉じ等）。

### 7.4 `FEEDBACK` の各項目の意味

| 項目 | サーボ基板での意味 |
|---|---|
| 位置 | 補間中の**指令角** [0.1deg]。実測ではない |
| 到達フラグ | §7.3 のとおり推定 |
| センサ入力 | サーボのスロットでは常に 0。`TouchSensor` スロットは**自分の `FEEDBACK`** でこのビットを立てる（§5.2） |

### 7.5 緊急停止・ウォッチドッグ時は「現在角を保持」する

DC 用は出力を切ってコーストさせるが、**サーボは PWM を止めると脱力して back-drivable に
なる**。壁が自重で倒れ、グリッパが把持中のワークを落とす。したがってサーボ基板では
**新しい角度指令の受け付けを止め、その時点の角度を保持し続ける**のを既定とする。

「受け付けを止める」は文字どおりで、**出力禁止中に届いた `SET_TARGET` は目標角として
採用しない**（ウォッチドッグは養う。§6）。採用すると次の 2 つが起きる。

- PC は §5.1 の契約どおり最後の指令を 20Hz で再送し続けるので、再送のたびに補間が
  再アンカーされ、次の補間ティックで `slew_rate × ティック周期` だけ進んでから凍結する。
  既定値なら 1 秒のラッチで 7.2 度動く（グリッパの全ストロークは 5 度、壁は 6 度）
- ラッチ中に指令された角度が解除後に実行される。`SET_TARGET` と解除フレームが同じ
  受信バッチに入ると、凍結を挟まずに補間が走る

**凍結は補間より先に行う。** 後ろに置くと、ウォッチドッグ満了のようにフレームを伴わない
出力禁止では、満了の瞬間に 1 ティック分だけ進んでから凍結することになる。

脱力させたい機構のために `config.h` の `kEStopDetach` で切り替えられるようにしてあるが、
既定は保持（`false`）。

### 7.6 サーボが使う `SET_PARAM`

§3.3 の表のうち、サーボ基板が使うのは `command_timeout_ms`（`0x01`）/
`feedback_interval_ms`（`0x02`）/ `reached_tolerance`（`0x03`）/ `slew_rate`（`0x04`）/
`angle_min`（`0x05`）/ `angle_max`（`0x06`）。`max_duty`（`0x00`）は制御則を持たないので無視する。

**`reached_tolerance` の既定値はサーボ基板では 0。** サーボは実測値を持たず
「目標角 − 指令角」がそのまま補間の残りなので、0 が「補間が完了した時点で到達」（§7.3）を
意味する。0 以外にすると補間完了より手前で到達を報告する。

**`SET_PARAM` は宛先がデバイス ID＝スロットなので、これらは自動的にスロット単位で効く。**
ただし `feedback_interval_ms` だけは基板全体で 1 つ持つ（スロットごとに変えると
送信位相の分散が崩れる）。

**再起動で既定へ戻ることを忘れないこと。** 値は RAM 上のみで、瞬断すると `config.h` の
値に戻る。`FEEDBACK` の bit5（起動後未受信）で PC から検出できる（§3.2）。

**出力が許可されていない間（緊急停止ラッチ中 / ウォッチドッグ満了中 / 起動後未受信）は
`0x03`〜`0x06` を効かせず、値を保留して出力の許可と同時に取り込む。**
`angle_min` / `angle_max` は目標角を新しい範囲へクランプするので、素通しにすると
**§7.5 が入口で止めているはずの「新しい角度指令の受け付け」を `SET_PARAM` 経由で
できてしまう**（`SET_TARGET` は `ServoChannel::setTarget` が拒否するのに `SET_PARAM` は
拒否しない、という非対称が実際にあった）。取り込みの瞬間も現在角は動かさない
（§3.5「解除した瞬間に動き出さない」）ので、狭めた範囲が効くのは次の `SET_TARGET` から。

**可動範囲を狭めても現在角はスルーレート制限に従って戻る。** `angle_min` を上げた瞬間に
指令パルスをその角度へ飛ばしてはならない（§7.3 のスルーレート制限が外側から破られる）。
クランプが掛かるのは目標角だけで、範囲外に出た現在角は補間で範囲内へ戻る。

### 7.7 サーボの可動角（180 / 270）は `config.h` だけが知る

**プロトコルにも PC 側 yaml にも「このサーボは何度型か」は現れない。** `SET_TARGET` の
目標値も `FEEDBACK` の位置も**出力軸の絶対角 [deg]**（§4）であり、角度 → パルス幅の
変換だけが `config.h` の `ServoPulseSpec{minUs, maxUs, angleRangeDeg}` にある。

```
ratio = angleDeg / angleRangeDeg     (0.0 .. 1.0 にクランプ)
pulse = minUs + (maxUs - minUs) * ratio
```

したがって **180 度サーボへ載せ替えても `config/<robot>_positions.yaml` は 1 行も
変わらない**。直すのは `config.h` のその行だけである。この責務分離が、機構担当が
positions の数値だけを差し替えられる前提を支えている。

**サンプルにありがちな「角度へ 180/270 を掛けて `write()` の 0-180 に押し込む」変換は
しない。** 分解能が 2/3 に落ち、可動範囲の端が表現できなくなる。ファームは
`Servo::writeMicroseconds()` でパルス幅を直接指令する。

守るべき規則は 4 つ。

- **`angleRangeDeg` と `minUs` / `maxUs` は 3 値セットで直す。** 180 度サーボは
  500-2400us とは限らない（1000-2000 や 500-2500 が普通にある）。`angleRangeDeg` だけ
  直して残り 2 つを放置すると、載せ替えた意味がないままずれ方だけが変わる。
  `config.h` は型ごとの定数（`kServoPulse270` / `kServoPulse180`）を用意してあるので、
  スロット表のその行を差し替える
- **スロットごとに違う型を挿してよい。** `ServoPulseSpec` はスロット表の各行が持つので、
  1 枚の基板に 270 度と 180 度を混ぜられる
- **0deg 未満の角度は表現できない。** `ratio` を 0.0 でクランプするので、負の角度は
  すべて `minUs` に張り付く。`positions` は **0 起点の片側絶対角**で書くこと
  （270 度サーボの中央を 0 として ±135 と書く形は取れない）。中央を基準にしたい機構は
  `axes.<軸>.offset` で寄せる
- **型を変えたら `kFirmwareVersion` を上げる。** `INFO` の Byte3-4（§3.4）が
  `angleRangeDeg` を自己申告し、PC 側が `expected_angle_range_deg` と突き合わせる。
  **この照合だけが、型の取り違えを CAN 越しに見える形にしている**

## 8. 既知の制限と TODO

| 項目 | 内容 | 対応 |
|---|---|---|
| PC 側の目標値再送 | §5.1 の契約。PC 側は最後に指令した目標値を `command_timeout_ms` 以内に再送し続ける必要がある | PC 側の周期再送で満たす。再送が間に合わない状態は運用上の異常であり、`command_timeout_ms` を伸ばしたり `WATCHDOG_ENABLED` を 0 にして覆い隠してはならない |
| **どちらの基板もフィードバック回路を持たない** | エンコーダ・電流センス・温度センサとも非搭載。DC 用は位置・速度とも 0 で到達フラグも立たず、サーボ用は位置が「指令角」・到達が推定値 | **仕様として確定**。DC の位置・速度制御と PID は実装ごと存在しない（§4） |
| 速度・電流・温度 | どの基板も測る手段を持たない | **プロトコルから外した**。`FEEDBACK` に予約バイトは無く（§3.2。状態フラグ 1 バイト + 位置を持つ基板だけが 2 バイト）、空きは状態フラグの **bit6-7 だけ**。過負荷の検知は機構側の設計と目視でカバー。測れる基板が現れたら bit6-7 か末尾のバイトに定義し直す |
| **電磁弁の動作確認が自動化できない** | 弁が開いたかを観測する手段が 1 つも無い（圧力センサもリミットスイッチも非搭載）。到達フラグを立てると、断線したソレノイドも「到達」と報告される（§9.3） | **仕様として確定**。`on_off` 軸は到達判定を持たないので動作確認シーケンスは `settle_s` の固定待ちへ落ち、鳴ったかどうかは `config/checklist.yaml` の `valves_actuate` で指差喚呼による目視・打音確認を行う |
| **電磁弁基板に物理非常停止入力が無い** | サンプル基板に DC 用の `REF` に相当するピンが存在しない | 物理停止は DC 基板が受け、PC 経由でブロードキャスト `E_STOP` として伝わる（§9.4）。電磁弁基板だけが取り残される経路は無いが、**DC 基板が繋がっていない構成では物理停止が効かない** |
| **DC の動作確認が自動化できない** | 回ったかどうかを観測する手段が 1 つも無い。以前は `FEEDBACK` の velocity で回転検出していたが、実機では必ず「回転検出なし」で落ち、しかも原因が配線不良にしか見えない | **対応済み**。`duty` 軸は到達判定を持たないので動作確認シーケンスは `settle_s` の固定待ちへ落ち、回ったかどうかは `config/checklist.yaml` の `conveyor_run` で指差喚呼による目視確認を行う |
| **DC 用基板に出力禁止（`DIS`）が無い** | 止める手段は PWM 0% の一重のみ | 出力へ至る経路を `DcChannel::outputDuty()` の 1 本に絞り、そこが必ず安全機構を通る。物理非常停止の `REF`（§5.2）を追加の防壁として取り込む |
| **サーボの到達フラグは推定値** | 脱調・過負荷・メカ干渉で実際には動いていなくても「到達」と報告する（§7.3） | 危険な動作には `require_trigger` を付けて人の目視確認を挟む |
| **サーボ基板の Flash / SRAM が小さい** | Arduino Nano は Flash 32KB / SRAM 2KB。ライブラリ 1 つで足りなくなる（RGB LED に FastLED を使うと収まらない） | Adafruit NeoPixel を使い、追加時は必ず使用率を確認する。足りなくなったら `ENABLE_SERIAL_DEBUG` を 0 にする |
| **MCP2515 を 16MHz 水晶で 1Mbps** | サンプルポイントの余裕が乏しい設定として知られている | 実機で通信エラーが出るなら、バス全体を 500kbps へ下げる（M3508・EDULITE 側も揃える必要がある） |
| センサを yaml に登録し忘れると届かない | センサは 1 台の CAN デバイスなので、`config/<robot>.yaml` の `motors:` に無いと受信ループがフレームを誰にも配らない | 照合する仕組みは無い。仕様書 §2.2 の ID 表が唯一の対応表 |
| `SET_PARAM` | PC 側は送っていない（`set_param` コマンドは **M3508 の PC 側 PID 専用**） | 自作モタドラの設定値は `config.h` をビルド時に確定させる運用でカバー。フレーム定義は残す（実機で可動範囲を詰めるときに使う） |
| `SET_MODE` | **廃止した。** 両基板ともモードが固定で、実装のないフレームがコマンド種別を 1 つ占めていた | 制御則を持つ基板が現れたら予約値（`0b101`–`0b111`）から 1 つ取る |
| 予約コマンド種別 | 受信ループが未定義値のフレームで停止する問題 | **対応済み**。`matches_feedback` は `try_parse_can_id` を使い、未定義値と Extended Frame に対して例外ではなく `False` を返す |
| 位置の折り返し | ±3276.7deg で飽和する | サーボ用のみが位置を送るため、可動範囲内で問題にならない |
| 未使用チャンネル | 電磁弁基板の 7ch 目・8ch 目（配線が無い）。かつては DC 基板とサーボ基板にも空きがあった | PC 側 yaml に登録が無く、指令が来ないので動かない。使うときに yaml へモータを足すだけでよい（ファーム側の変更は不要） |
| 通電前 TODO（DC） | `REF` の極性、`DIR` の極性、duty 0 がコーストかブレーキか、`max_duty` の実用値 | `config.h` の `TODO(実機で確認)` に集約 |
| 通電前 TODO（サーボ） | タッチセンサの極性、`angle_min` / `angle_max` の実測、サーボのパルス幅と可動角 | 同上。**可動範囲が広すぎるとメカストッパに当たったまま停動して焼損する**ので最優先 |
| **サーボの型（180 / 270）は自己申告に頼る** | `config.h` の `ServoPulseSpec` と実物の型が食い違っても、指令角どおりに動いたようにしか見えない（§7.7） | `INFO` の Byte3-4 で申告させ、`config/<robot>.yaml` の `expected_angle_range_deg` と照合して `is_fault()` に倒す（§3.4）。**実物の型そのものを測る手段は無い**ので、照合できるのは「ファームに書いた値」と「yaml に書いた値」の一致まで |

## 9. 電磁弁用モタドラ固有の扱い

フレーム形式は他の 2 枚と完全に同じで、違いは「出力が ON/OFF の 2 値しかない」ことと
「基板が STM32 に載っている」ことに由来する。ファームは `firmware/solenoid/`。

**電磁弁基板は STM32F303K8T6 で、UNO R4 Minima とも Arduino Nano とも別物である。**

| | DC 用 | サーボ用 | 電磁弁用 |
|---|---|---|---|
| MCU | UNO R4 Minima（RA4M1 / 32bit） | Arduino Nano（ATmega328P / 8bit） | **STM32F303K8T6（Cortex-M4F / 32bit）** |
| CAN | R4 内蔵ペリフェラル（D4/D5） | MCP2515 を SPI で外付け | **内蔵 bxCAN（PA11 / PA12 固定）** |
| 出力 | PWM 1 本 + 方向 1 本 × 3ch | サーボパルス × 5 スロット | **GPIO の ON/OFF × 6ch** |
| ビルド | PlatformIO | PlatformIO | **STM32CubeMX + CMake** |
| Flash / RAM | 256KB / 32KB | 32KB / 2KB | 64KB / 12KB |

プロトコルは同じでも、**ピン配置を他の 2 枚から類推してはならない。**

### 9.1 1 基板が 6ch を持ち、すべて同じ役割

DC 用・サーボ用と違い、チャンネルごとの役割の切り替えは無い。6ch はすべて
電磁弁（またはそれに準じる ON/OFF 負荷）の駆動口で、`config.h` の
`kSolenoidChannels[]` が持つのはピンと表示名だけである。

- スロットごとに独立したデバイス ID を持ち、**PC からは別々のモータとして見える**
- DIP スイッチは基板番号（§2.2 の Bit5..3）そのもので、4bit あるが基板番号は 3bit。
  8 以上を設定した基板は全チャンネルが未設定になる（駆動拒否）
- **7ch 目・8ch 目は配線が存在しないが、デバイス ID の下位 3bit は 6 個しか使わない
  だけで詰め直さない。** 詰めると基板番号 1 枚目の ID が動き、PC 側 yaml の
  `can_id` を書き直すことになる

### 9.2 `on_off` モードのみを受け付ける

`position` / `velocity` / `duty` の `SET_TARGET` は**無視する**（モードは `on_off` 固定）。

目標値は **0 = OFF / 非 0 = ON** で、しきい値は無い。`duty` を流用せずに
専用の制御タイプを立てたのは、**「duty 0.3 の電磁弁」という意味を持たない指令を
構造的に作れなくするため**である。duty を受け付けると、DC 基板宛のつもりで書いた
`0.3` が電磁弁を全開にし、しかも PC 側の config からは正当な値に見える。

**PC 側は `positions` の名前付き状態でしか値を引かない。** 開/閉は
`config/sub_hand_positions.yaml` の `open` / `closed` として書かれており、
`on_off` 軸に `manual:`（連続値の可動範囲）は書けない（`lib/sequence/positions.py` が拒否する）。

### 9.3 到達フラグは立てない

**この基板は弁が実際に開いたかを観測する手段を持たない。** 圧力センサも
リミットスイッチも無く、分かるのは「指令どおり GPIO を駆動した」ことだけである。

そこで **`FEEDBACK` の到達フラグは常に 0 にする**（DC 基板と同じ扱い）。
指令を出した瞬間に到達を立てると、断線したソレノイドも抜けたコネクタも
「到達」と報告され、UI にもヘルス判定にも**測ったように見える到達**が流れ込む。

PC 側も到達を待たない。`on_off` 軸は `command_mode` が `position` ではないので
`AxisHandle.set_target_value` が固定待ち（`settle_s`）へ落ちる。弁の切り替わりに
要る時間は機構側の定数なので、`config/sub_hand_positions.yaml` の `settle_s` が持つ。

**したがって動作確認（セッティングタイム）も自動化できない。**
`on_off` 軸は到達判定を持たないので動作確認シーケンスは 6 個を 1 個ずつ開閉して
`settle_s` だけ待ち、鳴ったかどうかは `config/checklist.yaml` の `valves_actuate` で
指差喚呼による目視・打音確認を行う。

### 9.4 緊急停止・ウォッチドッグ時は全 ch OFF（消磁）

DC 用と同じく出力を落とす。サーボ用の「現在角を保持」に相当する扱いは**持たない**。

- 電磁弁は通電している間だけ開くので、**止める = 消磁**であり、これが唯一の安全側である
- **吸着で保持しているワークは落ちる。** これは承知の上の設計で、断線・PC 停止・
  操縦者の緊急停止のいずれでも確実に無通電へ倒れることを優先している。
  「保持したまま止まる」を選ぶと、通電したまま復旧不能になった弁を現場で
  切り分ける手段が無くなる
- 出力へ至る経路は `SolenoidChannel::outputOn()` の 1 本に絞ってあり、
  そこが必ず `MotorSafety::isOutputAllowed()` を通る（DC 用の `DcChannel::outputDuty()`
  と同じ形）。ゲートを迂回する経路を `app.cpp` に作ってはならない

**物理非常停止スイッチ（`REF`）の入力はこの基板には無い。** サンプル基板に
そのピンが存在しないためで、物理停止は DC 基板が受けて PC 経由で伝わる
（`FEEDBACK` の緊急停止ビット → サーバー全体の緊急停止 → ブロードキャスト `E_STOP`）。

### 9.5 電磁弁が使う `SET_PARAM`

§3.3 の表のうち、電磁弁基板が使うのは `command_timeout_ms`（`0x01`）と
`feedback_interval_ms`（`0x02`）だけ。`max_duty` は出力が 2 値なので意味を持たず、
サーボ固有の 4 つ（`0x03`–`0x06`）も同様に無視する。

### 9.6 ポンプは電磁弁基板ではなく DC 基板が動かす

サブハンドの吸気ポンプ（`pump_vac`）と排気ポンプ（`pump_blow`）は
**DC 基板 #0 の空きチャンネル**（`0x81` / `0x82`）に載せる（§2.2 の表）。
電磁弁基板の 6ch はすべて弁で埋まっており、またポンプは起動電流が大きく
`max_duty` で立ち上がりを抑えられる DC 基板の側が適している。

**この 2 台は `control_type: duty` であって `on_off` ではない。** 出力段が
PWM 1 本 + 方向 1 本なので、`on_off` を送っても DC 基板は黙って捨てる（§3.1）。
