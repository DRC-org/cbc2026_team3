# 自作モータドライバ CAN プロトコル仕様

DC モータ用・サーボ用の自作モータドライバ（以下モタドラ）と PC 間の CAN 通信仕様。
**この文書がプロトコルの単一情報源**であり、PC 側 `lib/drivers/generic.py` と
ファームウェア `firmware/` の双方がこれに従う。片方だけを変更してはならない。

`docs/impl_plan.md` の「自作モータドライバ用 CAN プロトコル」節は本書への参照だけを置き、
仕様は書かない。バイト列を 2 箇所に書くと片方が古くなったことに誰も気付けないため、
フレーム定義・状態フラグ・パラメータ ID・制御モードの単位・安全機構は本書のみが持つ。
プロトコルを実装・変更するときは本書だけを見ること。

---

## 1. 物理層

| 項目 | 値 |
|---|---|
| 規格 | CAN 2.0A（Standard Frame, 11bit ID） |
| ビットレート | 1 Mbps |
| バス | `can_generic`（`config/can_buses.yaml` 参照） |

Extended Frame は使わない。同じ PC 上の RobStride EDULITE 05 が Extended Frame を
使うが物理バスが別系統であり、仮に混線しても ID 空間が重ならないようにしてある。

---

## 2. CAN ID レイアウト

```
Bit10..8 (3bit): コマンド種別
Bit7..0  (8bit): デバイス ID
```

### 2.1 コマンド種別

| 種別 | 値 | 方向 | 説明 |
|---|---|---|---|
| `SET_TARGET` | `0b000` | PC → モタドラ | 目標値設定 |
| `FEEDBACK` | `0b001` | モタドラ → PC | 状態フィードバック |
| `SET_MODE` | `0b010` | PC → モタドラ | 制御モード変更 |
| `SET_PARAM` | `0b011` | PC → モタドラ | パラメータ変更 |
| （予約） | `0b100` | — | 将来拡張用。**使用禁止** |
| （予約） | `0b101` | — | 将来拡張用。**使用禁止** |
| （予約） | `0b110` | — | 将来拡張用。**使用禁止** |
| `E_STOP` | `0b111` | PC → モタドラ | 緊急停止 / 解除 |

**予約値を勝手に使ってはならない。** PC 側 `GenericDriver.matches_feedback` は
未定義のコマンド種別を「自分宛でないフレーム」として無視するため、予約値を送っても
そのフレームは**どこにも届かないまま捨てられる**。拡張するときは必ず PC 側の
`CommandType` enum を先に更新すること。

なお、以前は `parse_can_id` が未定義値で例外を送出し、それが `CANManager._receive_loop` まで
伝播してバス 1 系統の受信ループごと停止する（＝そのバスの全モータが永久に STALE になる）
状態だった。現在は `matches_feedback` が不正な ID と Extended Frame を握りつぶすため、
想定外のフレームが流れても受信は止まらない。

### 2.2 デバイス ID

| 範囲 | 用途 |
|---|---|
| `0x00` | 予約（未設定）。**この ID のモタドラは駆動してはならない** |
| `0x01`～`0xFE` | 個別デバイス |
| `0xFF` | ブロードキャスト（`E_STOP` のみ） |

**デバイス ID はスロット単位で持つ。** DC 用・サーボ用とも 1 枚の基板が複数の
アクチュエータを駆動し、PC からは別々のモータとして見える。基板は `config.h` の
スロット表に**基準デバイス ID** を持ち、DIP スイッチはその表全体に加える
**ブロックオフセット**として働く。同一ファームの基板を複数枚使うとき、2 枚目の DIP を
1 段上げるだけで全スロットの ID がまとめて次のブロックへ移る。

| 基板 | スロット | DIP | 刻み幅 | ID 帯 | 収容枚数 |
|---|---|---|---|---|---|
| サーボ用 | 5 | 4bit | **5（スロット数）** | `0x01`–`0x10` | 3 枚（DIP 0–2） |
| DC 用 | 3 | 2bit | **3（スロット数）** | `0x11`–`0x1C` | 4 枚（DIP 0–3） |

**刻み幅は「実際に使うアクチュエータの台数」ではなく「スロット数」である。**
サーボ基板はスロットの役割（サーボ / センサ）を配線で選べるので（§7.1）、センサに
使ったスロットも ID を 1 つ予約したままにしないと、役割を変えた瞬間にブロックの幅が
縮んで隣の基板と重なる。刻み幅 1 で足した場合も同じで、DIP を 1 段上げた基板の
ブロックが隣のブロックへ食い込む。そうなると 1 通の `SET_TARGET` で 2 台が同時に動き、
PC 側の受信ループは最初にマッチした 1 台で打ち切るのでもう一方は永久に STALE になる。

**帯からはみ出したブロックは未設定へ倒す。** 倒さずに割り当てると、サーボ基板の DIP を
上げただけで DC 基板の帯を踏む（4bit × 刻み幅 5 は `0x4C` まで伸びる）。未設定にして
おけば LED が赤く速く点滅し、DIP の設定ミスがその場で目に見える。オフセット適用の
結果が `0x00`（未設定）や `0xFF`（ブロードキャスト予約）へ回り込むチャンネルも同様。

オフセット適用後のデバイス ID が `0x00` のスロットは「設定忘れ」とみなし、
LED を赤点滅させて駆動を拒否する。設定ミスで意図しないアクチュエータが動くより、
動かない方が安全なため。

**デバイス ID はバス単位でロボット横断に一意でなければならない**（`config/*.yaml` の
`can_id`）。メインハンドとサブハンドは物理的に同じ `can_generic` を共有しており、
重複すると PC 側の受信ループが最初にマッチした 1 台で打ち切るため、もう一方は
永久にフィードバックを得られない。この一意性は `tests/test_robot_sequences.py` で
検証している。

現在の割り当て（どちらの基板も DIP=0）:

| デバイス ID | モータ | 種別 | 基板 / スロット | ピン |
|---|---|---|---|---|
| `0x01` | `gripper`（メインハンド） | サーボ | サーボ基板 SV0 | D4 |
| `0x02` | `origin_sensor`（メインハンド） | **センサ** | サーボ基板 SV4 | D8 |
| `0x03` | `wall_f`（メインハンド） | サーボ | サーボ基板 SV1 | D5 |
| `0x04` | `wall_r`（メインハンド） | サーボ | サーボ基板 SV2 | D6 |
| `0x05` | `sub_gripper`（サブハンド） | サーボ | サーボ基板 SV3 | D7 |
| `0x11` | `conveyor`（メインハンド） | DC | DC 基板 ch0 | D11 / D12 |
| `0x12` | （未使用） | DC | DC 基板 ch1 | D10 / D3 |
| `0x13` | （未使用） | DC | DC 基板 ch2 | D9 / D7 |

**自作サーボはこの 1 枚で 4 台すべてまかなえる。** サーボ基板を増やす場合は
DIP=1 → `0x06`〜`0x0A`、DIP=2 → `0x0B`〜`0x0F`。DC 基板を増やす場合は
DIP=1 → `0x14`〜`0x16`、DIP=2 → `0x17`〜`0x19`、DIP=3 → `0x1A`〜`0x1C`。

## 3. フレーム定義

全フレーム DLC = 8。浮動小数点は **IEEE754 float32 リトルエンディアン**。
予約バイトは送信側が 0 で埋め、受信側は**内容を無視する**（将来の拡張余地を残すため）。

### 3.1 `SET_TARGET`（PC → モタドラ）

```
Byte 0   : 制御タイプ (0=position, 1=velocity, 2=duty)
Byte 1   : 予約
Byte 2-5 : 目標値 (float32, little-endian)
Byte 6-7 : 予約
```

制御タイプが Byte 0 に入っているため、`SET_MODE` を送らなくてもモード切り替えが起きる
（現行の 2 枚はどちらもモードが固定なので、受理できないタイプは黙って捨てる。§4 / §7.2）。

**受信するたびにコマンドウォッチドッグ（§5.1）がリセットされる。**

**目標値が NaN のフレームは解釈できないものとして捨てる**（ウォッチドッグは養う。
通信自体は生きているため）。NaN は比較がすべて false になるので、可動範囲クランプも
duty クランプも素通りする。目標値として保持してしまうと、以後の出力が NaN のままになり、
`max_duty` クランプが 0 へ落とすので「無言で止まったモータ」になる（`FEEDBACK` の
診断ビットも到達フラグも立たない）。同じ理由で `SET_PARAM`（§3.4）の値が NaN の
フレームも捨てる。

### 3.2 `FEEDBACK`（モタドラ → PC）

```
Byte 0-1 : 現在位置 (int16, 0.1deg 単位, 出力軸)
Byte 2-3 : 現在速度 (int16, rpm, 出力軸)
Byte 4-6 : 予約（送信側は 0 で埋め、受信側は読まない）
Byte 7   : 状態フラグ
             bit0 = 目標到達
             bit1 = 予約
             bit2 = 予約
             bit3 = 緊急停止中
             bit4 = ウォッチドッグ作動中
             bit5 = デバイス ID 未設定
             bit6 = センサ入力
             bit7 = 予約
```

- 送信周期は **100Hz**（`SET_PARAM` で変更可）。PC 側の `feedback_timeout_ms` 既定 500ms に
  対して十分な余裕がある
- **位置は ±3276.7deg で折り返す**。連続回転する軸（コンベア等）で位置制御をしてはならない
  （現行の DC 用基板はそもそも位置制御を持たない。§4）
- 位置・速度を送る基板では**減速機の出力軸換算**とする。換算に必要な定数はファーム側の
  `config.h` が持つ（PC 側は換算を知らない）
- **電流・温度・過電流・過熱は自作モタドラのプロトコルから外してある。** どちらの基板も
  電流センスも温度センサも持たず、今後も持たない。**組み立てる側も読む側もコードを
  持たない** —— 常に 0 の値を運ぶと、UI にもヘルス判定にも「測ったように見える 0」が
  流れ込む。バイト（Byte4-6）とビット（bit1 / bit2）だけを予約として残す
  （センサを積んだ基板が現れたときの置き場）
- **観測手段を持たない項目は 0 を送る。** 現行の基板はどちらもフィードバック回路を持たない:

  | 基板 | 位置 | 速度 | bit0 到達 |
  |---|---|---|---|
  | DC 用 | 常に 0 | 常に 0 | **立てない** |
  | サーボ用 | 指令角（§7.4） | スルーレート換算 | 補間の推定値（§7.3） |

  bit6 だけは例外で、**基板に載ったセンサ入力**を報告する（§5.2）。フィードバック回路
  ではないので上の表には入らない。**センサは 1 個ずつ独立したデバイス ID で FEEDBACK を
  送る**ので、1 枚に何個載っていてもビットは 1 つで足りる。

  **DC 用モタドラはエンコーダ・電流センス・温度センサのいずれも持たない。** 観測手段が
  1 つも無いので、`FEEDBACK` で意味のある値は状態フラグの bit3〜bit5 だけである。
  bit0（到達）を立てないのは、`duty` に到達の概念が無いため —— 「指令したから到達した」は
  実測でも推定でもない嘘になる。**PC 側はこの基板の動作を自動判定できない**ので、
  動作確認は `motor_check.magnitude: 0` で除外し、指差喚呼で目視確認する（§8）
- bit3～bit5 は PC 側 `GenericDriver.update_state` が保持し、`e_stop_active` /
  `watchdog_active` / `device_id_unconfigured` プロパティで読める。
  **bit5（デバイス ID 未設定）は `is_fault()` を True にする**（設定ミスは運用前に必ず
  気付くべきなので、警告ではなく異常として扱う）。bit3・bit4 は異常ではないが
  `check_safety_error()` が動作確認を拒否する理由になる（駆動できない状態で動作確認しても
  必ず失敗し、原因が分からないため）
- **bit4（ウォッチドッグ作動中）は「一度でも `SET_TARGET` を受けたうえで途絶した」ことだけを
  意味する。** 電源投入後まだ 1 通も受けていない基板は bit4 を立てない（出力は §5.4 のとおり
  停止したまま）。未受信でも立てると、PC 側 `check_safety_error()` が最初の指令を送る前に
  セッティングタイムの動作確認を「CAN 通信途絶」として打ち切り、健全な基板に対して配線を
  疑わせる誤誘導になる。**出力停止の条件と bit4 の条件は別物である**（§5.1）

### 3.3 `SET_MODE`（PC → モタドラ）

```
Byte 0   : 制御タイプ (0=position, 1=velocity, 2=duty)
Byte 1-7 : 予約
```

目標値を変えずに制御則だけを切り替える。

**現行のファームはどちらもこのフレームを無視する。** DC 用は `duty` 固定（§4）、
サーボ用は `position` 固定（§7.2）で、切り替えられる制御則を持たないため。
PC 側も送っていない（§8）。フレーム定義は将来モードを持つ基板が現れたときのために残す。

モードを持つ基板を実装する場合、**切り替え時は目標値を 0 にリセットしなければならない。**
前のモードの目標値が別の次元で解釈されて暴走するのを防ぐため（例: 位置目標 90.0 [deg] が
duty 90.0 = 9000% として解釈される事故）。

### 3.4 `SET_PARAM`（PC → モタドラ）

```
Byte 0   : パラメータ ID
Byte 1   : 予約
Byte 2-5 : 値 (float32, little-endian)
Byte 6-7 : 予約
```

| ID | パラメータ | 単位 | 既定値 | DC 用 | サーボ用 | 説明 |
|---|---|---|---|---|---|---|
| `0x00` | `kp` | — | — | 無視 | 無視 | PID ゲイン。制御則を持つ基板が現れたときのための予約 |
| `0x01` | `ki` | — | — | 無視 | 無視 | 同上 |
| `0x02` | `kd` | — | — | 無視 | 無視 | 同上 |
| `0x03` | `max_duty` | 0.0–1.0 | 0.30 | **有効** | 無視 | duty 絶対値の上限。安全のため既定は低め |
| `0x04` | `command_timeout_ms` | ms | 500 | **有効** | **有効** | コマンドウォッチドッグの猶予（§5.1）。**受け付けは 50〜2000ms** |
| `0x05` | `feedback_interval_ms` | ms | 10 | **有効** | **有効** | `FEEDBACK` 送信周期。**受け付けは 1〜1000ms** |
| `0x06` | `overcurrent_threshold_ma` | mA | — | 無視 | 無視 | 電流センスを持つ基板が現れたときのための予約 |
| `0x07` | `reached_tolerance` | deg / rpm | 0（サーボ） | 無視 | **有効** | 到達フラグの許容差（§7.6） |
| `0x10`–`0x12` | サーボ可動範囲 | — | — | 無視 | **有効** | §7.6 |

**受け付けないパラメータは黙って捨てる。** 内部に保持すると、PC 側からは
「設定できたのに効かない値」に見える。

**パラメータは RAM 上のみで、電源を切ると既定値へ戻る。** EEPROM へ保存しないのは、
壊れた値を保存すると次の電源投入で原因不明の暴走になり、現場で切り分けられなくなるため。
恒久的に変えたい値は `config.h` に書いてビルドし直す。

**既定値の置き場は「PC 側との契約かどうか」で分ける。** `command_timeout_ms` は PC 側の
目標値再送周期の根拠、`feedback_interval_ms` は PC 側の STALE 判定が前提にしている送信周期で、
どちらも基板ごとに変えてよい値ではない。この 2 つはファーム側では
`firmware/lib/MotorCan/src/MotorCanProtocol.h`（`kDefaultCommandTimeoutMs` /
`kDefaultFeedbackIntervalMs`）が唯一の定義を持つ。両基板の `config.h` に同じ数字を書くと、
仕様が動いたとき片方だけが古くなる。`max_duty` / `reached_tolerance` はアクチュエータ単位の
チューニング値なので各 `config.h` が持つ。

**`command_timeout_ms` には上限が要る。** §5.1 は「`WATCHDOG_ENABLED` に `SET_PARAM` の
ID は無く、最後の砦が 1 フレームで外れる経路を作らない」と定めているが、猶予そのものを
49.7 日（`(uint32_t)(-1.0f)`）へ伸ばせば同じ結果になる。上限は既定の 4 倍とし、
それを超える値は上限へ丸める。下限 50ms は PC 側の再送周期の目安（§5.1）で、
それより短い猶予は契約どおり再送している健全な機体を止めるだけで安全性を上げない。
負値・0 も RA4M1 では 0 に飽和して「起動直後から永久に出力禁止」に倒れるため、下限へ丸める。
`feedback_interval_ms` も同様に、0 はバスを埋め、極端に長い周期は PC からは
「基板が死んだ（STALE）」ようにしか見えないので、両端を丸める。

**範囲外は境界値へ丸め、NaN のフレームだけは捨てて現在値を保つ**（§3.1）。
化けた float32 を `uint32_t` へ直接キャストするのは未定義動作で、処理系によって
0 にも 4294967295 にも化ける。

未知のパラメータ ID は無視する（PC 側の新しいファームと古い基板が混在しても止まらないように）。

### 3.5 `E_STOP`（PC → モタドラ）

CAN ID = `0b111 << 8 | デバイス ID`。ブロードキャストは `0x7FF`（デバイス ID `0xFF`）。

```
Byte 0   : 0x00 = 緊急停止 / 0x01 = 解除
Byte 1   : 解除時のみ 0x5A（それ以外の値なら解除しない）
Byte 2   : 解除時のみ 0xA5（それ以外の値なら解除しない）
Byte 3-7 : 予約
```

- **停止**: 出力を即座に停止する。以後 `SET_TARGET` を受け取っても**駆動しない**（ラッチ）。
  DC 用基板にゲートドライバの出力禁止（`DIS`）は無く、止める手段は PWM を 0% に
  することだけである（§5.2）
- **解除**: `Byte1=0x5A` かつ `Byte2=0xA5` のときのみラッチを解除する。
  マジックバイトを要求するのは、1 バイトの値だけで安全装置が解除されるのを避けるため
- 解除直後は**その場から動き出さない目標値**から始める。停止前の目標値を復元すると、
  解除した瞬間にモータが動き出して人を巻き込む
  - DC 用（`duty`）では **0**（＝停止）
  - サーボ用（`position`）では **その時点の現在角**。このモードで 0 は原点への移動指令であり、
    0 に落とすこと自体が「解除した瞬間に動き出す」ことになる（§7.5）

PC 側では `GenericDriver.encode_e_stop()` が停止フレーム、`activation_steps()` が
解除フレームを生成する。解除は `CANManager.activate_motors()` 経由で、
サーバの緊急停止解除（`e_stop_release`）と起動時に送られる。

## 4. 制御モードと単位

| モード | 値 | 目標値の単位 | 受理する基板 |
|---|---|---|---|
| `position` | 0 | deg（出力軸） | **サーボ用のみ**（§7.2） |
| `velocity` | 1 | rpm（出力軸） | **どちらも受理しない** |
| `duty` | 2 | **-1.0 ～ +1.0**（符号 = 回転方向） | **DC 用のみ** |

**DC 用モタドラは `duty` しか受理しない。** エンコーダを持たないので位置・速度を
観測する手段が無く、閉ループ制御そのものが成立しないため（§8）。`position` /
`velocity` の `SET_TARGET` は黙って捨てる。捨てずに値だけ使うと、位置目標
90.0 [deg] が duty 90.0（＝ 9000%）の全力指令として解釈される。

**duty は -1.0～+1.0 であって百分率ではない。** `pulse_perc()` は百分率を取るため、
ファーム内で 100 倍する。

duty の絶対値は `max_duty`（既定 0.30）で必ずクランプし、**クランプしてから**
「PWM に出す大きさ」と「方向ピンの向き」に分ける（DC 基板の出力段は
PWM 1 本 + 方向 1 本）。duty 0 は方向を反転させない側に倒すこと。0 を「負」と
扱うと、停止指令が届くたびに方向ピンが反転して機構に衝撃が入る。

## 5. 安全機構

### 5.1 コマンドウォッチドッグ

**`command_timeout_ms`（既定 500ms）の間、自分宛の `SET_TARGET` を 1 通も受信しなければ
出力を停止する。** PC の停止・CAN ケーブル断・コネクタ抜けでモータが回りっぱなしになるのを
防ぐ最後の砦であり、これが無いとコンベアは PC が落ちても回り続ける。

停止後も `FEEDBACK` の送信は継続し、`bit4`（ウォッチドッグ作動中）を立てる。
新しい `SET_TARGET` を受信したら通常動作へ復帰する（ラッチしない。通信が復旧すれば
操縦者の操作で動かせるべきなので）。

**出力停止の条件と `bit4` の条件は別物である。**

| 状態 | 出力 | `FEEDBACK` bit4 |
|---|---|---|
| 電源投入後まだ `SET_TARGET` を 1 通も受けていない | 停止（§5.4） | **立てない** |
| `SET_TARGET` を受けた後 `command_timeout_ms` 以上途絶 | 停止 | 立てる |
| `SET_TARGET` を受信できている | 通常 | 立てない |

bit4 は「CAN 通信が途絶した」ことの報告であって「駆動できない」ことの報告ではない。
未受信の起動直後にまで立てると、PC 側 `check_safety_error()` が最初の指令を送る前に
動作確認を打ち切り、健全な基板の配線を疑わせる。一方で出力は未受信でも許可しない
（通信が始まる前に何かの拍子で駆動されるのを防ぐため）。この 2 条件を 1 つにまとめてはならない。

> **PC 側は最後に指令した目標値を `command_timeout_ms` 以内に再送し続けること。**
> これはプロトコル上の契約であり、目標値が変化したときにしか `SET_TARGET` を送らない実装では
> 満たせない（コンベアに `run` を指令しても既定 500ms 後に止まる）。猶予に対して十分な余裕が
> 要るので、再送周期は `command_timeout_ms` の数分の 1 —— 既定 500ms なら 50ms 周期（20Hz）
> —— を目安とする。

`config.h` の `WATCHDOG_ENABLED` を 0 にすると、DC 用・サーボ用のどちらのファームでも
ウォッチドッグそのものが無効になる（途絶しても駆動ゲートを通し、bit4 も報告しない）。
**PC の停止やケーブル断に対する最後の砦を外すことになるので、試合では既定の 1 のまま使う。**

**無効化しても §5.4 の「`SET_TARGET` を 1 通も受け取るまで出力を許可しない」ゲートは外れない。**
この 2 つは別の条件であり、無効化で外れるのは「途絶したら止める」ことだけである。
まとめて 1 つの条件にすると、`WATCHDOG_ENABLED` が 0 の基板は CAN 通信を 1 通も
受けないまま `setup()` でゲートドライバを開く（電源投入と同時に駆動可能になる）。
ベンチ確認の逃げ道は残る——最初の `cansend` でゲートが開く。

有効/無効は `MotorSafety` が持つ実行時フラグで、`setup()` が `config.h` の値を写す
（`MotorSafety::setWatchdogEnabled()`）。ビルド時の `#if` を各 `main.cpp` に置くと同じ分岐を
両ファームが各自で持つことになり、片方に入れ忘れても誰も気付けない。写し忘れた場合は
有効側に倒れる。**`SET_PARAM` にこのフラグの ID は無く、CAN からは変更できない。**
最後の砦が 1 フレームで外れる経路を作らないため。無効化するにはビルドし直すしかない。

駆動の可否は必ず `MotorSafety::isOutputAllowed()` を通す。ウォッチドッグの満了だけを
見る判定（`isExpired()`）を駆動ゲートに直接書くと、この無効化フラグと緊急停止ラッチの
両方を迂回する。

### 5.2 緊急停止

§3.5 のとおりラッチ式。ソフトウェアの緊急停止であり、**ハードウェアの非常停止スイッチの
代替ではない**。

**DC 用基板には出力禁止ピン（`DIS`）が無い。** 止める手段は PWM を 0% にすることだけで、
防壁は一重である。そのぶん、出力へ至る経路を 1 本に絞り、その 1 本が必ず安全機構を
通るようにしてある（`DcChannel::outputDuty()` が出力禁止中に 0 を返す）。

#### 物理非常停止スイッチの検知（`REF`）

DC 用基板は物理非常停止スイッチの状態を `REF` ピン（D2、**LOW = 押されている**）で
読める。ファームはこれを緊急停止ラッチへ落とし、`FEEDBACK` bit3 で PC へ報告する。

- **押下でラッチし、離しても自動復帰しない。** レベル追従にすると、PC が §5.1 の契約どおり
  20Hz で目標値を再送し続けている以上、**スイッチを離した瞬間に機体が動き出す**。
  解除は `E_STOP`(0x01) の解除フレーム、すなわち操縦者の明示操作だけに限る
- 押している間は、解除フレームが届いてもファームが次のループで再ラッチする。
  「押している間は絶対に動かない」が、フレームの到着順に依らず成立する
- `INPUT_PULLUP` で読むので、**断線したときも「押されている」側へ倒れる**
- 電源投入時に押されていれば、その状態から始める（bit3 を立てずに起動すると、
  PC からは「解除済み」に見える）

#### センサ入力（サーボ基板のスロット）

サーボ基板は 5 本の信号線を持ち、**そのうち何本でもデジタル入力として使える**（§7.1）。
「サーボ 2 + センサ 2 + 空き 1」でも「センサだけ」でも成立する。現構成では `SV4`
（D8、**LOW = 接触**）にタッチセンサを 1 つ繋ぎ、**原点合わせ**に使う。

- **基板は状態を報告するだけで、判断を一切持たない。** しきい値もリトライも停止判断も
  PC 側のシーケンスが持つ。基板に持たせると、機構の調整のたびにファームを焼き直すことになる
- **センサは 1 個ずつ独立した CAN デバイスとして `FEEDBACK` を送り、`Byte7` の bit6 で
  状態を報告する。** サーボのフレームに相乗りさせてはならない —— 相乗り先の無い
  「センサだけの基板」が成立せず（誰も `FEEDBACK` を送らないので永久に読めない）、
  載せられる個数も予約ビットの数で頭打ちになる。1 スロット = 1 デバイスに揃えれば、
  サーボ・センサ・空きが何個ずつでも同じ規則で動く
- センサの `FEEDBACK` は位置・速度とも 0 で、状態フラグも bit5
  （デバイス ID 未設定）と bit6 だけ。**bit3 / bit4 は立てない** —— 駆動されないので
  緊急停止もウォッチドッグも意味を持たず、立てると PC 側 `check_safety_error()` が
  「駆動できない状態」と読んで動作確認を打ち切る
- センサはどのコマンドも受け付けない（自分宛の `E_STOP` もブロードキャストも含む）。
  止める出力が無く、ラッチしても意味が無いため
- `INPUT_PULLUP` で読む。極性は `config.h` の `sensorActiveLow` で切り替える
- **接触は異常ではない。** PC 側 `GenericDriver.sensor_active` は `is_fault()` にも
  `check_safety_error()` にも入らない。入れると、原点合わせで触れさせるたびに機体が
  FAULT になりシーケンスが止まる

**PC 側はセンサを `config/<robot>.yaml` の `motors:` に 1 台として登録すること。**
登録しないと `CANManager` の受信ループがそのフレームを誰にも配らず、接触が PC まで届かない。
目標値を一度も持たないので `GenericTargetRefresher` は `SET_TARGET` を送らず、
`motor_check.magnitude: 0` で動作確認からは外れるが、**途絶は STALE として検出される**
（センサが死んだまま原点合わせを続けないために要る）。

**PC 側は bit3 をサーバー全体の緊急停止へ伝播する。** `RobotServer` は配信ループごとに
`GenericDriver.e_stop_active` を見て、立っていれば `activate_e_stop()` を発動する。
拾わないと、機体は止まっているのに UI は平常のままになり、操縦者はシーケンスが
進まない理由を画面から知る手段が無い。

判定は**解除フレームを送った時刻より後に届いたフィードバック**に限る。解除は
「解除フレーム送信 → 基板がラッチを外す → 次の `FEEDBACK`」の順に伝わるので、
送信前のフィードバックに残った bit3 を信じると、解除した瞬間にサーバーが自分で
止め直し、二度と解除できない機体になる。

### 5.3 duty 上限

`max_duty` で常にクランプする。ファームの既定値は **0.30**（`SET_PARAM` 0x03 で
チャンネルごとに変更可）。上限はチャンネル単位の値であって、基板単位ではない。

### 5.4 起動時の状態

電源投入直後は必ず以下の状態から始める。

- 出力停止（duty 0）
- 目標値 = 0（DC 用は `duty` 0、サーボ用は `config.h` の初期角）
- 緊急停止ラッチ = **解除済み**（PC からの解除を待たずに動ける必要があるため。
  停止させたいなら PC が明示的に `E_STOP` を送る）
- コマンドウォッチドッグ = **未受信**。`SET_TARGET` を 1 通も受け取るまで出力は許可しないが、
  `FEEDBACK` bit4 は立てない（§5.1 の表）
- デバイス ID が `0x00` なら駆動拒否

## 6. 状態遷移

```
        電源投入
           |
           v
   [ID 未設定?] --yes--> (駆動拒否・赤点滅・FEEDBACK bit5)
           | no
           v
        [待機] --SET_TARGET--> [駆動]
           ^                     |
           |   ウォッチドッグ満了  |
           +---------------------+
           |
           |  E_STOP(0x00)
           v
      [緊急停止ラッチ] --E_STOP(0x01,0x5A,0xA5)--> [待機]
           ^
           |  REF(物理非常停止) 押下  ※ DC 用のみ。押している間は毎ループ再ラッチ
           |
```

図の `[待機]` には「電源投入後まだ指令を受けていない」場合と「指令が途絶えて戻ってきた」場合の
2 つがあり、どちらも駆動しないが、**`FEEDBACK` bit4 が立つのは後者だけ**である（§5.1）。

緊急停止ラッチ中は `SET_TARGET` を受け取っても駆動しないが、**ウォッチドッグの
タイマはリセットする**（解除直後にウォッチドッグが即満了しないように）。

## 7. サーボ用モタドラ固有の扱い

フレーム形式は DC 用と完全に同じで、違いは「サーボが位置フィードバックを持たない」ことと
「基板が別の MCU に載っている」ことに由来する。ファームは `firmware/servo/`。

**サーボ基板は Arduino Nano（ATmega328P / 8bit / 5V）で、DC 用の UNO R4 Minima とは
ハードウェアが別物である。**

| | DC 用 | サーボ用 |
|---|---|---|
| MCU | UNO R4 Minima（RA4M1 / 32bit） | **Arduino Nano（ATmega328P / 8bit）** |
| CAN | R4 内蔵ペリフェラル（D4/D5 固定） | **MCP2515 を SPI で外付け**（CS=D10 / INT=D3 / 16MHz） |
| PWM | `PwmOut`（R4 専用） | **`Servo` ライブラリ**（`writeMicroseconds`） |
| 空きピン | 多い | **D11/D12/D13 を SPI が占有。D13 は SCK なのでステータス LED に使えない** |
| Flash / RAM | 256KB / 32KB | **32KB / 2KB** |

プロトコルは同じでも、**ピン配置を DC 用から類推してはならない。** 追加のライブラリを
入れるときは Flash と SRAM の使用率を必ず確認すること。

### 7.1 1 基板が 5 スロットを持ち、スロットごとに役割が違う

サーボ基板は 5 本の信号線（`SV0`〜`SV4`）を持ち、**どれもサーボ出力にもデジタル入力にも
なる**。何を繋ぐかは配線で決まるので、ファームは `config.h` のスロット表に役割を持つ。

| 役割 | 意味 |
|---|---|
| `Servo` | サーボ出力。自分のデバイス ID 宛の `SET_TARGET` で動き、`FEEDBACK` を送る |
| `TouchSensor` | デジタル入力。自分のデバイス ID で `FEEDBACK` を送り、bit6 で状態を報告するだけ（§5.2） |
| `Unused` | 何も繋がない。`pinMode` すら触らない |

**役割の組み合わせは自由で、それぞれ何個でもよい**（センサだけの基板も成立する）。
現構成はサーボ 4 台（`gripper` / `wall_f` / `wall_r` / `sub_gripper`）が 1 枚で収まるので、
残る 1 スロットをタッチセンサに充てている。組み合わせを変えるときは `config.h` の
その行の `SlotRole` を書き換えるだけでよい（**デバイス ID は動かさないこと** —
スロットに固定しておくと、配線を差し替えても PC 側 yaml の `can_id` が無変更で済む）。

これが成立するのは **`Unused` 以外のスロットをすべて CAN デバイスにしてある**ためで、
センサも自分のデバイス ID で `FEEDBACK` を送る。

- スロットごとに独立したデバイス ID を持ち、**PC からは別々のモータとして見える**
  （`config/main_hand.yaml` の `gripper` / `wall_f` / `wall_r` がそれぞれ別の `can_id` を
  持つのはこのため）
- 基板は自分のスロット表に載っているデバイス ID 宛のフレームだけを処理する
- `FEEDBACK` はスロットごとに個別の CAN ID で送る
- **`Unused` のスロットだけ実効デバイス ID を `0x00` にする。** そのスロット宛の
  フレームで何かが起きる経路を構造的に無くすため
- DIP スイッチはスロット表**全体に加えるブロックオフセット**として働き、刻み幅は
  スロット数（§2.2）。**`Unused` にしたスロットも ID を 1 つ予約したままにする** —
  予約をやめると、配線で役割を変えた瞬間にブロックの幅が縮んで隣の基板と重なる
- オフセット適用後のデバイス ID が `0x00` になったスロット、および帯からはみ出した
  スロットは駆動しない（§2.2 と同じ規則）

### 7.2 `position` モードのみを受け付ける

`velocity` / `duty` の `SET_TARGET` と `SET_MODE` は**無視する**（モードは `position` のまま）。
サーボは角度指令しか受け付けず、duty 値を角度として解釈すると想定外の位置へ飛ぶため。

目標値の単位は **deg**。チャンネルごとの `angle_min` / `angle_max` で必ずクランプする。
可動範囲外を指令するとサーボがメカストッパに当たったまま停動し、短時間で焼損する。
DC 用の `max_duty` に相当する保護であり、省略してはならない。

### 7.3 到達フラグはファームの推定値

**サーボは位置フィードバックを返さないため、`FEEDBACK` bit0（到達）は実測ではなく推定である。**
ファームは指令角と現在角の差をスルーレート（`slew_rate`）で割って所要時間を求め、
補間が完了した時点で bit0 を立てる。

つまり **脱調・過負荷・メカ干渉で実際には動いていなくても到達と報告する**。
PC 側 `move_to` はこのフラグで次のステップへ進むため、**機構が引っかかっていても
シーケンスは進む**。危険な動作には必ず `require_trigger` を付けて
人間の目視確認を挟むこと（`robots/main_hand.py` のハンド閉じ等）。

### 7.4 `FEEDBACK` の各項目の意味

| 項目 | サーボ基板での意味 |
|---|---|
| 位置 | 補間中の**指令角** [0.1deg]。実測ではない |
| 速度 | そのときのスルーレートを rpm 換算した値。停止中は 0 |
| bit0 到達 | §7.3 のとおり推定 |
| bit6 センサ入力 | サーボのスロットでは常に 0。`TouchSensor` スロットは**自分の `FEEDBACK`** でこのビットを立てる（§5.2） |

### 7.5 緊急停止・ウォッチドッグ時は「現在角を保持」する

DC 用は出力を切ってコーストさせるが、**サーボは PWM を止めると脱力して back-drivable に
なる**。壁が自重で倒れ、グリッパが把持中のワークを落とす。したがってサーボ基板では
**新しい角度指令の受け付けを止め、その時点の角度を保持し続ける**のを既定とする。

「受け付けを止める」は文字どおりで、**出力禁止中に届いた `SET_TARGET` は目標角として
採用しない**（ウォッチドッグは養う。§6）。採用すると次の 2 つが起きる。

- PC は §5.1 の契約どおり最後の指令を 20Hz で再送し続けるので、再送のたびに補間が
  再アンカーされ、次の補間ティックで `slew_rate × ティック周期` だけ進んでから凍結する。
  既定値なら 1 秒のラッチで 7.2 度動く（グリッパの全ストロークは 5 度、壁は 6 度）
- ラッチ中に指令された角度が解除後に実行される。`SET_TARGET` と解除フレームが同じ
  受信バッチに入ると、凍結を挟まずに補間が走る

**凍結は補間より先に行う。** 後ろに置くと、ウォッチドッグ満了のようにフレームを伴わない
出力禁止では、満了の瞬間に 1 ティック分だけ進んでから凍結することになる。

脱力させたい機構のために `config.h` の `kEStopDetach` で切り替えられるようにしてあるが、
既定は保持（`false`）。

### 7.6 `SET_PARAM` のサーボ向け割り当て

§3.4 の共通 ID のうち、サーボ基板が使うのは `command_timeout_ms`（`0x04`）/
`feedback_interval_ms`（`0x05`）/ `reached_tolerance`（`0x07`）のみ。
`kp` / `ki` / `kd` / `max_duty` / `overcurrent_threshold_ma` は**無視する**（制御則を持たないため）。

**`reached_tolerance`（`0x07`）の既定値はサーボ基板だけ 0 で、§3.4 の 1.0 / 5.0 とは違う。**
サーボは実測値を持たず「目標角 − 指令角」がそのまま補間の残りなので、0 が
「補間が完了した時点で到達」（§7.3）を意味する。0 以外にすると補間完了より手前で到達を報告する。

サーボ固有パラメータを `0x10` 番台に確保する。**`SET_PARAM` は宛先がデバイス ID＝
チャンネルなので、これらは自動的にチャンネル単位で効く。**

| ID | パラメータ | 単位 | 既定値 | 説明 |
|---|---|---|---|---|
| `0x07` | `reached_tolerance` | deg | **0** | §7.3 の到達推定。0 = 補間完了で到達（§3.4 の 1.0 とは違う） |
| `0x10` | `slew_rate` | deg/s | 90 | 最大角速度。到達推定時間の根拠でもある |
| `0x11` | `angle_min` | deg | 機体依存 | 可動範囲の下限 |
| `0x12` | `angle_max` | deg | 機体依存 | 可動範囲の上限 |
