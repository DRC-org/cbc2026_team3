# 自作モータドライバ CAN プロトコル仕様

DC モータ用・サーボ用の自作モータドライバ（以下モタドラ）と PC 間の CAN 通信仕様。
**この文書がプロトコルの単一情報源**であり、PC 側 `lib/drivers/generic.py` と
ファームウェア `firmware/` の双方がこれに従う。片方だけを変更してはならない。

`docs/impl_plan.md` の「自作モータドライバ用 CAN プロトコル」節は本書への参照だけを置き、
仕様は書かない。バイト列を 2 箇所に書くと片方が古くなったことに誰も気付けないため、
フレーム定義・状態フラグ・パラメータ ID・制御モードの単位・安全機構は本書のみが持つ。
プロトコルを実装・変更するときは本書だけを見ること。

---

## 1. 物理層

| 項目 | 値 |
|---|---|
| 規格 | CAN 2.0A（Standard Frame, 11bit ID） |
| ビットレート | 1 Mbps |
| バス | `can_generic`（`config/can_buses.yaml` 参照） |

Extended Frame は使わない。同じ PC 上の RobStride EDULITE 05 が Extended Frame を
使うが物理バスが別系統であり、仮に混線しても ID 空間が重ならないようにしてある。

## 2. CAN ID レイアウト

```
Bit10..8 (3bit): コマンド種別
Bit7..0  (8bit): デバイス ID
```

### 2.1 コマンド種別

| 種別 | 値 | 方向 | 説明 |
|---|---|---|---|
| `SET_TARGET` | `0b000` | PC → モタドラ | 目標値設定 |
| `FEEDBACK` | `0b001` | モタドラ → PC | 状態フィードバック |
| `SET_MODE` | `0b010` | PC → モタドラ | 制御モード変更 |
| `SET_PARAM` | `0b011` | PC → モタドラ | パラメータ変更 |
| （予約） | `0b100` | — | 将来拡張用。**使用禁止** |
| （予約） | `0b101` | — | 将来拡張用。**使用禁止** |
| （予約） | `0b110` | — | 将来拡張用。**使用禁止** |
| `E_STOP` | `0b111` | PC → モタドラ | 緊急停止 / 解除 |

**予約値を勝手に使ってはならない。** PC 側 `GenericDriver.matches_feedback` は
未定義のコマンド種別を「自分宛でないフレーム」として無視するため、予約値を送っても
そのフレームは**どこにも届かないまま捨てられる**。拡張するときは必ず PC 側の
`CommandType` enum を先に更新すること。

なお、以前は `parse_can_id` が未定義値で例外を送出し、それが `CANManager._receive_loop` まで
伝播してバス 1 系統の受信ループごと停止する（＝そのバスの全モータが永久に STALE になる）
状態だった。現在は `matches_feedback` が不正な ID と Extended Frame を握りつぶすため、
想定外のフレームが流れても受信は止まらない。

### 2.2 デバイス ID

| 範囲 | 用途 |
|---|---|
| `0x00` | 予約（未設定）。**この ID のモタドラは駆動してはならない** |
| `0x01`～`0xFE` | 個別デバイス |
| `0xFF` | ブロードキャスト（`E_STOP` のみ） |

デバイス ID は基板上の DIP スイッチ 4bit で設定する（`0x00`～`0x0F`）。
DIP が `0x00` のままの基板は「設定忘れ」とみなし、LED を赤点滅させて駆動を拒否する。
設定ミスで意図しないアクチュエータが動くより、動かない方が安全なため。

**デバイス ID はバス単位でロボット横断に一意でなければならない**（`config/*.yaml` の
`can_id`）。メインハンドとサブハンドは物理的に同じ `can_generic` を共有しており、
重複すると PC 側の受信ループが最初にマッチした 1 台で打ち切るため、もう一方は
永久にフィードバックを得られない。この一意性は `tests/test_robot_sequences.py` で
検証している。

現在の割り当て:

| デバイス ID | モータ | 種別 |
|---|---|---|
| `0x01` | `gripper`（メインハンド） | サーボ |
| `0x02` | `conveyor`（メインハンド） | DC |
| `0x03` | `wall_f`（メインハンド） | サーボ |
| `0x04` | `wall_r`（メインハンド） | サーボ |
| `0x05` | `sub_gripper`（サブハンド） | サーボ |

## 3. フレーム定義

全フレーム DLC = 8。浮動小数点は **IEEE754 float32 リトルエンディアン**。
予約バイトは送信側が 0 で埋め、受信側は**内容を無視する**（将来の拡張余地を残すため）。

### 3.1 `SET_TARGET`（PC → モタドラ）

```
Byte 0   : 制御タイプ (0=position, 1=velocity, 2=duty)
Byte 1   : 予約
Byte 2-5 : 目標値 (float32, little-endian)
Byte 6-7 : 予約
```

制御タイプが Byte 0 に入っているため、`SET_MODE` を送らなくてもモード切り替えが起きる。
モタドラは Byte 0 のタイプで即座に制御則を切り替える。

**受信するたびにコマンドウォッチドッグ（§5.1）がリセットされる。**

**目標値が NaN のフレームは解釈できないものとして捨てる**（ウォッチドッグは養う。
通信自体は生きているため）。NaN は比較がすべて false になるので、可動範囲クランプも
duty クランプも素通りする。DC 側では PID の積分項に一度入ると、以後**正常な目標に対しても**
出力が NaN のままになり、`max_duty` クランプが 0 へ落とすので「無言で止まったモータ」に
なる（`FEEDBACK` の診断ビットも到達フラグも立たない）。同じ理由で `SET_PARAM`（§3.4）の
値が NaN のフレームも捨てる。

### 3.2 `FEEDBACK`（モタドラ → PC）

```
Byte 0-1 : 現在位置 (int16, 0.1deg 単位, 出力軸)
Byte 2-3 : 現在速度 (int16, rpm, 出力軸)
Byte 4-5 : 電流 (int16, mA, 符号は回転方向)
Byte 6   : 温度 (uint8, ℃)
Byte 7   : 状態フラグ
             bit0 = 目標到達
             bit1 = 過電流
             bit2 = 過熱
             bit3 = 緊急停止中
             bit4 = ウォッチドッグ作動中
             bit5 = デバイス ID 未設定
             bit6-7 = 予約
```

- 送信周期は **100Hz**（`SET_PARAM` で変更可）。PC 側の `feedback_timeout_ms` 既定 500ms に
  対して十分な余裕がある
- **位置は ±3276.7deg で折り返す**。連続回転する軸（コンベア等）で位置制御をしてはならない。
  連続回転軸の状態は速度で見ること
- 位置・速度は**減速機の出力軸換算**。エンコーダ CPR と減速比はファーム側の
  `config.h` に持つ（PC 側は換算を知らない）
- **センサを持たない項目は 0 を送る。** DC モタドラは温度センサを持たないため常に 0 であり、
  PC 側の温度警告（既定 65℃）は発火しない。これは既知の制限（§8）
- **電流も基板の実装に従う。** DC 用ファームはビルド時フラグ `HAS_CURRENT_SENSE` が 0 の基板で
  電流を常に 0 とし、bit1（過電流）も立てない。センス回路の無い基板は SENS ピンが浮き、
  ADC の振れがそのまま電流値として過電流しきい値を跨ぐため、値を送れば必ず誤発火する。
  サーボ基板は電流センスを持たないので常にこの扱い（§7.4）
- bit3～bit5 は PC 側 `GenericDriver.update_state` が保持し、`e_stop_active` /
  `watchdog_active` / `device_id_unconfigured` プロパティで読める。
  **bit5（デバイス ID 未設定）は `is_fault()` を True にする**（設定ミスは運用前に必ず
  気付くべきなので、警告ではなく異常として扱う）。bit3・bit4 は異常ではないが
  `check_safety_error()` が動作確認を拒否する理由になる（駆動できない状態で動作確認しても
  必ず失敗し、原因が分からないため）
- **bit4（ウォッチドッグ作動中）は「一度でも `SET_TARGET` を受けたうえで途絶した」ことだけを
  意味する。** 電源投入後まだ 1 通も受けていない基板は bit4 を立てない（出力は §5.4 のとおり
  停止したまま）。未受信でも立てると、PC 側 `check_safety_error()` が最初の指令を送る前に
  セッティングタイムの動作確認を「CAN 通信途絶」として打ち切り、健全な基板に対して配線を
  疑わせる誤誘導になる。**出力停止の条件と bit4 の条件は別物である**（§5.1）

### 3.3 `SET_MODE`（PC → モタドラ）

```
Byte 0   : 制御タイプ (0=position, 1=velocity, 2=duty)
Byte 1-7 : 予約
```

目標値を変えずに制御則だけを切り替える。**切り替え時、モタドラは目標値を 0 に
リセットし、PID の内部状態（積分項）をクリアする。** 前のモードの目標値が別の次元で
解釈されて暴走するのを防ぐため（例: 位置目標 90.0 [deg] が duty 90.0 = 9000% として
解釈される事故）。

### 3.4 `SET_PARAM`（PC → モタドラ）

```
Byte 0   : パラメータ ID
Byte 1   : 予約
Byte 2-5 : 値 (float32, little-endian)
Byte 6-7 : 予約
```

| ID | パラメータ | 単位 | 既定値 | 説明 |
|---|---|---|---|---|
| `0x00` | `kp` | — | 機体依存 | 位置/速度制御の比例ゲイン |
| `0x01` | `ki` | — | 0 | 積分ゲイン |
| `0x02` | `kd` | — | 0 | 微分ゲイン |
| `0x03` | `max_duty` | 0.0–1.0 | 0.30 | duty 絶対値の上限。安全のため既定は低め |
| `0x04` | `command_timeout_ms` | ms | 500 | コマンドウォッチドッグの猶予（§5.1）。**受け付けは 50〜2000ms** |
| `0x05` | `feedback_interval_ms` | ms | 10 | `FEEDBACK` 送信周期。**受け付けは 1〜1000ms** |
| `0x06` | `overcurrent_threshold_ma` | mA | 機体依存 | 過電流フラグのしきい値 |
| `0x07` | `reached_tolerance` | deg / rpm | 1.0 / 5.0 | 到達フラグの許容差 |

**パラメータは RAM 上のみで、電源を切ると既定値へ戻る。** EEPROM へ保存しないのは、
壊れた値を保存すると次の電源投入で原因不明の暴走になり、現場で切り分けられなくなるため。
恒久的に変えたい値は `config.h` に書いてビルドし直す。

**既定値の置き場は「PC 側との契約かどうか」で分ける。** `command_timeout_ms` は PC 側の
目標値再送周期の根拠、`feedback_interval_ms` は PC 側の STALE 判定が前提にしている送信周期で、
どちらも基板ごとに変えてよい値ではない。この 2 つはファーム側では
`firmware/lib/MotorCan/src/MotorCanProtocol.h`（`kDefaultCommandTimeoutMs` /
`kDefaultFeedbackIntervalMs`）が唯一の定義を持つ。両基板の `config.h` に同じ数字を書くと、
仕様が動いたとき片方だけが古くなる。`max_duty` / `overcurrent_threshold_ma` / `kp`・`ki`・`kd` /
`reached_tolerance` はアクチュエータ単位のチューニング値なので各 `config.h` が持つ。

**`command_timeout_ms` には上限が要る。** §5.1 は「`WATCHDOG_ENABLED` に `SET_PARAM` の
ID は無く、最後の砦が 1 フレームで外れる経路を作らない」と定めているが、猶予そのものを
49.7 日（`(uint32_t)(-1.0f)`）へ伸ばせば同じ結果になる。上限は既定の 4 倍とし、
それを超える値は上限へ丸める。下限 50ms は PC 側の再送周期の目安（§5.1）で、
それより短い猶予は契約どおり再送している健全な機体を止めるだけで安全性を上げない。
負値・0 も RA4M1 では 0 に飽和して「起動直後から永久に出力禁止」に倒れるため、下限へ丸める。
`feedback_interval_ms` も同様に、0 はバスを埋め、極端に長い周期は PC からは
「基板が死んだ（STALE）」ようにしか見えないので、両端を丸める。

**範囲外は境界値へ丸め、NaN のフレームだけは捨てて現在値を保つ**（§3.1）。
化けた float32 を `uint32_t` へ直接キャストするのは未定義動作で、処理系によって
0 にも 4294967295 にも化ける。

未知のパラメータ ID は無視する（PC 側の新しいファームと古い基板が混在しても止まらないように）。

### 3.5 `E_STOP`（PC → モタドラ）

CAN ID = `0b111 << 8 | デバイス ID`。ブロードキャストは `0x7FF`（デバイス ID `0xFF`）。

```
Byte 0   : 0x00 = 緊急停止 / 0x01 = 解除
Byte 1   : 解除時のみ 0x5A（それ以外の値なら解除しない）
Byte 2   : 解除時のみ 0xA5（それ以外の値なら解除しない）
Byte 3-7 : 予約
```

- **停止**: 出力を即座に停止（コースト）し、ゲートドライバの `DIS` をアサートする。
  以後 `SET_TARGET` を受け取っても**駆動しない**（ラッチ）
- **解除**: `Byte1=0x5A` かつ `Byte2=0xA5` のときのみラッチを解除する。
  マジックバイトを要求するのは、1 バイトの値だけで安全装置が解除されるのを避けるため
- 解除直後は**その場から動き出さない目標値**から始める。停止前の目標値を復元すると、
  解除した瞬間にモータが動き出して人を巻き込む
  - `duty` / `velocity` では **0**（＝停止）
  - `position` では **その時点の現在位置**。このモードで 0 はエンコーダ原点への移動指令であり、
    0 に落とすこと自体が「解除した瞬間に動き出す」ことになる（サーボが §7.5 で現在角を
    保持するのと同じ理由。制御モードは変えない）

PC 側では `GenericDriver.encode_e_stop()` が停止フレーム、`activation_steps()` が
解除フレームを生成する。解除は `CANManager.activate_motors()` 経由で、
サーバの緊急停止解除（`e_stop_release`）と起動時に送られる。

## 4. 制御モードと単位

| モード | 値 | 目標値の単位 | 対象 |
|---|---|---|---|
| `position` | 0 | deg（出力軸） | サーボ、位置決めする DC |
| `velocity` | 1 | rpm（出力軸） | 速度制御する DC |
| `duty` | 2 | **-1.0 ～ +1.0**（符号 = 回転方向） | 開ループ駆動の DC |

**duty は -1.0～+1.0 であって百分率ではない。** サンプルコードの `pulse_perc()` は
百分率を取るため、ファーム内で 100 倍する。`config/main_hand.yaml` の
`conveyor.motor_check.magnitude: 0.3` は 30% duty を意味する。

duty の絶対値は `max_duty`（既定 0.30）で必ずクランプする。

## 5. 安全機構

### 5.1 コマンドウォッチドッグ

**`command_timeout_ms`（既定 500ms）の間、自分宛の `SET_TARGET` を 1 通も受信しなければ
出力を停止する。** PC の停止・CAN ケーブル断・コネクタ抜けでモータが回りっぱなしになるのを
防ぐ最後の砦であり、これが無いとコンベアは PC が落ちても回り続ける。

停止後も `FEEDBACK` の送信は継続し、`bit4`（ウォッチドッグ作動中）を立てる。
新しい `SET_TARGET` を受信したら通常動作へ復帰する（ラッチしない。通信が復旧すれば
操縦者の操作で動かせるべきなので）。

**出力停止の条件と `bit4` の条件は別物である。**

| 状態 | 出力 | `FEEDBACK` bit4 |
|---|---|---|
| 電源投入後まだ `SET_TARGET` を 1 通も受けていない | 停止（§5.4） | **立てない** |
| `SET_TARGET` を受けた後 `command_timeout_ms` 以上途絶 | 停止 | 立てる |
| `SET_TARGET` を受信できている | 通常 | 立てない |

bit4 は「CAN 通信が途絶した」ことの報告であって「駆動できない」ことの報告ではない。
未受信の起動直後にまで立てると、PC 側 `check_safety_error()` が最初の指令を送る前に
動作確認を打ち切り、健全な基板の配線を疑わせる。一方で出力は未受信でも許可しない
（通信が始まる前に何かの拍子で駆動されるのを防ぐため）。この 2 条件を 1 つにまとめてはならない。

> **PC 側は最後に指令した目標値を `command_timeout_ms` 以内に再送し続けること。**
> これはプロトコル上の契約であり、目標値が変化したときにしか `SET_TARGET` を送らない実装では
> 満たせない（コンベアに `run` を指令しても既定 500ms 後に止まる）。猶予に対して十分な余裕が
> 要るので、再送周期は `command_timeout_ms` の数分の 1 —— 既定 500ms なら 50ms 周期（20Hz）
> —— を目安とする。

`config.h` の `WATCHDOG_ENABLED` を 0 にすると、DC 用・サーボ用のどちらのファームでも
ウォッチドッグそのものが無効になる（途絶しても駆動ゲートを通し、bit4 も報告しない）。
**PC の停止やケーブル断に対する最後の砦を外すことになるので、試合では既定の 1 のまま使う。**

**無効化しても §5.4 の「`SET_TARGET` を 1 通も受け取るまで出力を許可しない」ゲートは外れない。**
この 2 つは別の条件であり、無効化で外れるのは「途絶したら止める」ことだけである。
まとめて 1 つの条件にすると、`WATCHDOG_ENABLED` が 0 の基板は CAN 通信を 1 通も
受けないまま `setup()` でゲートドライバを開く（電源投入と同時に駆動可能になる）。
ベンチ確認の逃げ道は残る——最初の `cansend` でゲートが開く。

有効/無効は `MotorSafety` が持つ実行時フラグで、`setup()` が `config.h` の値を写す
（`MotorSafety::setWatchdogEnabled()`）。ビルド時の `#if` を各 `main.cpp` に置くと同じ分岐を
両ファームが各自で持つことになり、片方に入れ忘れても誰も気付けない。写し忘れた場合は
有効側に倒れる。**`SET_PARAM` にこのフラグの ID は無く、CAN からは変更できない。**
最後の砦が 1 フレームで外れる経路を作らないため。無効化するにはビルドし直すしかない。

駆動の可否は必ず `MotorSafety::isOutputAllowed()` を通す。ウォッチドッグの満了だけを
見る判定（`isExpired()`）を駆動ゲートに直接書くと、この無効化フラグと緊急停止ラッチの
両方を迂回する。

### 5.2 緊急停止

§3.5 のとおりラッチ式。ソフトウェアの緊急停止であり、**ハードウェアの非常停止スイッチの
代替ではない**。

### 5.3 duty 上限

`max_duty` で常にクランプする。ファームの既定値は **0.30**。
サンプルコードでは `maxDuty` が初期化されないまま `constrain(motorPower, 0, maxDuty)` に
渡されており、実際には常に 0 になってモータが回らない。既定値を明示的に持つこと。

### 5.4 起動時の状態

電源投入直後は必ず以下の状態から始める。

- 出力停止（duty 0、コースト）
- 制御モード = `duty`、目標値 = 0
- 緊急停止ラッチ = **解除済み**（PC からの解除を待たずに動ける必要があるため。
  停止させたいなら PC が明示的に `E_STOP` を送る）
- コマンドウォッチドッグ = **未受信**。`SET_TARGET` を 1 通も受け取るまで出力は許可しないが、
  `FEEDBACK` bit4 は立てない（§5.1 の表）
- デバイス ID が `0x00` なら駆動拒否

## 6. 状態遷移

```
        電源投入
           |
           v
   [ID 未設定?] --yes--> (駆動拒否・赤点滅・FEEDBACK bit5)
           | no
           v
        [待機] --SET_TARGET--> [駆動]
           ^                     |
           |   ウォッチドッグ満了  |
           +---------------------+
           |
           |  E_STOP(0x00)
           v
      [緊急停止ラッチ] --E_STOP(0x01,0x5A,0xA5)--> [待機]
```

図の `[待機]` には「電源投入後まだ指令を受けていない」場合と「指令が途絶えて戻ってきた」場合の
2 つがあり、どちらも駆動しないが、**`FEEDBACK` bit4 が立つのは後者だけ**である（§5.1）。

緊急停止ラッチ中は `SET_TARGET` を受け取っても駆動しないが、**ウォッチドッグの
タイマはリセットする**（解除直後にウォッチドッグが即満了しないように）。

## 7. サーボ用モタドラ固有の扱い

フレーム形式は DC 用と完全に同じで、違いは「サーボが位置フィードバックを持たない」ことに
由来する。ファームは `firmware/servo/`。

### 7.1 1 基板が複数チャンネルを持つ

サーボ基板は 1 枚で複数のサーボを駆動する。**チャンネルごとに独立したデバイス ID を持ち、
PC からは別々のモータとして見える**（`config/main_hand.yaml` の `gripper` / `wall_f` /
`wall_r` がそれぞれ別の `can_id` を持つのはこのため）。

- 基板は自分のチャンネル表に載っているデバイス ID 宛のフレームだけを処理する
- `FEEDBACK` はチャンネルごとに個別の CAN ID で送る
- DIP スイッチはチャンネル表**全体に加えるオフセット**として働く（同一ファームの基板を
  複数枚使うため）。DC 用の「DIP がそのままデバイス ID」とは意味が違う
- オフセット適用後のデバイス ID が `0x00` になったチャンネルは駆動しない（§2.2 と同じ規則）

### 7.2 `position` モードのみを受け付ける

`velocity` / `duty` の `SET_TARGET` と `SET_MODE` は**無視する**（モードは `position` のまま）。
サーボは角度指令しか受け付けず、duty 値を角度として解釈すると想定外の位置へ飛ぶため。

目標値の単位は **deg**。チャンネルごとの `angle_min` / `angle_max` で必ずクランプする。
可動範囲外を指令するとサーボがメカストッパに当たったまま停動し、短時間で焼損する。
DC 用の `max_duty` に相当する保護であり、省略してはならない。

### 7.3 到達フラグはファームの推定値

**サーボは位置フィードバックを返さないため、`FEEDBACK` bit0（到達）は実測ではなく推定である。**
ファームは指令角と現在角の差をスルーレート（`slew_rate`）で割って所要時間を求め、
補間が完了した時点で bit0 を立てる。

つまり **脱調・過負荷・メカ干渉で実際には動いていなくても到達と報告する**。
PC 側 `move_to` はこのフラグで次のステップへ進むため、**機構が引っかかっていても
シーケンスは進む**。危険な動作には必ず `require_trigger` を付けて
人間の目視確認を挟むこと（`robots/main_hand.py` のハンド閉じ等）。

### 7.4 `FEEDBACK` の各項目の意味

| 項目 | サーボ基板での意味 |
|---|---|
| 位置 | 補間中の**指令角** [0.1deg]。実測ではない |
| 速度 | そのときのスルーレートを rpm 換算した値。停止中は 0 |
| 電流 | 常に 0（電流センス無し） |
| 温度 | 常に 0（温度センサ無し） |
| bit0 到達 | §7.3 のとおり推定 |
| bit1 過電流 / bit2 過熱 | 常に 0（検出手段が無い） |

### 7.5 緊急停止・ウォッチドッグ時は「現在角を保持」する

DC 用は出力を切ってコーストさせるが、**サーボは PWM を止めると脱力して back-drivable に
なる**。壁が自重で倒れ、グリッパが把持中のワークを落とす。したがってサーボ基板では
**新しい角度指令の受け付けを止め、その時点の角度を保持し続ける**のを既定とする。

「受け付けを止める」は文字どおりで、**出力禁止中に届いた `SET_TARGET` は目標角として
採用しない**（ウォッチドッグは養う。§6）。採用すると次の 2 つが起きる。

- PC は §5.1 の契約どおり最後の指令を 20Hz で再送し続けるので、再送のたびに補間が
  再アンカーされ、次の補間ティックで `slew_rate × ティック周期` だけ進んでから凍結する。
  既定値なら 1 秒のラッチで 7.2 度動く（グリッパの全ストロークは 5 度、壁は 6 度）
- ラッチ中に指令された角度が解除後に実行される。`SET_TARGET` と解除フレームが同じ
  受信バッチに入ると、凍結を挟まずに補間が走る

**凍結は補間より先に行う。** 後ろに置くと、ウォッチドッグ満了のようにフレームを伴わない
出力禁止では、満了の瞬間に 1 ティック分だけ進んでから凍結することになる。

脱力させたい機構のために `config.h` の `kEStopDetach` で切り替えられるようにしてあるが、
既定は保持（`false`）。

### 7.6 `SET_PARAM` のサーボ向け割り当て

§3.4 の共通 ID のうち、サーボ基板が使うのは `command_timeout_ms`（`0x04`）/
`feedback_interval_ms`（`0x05`）/ `reached_tolerance`（`0x07`）のみ。
`kp` / `ki` / `kd` / `max_duty` / `overcurrent_threshold_ma` は**無視する**（制御則を持たないため）。

**`reached_tolerance`（`0x07`）の既定値はサーボ基板だけ 0 で、§3.4 の 1.0 / 5.0 とは違う。**
サーボは実測値を持たず「目標角 − 指令角」がそのまま補間の残りなので、0 が
「補間が完了した時点で到達」（§7.3）を意味する。0 以外にすると補間完了より手前で到達を報告する。

サーボ固有パラメータを `0x10` 番台に確保する。**`SET_PARAM` は宛先がデバイス ID＝
チャンネルなので、これらは自動的にチャンネル単位で効く。**

| ID | パラメータ | 単位 | 既定値 | 説明 |
|---|---|---|---|---|
| `0x07` | `reached_tolerance` | deg | **0** | §7.3 の到達推定。0 = 補間完了で到達（§3.4 の 1.0 とは違う） |
| `0x10` | `slew_rate` | deg/s | 90 | 最大角速度。到達推定時間の根拠でもある |
| `0x11` | `angle_min` | deg | 機体依存 | 可動範囲の下限 |
| `0x12` | `angle_max` | deg | 機体依存 | 可動範囲の上限 |
