# 実機で観測された事象（新しい順）

各エントリは「いつ / 何が起きたか（症状・実測値）/ どう決着したか」だけを持つ。
設計の理由は `docs/invariants.md`、現況は `docs/checks_and_health.md` が正。

## 2026-09-09 リミットスイッチを NC 接点へ替え、センサ極性を 7 本とも反転した

前日 2026-09-08 にサーボ基板 #1 のサブハンド 4 本（`0x349`〜`0x34C`）を **NO 接点**で実測した
—— `INPUT_PULLUP` で開放 HIGH・押下 LOW、`FEEDBACK` の bit4 は開放 `0x00` / 押下 `0x10`、
`sensorActiveLow: true`。`rotate`（基板 #0 SV3）が `false` なのは、あちらだけ NC だったから。
4 本とも押下と開放の両方を `candump` で観測した（下端は最初の測定で押下が 1 通も出なかったが、
原因は下記の配線ずれで、挿し直した後に `0x34C` で `0x00` → `0x10` → `0x00` を 2 回観測）。

その測定で踏んだ穴が 2 つ:

- **配線が 1 スロットずれていた。** サブの 4 本が SV1〜SV4 ではなく SV0〜SV3（`0x348`〜`0x34B`）
  に刺さっており、`0x348` は `config/main_hand.yaml` の `y_axis_l_origin_sensor` の枠なので
  **サブハンドの前端を踏むとメインハンドの `y_axis` 左原点が反応した**。PC 側にはどこにも出ない
  —— どちらも `sensors:` に登録済みで `FEEDBACK` は 100Hz で正常に届くため、ヘルスは全部 `ok`
  のまま。挿し直した後にも同じずれが残っていて（押しっぱなしの静止値で上端が `0x34A`、下端が
  `0x34B`）、手掛かりは「押した本数と反応した本数が合わない」ことだけだった。前端 → 後端 →
  上端 → 下端の順に `0x349` → `0x34A` → `0x34B` → `0x34C` が立ち、`0x348` が一度も反応しない
  ことで決着
- **静止値だけを見て「6 本とも極性が逆」という誤読が立った。** 未配線（HIGH）と NO の開放
  （HIGH）、NC の平常時（LOW）と NO の押下（LOW）は 1 点では区別できない

09-09 にスイッチを **NC 接点へ交換**し（`c6cb21f`）、`firmware/servo/include/config.h` の
`sensorActiveLow` を **7 本とも `false`** にした（未実測の `y_axis` 左右 2 本の仮値も同じく
反転）。交換後に `candump` で両状態を見た記録は無い。**`kFirmwareVersion` は 6 のまま
上げていない**ので、交換前のビルドが載った基板も `INFO` で 6 を名乗り、`expected_firmware: 6`
の照合を素通りする —— その基板は零点確定の離脱段で「離せませんでした」に落ち、可動端保護は
触れていない間だけ原点側を塞ぎ、端に触れた瞬間に守りが外れる。現況は
`docs/mechanism_handoff.md` §4-1。

## 2026-09-08 `y_axis` の零点確定を左右 2 本のスイッチで組んだ

サーボ基板 3 枚の割当が固まり、`y_axis` の左右に原点リミットスイッチが 1 本ずつ付いた
（右 = 基板 #0 SV4 `0x44` / 左 = 基板 #1 SV0 `0x48`。#0 に空きが無いので 2 枚にまたがる）。
2 本目は予備ではなく、**原点の決め方そのものを変えた** —— 片方が当たった瞬間の姿勢を原点に
すると機構の遊びぶんが焼き付き、遊びの向きは前回の移動方向で変わるので「原点合わせをしたのに
毎回少しずつ違う場所が原点になる」という**再現しない**ずれになる。探索の後に整列段を挟み、
「両方が押された姿勢」を原点にした。

組む途中で 2 つの穴が見つかった。**同期補正が整列を打ち消していた** —— `sync_kp` が意味を
持つ前提は「全員が位置制御中」と「全員が同じ軸位置を目標にしている」の 2 つで、実装は前者しか
見ていなかった。整列段は後者を意図的に崩す段なので、実測でずれ 1mm に対し片側 −440counts・
相方 +440counts が乗り、**進めたい側は押し戻され、保持側は前へ引きずられた**（`sync_limit`
1250counts に対して 1mm で 3 分の 1 以上を使い切る）。**保持側を毎歩実測へ再アンカーすると
歯止めが 1 つも発火しない** —— 遊びが無い機構では進めた側が保持側を引きずり、目標が引きずられた
先へ追従するので左右のずれが増えず、`align_distance` にも停滞判定にも掛からないまま軸ごと
機構端まで走る。固定保持にして停滞判定（3 歩）で拾う形にした。

決着: `homing.sensors`（モータ名 → センサ名の対応表）と整列段、`align_distance`（`sensors` を
書いた軸には必須・`sync_tolerance` より真に小さいことを起動時に強制）、
`SyncGroup.targets_share_axis_value()` による補正の自動停止。歯止めは 7 つになった。
**config は有効化したが実機ではまだ 1 度も走らせていない** —— `direction` / 左右 2 本の極性 /
`align_distance` 5.0mm / `step` 0.5mm はどれも未実測で、探索は 650.0 / 0.5 = 1300 歩
（最短 65 秒・最悪 325 秒）。現在の規則は `docs/invariants.md` の「左右にスイッチが 1 本ずつ
付く軸は『両方が押された姿勢』を原点にする」、失敗経路の対応表は
`docs/checks_and_health.md` の零点確定節。

## 2026-09-08 指令してから待ち始めるまでの窓で消えた目標が「到達」になっていた

`move_to` は全軸へ指令を送り終えてから `wait_reached` をまとめて作る。その数 ms の窓に
緊急停止（`TargetRefresher.clear_targets()`）が挟まると、`wait_reached` は目標が無い状態で
待ち始め、「目標が無ければ到達済み」に吸われて **True** を返していた。**症状は「E-STOP を
踏んだのにシーケンスの進捗だけが 1 つ先へ進む」**で、解除後の再開位置が姿勢と食い違う。
この不具合は `asyncio.sleep(0.01)` で緊急停止を狙う「実時間で狙うテスト」が隠しており、
CI で不定期に `assert ['move','after'] == ['move']` として現れ、再実行で緑になるため
**フレークとして片付く形**をしていた。

決着: `wait_reached(expect_target=True)` を呼び出し側の宣言として足し、テストを到達判定の
フックで毎回同じ順序で再現する形へ張り替えた。

## 2026-09-08 PID ゲインの値検査が破れていた

`pid` はキー名だけを起動時に突き合わせ、値の検査を「数値でなければ警告して既定値」に
預けていた。yaml の `true` は `float()` を通って 1.0 として静かに効き、`.inf` / `.nan` も
例外を投げないので**警告 0 件でそのまま採用される**（`kp: .inf` が有効なゲインとして起動）。

決着: `_parse_pid` が `_number()` を呼んで bool・非数値・NaN・無限大を弾く（`null` は許す）。

## 2026-09-08 畳み込みの上限を確かめるテストが分岐へ到達していなかった

`_settle_pending_reenergize` の待ち上限を確かめているつもりのテストが、**`asyncio.wait` の
`timeout` を `None` にしても通っていた**（実測 0.24s）。根拠にしていた前提が事実と違った
—— docstring は「エグゼキュータへ入った `bus.send` は `Task.cancel()` では止まらない」と
書いていたが、**待っている側の Task は `cancel()` した瞬間に `CancelledError` を受け取る**
（実測 0.000s）。上限が効くのは相手が `CancelledError` を握り潰す場合だけで、現状の鎖に
その箇所は無い。

決着: 保険と分かったうえで残し、テストを居座るコルーチンへ張り替えた（定数は改名）。

## 2026-09-08 起動・実行時ログが読めない

要求は「制御プログラムのログが見にくい。特に Web サーバーのログは要らない」。実測は 4 つ。

- **定型部だけで 60 桁超**（`2026-09-08 09:20:45,337 [INFO] lib.control.position_loop:`）。
  本文が端末の右端へ押し出される
- **アクセスログがリロード 1 回で数十行**（SPA なので index.html / JS / CSS / 自己ホスト
  フォントが並ぶ）。直前の CAN・シーケンスのログが画面外へ流れる
- **ステップログが `@step` のラベルと 2 箇所に分かれ、44 行あって実際にずれていた** ——
  `@step("ハンド閉じる (受け取り)")` の本体は `[sub_hand] ハンド閉じる`、
  `@step("ワーク解放 (配置)")` の本体は `[sub_hand] ワーク解放`
- **起動ログの最長行が 300 桁超**。`ロボット登録` が 5 組の名前を Python の repr のまま並べ、
  しきい値は dataclass の repr、指差喚呼は `{'pre_match': 27}` で値が埋もれていた

決着: `lib/logging_setup.py` を体裁の単一情報源にし（時刻 + 5 桁レベル + 14 桁ロガー名）、
アクセスログを二重に止め、`--log-level` を足し、ステップログをエンジン 1 箇所へ、

## 2026-09-07 サーボ基板 3 枚目（UNO R4 Minima）で `INFO` の潜在欠陥が顕在化した

3 枚目だけ MCU が違う（#0/#1 = Nano + MCP2515、**#2 = UNO R4 Minima + 内蔵 CAN**。
サーボピンは #2 が SV0=D9 / SV1=D11 / SV2=D10 / SV3=D6 / SV4=D3、RGB は D8）。
改修中に `loop()` が `INFO` を 5 スロット分まとめて同じ反復で送っていることが見つかった。
**#2 の `Arduino_CAN` は標準 ID の mailbox を 1 本しか使わない**（`write()` が
`CAN_MAILBOX_ID_0` 固定）ので 2 通目以降が必ず落ち、`kInfoIntervalMs`(1000) が
`feedback_interval_ms`(10) の整数倍で位相が固定されるため**毎回同じスロットだけが出て
残り 4 本は永久に 1 通も出ない**。**サーボが今まで無症状だったのは MCP2515 が TX 3 本を
持ち空きを待つからでしかなく、同じ欠陥がずっとハードの余裕に隠されていた。**

決着: DC / 電磁弁と同じ「1 反復 1 通・落ちたスロットは添字を進めず次の反復で送り直す」へ
揃えた（`#if` による MCU 分岐は入れない）。ビルドは
`pio run -e nano` と `-e uno_r4_minima` の**両方**を通す必要がある。`kFirmwareVersion` は
5 のまま（CAN 上の振る舞いが変わっていないため）。

## 2026-09-06 コート別位置定数の初の実使用（`conveyor` の搬送方向）

赤コートと青コートでコンベアの搬送方向が逆になるという機構要件が判明。duty は −1.0〜+1.0 で
符号がそのまま回転方向なので、`run: { red: 0.3, blue: -0.3 }` の **1 行だけ**で済んだ
（Python も TypeScript も `sequences/*.py` も 1 行も変えていない）。**仕組みだけがあって一度も
使われていなかったものが、初めて実使用に入った。**

- **赤 = +0.3 / 青 = −0.3 は仮置き。** どちらが正転かは配線と機構が決め、ファーム側の
  `kDirForwardIsLow` も未確認。逆でも機構は壊れず「両コートともワークを反対向きへ送る」
  としてしか現れないので、**試合当日にしか症状が出ない**
- コート依存は `conveyor` の搬送方向だけ（`y_axis` / `rotate` の位置はコート非依存と機構側が
  結論）。機構が変わったら再確認が要る
- 指差喚呼 `conveyor_run` の文言を直した —— 動作確認は `run` → `stop` の 1 往復しか回さず、
  **確認できるのは選択中のコートの向きだけ**である

## 2026-09-06 `INFO` を一度も受けていない基板があると焼き忘れ検出が黙って無効になる

DC 基板は mailbox が 1 本しか無く、まとめ送りのコードでは `INFO` が **1 通も出ない**。
PC は `INFO` の未受信を照合しない（正しい）ので FAULT にならないが、同時に
`GenericDriver.info_mismatch` による焼き忘れ検出も働かず、**気付ける経路そのものが存在
しなかった**。ヘルスにも `is_fault()` にも一切出ない点で「励磁されていない」と同型。

決着: FAULT でも STALE でもない第 3 の状態として `firmware_confirmed()` を足し、起動から
`_FIRMWARE_INFO_GRACE_S`（3 秒）を過ぎても未確認のモータを
`safety.firmware_unconfirmed_motors` として配信（診断ツリーに青チップ）。**STALE のモータは
対象外**（基板ごと落ちていれば既に warning で出るうえ、手当てが逆になる —— この報告が残したい
のは「`FEEDBACK` は 10ms で届くのに `INFO` だけ出ない」ケースで、電源・CAN 配線を疑っても
必ず空振りする）。UI の文面はファームの焼き直しと `candump`。

## 2026-09-06 再励磁コマンドと 3 度の敵対的レビューで見つかった穴

「励磁されていない」の復帰経路が緊急停止の解除か再起動しか無く**どちらも試合を止める**ため、
WS コマンド `reenergize_motors` を足した。レビューで次々に穴が出た（3 件の敵対的レビューを
1 つにまとめてある）。

- **剥がさずに励磁すると「現在角を書いてから励磁」が 1 周期で無効化される。** フォルト直前の
  古い目標やラッチが生きたままだと、enable 直後の再送（最大 50ms 後）が古い値で上書きする
- **励磁そのものを全モータへ渡していた。** 移動中の健全なモータを一瞬止めて enable し直す
  形で割り込む。`activate_motors(only=…)` を足した
- **手動のジョグ起点を捨てていなかった。** 落ちた分だけ次のジョグが飛ぶ。当初 `manual.reset()`
  （ロボット全体）にしたが、`sub_lift` 1 台の再励磁で無関係な `sub_arm_joint` の起点まで
  捨てていたので `reset_axes_for_motors()` へ絞った
- **ペア展開が「disable は機構を動かさない」前提を初めて破っていた。** 片側が無励磁のとき
  相方も対象に入るが、`feedback_probe_message()` は **disable** なので健全な相方が保持トルクを
  失う。宣言順（`rotate_r` → `rotate_l`）では**軸が両側とも無励磁になる窓**が開く
  （復帰まで約 100ms、**最悪 550ms**）。会場カードは「機体は動かない」と断言しているので
  操縦者はワークを掴んだまま押す。`CANManager._may_probe_for_feedback` を 1 箇所だけ置いた
- **排他が片方向にしかなかった。** `_reactivate_motors` / `_motor_check_environment_deny` /
  `_apply_operation_mode` が在飛を見ておらず、`_manual_target` にも同じガードが無かった。
  シーケンス系（`sequence_start` / `sequence_jump` / `trigger`）は 1 方向も塞いでいなかった
- **緊急停止インターロックが完全に無テストだった。** 変異で確認すると、再励磁経路だけ
  `should_abort` を渡さない変異も、再励磁側の停止フレーム再送だけを消す変異も**1 件も
  落ちなかった**（1913 passed）
- **`_reactivate_motors` の docstring の待ちの根拠が逆だった（危険な嘘）。** 「古いタスクは
  中断へ向かっている」ではなく、実際は中断されず最後まで走る。有界であることは変わらない
  ——現行 config の実測上限は `sub_hand` 3 台で最悪 1.5 秒、`main_hand` 2 台で最悪 1.0 秒
- **成功直後の 1 周期（実測 ~50ms）だけ画面が「直っていない」と言っていた**
  （`_energize_expected_since` を置き直していなかった）

現在の規則は `docs/invariants.md` の「再励磁（`reenergize_motors`）」、手順は
`docs/venue_recovery.md` §3-5。

## 2026-09-05 診断カラムに「測ったように見える 0」が並んでいた

`conveyor` が **「0.0 / 0.0 / 0.0 / 0.0℃」**と表示されていた。DC 基板はエンコーダも電流センスも
温度センサも積んでおらず `FEEDBACK` は状態フラグ 1 バイト（DLC=1）しか送らないので、
どれも測った値ではない。**画面からは「本当に 0」と「そもそも測っていない」が区別できない。**
出どころは `MotorState` の 4 値が float 固定で、その詰め物が配信へ素通ししていたこと。
契約フィクスチャも嘘をついていた —— `ws-contract.json` の `gripper` はモックの
`MotorState(temperature=30.0)` で作られ、**温度を測れない基板が 30.0℃ を報告する契約**が
焼き付いていた。

決着: `TelemetrySupport` をドライバが宣言し、倒すのは `_measured_only()` と
`CANManager.health()` の 2 箇所だけ。UI は `null`（測る手段が無い）と `MALFORMED`（読めない）を
`readMeasured()` で厳密に分ける。位置を測れないモータの POS 欄にだけ PC の指令値（`→0.30` /
`→ON`）を出す（実出力ではないので `→` と `title` で断る）。現在の規則は
`docs/invariants.md` の「測れない項目は配信の境界で `null` へ倒す」。

## 2026-09-05 動作確認の実行中に緊急停止が押せなかった

`MotorCheckPanel` は `Modal` で描かれ、起動確認ダイアログの「開始」がそのまま自動で開いて
いた。`.modal` は全画面 fixed オーバーレイなので、**両ハンドの全アクチュエータが順に駆動
されているあいだずっと、ヘッダーの EMG STOP がオーバーレイに覆われてクリックできない**

**止める手段だけが画面から消える**壊れ方で、操縦者には「押したらパネルが閉じた」としか見えない。

決着: 進捗と結果を `MatchPrep` のインライン展開へ移した（判定も配信も触っていない）。

## 2026-09-05 EDULITE が無励磁のまま放置される経路が実在した

`rotate` が**指令しても動かない**。静止摩擦や機構の引っかかりを疑って `step` と
`position_kp` を触ったが、原因は**無励磁**だった。経路は UNDERVOLTAGE で fault → 励磁が
落ちる → 電圧が戻って **fault は消える** → しかし励磁には戻らない（`mode_state` は 0 のまま）。

**この状態はヘルスに何も出さない** —— 20Hz の問い合わせにフィードバックは正常に届くので
STALE にならず、`fault_bits` は 0 に戻っているので `is_fault()` にも掛からず、CAN のエラー
カウンタにも異常が出ない。つまり**ヘルスは OK のまま「指令しても動かない」だけが残る**。

決着: `state.safety.unenergized_motors` として配信（`is_energized()`）。復帰には
`activate_motors` を通る経路が要る（目標値再送は enable を 1 通も送らない）。
**切り分けの教訓: 「指令しても動かない」ときは機構を疑う前に励磁状態を見る。**

## 2026-09-05 スイッチに当たっているのに探索が止まらなかった

## 2026-09-04 受信の取りこぼしと累積角への 360deg 注入

**症状**: `y_axis` を何回か動かしていると走行中に軸が荒れて（左右が押し合って）`SyncMonitor` の
同期ずれで全体緊急停止。**ログにも UI にも前触れが無い。** 2 つの不具合が直列に並んでいた。

**① 受信が 1 通ごとにエグゼキュータへ往復していた。** 往復コストは実測 **168us/通**。C620 は
1 台 1kHz なので M3508 2 台 + `can_generic` で **4200 通/秒**になり、**受信だけで 1 コアが埋まる**
（実測 CPU 83.5%）。追いつかない分はカーネルが捨て、実機の `ip -s link` は
**`can_m3508` の受信 369 万通に対し 77 万通（17%）が `rx_dropped`** だった。

**② 折り返し推定のガードが、まさに要る場面でだけ素通りしていた。** 窓の長さを
`time.monotonic()`（処理時刻）で測っていたが、取りこぼし中は滞留から詰めて処理するので
**処理間隔は 1ms 程度にしか見えない**。巡航 200mm/s = モータ軸 1834rpm = 250counts/ms なので
半周 4096counts に達するのは **16ms** ——**16ms 分が捨てられるだけで累積角へ 1 回転 = 360deg
= 6.54mm**（`scale` 55.0131deg/mm）が入る。再現結果:

| 捨てられた窓 | 位置の誤差 | 再アンカー | 原点信頼 |
|---|---|---|---|
| 5ms / 10ms | 0.000mm | 0 回 | True |
| 16ms / 20ms / 30ms | **−6.544mm** | **0 回** | **True** |
| 50ms | **−13.088mm** | **0 回** | **True** |

**この誤差はどこにも報告されない**（再アンカーを通らないので `health_detail()` は黙ったまま）。
「ガガガガ」の正体は、注入が左右一方にしか乗らないため PID が偏差 360deg を埋めにいって飽和
（`kp` 32 × 360 = 11520counts、`output_limit` 5000）し、同時に同期補正が `sync_limit`
1250counts に張り付いて直結した左右が押し合うこと。1 発 6.54mm は `sync_tolerance` 10mm を
一度では超えないので、**2 発目かより長い窓で超えて緊急停止**する ——「何回か動かしていると」。

決着: ①受信をイベントループの可読通知（`loop.add_reader`）で受ける ——
**1 通 168us → 47.5us、受信全体の CPU 83.5% → 34.8%**。②窓の長さをフレーム自身のタイム
スタンプで測る。**②は①が効いていても外せない**（窓は負荷次第で再び開く）。
現在の規則は `docs/invariants.md` の「窓の長さはフレーム自身のタイムスタンプで測る」。

## 2026-09-04 実運用ストローク（150mm）で 3.6 倍速くした

きっかけは「遅すぎる、4 倍ほど速くしてほしい」。**最初は振幅 15mm で測っていたが、それは
位置定数が 0〜15mm の仮値だったからで、実運用の移動距離ではない**（実際は 150mm 以上が主）。
振幅 15mm では巡航が 0%（三角プロファイル）で `max_acceleration` が、150mm では巡航が 94% で

- **律速は `output_limit` だった。** 15mm で a≥1200 にすると指令が 2000counts に張り付く。

- **`max_acceleration` は速さではなく滑らかさで決めた。** 4800 → 1200 で 150mm の所要時間は

32, 10, 1.0 で据え置き / `sync_kp`,`sync_limit` 8.0, 500 → **16.0, 1250** /

## 2026-08-26 テレメトリ配信の堅牢化

ライトテーマ移行を `--dry-run` の実機描画で確認している最中に、**画面が「接続中」を表示した

（幅 358px）で `MatchTimer` が **157px** まで縮んで font-size 3.4em の数字が枠からはみ出し、
`SubsystemStatus` は **424px** へ膨らんで右端がビューポートを **58px** 超過した。
また `flex-shrink` の既定で、機体状態が強制展開した瞬間に試合時間の caption が数字に重なって
読めなくなった（削れる余地の無い側に `shrink-0`、内部スクロールを持つ側に溢れを引き受けさせる）。

## 2026-08-26 ライトテーマ化と daisyUI の落とし穴

配色を面 `#ffffff` / 地 `#eef1f4` / 沈み `#d5dbe2` / 文字 `#181b1f` へ移行（状態色は
success `#2f7a4f` / warning `#96620a` / error `#b3372c` / info `#25667f`。「白抜き文字で AA」と
「`badge-soft` の淡色地で AA」の両方を満たす値）。`index.css` は 227 行 → 約 150 行、
ヘッダーとタブの統合で 2 段（約 3.6rem）→ 1 段（約 2.2rem）、1366x768 で縦 4% を操作領域へ戻した。

実測で判明した罠: `card-xs` / `table-xs` は **padding だけでなく font-size まで直接指定**し
ルートの `clamp()` スケーリングから外れる / range のつまみの既定色が白でパネル上で見えない /
`:disabled` の既定が地 10%・文字 20% で状態表示を兼ねる無効ボタンが読めない /
lucide の `absoluteStrokeWidth` は `size="1em"` で NaN になり線が消える。
dry-run 実機描画で見つけた不具合では、**セッティングタイム中ずっと動作確認ボタンが押せない**
（`sequenceRunning` をステップ番号から推定していたが準備中は `step_index=0 / total_steps>0` が
常に成立）が最も重い。判定をサーバーと同じ「フェーズ」に合わせた。
