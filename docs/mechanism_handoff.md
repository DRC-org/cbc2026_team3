**機構担当と制御担当が一緒に上から潰すための表。** 制御側の数値は**大半が今も**
「**機構が付いていない状態で誰かが起動しても壊れない**」ことだけを狙った安全側の
微小値である。実測で確定したのは、メインハンドの `y_axis` と `rotate` の一部だけ。

実測で確定。§4）—— **この 2 本は `y_axis` の零点確定を有効化したことで「あると望ましい」
から「未実測のまま初回を回すと必ず離脱段で止まる」へ格上げされた**、
**サブハンドはほぼ全部**（§2）。`y_axis` のゲインも**短距離（15mm）では取り直していない**。
極性のように**スロットごと・軸ごとにしか決まらない値は、確定した 1 つを他へ広げてはならない。**

**機構を壊さない代わりに、人が見なければ気付けない仮値もある** ——
`positions.conveyor.run` のコート別の符号（赤を正転とした割り当て。§1）がそれで、逆でも
コンベアは回るので**自動判定は素通りする**（duty 軸は到達判定を持たない）。気付ける機会は
指差喚呼 `conveyor_run` で人が向きを見るときだけで、そこを通すと**両コートともワークを
反対向きへ送る**という形でしか現れない。

この一覧が無いと、当日は「動かしてみて、おかしいところだけ直す」ことになる。
それでは**危険な向きに間違っている値ほど、壊してからでないと気付けない**。

## 0. 最優先の 4 つ — **これだけは機構が付いた日のうちに**

他は「動かない・届かない」で済むが、この 4 つは**壊す向き**に間違っている。
上の 3 つは「広すぎる」ことが危険で、広すぎても平常時は何の症状も出さない。
4 つ目（基板 #2 の初期角）だけは向きが違い、**電源を入れた瞬間に機構がその角へ飛ぶ**
—— 測る前に通電する機会が最初に来るぶん、実質いちばん早く踏む。
**行が増減したら見出しの数も直すこと** —— 数はこの節が「その日のうちに閉じきれる短い表」
であることの宣言で、表と食い違うと閉じたかどうかを数えられなくなる。

| 対象 | 現在値 | 場所 | 何が起きるか |
|---|---|---|---|
| `rotate` の `homing.search_distance` | **180.0deg** | `config/main_hand_positions.yaml` | **広すぎると機構端まで押し込む。** 「当たるまで動かす」動作に対する唯一の無人の歯止めで、配線が抜けたセンサは「いつまでも当たらない」形でしか現れない。現在値は `manual` の全幅そのままの暫定値なので、実測のスイッチ位置 + わずかな余裕へ詰める。**2026-09-05 の零点確定はスイッチに触れた状態から始めたので、この値は一度も試されていない** —— 実際に何 deg で当たるかは、触れていない位置から始めたときに初めて分かる。**`direction` −1 のほうは同日に実機で裏付けられた**（離脱後に寄せ直した向きが正しかった）ので、2 つを混同しないこと |
| `y_axis` の `homing.search_distance` | **650.0mm** | `config/main_hand_positions.yaml` | 同上。**2026-09-08 に `homing:` を有効化した**（§1）ので、この歯止めは**もう効く経路に載っている**。現在値は `manual` の全幅（0.0〜650.0mm）と一致させた暫定値で、実測のスイッチ位置 + わずかな余裕へ詰める。**この軸はまだ 1 度も実機で走らせていないので、`direction` −1 も左右 2 本の極性も未実測**である（§4）—— `rotate` と違って「向きは裏付けられている」と言える材料が 1 つも無い |
| サーボの可動範囲クランプ（`kGripperLimits` / `kWallFLimits` / `kWallRLimits` / `kSubRotateRLimits` / `kSubRotateLLimits` / `kSubPitchRLimits` / `kSubPitchLLimits` / `kSubOffsetLimits`） | **8 本とも `{0.0, 270.0, 90.0}`**（0〜270deg / 90deg/s） | `firmware/servo/include/config.h` | **広すぎるとサーボが機構に当たったまま押し続けて焼損する。** 現在値は**サーボの全可動域**なので、クランプは実質効いていない（位置定数を実運用値へ更新したときに全域へ開けた）。**駆動する 8 スロットが 1 本ずつ独立した定数を持つ**（共有だと 1 スロットの都合で他スロットのクランプまで一緒に緩む）。実可動域が決まったら**そのスロットの定数だけ**すぐに狭める。ファームを焼き直すので、当日の作業順で後回しにしないこと。**左右ペア（`sub_rotate_r`/`_l`・`sub_pitch_r`/`_l`）も 1 本ずつ測る** —— 逆回転側は絶対角を折り返して届くので、同じ論理位置でも左右で角度が違う。**スルーレート 90deg/s は位置定数の `timeout_s` と対**で、`tests/test_servo_travel_budget.py` が突き合わせている |
| **サーボ基板 #2 の 5 スロットの `initialAngleDeg`** | **5 本とも 0.0f（仮値）** | `firmware/servo/include/config.h` | **この基板は通電した瞬間に 5 本ともこの角へ駆動する**（`Unused` だった間は attach すらしなかったので、動くようになったのは 5 スロットが `Servo` になってからである）。**仮値のまま機構を付けてはならない** —— 通電のたび、そして基板が瞬断で再起動するたびに 0deg へ飛ぶ。再起動は `FEEDBACK` の「起動後未受信」ビットとして PC に出るが、**飛んだ後にしか出ない**。§2 の `positions.sub_rotate` / `sub_pitch` / `sub_offset` の `home` と揃えること |

**`search_distance` を詰めるときは `manual` の `min`/`max` も同時に実測へ寄せる。**
片方だけ動かすと「原点に届かない」か「宣言した可動範囲の外まで押し込む」のどちらかになる。
`rotate` は今その約束どおりで、`search_distance` 180.0deg は `manual` の全幅
（0.0〜180.0deg）と一致している。**`y_axis` も 2026-09-08 に揃った** —— かつては
仮値時代の `manual` 全幅（`20.0 - (-2.0)` = 22.0）のまま取り残されて実ストローク 650mm に
届かなかったが、有効化と同時に 650.0mm（= `manual` の全幅 `650.0 - 0.0`）へ取り直した。
**この対だけは 2 箇所に分かれて書かれているので、片方だけ動かされたことを機械的に検出
するのは `tests/test_main_positions_config.py` の一致検査だけである。**

### 探索時間はセッティングタイムから引かれる

`search_distance / step` が歩数で、1 歩ごとに `settle_s` を最低 1 回待つ。
`rotate` の現在値では 180.0 / 1.0 = 180 歩 × 0.05s = **最短 9 秒**、1 歩の追従待ちに
`_FOLLOW_ATTEMPTS`（5 回）を使い切ると 1 歩 0.25 秒で**最悪 45 秒**。動作確認を回す
たびにこれが入る。**縮めてよいのは `step` だけ** —— `search_distance` は歯止めなので
速さのために縮めてはならない。

**ただし `step` には静止摩擦由来の下限がある（2026-09-05 に実機で判明）。**
0.5deg では `position_kp` 30.0 が生むトルクが減速機の保持力と静止摩擦を超えられず、
離脱段で 3 歩連続して進まず `HomingError` になった。手動操縦では 1.0deg で動くが、
ホーミングは 1 歩ごとに静止するので**毎歩で静止摩擦を超え直す**必要があり、閾値
ぎりぎりの値だと停滞判定（`step/2` 未満が 3 歩連続）へ落ちる。**現在値 1.0deg は
動かなかった 0.5 の 2 倍しかない** —— **実機で `HomingError` が出るようなら 1.5 前後へ
戻す判断が要る**（機構担当と一緒に見る値。`config` だけを見て決められない）。

**`step` はそのまま原点の分解能である** —— スイッチが ON になる瞬間を `step` 刻みでしか
刻めないので、原点誤差の上限が `step` になる。`rotate` の `tolerance` が 2.0deg なので、
現在値 1.0 は**その半分**にあたる。**検出の遅れによる行き過ぎも最大 1 歩ぶん**なので、
可動範囲の端（0deg）にあるスイッチを越えて機構に当たる量も同じだけ縮む。

## 3-1. `y_axis` の左右ずれを詰める

**2026-09-03 に実機で一通り詰めた。以下は実測に基づく。**

### この軸で起きていること（実測）

`y_axis` は左右 2 台の M3508 がラックを介して直結しているが、**左右で静止摩擦が
大きく違い、しかも遊びのせいで片方がもう片方を連れ回さない**。減速比 19:1 なので、
片側を数 mm 回した程度では反対側は動かない（連れ回すには大きく動かすことになり、
負荷の面で望ましくない）。実測値：

| kp | 出た指令 | 右 | 左 |
|---|---|---|---|
| 4〜8 | 110〜220 counts | 動かない | 動かない |
| 16 | 440 counts | **動く** | 動かない（1mm も） |
| 40 | 440〜554 counts | 動く | 動き出す境界 |
| 72 | 800 counts | 動く | 動くが行き過ぎ 434〜653% |

`kp=4` / 振幅 2mm では**右だけが目標に到達し、左が 1.970mm 取り残されて**
`sync_tolerance` 超過でラッチした。30 秒の波形でも、右が 1.019mm 動く間に
左は 0.046mm しか動いていない。

**したがって「片方が他方を連れ回す」前提は成り立たない。両方を能動的に、
揃えて動かす必要がある。** これが 3 項すべてに役割がある理由である。

### 決まった値と、それぞれの役割

| 値 | 役割 |
|---|---|
| `kp` **32** | 重い側（左）が静止摩擦を超えるのに要る。16 では左が動かない |
| `ki` **10** | **偏差が残り続ける側でだけ積分が育つ。** 右は先に動いて偏差が消えるので育たず、左だけ増える —— 左右の非対称性に自動で追従する |
| `kd` **1.0** | 行き過ぎを 50〜113% から 0〜5% へ抑える。**これが無いと `kp` を上げられない** |
| `integral_limit` **400** | `ki` を入れた以上必須。機構端で積分が育つと拘束が外れた瞬間に暴走する |
| `sync_kp` **8** | 移動中のずれ最大を半減（0.275mm → 0.130mm）。`kp` の 1/4 |
| `sync_limit` **500**（本番）| 押し合いの歯止め。現状のずれ量では届かないが、外してはならない |

改善の推移（移動中のずれ最大）：

```
kp=16 のみ              0.860mm
  + ki=10               0.411mm   左が動き出す
  + kd=1.0              0.220mm   行き過ぎが消える
  + kp=32               0.178mm
  + sync_kp=8           0.130mm   ← 現在値
```

### 測り方 —— 画面では読めない

**同期偏差は WS 配信（20Hz）の瞬時値としてしか出ない。** 移動は数百 ms で終わるので、
画面では「移動中に最大どれだけ開いたか」を追えない。**補正の効果は移動中のピークに
しか現れない**ので、必ず次のどちらかで測ること。

```bash
# 送信しない観測ツール。main.py と同時に走らせてよい。
# 無励磁のまま手で機構を動かせば、可動範囲の実測にも使える
uv run python scripts/sync_probe.py --csv /tmp/run.csv

# ステップ応答を取り、条件だけを変えた同一条件の試行を並べて比べる（機体が動く）
uv run python scripts/tune_y_axis.py --amplitude 1.5 --kp 24,32 --ki 10 --kd 1.0 --sync-kp 8
```

`tune_y_axis.py` が振れるつまみは **8 つ**（`--kp` / `--ki` / `--kd` / `--sync-kp` /
`--output-limit` / `--max-velocity` / `--max-acceleration` / `--velocity-ff`）で、
どれもカンマ区切りでスイープできる。**ただし同時にスイープしてよいのは 8 つのうち 1 つだけ**（2 つ同時に
振ると、組み合わせの数だけ機体が動くうえ、どちらが効いたのか読めない結果が並ぶ）。
プロファイルのつまみも同じ 1 本の制限に入る —— ゲインと軌道を同時に振ったら、なおさら
読めない。試行ごとに制御ループとプロファイルを作り直すので、前の試行の積分・ラッチ・
軌道は持ち越さない。

**プロファイルの既定は config が持つ。** 位置定数に `axes.<軸>.motion` が書いてあれば
何も渡さなくてもそれが使われる（**本番とまったく同じ制御で測れる**）。
`--max-velocity` と `--max-acceleration` は**対でしか渡せず**、`--velocity-ff` だけを
渡すとプロファイルが無い＝参照速度が存在しないので拒否される。

**まず飽和率を読むこと。** 出力が上限に張り付いている間は**ゲインを変えても応答が
変わらない**ので、飽和を見ずに `kp` を振ると「上げても下げても同じ」という観察から
抜け出せない。飽和率は比較表の右端に必ず出る（動かなかった試行でも出る）。
プロファイルを有効にしているなら、**飽和はプロファイルが機構の能力を超えている合図**
でもある —— そのときはゲインではなく `max_acceleration` / `max_velocity` を下げる。

**`--dwell` はプロファイルの移動時間より長く取る。** 記録窓が移動の途中で閉じると、
行き過ぎも整定も**まだ起きていない**ものを測ることになり、指標が一律に良い方へ嘘をつく
（しかも「速いプロファイルほど数字が良い」という逆向きの結論が出る）。短すぎる
`--dwell` はツールが起動時に拒否して必要な値を提示する。

### 手順 2. `max_acceleration` を上げる

```bash
uv run python scripts/tune_y_axis.py ... --amplitude 15 --dwell 3.0 \
    --max-acceleration 300,600,1000
```

**この軸は摩擦支配である。** 重い側の静止摩擦だけで 500counts 相当あり、質量を
加速するのに要る力はそれに比べて桁違いに小さい。したがって**制御側から見た余裕は
大きい**。効く制約は制御ではなく:

- **機構強度**（ラック・ピニオン・取り付け）
- **ワーク保持力**（グリッパ・吸着が加速度に負けて滑る / 落ちる）

**中止条件**

- **飽和率が上がり始めたら、その 1 つ手前を採る。** 飽和は「プロファイルが機構の
  能力を超えた」合図である
- **打音・振動が出たら止める。** 数字より先に耳と手で分かる。機構強度の限界は
  比較表には出ない
- **ワークが滑る・落ちる。** 保持力の限界。ここは制御では埋められないので、
  **加速度を下げる**のが正しい対処
- 行き過ぎが増える方向へ動いたら、それは加速度ではなく PID の問題（手順 4 へ）

### 手順 3. `max_velocity` を上げる —— **`velocity_ff` と `kd` は必ずセット**

```bash
# まず速度だけ
uv run python scripts/tune_y_axis.py ... --amplitude 15 --dwell 3.0 \
    --max-velocity 50,80
# 次に、その速度で velocity_ff を振る
uv run python scripts/tune_y_axis.py ... --amplitude 15 --dwell 3.0 \
    --max-velocity 80 --velocity-ff 0,1.0,1.6
```

**`kd` の単位は counts/(deg/s) なので、巡航速度がそのまま制動として出力に乗る。**
`kd`=1.0 で 50mm/s = 2750deg/s を出すと **D 項だけで −2750counts**、本番の巡航
200mm/s = 11003deg/s なら **−11003counts** になり、こちらは `output_limit` 5000 を
超えて**逆向きに飽和する**。プロファイルで消したはずの飽和が、速度を上げた途端に
別の理由で戻ってくる（**上限を上げても速度を上げれば追いつかれる** —— この対を崩した
ままで速くしようとすると必ずここへ落ちる）。

定常追従では実測速度 ≒ 参照速度なので、**参照速度へ `kd` と同じ係数を掛けて足せば
その制動をちょうど打ち消せる**。これが `velocity_ff = kd` の根拠。

- **`max_velocity` を動かしたら `velocity_ff` と `kd` を必ず見直す。** 片方だけ動かすと
  巡航中に D 項が出力を食い潰し、**飽和率だけが上がって速くならない**
- 決まった値は **`config/main_hand.yaml` の `pid.kd` と
  `config/main_hand_positions.yaml` の `motion.velocity_ff` の両方**へ書く
  （2 ファイルにまたがるので、片方だけ直しやすい）
- **`velocity_ff` は UI から見えず、実行中に変更もできない。** 起動ログ
  （`台形プロファイル: … velocity_ff=…`）が今どの値で動いているかを知る唯一の経路

**中止条件**

- **巡航区間で飽和率が上がる** —— まず `velocity_ff` を `kd` と揃えたか確認する。
  揃っていて出るなら、その速度は `output_limit` に対して過大
- **止まり際の行き過ぎが増える** —— 減速そのものは加速度で決まるので、これは
  PID の追従の問題（手順 4）
- **異音・共振。** 手順 2 と同じく、数字より先に出る

### 手順 4. その状態で PID を再調整する

**プロファイル導入で問題の性質が変わっている。**

| | プロファイル前 | プロファイル後 |
|---|---|---|
| PID が見る入力 | 全ストロークぶんのステップ | **速度制限された中間目標との追従誤差**（数百 μm） |
| PID の仕事 | 飽和したバンバン制御をなだめる | **追従誤差を最小化する** |
| `kp` の意味 | 大きいほど早く飽和する | そのまま追従の硬さ |
| `kd` の意味 | 飽和中は出力に現れない | **常に効く**（`velocity_ff` と対で見る） |

したがって **§3-1 の値（kp 32 / ki 10 / kd 1.0）は出発点であって答えではない。**
同じ数字でも意味が変わっている。手順 1〜3 で軌道が決まってから、**同じ振幅・同じ
プロファイルのまま**ゲインだけを振ること。

```bash
uv run python scripts/tune_y_axis.py ... --amplitude 15 --dwell 3.0 --kp 24,32,48
```

- **一度に振ってよいのは 8 つのつまみのうち 1 つだけ**（ツールが拒否する）
- **左右は必ず同じ値に保つ**（追従特性が違うと左右が押し合う）
- 追従誤差の見積もりは**摩擦ぶんの 0.284mm 程度**（静止摩擦 500counts / `kp` 32 /
  `scale` 55.0131 なので `output_limit` には依らない）で、本番の `output_limit` 5000 に
  対しては **90% が余裕として残る**計算。実測がこれと桁で違うなら、摩擦か `scale` の
  前提が崩れている

### 手順 5. 予告 —— 低速域のスティックスリップ

**これは観測ではなく予測である。出るかどうかは実機でしか分からない。**

この軸は静止摩擦が大きい（§3-1 の実測で重い側 500counts 相当）。プロファイルを
入れると**中間目標がゆっくり動く低速域ができる** —— 立ち上がりと止まり際である。
そこでは追従誤差が小さいので PID の出力も小さく、**電流が静止摩擦を超えられない**
可能性がある。症状は:

> **動かない → 誤差が溜まって急に動く → 行き過ぎる → また止まる** の繰り返し
> （スティックスリップ）。左右で静止摩擦が違うので、**片側だけに出れば
> `sync_tolerance` 超過として緊急停止に化ける**。

対抗手段は既に 2 つ入っている:

| 手段 | 現在値 | 効き方 |
|---|---|---|
| `ki` | **10**（`config/main_hand.yaml`） | **まさにこの役割。** 動かない側でだけ積分が育ち、静止摩擦を超えるまで電流を積む。§3-1 で「左右の非対称性に自動で追従する」として入れた項 |
| `velocity_ff` | **1.0**（`motion`） | 参照速度に比例した電流を**誤差が出る前に**乗せるので、止まっている時間そのものを短くする |

**それでも足りなければ静摩擦補償**（参照速度の符号に応じた定数電流を足す）を検討する。
**今回は入れていない。** 理由は 3 つ:

- **単位が counts** で、`motion` 節が持つ人間の単位（mm/s・mm/s²）と混ざる。
  同じ節に置くと「片方だけ人間の単位でない値」になり、`scale` を変えた日に
  黙って意味が変わる
- **必要性がまだ推測でしかない。** 上のとおり未観測であり、要らない機構を
  先に足すと「入っているのに効いているか分からない項」が増える
- **`ki` が部分的に代替している。** 静摩擦補償を足すなら `ki` との役割分担を
  決めてからでないと、両方が同じずれを埋めに行って押し合う

入れると決めたときは、**`ki` を下げることとセットで**評価すること。

### 4-1. サブハンドのリミットスイッチ極性の実測（2026-09-08）

**結論: `sensorActiveLow: true` が正しい。`config.h` の仮値がそのまま正解だった。**

サーボ基板 #1 のサブハンド 4 本は **NO（押すと閉じる）** で、センサスロットは
`INPUT_PULLUP` なので開放は必ず HIGH、押下で GND へ落ちて LOW になる。
`FEEDBACK` の bit4（`status_flag::kSensor`）は開放 `0x00` / 押下 `0x10`。
`rotate`（基板 #0 SV3）が `false` なのは、あちらが **NC** で平常時に GND へ閉じて
いるからで、**型が違うだけである。極性を他のスロットへ広げてはならない**という §4 の
戒めはそのまま生きている。

**4 本とも押下と開放の両方を `candump` で観測した。** 下端の 1 本だけは最初の測定で
バス上に押下が 1 通も出ず未確認のまま残っていたが、原因は極性ではなく後述の配線ずれで、
挿し直したあとに `0x34C` で `0x00` → `0x10` → `0x00` を 2 回とも観測した。

**踏んだ落とし穴: 配線が 1 スロットずれていた。** 測り始めた時点でサブの 4 本は
SV1〜SV4（`0x349`〜`0x34C`）ではなく **SV0〜SV3（`0x348`〜`0x34B`）** に刺さっていた。
`0x348` は `config/main_hand.yaml` の `y_axis_l_origin_sensor` の枠なので、
**サブハンドの前端を踏むとメインハンドの `y_axis` 左原点が反応する**状態だった。
症状は PC 側のどこにも出ない —— どちらも `sensors:` に登録済みで `FEEDBACK` は
正常に届くため、ヘルスは全部 `ok` のまま「押していないスイッチが反応する」だけになる。
配線は測定後にずらして直した。

**そのうえで、同じずれが直した後にも残っていた。** 直したはずの状態で 4 本を順に
押しても反応するのは 1 本だけで、1 本ずつ押しっぱなしにして静止値を読むと
**上端が `0x34A`（SV2）、下端が `0x34B`（SV3）** —— 依然として 1 スロット手前だった
（`0x34C` には何も刺さっていないので、下端を押してもどの ID も動かない）。
**手掛かりは「押した本数と反応した本数が合わない」ことだけである** —— 5 スロットとも
`FEEDBACK` は 100Hz で届き続けるので、PC 側のヘルスは全部 `ok` のままになる。
挿し直したあと、前端 → 後端 → 上端 → 下端の順に押して
`0x349` → `0x34A` → `0x34B` → `0x34C` が宣言順どおりに立つこと、および
**`0x348`（メインハンドの `y_axis` 左原点）が一度も反応しないこと**を確認した。

**極性は「押して両方の状態を見る」以外の方法では決まらない。** 静止状態の 1 点だけを
見ると、未配線（プルアップで HIGH）と NO の開放（同じく HIGH）が区別できず、
NC の平常時（LOW）と NO の押下（同じく LOW）も区別できない。実際にこの日、
静止値だけを見ていた段階では「6 本とも極性が逆」という誤った読みが立った。

手順（再現するとき）:

```bash
scripts/setup_can.sh
# 版番号: 6 が返ること (0x440-0x444 / 0x448-0x44C)
timeout 3 candump can_generic | grep -E "  4[0-9A-F][0-9A-F] "
# 極性: 1 本ずつ押して bit4 (0x10) の立ち下がり/立ち上がりを見る
candump -x -t a can_generic,348:7FF,349:7FF,34A:7FF,34B:7FF,34C:7FF
# 配線とスロットの対応: 1 本を押しっぱなしにして静止値を読むほうが確実。
# 変化監視は押下の一瞬を取り逃がすが、こちらは取り逃がさない（0x348 も必ず含めること
# —— ずれの行き先がメインハンドの y_axis 左原点だからである）
timeout 1 candump can_generic,348:7F8
```
