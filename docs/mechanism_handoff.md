# 機構引き継ぎチェックリスト — 機構が付いた日に埋める値

**機構担当と制御担当が一緒に上から潰すための表。** 制御側の数値は今のところ
「**機構が付いていない状態で誰かが起動しても壊れない**」ことだけを狙った安全側の
微小値で、**確定しているのは `y_axis` の `scale` ただ 1 つ**である。

この一覧が無いと、当日は「動かしてみて、おかしいところだけ直す」ことになる。
それでは**危険な向きに間違っている値ほど、壊してからでないと気付けない**。

> 手順（値をどう測るか・どう反映するか）は `docs/impl_plan.md` の
> 「Phase 5 > 機構完成後にやること」。**この表は「何を埋めるか」の棚卸し**で、
> 埋め方はあちらを見る。設計の理由は `CLAUDE.md`。

## 0. 最優先の 2 つ — **これだけは機構が付いた日のうちに**

他は「動かない・届かない」で済むが、この 2 つは**壊す向き**に間違っている。
どちらも「広すぎる」ことが危険で、広すぎても平常時は何の症状も出さない。

| 対象 | 現在値 | 場所 | 何が起きるか |
|---|---|---|---|
| `y_axis` の `homing.search_distance` | **22.0mm** | `config/main_hand_positions.yaml` | **広すぎると機構端まで押し込む。** 「当たるまで動かす」動作に対する唯一の無人の歯止めで、配線が抜けたセンサは「いつまでも当たらない」形でしか現れない。実測ストローク全長 + わずかな余裕へ詰める |
| サーボの `kProvisionalLimits` | **`{0.0, 30.0, 90.0}`**（0〜30deg / 90deg/s） | `firmware/servo/include/config.h` | **広すぎるとサーボが機構に当たったまま押し続けて焼損する。** 名前のとおり暫定値。実可動域が決まったら**すぐに**狭める。ファームを焼き直すので、当日の作業順で後回しにしないこと |

**`search_distance` を詰めるときは `manual` の `min`/`max` も同時に実測へ寄せる。**
片方だけ動かすと「原点に届かない」か「宣言した可動範囲の外まで押し込む」のどちらかになる。
現在値 22.0 は `manual` の全幅（`20.0 - (-2.0)`）に合わせてあり、可動範囲の上端から
始めても下端までは必ず届き、下端より先へは行かない。

## 3-1. `y_axis` の左右ずれを詰める

**2026-09-03 に実機で一通り詰めた。以下は実測に基づく。**

### この軸で起きていること（実測）

`y_axis` は左右 2 台の M3508 がラックを介して直結しているが、**左右で静止摩擦が
大きく違い、しかも遊びのせいで片方がもう片方を連れ回さない**。減速比 19:1 なので、
片側を数 mm 回した程度では反対側は動かない（連れ回すには大きく動かすことになり、
負荷の面で望ましくない）。実測値：

| kp | 出た指令 | 右 | 左 |
|---|---|---|---|
| 4〜8 | 110〜220 counts | 動かない | 動かない |
| 16 | 440 counts | **動く** | 動かない（1mm も） |
| 40 | 440〜554 counts | 動く | 動き出す境界 |
| 72 | 800 counts | 動く | 動くが行き過ぎ 434〜653% |

`kp=4` / 振幅 2mm では**右だけが目標に到達し、左が 1.970mm 取り残されて**
`sync_tolerance` 超過でラッチした。30 秒の波形でも、右が 1.019mm 動く間に
左は 0.046mm しか動いていない。

**したがって「片方が他方を連れ回す」前提は成り立たない。両方を能動的に、
揃えて動かす必要がある。** これが 3 項すべてに役割がある理由である。

### 決まった値と、それぞれの役割

| 値 | 役割 |
|---|---|
| `kp` **32** | 重い側（左）が静止摩擦を超えるのに要る。16 では左が動かない |
| `ki` **10** | **偏差が残り続ける側でだけ積分が育つ。** 右は先に動いて偏差が消えるので育たず、左だけ増える —— 左右の非対称性に自動で追従する |
| `kd` **1.0** | 行き過ぎを 50〜113% から 0〜5% へ抑える。**これが無いと `kp` を上げられない** |
| `integral_limit` **400** | `ki` を入れた以上必須。機構端で積分が育つと拘束が外れた瞬間に暴走する |
| `sync_kp` **8** | 移動中のずれ最大を半減（0.275mm → 0.130mm）。`kp` の 1/4 |
| `sync_limit` **500**（本番）| 押し合いの歯止め。現状のずれ量では届かないが、外してはならない |

改善の推移（移動中のずれ最大）：

```
kp=16 のみ              0.860mm
  + ki=10               0.411mm   左が動き出す
  + kd=1.0              0.220mm   行き過ぎが消える
  + kp=32               0.178mm
  + sync_kp=8           0.130mm   ← 現在値
```

### 測り方 —— 画面では読めない

**同期偏差は WS 配信（20Hz）の瞬時値としてしか出ない。** 移動は数百 ms で終わるので、
画面では「移動中に最大どれだけ開いたか」を追えない。**補正の効果は移動中のピークに
しか現れない**ので、必ず次のどちらかで測ること。

```bash
# 送信しない観測ツール。main.py と同時に走らせてよい。
# 無励磁のまま手で機構を動かせば、可動範囲の実測にも使える
uv run python scripts/sync_probe.py --csv /tmp/run.csv

# ステップ応答を取り、ゲインだけを変えた同一条件の試行を並べて比べる（機体が動く）
uv run python scripts/tune_y_axis.py --amplitude 1.5 --kp 24,32 --ki 10 --kd 1.0 --sync-kp 8
```

`tune_y_axis.py` はスイープできるパラメータを 1 つに限る（2 つ同時に振ると
どちらが効いたのか読めない結果が並ぶ）。試行ごとに制御ループを作り直すので、
前の試行の積分やラッチは持ち越さない。

### まだやっていないこと

**検証したのは振幅 1.5mm まで、`output_limit` 800 での話である。**

- **実運用のストローク（5〜15mm）では未検証。** 本番の `output_limit` 2000 では
  偏差 1.14mm（= 2000/32/55.0131）で飽和するので、大きな移動は最初から飽和した
  まま加速することになる。**可動範囲を実測したら、その振幅で必ず取り直すこと**
- **可動範囲そのものが未実測。** `config/main_hand_positions.yaml` の `manual`
  （−2.0〜20.0mm）も `positions`（0〜15mm）も仮値のまま。実測は
  `scripts/sync_probe.py` を無励磁で走らせ、手で端から端まで動かせば読める
  （送信しないので安全）
- **定常偏差が 0.12〜0.19mm 残る。** 到達許容差 1.0mm に対しては十分小さいが、
  詰めるなら `ki` か `output_limit` を上げる

## 5. 埋め終わったら

1. `uv run pytest` — 値だけを変えたぶんはテストの追随不要。ただし**軸名・位置名を
   増減した / `robots/*.py` のステップ名やラベルを変えた場合は追随が要る**
   （`docs/impl_plan.md` の「Phase 5 > 機構完成後にやること」の表を参照）
2. `scripts/setup_can.sh --strict` が全バス起動で通ること
3. **`--dry-run` ではなく実機で動作確認シーケンスを 1 回通す。**
   ホーミングを含む全アクチュエータが順に動く
4. `config/checklist.yaml` の指差喚呼を上から 1 回読み上げる。
   特に `sub_lift_holds`（自重落下）と `estop_functional`（非常停止が効くこと）
