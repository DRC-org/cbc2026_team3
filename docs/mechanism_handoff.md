# 機構引き継ぎチェックリスト — 機構が付いた日に埋める値

**機構担当と制御担当が一緒に上から潰すための表。** 制御側の数値は今のところ
「**機構が付いていない状態で誰かが起動しても壊れない**」ことだけを狙った安全側の
微小値で、**確定しているのは `y_axis` の `scale` ただ 1 つ**である。

この一覧が無いと、当日は「動かしてみて、おかしいところだけ直す」ことになる。
それでは**危険な向きに間違っている値ほど、壊してからでないと気付けない**。

> 手順（値をどう測るか・どう反映するか）は `docs/impl_plan.md` の
> 「Phase 5 > 機構完成後にやること」。**この表は「何を埋めるか」の棚卸し**で、
> 埋め方はあちらを見る。設計の理由は `CLAUDE.md`。

---

## 0. 最優先の 2 つ — **これだけは機構が付いた日のうちに**

他は「動かない・届かない」で済むが、この 2 つは**壊す向き**に間違っている。
どちらも「広すぎる」ことが危険で、広すぎても平常時は何の症状も出さない。

| 対象 | 現在値 | 場所 | 何が起きるか |
|---|---|---|---|
| `y_axis` の `homing.search_distance` | **22.0mm** | `config/main_hand_positions.yaml` | **広すぎると機構端まで押し込む。** 「当たるまで動かす」動作に対する唯一の無人の歯止めで、配線が抜けたセンサは「いつまでも当たらない」形でしか現れない。実測ストローク全長 + わずかな余裕へ詰める |
| サーボの `kProvisionalLimits` | **`{0.0, 30.0, 90.0}`**（0〜30deg / 90deg/s） | `firmware/servo/include/config.h` | **広すぎるとサーボが機構に当たったまま押し続けて焼損する。** 名前のとおり暫定値。実可動域が決まったら**すぐに**狭める。ファームを焼き直すので、当日の作業順で後回しにしないこと |

**`search_distance` を詰めるときは `manual` の `min`/`max` も同時に実測へ寄せる。**
片方だけ動かすと「原点に届かない」か「宣言した可動範囲の外まで押し込む」のどちらかになる。
現在値 22.0 は `manual` の全幅（`20.0 - (-2.0)`）に合わせてあり、可動範囲の上端から
始めても下端までは必ず届き、下端より先へは行かない。

## 3-1. `y_axis` の左右ずれを詰める

**2026-09-03 に実機で一通り詰めた。以下は実測に基づく。**

### この軸で起きていること（実測）

`y_axis` は左右 2 台の M3508 がラックを介して直結しているが、**左右で静止摩擦が
大きく違い、しかも遊びのせいで片方がもう片方を連れ回さない**。減速比 19:1 なので、
片側を数 mm 回した程度では反対側は動かない（連れ回すには大きく動かすことになり、
負荷の面で望ましくない）。実測値：

| kp | 出た指令 | 右 | 左 |
|---|---|---|---|
| 4〜8 | 110〜220 counts | 動かない | 動かない |
| 16 | 440 counts | **動く** | 動かない（1mm も） |
| 40 | 440〜554 counts | 動く | 動き出す境界 |
| 72 | 800 counts | 動く | 動くが行き過ぎ 434〜653% |

`kp=4` / 振幅 2mm では**右だけが目標に到達し、左が 1.970mm 取り残されて**
`sync_tolerance` 超過でラッチした。30 秒の波形でも、右が 1.019mm 動く間に
左は 0.046mm しか動いていない。

**したがって「片方が他方を連れ回す」前提は成り立たない。両方を能動的に、
揃えて動かす必要がある。** これが 3 項すべてに役割がある理由である。

### 決まった値と、それぞれの役割

| 値 | 役割 |
|---|---|
| `kp` **32** | 重い側（左）が静止摩擦を超えるのに要る。16 では左が動かない |
| `ki` **10** | **偏差が残り続ける側でだけ積分が育つ。** 右は先に動いて偏差が消えるので育たず、左だけ増える —— 左右の非対称性に自動で追従する |
| `kd` **1.0** | 行き過ぎを 50〜113% から 0〜5% へ抑える。**これが無いと `kp` を上げられない** |
| `integral_limit` **400** | `ki` を入れた以上必須。機構端で積分が育つと拘束が外れた瞬間に暴走する |
| `sync_kp` **8** | 移動中のずれ最大を半減（0.275mm → 0.130mm）。`kp` の 1/4 |
| `sync_limit` **500**（本番）| 押し合いの歯止め。現状のずれ量では届かないが、外してはならない |

改善の推移（移動中のずれ最大）：

```
kp=16 のみ              0.860mm
  + ki=10               0.411mm   左が動き出す
  + kd=1.0              0.220mm   行き過ぎが消える
  + kp=32               0.178mm
  + sync_kp=8           0.130mm   ← 現在値
```

### 測り方 —— 画面では読めない

**同期偏差は WS 配信（20Hz）の瞬時値としてしか出ない。** 移動は数百 ms で終わるので、
画面では「移動中に最大どれだけ開いたか」を追えない。**補正の効果は移動中のピークに
しか現れない**ので、必ず次のどちらかで測ること。

```bash
# 送信しない観測ツール。main.py と同時に走らせてよい。
# 無励磁のまま手で機構を動かせば、可動範囲の実測にも使える
uv run python scripts/sync_probe.py --csv /tmp/run.csv

# ステップ応答を取り、条件だけを変えた同一条件の試行を並べて比べる（機体が動く）
uv run python scripts/tune_y_axis.py --amplitude 1.5 --kp 24,32 --ki 10 --kd 1.0 --sync-kp 8
```

`tune_y_axis.py` が振れるつまみは **7 つ**（`--kp` / `--ki` / `--kd` / `--sync-kp` /
`--max-velocity` / `--max-acceleration` / `--velocity-ff`）で、どれもカンマ区切りで
スイープできる。**ただし同時にスイープしてよいのは 7 つのうち 1 つだけ**（2 つ同時に
振ると、組み合わせの数だけ機体が動くうえ、どちらが効いたのか読めない結果が並ぶ）。
プロファイルのつまみも同じ 1 本の制限に入る —— ゲインと軌道を同時に振ったら、なおさら
読めない。試行ごとに制御ループとプロファイルを作り直すので、前の試行の積分・ラッチ・
軌道は持ち越さない。

**プロファイルの既定は config が持つ。** 位置定数に `axes.<軸>.motion` が書いてあれば
何も渡さなくてもそれが使われる（**本番とまったく同じ制御で測れる**）。
`--max-velocity` と `--max-acceleration` は**対でしか渡せず**、`--velocity-ff` だけを
渡すとプロファイルが無い＝参照速度が存在しないので拒否される。

**まず飽和率を読むこと。** 出力が上限に張り付いている間は**ゲインを変えても応答が
変わらない**ので、飽和を見ずに `kp` を振ると「上げても下げても同じ」という観察から
抜け出せない。飽和率は比較表の右端に必ず出る（動かなかった試行でも出る）。
プロファイルを有効にしているなら、**飽和はプロファイルが機構の能力を超えている合図**
でもある —— そのときはゲインではなく `max_acceleration` / `max_velocity` を下げる。

**`--dwell` はプロファイルの移動時間より長く取る。** 記録窓が移動の途中で閉じると、
行き過ぎも整定も**まだ起きていない**ものを測ることになり、指標が一律に良い方へ嘘をつく
（しかも「速いプロファイルほど数字が良い」という逆向きの結論が出る）。短すぎる
`--dwell` はツールが起動時に拒否して必要な値を提示する。

### まだやっていないこと

**検証したのは振幅 1.5mm まで、`output_limit` 800 での話である。**

- **実運用のストローク（5〜15mm）では未検証。** 本番の `output_limit` 2000 では
  偏差 1.14mm（= 2000/32/55.0131）で飽和するので、最終目標をそのまま入れると
  大きな移動は最初から飽和したまま加速することになる。**これを塞ぐために
  `axes.y_axis.motion`（台形速度プロファイル）を入れたが、その値も机上の計算値で
  実機未検証。** 可動範囲を実測したら、§3-2 の順で必ず取り直すこと
- **PID は「飽和したバンバン制御をなだめる」条件で詰めた値のまま。** プロファイルを
  入れると PID の仕事は**追従誤差の最小化**に変わるので、同じ数字でも意味が違う
- **可動範囲そのものが未実測。** `config/main_hand_positions.yaml` の `manual`
  （−2.0〜20.0mm）も `positions`（0〜15mm）も仮値のまま。実測は
  `scripts/sync_probe.py` を無励磁で走らせ、手で端から端まで動かせば読める
  （送信しないので安全）
- **定常偏差が 0.12〜0.19mm 残る。** 到達許容差 1.0mm に対しては十分小さいが、
  詰めるなら `ki` か `output_limit` を上げる

## 3-2. `y_axis` を実運用ストロークで速くする —— 次に実機へ触る人の手順

**この節はまだ誰も実機で試していない。** 台形速度プロファイル
（`axes.y_axis.motion`）を入れたところまでが済んでおり、入っている値は
**すべて机上の計算値**である。以下は「その値から実機で上げていく」手順で、
**上から順に、1 段ずつ**やること。順番を飛ばすと、どれが効いたのか読めない結果だけが残る。

> **なぜプロファイルが要るのかは `docs/impl_plan.md` の「台形速度プロファイル」節。**
> 要点だけ: 偏差 1.14mm（= 2000/32/55.0131）で P 項が飽和し、飽和中はフル電流の
> 定加速になるので、**止まりきれるのは移動距離 2.3mm まで**。§3-1 で詰めた振幅 1.5mm は
> その内側だった。**`kd` を上げても直らない**（飽和中は D 項も出力に現れない）。

### 準備 —— 測る前に揃えるもの

1. **可動範囲を実測する。** 無励磁のまま手で端から端まで動かす。送信しないので安全。

   ```bash
   uv run python scripts/sync_probe.py --csv /tmp/stroke.csv
   ```

2. **実測値を `config/main_hand_positions.yaml` の `manual` と `positions` へ反映する。**
   `axes.y_axis.homing.search_distance`（現在 22.0mm）も**同時に**詰める
   —— 片方だけ動かすと「原点に届かない」か「宣言した可動範囲の外まで押し込む」の
   どちらかになる（§0）。

3. **チューニングは `config/bench/y_axis_tuning/` の robot config で回し、位置定数だけを
   本番へ差し替える。**

   ```bash
   uv run python scripts/tune_y_axis.py \
       --config config/bench/y_axis_tuning/main_hand.yaml \
       --system config/bench/y_axis_tuning/system.yaml \
       --positions config/main_hand_positions.yaml \
       --amplitude 15 --dwell 3.0
   ```

   - **`--config` に本番の `config/main_hand.yaml` を渡してはならない。** このツールは
     モータ構成に現れるバスから 1 本を選んで開く実装で、本番 config は 3 本
     （`m3508_bus` / `edulite_bus` / `generic_bus`）を持つため**どれが選ばれるか実行ごとに
     変わる**。ベンチ側の robot config は `m3508_bus` の 1 本だけなので迷いようがない。
   - `--positions` に本番の位置定数を渡すのは、**`motion` と広い `manual` がそちらにしか
     無い**ため。ベンチ側の位置定数（`manual` ±2mm）では実運用振幅がそもそも通らない。
   - **ただしベンチ側の `output_limit` は 800、本番は 2000。** 飽和の境界が
     0.45mm と 1.14mm で 2.5 倍違うので、**下の手順 1 に入る前にベンチ側の
     `output_limit` を本番と同じ 2000 へ上げること**（上げないと、ここで見た応答が
     本番で再現しない）。上げた時点で機体が出せる力も 2.5 倍になるので、
     **可動範囲の実測と `manual` の反映が済んでいることが前提**。
   - **原点は「起動した瞬間の姿勢」である。** 起動前に軸をストロークの中ほどへ
     寄せておくこと（ベンチ構成にはリミットスイッチが無い）。

4. **人を可動範囲から出す。** 以降のどの段でも機体が動く。

### 手順 1. 現状確認 —— 今の値のまま実運用振幅を 1 往復

```bash
uv run python scripts/tune_y_axis.py \
    --config config/bench/y_axis_tuning/main_hand.yaml \
    --system config/bench/y_axis_tuning/system.yaml \
    --positions config/main_hand_positions.yaml \
    --amplitude 15 --dwell 3.0 --cycles 1
```

**引数でプロファイルを指定しない。** config の `motion`（v 50 / a 300 / vff 1.0）が
そのまま使われ、**本番とまったく同じ制御**になる。

見るのは 3 つ:

| 見るもの | 期待 | 外れていたら |
|---|---|---|
| **飽和率** | **0% に近いこと**（比較表の右端） | ここが本題。0 でないなら、この段を通過してはならない（下の中止条件） |
| **行き過ぎ** | 0〜数 % | 大きいなら `max_acceleration` が機構に対して過大。上げるのではなく**下げる**方向へ |
| **移動中のずれ最大** | §3-1 の 0.130mm と同じ桁 | 桁が違うなら §3-1 の `sync_kp` を実運用振幅で取り直す（プロファイル導入前の値である） |

**中止条件（この段で止めて、先へ進まない）**

- **飽和率が 10% を超える** —— プロファイルが機構の能力を超えている。`max_acceleration`
  を半分にして測り直す。ゲインを触ってはならない（飽和中は何を変えても応答が変わらない）
- **`sync_tolerance` 超過で緊急停止した** —— 速度・加速度ではなく左右の追従差の問題。
  §3-1 に戻って `sync_kp` を実運用振幅で取り直す
- **`timeout_s` 到達で失敗する** —— 起動時の検証（`_check_motion_timeout`）を通っている
  以上、プロファイルの所要時間の問題ではない。機構が引っかかっているか、片側が
  動いていない。**動かして直す段ではない**

### 手順 2. `max_acceleration` を上げる

```bash
uv run python scripts/tune_y_axis.py ... --amplitude 15 --dwell 3.0 \
    --max-acceleration 300,600,1000
```

**この軸は摩擦支配である。** 重い側の静止摩擦だけで 500counts 相当あり、質量を
加速するのに要る力はそれに比べて桁違いに小さい。したがって**制御側から見た余裕は
大きい**。効く制約は制御ではなく:

- **機構強度**（ラック・ピニオン・取り付け）
- **ワーク保持力**（グリッパ・吸着が加速度に負けて滑る / 落ちる）

**中止条件**

- **飽和率が上がり始めたら、その 1 つ手前を採る。** 飽和は「プロファイルが機構の
  能力を超えた」合図である
- **打音・振動が出たら止める。** 数字より先に耳と手で分かる。機構強度の限界は
  比較表には出ない
- **ワークが滑る・落ちる。** 保持力の限界。ここは制御では埋められないので、
  **加速度を下げる**のが正しい対処
- 行き過ぎが増える方向へ動いたら、それは加速度ではなく PID の問題（手順 4 へ）

### 手順 3. `max_velocity` を上げる —— **`velocity_ff` と `kd` は必ずセット**

```bash
# まず速度だけ
uv run python scripts/tune_y_axis.py ... --amplitude 15 --dwell 3.0 \
    --max-velocity 50,80
# 次に、その速度で velocity_ff を振る
uv run python scripts/tune_y_axis.py ... --amplitude 15 --dwell 3.0 \
    --max-velocity 80 --velocity-ff 0,1.0,1.6
```

**`kd` の単位は counts/(deg/s) なので、巡航速度がそのまま制動として出力に乗る。**
`kd`=1.0 で 50mm/s = 2750deg/s を出すと、**D 項だけで −2750counts** になり、
`output_limit` 2000 を超えて**逆向きに飽和する**。プロファイルで消したはずの飽和が、
速度を上げた途端に別の理由で戻ってくる。

定常追従では実測速度 ≒ 参照速度なので、**参照速度へ `kd` と同じ係数を掛けて足せば
その制動をちょうど打ち消せる**。これが `velocity_ff = kd` の根拠。

- **`max_velocity` を動かしたら `velocity_ff` と `kd` を必ず見直す。** 片方だけ動かすと
  巡航中に D 項が出力を食い潰し、**飽和率だけが上がって速くならない**
- 決まった値は **`config/main_hand.yaml` の `pid.kd` と
  `config/main_hand_positions.yaml` の `motion.velocity_ff` の両方**へ書く
  （2 ファイルにまたがるので、片方だけ直しやすい）
- **`velocity_ff` は UI から見えず、実行中に変更もできない。** 起動ログ
  （`台形プロファイル: … velocity_ff=…`）が今どの値で動いているかを知る唯一の経路

**中止条件**

- **巡航区間で飽和率が上がる** —— まず `velocity_ff` を `kd` と揃えたか確認する。
  揃っていて出るなら、その速度は `output_limit` に対して過大
- **止まり際の行き過ぎが増える** —— 減速そのものは加速度で決まるので、これは
  PID の追従の問題（手順 4）
- **異音・共振。** 手順 2 と同じく、数字より先に出る

### 手順 4. その状態で PID を再調整する

**プロファイル導入で問題の性質が変わっている。**

| | プロファイル前 | プロファイル後 |
|---|---|---|
| PID が見る入力 | 全ストロークぶんのステップ | **速度制限された中間目標との追従誤差**（数百 μm） |
| PID の仕事 | 飽和したバンバン制御をなだめる | **追従誤差を最小化する** |
| `kp` の意味 | 大きいほど早く飽和する | そのまま追従の硬さ |
| `kd` の意味 | 飽和中は出力に現れない | **常に効く**（`velocity_ff` と対で見る） |

したがって **§3-1 の値（kp 32 / ki 10 / kd 1.0）は出発点であって答えではない。**
同じ数字でも意味が変わっている。手順 1〜3 で軌道が決まってから、**同じ振幅・同じ
プロファイルのまま**ゲインだけを振ること。

```bash
uv run python scripts/tune_y_axis.py ... --amplitude 15 --dwell 3.0 --kp 24,32,48
```

- **一度に振ってよいのは 7 つのつまみのうち 1 つだけ**（ツールが拒否する）
- **左右は必ず同じ値に保つ**（追従特性が違うと左右が押し合う）
- 追従誤差の見積もりは**摩擦ぶんの 0.284mm 程度**、`output_limit` の 75% が余裕として
  残る計算。実測がこれと桁で違うなら、摩擦か `scale` の前提が崩れている

### 手順 5. 予告 —— 低速域のスティックスリップ

**これは観測ではなく予測である。出るかどうかは実機でしか分からない。**

この軸は静止摩擦が大きい（§3-1 の実測で重い側 500counts 相当）。プロファイルを
入れると**中間目標がゆっくり動く低速域ができる** —— 立ち上がりと止まり際である。
そこでは追従誤差が小さいので PID の出力も小さく、**電流が静止摩擦を超えられない**
可能性がある。症状は:

> **動かない → 誤差が溜まって急に動く → 行き過ぎる → また止まる** の繰り返し
> （スティックスリップ）。左右で静止摩擦が違うので、**片側だけに出れば
> `sync_tolerance` 超過として緊急停止に化ける**。

対抗手段は既に 2 つ入っている:

| 手段 | 現在値 | 効き方 |
|---|---|---|
| `ki` | **10**（`config/main_hand.yaml`） | **まさにこの役割。** 動かない側でだけ積分が育ち、静止摩擦を超えるまで電流を積む。§3-1 で「左右の非対称性に自動で追従する」として入れた項 |
| `velocity_ff` | **1.0**（`motion`） | 参照速度に比例した電流を**誤差が出る前に**乗せるので、止まっている時間そのものを短くする |

**それでも足りなければ静摩擦補償**（参照速度の符号に応じた定数電流を足す）を検討する。
**今回は入れていない。** 理由は 3 つ:

- **単位が counts** で、`motion` 節が持つ人間の単位（mm/s・mm/s²）と混ざる。
  同じ節に置くと「片方だけ人間の単位でない値」になり、`scale` を変えた日に
  黙って意味が変わる
- **必要性がまだ推測でしかない。** 上のとおり未観測であり、要らない機構を
  先に足すと「入っているのに効いているか分からない項」が増える
- **`ki` が部分的に代替している。** 静摩擦補償を足すなら `ki` との役割分担を
  決めてからでないと、両方が同じずれを埋めに行って押し合う

入れると決めたときは、**`ki` を下げることとセットで**評価すること。
