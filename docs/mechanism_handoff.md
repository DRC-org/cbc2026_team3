# 機構引き継ぎチェックリスト — 機構が付いた日に埋める値

**機構担当と制御担当が一緒に上から潰すための表。** 制御側の数値は今のところ
「**機構が付いていない状態で誰かが起動しても壊れない**」ことだけを狙った安全側の
微小値で、**確定しているのは `y_axis` の `scale` ただ 1 つ**である。

この一覧が無いと、当日は「動かしてみて、おかしいところだけ直す」ことになる。
それでは**危険な向きに間違っている値ほど、壊してからでないと気付けない**。

> 手順（値をどう測るか・どう反映するか）は `docs/impl_plan.md` の
> 「Phase 5 > 機構完成後にやること」。**この表は「何を埋めるか」の棚卸し**で、
> 埋め方はあちらを見る。設計の理由は `CLAUDE.md`。

---

## 0. 最優先の 2 つ — **これだけは機構が付いた日のうちに**

他は「動かない・届かない」で済むが、この 2 つは**壊す向き**に間違っている。
どちらも「広すぎる」ことが危険で、広すぎても平常時は何の症状も出さない。

| 対象 | 現在値 | 場所 | 何が起きるか |
|---|---|---|---|
| `y_axis` の `homing.search_distance` | **22.0mm** | `config/main_hand_positions.yaml` | **広すぎると機構端まで押し込む。** 「当たるまで動かす」動作に対する唯一の無人の歯止めで、配線が抜けたセンサは「いつまでも当たらない」形でしか現れない。実測ストローク全長 + わずかな余裕へ詰める |
| サーボの `kProvisionalLimits` | **`{0.0, 30.0, 90.0}`**（0〜30deg / 90deg/s） | `firmware/servo/include/config.h` | **広すぎるとサーボが機構に当たったまま押し続けて焼損する。** 名前のとおり暫定値。実可動域が決まったら**すぐに**狭める。ファームを焼き直すので、当日の作業順で後回しにしないこと |

**`search_distance` を詰めるときは `manual` の `min`/`max` も同時に実測へ寄せる。**
片方だけ動かすと「原点に届かない」か「宣言した可動範囲の外まで押し込む」のどちらかになる。
**この対応関係は今は崩れている。** `axes.y_axis.manual` は実ストローク
（0.0〜650.0mm）へ更新済みだが、`search_distance`（22.0mm）は仮値時代の `manual` 全幅
（`20.0 - (-2.0)` = 22.0）に合わせた値のまま取り残されている。ホーミングの起点次第では
この距離でリミットスイッチへ届かない可能性がある。**次に実機で確認する人が
`search_distance` を実測ストロークへ詰めること。**

## 3-1. `y_axis` の左右ずれを詰める

**2026-09-03 に実機で一通り詰めた。以下は実測に基づく。**

### この軸で起きていること（実測）

`y_axis` は左右 2 台の M3508 がラックを介して直結しているが、**左右で静止摩擦が
大きく違い、しかも遊びのせいで片方がもう片方を連れ回さない**。減速比 19:1 なので、
片側を数 mm 回した程度では反対側は動かない（連れ回すには大きく動かすことになり、
負荷の面で望ましくない）。実測値：

| kp | 出た指令 | 右 | 左 |
|---|---|---|---|
| 4〜8 | 110〜220 counts | 動かない | 動かない |
| 16 | 440 counts | **動く** | 動かない（1mm も） |
| 40 | 440〜554 counts | 動く | 動き出す境界 |
| 72 | 800 counts | 動く | 動くが行き過ぎ 434〜653% |

`kp=4` / 振幅 2mm では**右だけが目標に到達し、左が 1.970mm 取り残されて**
`sync_tolerance` 超過でラッチした。30 秒の波形でも、右が 1.019mm 動く間に
左は 0.046mm しか動いていない。

**したがって「片方が他方を連れ回す」前提は成り立たない。両方を能動的に、
揃えて動かす必要がある。** これが 3 項すべてに役割がある理由である。

### 決まった値と、それぞれの役割

| 値 | 役割 |
|---|---|
| `kp` **32** | 重い側（左）が静止摩擦を超えるのに要る。16 では左が動かない |
| `ki` **10** | **偏差が残り続ける側でだけ積分が育つ。** 右は先に動いて偏差が消えるので育たず、左だけ増える —— 左右の非対称性に自動で追従する |
| `kd` **1.0** | 行き過ぎを 50〜113% から 0〜5% へ抑える。**これが無いと `kp` を上げられない** |
| `integral_limit` **400** | `ki` を入れた以上必須。機構端で積分が育つと拘束が外れた瞬間に暴走する |
| `sync_kp` **8** | 移動中のずれ最大を半減（0.275mm → 0.130mm）。`kp` の 1/4 |
| `sync_limit` **500**（本番）| 押し合いの歯止め。現状のずれ量では届かないが、外してはならない |

改善の推移（移動中のずれ最大）：

```
kp=16 のみ              0.860mm
  + ki=10               0.411mm   左が動き出す
  + kd=1.0              0.220mm   行き過ぎが消える
  + kp=32               0.178mm
  + sync_kp=8           0.130mm   ← 現在値
```

### 測り方 —— 画面では読めない

**同期偏差は WS 配信（20Hz）の瞬時値としてしか出ない。** 移動は数百 ms で終わるので、
画面では「移動中に最大どれだけ開いたか」を追えない。**補正の効果は移動中のピークに
しか現れない**ので、必ず次のどちらかで測ること。

```bash
# 送信しない観測ツール。main.py と同時に走らせてよい。
# 無励磁のまま手で機構を動かせば、可動範囲の実測にも使える
uv run python scripts/sync_probe.py --csv /tmp/run.csv

# ステップ応答を取り、条件だけを変えた同一条件の試行を並べて比べる（機体が動く）
uv run python scripts/tune_y_axis.py --amplitude 1.5 --kp 24,32 --ki 10 --kd 1.0 --sync-kp 8
```

`tune_y_axis.py` が振れるつまみは **8 つ**（`--kp` / `--ki` / `--kd` / `--sync-kp` /
`--output-limit` / `--max-velocity` / `--max-acceleration` / `--velocity-ff`）で、
どれもカンマ区切りでスイープできる。**ただし同時にスイープしてよいのは 8 つのうち 1 つだけ**（2 つ同時に
振ると、組み合わせの数だけ機体が動くうえ、どちらが効いたのか読めない結果が並ぶ）。
プロファイルのつまみも同じ 1 本の制限に入る —— ゲインと軌道を同時に振ったら、なおさら
読めない。試行ごとに制御ループとプロファイルを作り直すので、前の試行の積分・ラッチ・
軌道は持ち越さない。

**プロファイルの既定は config が持つ。** 位置定数に `axes.<軸>.motion` が書いてあれば
何も渡さなくてもそれが使われる（**本番とまったく同じ制御で測れる**）。
`--max-velocity` と `--max-acceleration` は**対でしか渡せず**、`--velocity-ff` だけを
渡すとプロファイルが無い＝参照速度が存在しないので拒否される。

**まず飽和率を読むこと。** 出力が上限に張り付いている間は**ゲインを変えても応答が
変わらない**ので、飽和を見ずに `kp` を振ると「上げても下げても同じ」という観察から
抜け出せない。飽和率は比較表の右端に必ず出る（動かなかった試行でも出る）。
プロファイルを有効にしているなら、**飽和はプロファイルが機構の能力を超えている合図**
でもある —— そのときはゲインではなく `max_acceleration` / `max_velocity` を下げる。

**`--dwell` はプロファイルの移動時間より長く取る。** 記録窓が移動の途中で閉じると、
行き過ぎも整定も**まだ起きていない**ものを測ることになり、指標が一律に良い方へ嘘をつく
（しかも「速いプロファイルほど数字が良い」という逆向きの結論が出る）。短すぎる
`--dwell` はツールが起動時に拒否して必要な値を提示する。

### まだやっていないこと

**検証したのは振幅 1.5mm まで、`output_limit` 800 での話である。**

- **実運用のストローク（5〜15mm）では未検証。** 本番の `output_limit` 2000 では
  偏差 1.14mm（= 2000/32/55.0131）で飽和するので、最終目標をそのまま入れると
  大きな移動は最初から飽和したまま加速することになる。**これを塞ぐために
  `axes.y_axis.motion`（台形速度プロファイル）を入れたが、その値も机上の計算値で
  実機未検証。** 可動範囲を実測したら、§3-2 の順で必ず取り直すこと
- **PID は「飽和したバンバン制御をなだめる」条件で詰めた値のまま。** プロファイルを
  入れると PID の仕事は**追従誤差の最小化**に変わるので、同じ数字でも意味が違う
- ~~**可動範囲そのものが未実測。** `config/main_hand_positions.yaml` の `manual`
  （−2.0〜20.0mm）も `positions`（0〜15mm）も仮値のまま。実測は
  `scripts/sync_probe.py` を無励磁で走らせ、手で端から端まで動かせば読める
  （送信しないので安全）~~ → **解消。** `manual` は 0.0〜650.0mm、`positions` は
  実測値（home 0.0 / work_1 120.0 / work_2 320.0 / work_3 520.0 / work_shared
  650.0mm）へ更新済み（§1）
- **定常偏差が 0.12〜0.19mm 残る。** 到達許容差 1.0mm に対しては十分小さいが、
  詰めるなら `ki` か `output_limit` を上げる

## 3-2. `y_axis` を実運用ストロークで速くする —— 次に実機へ触る人の手順

**この節は機構を付けた状態ではまだ誰も試していない。** 台形速度プロファイル
（`axes.y_axis.motion`）を入れたところまでが済んでおり、`config/main_hand*.yaml`
に入っている値は**すべて机上の計算値**である。以下は「その値から実機で上げていく」手順で、
**上から順に、1 段ずつ**やること。順番を飛ばすと、どれが効いたのか読めない結果だけが残る。

**ただし、この手順を机上ベンチ（直結していない空回し）で一度なぞった結果が §3-3 にある。**
そこで決まった値は本番へは持ってきていない（負荷が違う）が、**プロファイルの有無で
左右ずれが 6 倍違うこと**と**加速度を上げすぎると遅くなること**は先に読んでおくとよい。

> **なぜプロファイルが要るのかは `docs/impl_plan.md` の「台形速度プロファイル」節。**
> 要点だけ: 偏差 1.14mm（= 2000/32/55.0131）で P 項が飽和し、飽和中はフル電流の
> 定加速になるので、**止まりきれるのは移動距離 2.3mm まで**。§3-1 で詰めた振幅 1.5mm は
> その内側だった。**`kd` を上げても直らない**（飽和中は D 項も出力に現れない）。

### 準備 —— 測る前に揃えるもの

1. **可動範囲を実測する。** 無励磁のまま手で端から端まで動かす。送信しないので安全。

   ```bash
   uv run python scripts/sync_probe.py --csv /tmp/stroke.csv
   ```

2. **実測値を `config/main_hand_positions.yaml` の `manual` と `positions` へ反映する。**
   `axes.y_axis.homing.search_distance`（現在 22.0mm）も**同時に**詰める
   —— 片方だけ動かすと「原点に届かない」か「宣言した可動範囲の外まで押し込む」の
   どちらかになる（§0）。

3. **チューニングは `config/bench/y_axis_tuning/` の robot config で回し、位置定数だけを
   本番へ差し替える。**

   ```bash
   uv run python scripts/tune_y_axis.py \
       --config config/bench/y_axis_tuning/main_hand.yaml \
       --system config/bench/y_axis_tuning/system.yaml \
       --positions config/main_hand_positions.yaml \
   ```

   - **`--config` に本番の `config/main_hand.yaml` を渡してもよい。** このツールが開くのは
     `--axis` で指定した軸のモータが載っているバス 1 本だけなので、3 本
     （`m3508_bus` / `edulite_bus` / `generic_bus`）を持つ本番 config でも `m3508_bus` に
     決まる。ただし**本番 config を渡すと `output_limit` も本番の 2000 になる**ので、
     下の「ベンチ側は 800」の断りはベンチ側 robot config を使う場合の話になる。
   - `--positions` に本番の位置定数を渡すのは、**`motion` と広い `manual` がそちらにしか
     無い**ため。ベンチ側の位置定数（`manual` ±2mm）では実運用振幅がそもそも通らない。
   - **ただしベンチ側の `output_limit` は 800、本番は 2000。** 飽和の境界が
     0.45mm と 1.14mm で 2.5 倍違うので、**下の手順 1 に入る前にベンチ側の
     `output_limit` を本番と同じ 2000 へ上げること**（上げないと、ここで見た応答が
     本番で再現しない）。上げた時点で機体が出せる力も 2.5 倍になるので、
     **可動範囲の実測と `manual` の反映が済んでいることが前提**。
   - **原点は「起動した瞬間の姿勢」である。** 起動前に軸をストロークの中ほどへ
     寄せておくこと（ベンチ構成にはリミットスイッチが無い）。

4. **人を可動範囲から出す。** 以降のどの段でも機体が動く。

### 手順 1. 現状確認 —— 今の値のまま実運用振幅を 1 往復

```bash
uv run python scripts/tune_y_axis.py \
    --config config/bench/y_axis_tuning/main_hand.yaml \
    --system config/bench/y_axis_tuning/system.yaml \
    --positions config/main_hand_positions.yaml \
    --amplitude 15 --dwell 3.0 --cycles 1
```

**引数でプロファイルを指定しない。** config の `motion`（v 50 / a 300 / vff 1.0）が
そのまま使われ、**本番とまったく同じ制御**になる。

見るのは 3 つ:

| 見るもの | 期待 | 外れていたら |
|---|---|---|
| **飽和率** | **0% に近いこと**（比較表の右端） | ここが本題。0 でないなら、この段を通過してはならない（下の中止条件） |
| **行き過ぎ** | 0〜数 % | 大きいなら `max_acceleration` が機構に対して過大。上げるのではなく**下げる**方向へ |
| **移動中のずれ最大** | §3-1 の 0.130mm と同じ桁 | 桁が違うなら §3-1 の `sync_kp` を実運用振幅で取り直す（プロファイル導入前の値である） |

**中止条件（この段で止めて、先へ進まない）**

- **飽和率が 10% を超える** —— プロファイルが機構の能力を超えている。`max_acceleration`
  を半分にして測り直す。ゲインを触ってはならない（飽和中は何を変えても応答が変わらない）
- **`sync_tolerance` 超過で緊急停止した** —— 速度・加速度ではなく左右の追従差の問題。
  §3-1 に戻って `sync_kp` を実運用振幅で取り直す
- **`timeout_s` 到達で失敗する** —— 起動時の検証（`_check_motion_timeout`）を通っている
  以上、プロファイルの所要時間の問題ではない。機構が引っかかっているか、片側が
  動いていない。**動かして直す段ではない**

### 手順 2. `max_acceleration` を上げる

```bash
uv run python scripts/tune_y_axis.py ... --amplitude 15 --dwell 3.0 \
    --max-acceleration 300,600,1000
```

**この軸は摩擦支配である。** 重い側の静止摩擦だけで 500counts 相当あり、質量を
加速するのに要る力はそれに比べて桁違いに小さい。したがって**制御側から見た余裕は
大きい**。効く制約は制御ではなく:

- **機構強度**（ラック・ピニオン・取り付け）
- **ワーク保持力**（グリッパ・吸着が加速度に負けて滑る / 落ちる）

**中止条件**

- **飽和率が上がり始めたら、その 1 つ手前を採る。** 飽和は「プロファイルが機構の
  能力を超えた」合図である
- **打音・振動が出たら止める。** 数字より先に耳と手で分かる。機構強度の限界は
  比較表には出ない
- **ワークが滑る・落ちる。** 保持力の限界。ここは制御では埋められないので、
  **加速度を下げる**のが正しい対処
- 行き過ぎが増える方向へ動いたら、それは加速度ではなく PID の問題（手順 4 へ）

### 手順 3. `max_velocity` を上げる —— **`velocity_ff` と `kd` は必ずセット**

```bash
# まず速度だけ
uv run python scripts/tune_y_axis.py ... --amplitude 15 --dwell 3.0 \
    --max-velocity 50,80
# 次に、その速度で velocity_ff を振る
uv run python scripts/tune_y_axis.py ... --amplitude 15 --dwell 3.0 \
    --max-velocity 80 --velocity-ff 0,1.0,1.6
```

**`kd` の単位は counts/(deg/s) なので、巡航速度がそのまま制動として出力に乗る。**
`kd`=1.0 で 50mm/s = 2750deg/s を出すと、**D 項だけで −2750counts** になり、
`output_limit` 2000 を超えて**逆向きに飽和する**。プロファイルで消したはずの飽和が、
速度を上げた途端に別の理由で戻ってくる。

定常追従では実測速度 ≒ 参照速度なので、**参照速度へ `kd` と同じ係数を掛けて足せば
その制動をちょうど打ち消せる**。これが `velocity_ff = kd` の根拠。

- **`max_velocity` を動かしたら `velocity_ff` と `kd` を必ず見直す。** 片方だけ動かすと
  巡航中に D 項が出力を食い潰し、**飽和率だけが上がって速くならない**
- 決まった値は **`config/main_hand.yaml` の `pid.kd` と
  `config/main_hand_positions.yaml` の `motion.velocity_ff` の両方**へ書く
  （2 ファイルにまたがるので、片方だけ直しやすい）
- **`velocity_ff` は UI から見えず、実行中に変更もできない。** 起動ログ
  （`台形プロファイル: … velocity_ff=…`）が今どの値で動いているかを知る唯一の経路

**中止条件**

- **巡航区間で飽和率が上がる** —— まず `velocity_ff` を `kd` と揃えたか確認する。
  揃っていて出るなら、その速度は `output_limit` に対して過大
- **止まり際の行き過ぎが増える** —— 減速そのものは加速度で決まるので、これは
  PID の追従の問題（手順 4）
- **異音・共振。** 手順 2 と同じく、数字より先に出る

### 手順 4. その状態で PID を再調整する

**プロファイル導入で問題の性質が変わっている。**

| | プロファイル前 | プロファイル後 |
|---|---|---|
| PID が見る入力 | 全ストロークぶんのステップ | **速度制限された中間目標との追従誤差**（数百 μm） |
| PID の仕事 | 飽和したバンバン制御をなだめる | **追従誤差を最小化する** |
| `kp` の意味 | 大きいほど早く飽和する | そのまま追従の硬さ |
| `kd` の意味 | 飽和中は出力に現れない | **常に効く**（`velocity_ff` と対で見る） |

したがって **§3-1 の値（kp 32 / ki 10 / kd 1.0）は出発点であって答えではない。**
同じ数字でも意味が変わっている。手順 1〜3 で軌道が決まってから、**同じ振幅・同じ
プロファイルのまま**ゲインだけを振ること。

```bash
uv run python scripts/tune_y_axis.py ... --amplitude 15 --dwell 3.0 --kp 24,32,48
```

- **一度に振ってよいのは 8 つのつまみのうち 1 つだけ**（ツールが拒否する）
- **左右は必ず同じ値に保つ**（追従特性が違うと左右が押し合う）
- 追従誤差の見積もりは**摩擦ぶんの 0.284mm 程度**、`output_limit` の 75% が余裕として
  残る計算。実測がこれと桁で違うなら、摩擦か `scale` の前提が崩れている

### 手順 5. 予告 —— 低速域のスティックスリップ

**これは観測ではなく予測である。出るかどうかは実機でしか分からない。**

この軸は静止摩擦が大きい（§3-1 の実測で重い側 500counts 相当）。プロファイルを
入れると**中間目標がゆっくり動く低速域ができる** —— 立ち上がりと止まり際である。
そこでは追従誤差が小さいので PID の出力も小さく、**電流が静止摩擦を超えられない**
可能性がある。症状は:

> **動かない → 誤差が溜まって急に動く → 行き過ぎる → また止まる** の繰り返し
> （スティックスリップ）。左右で静止摩擦が違うので、**片側だけに出れば
> `sync_tolerance` 超過として緊急停止に化ける**。

対抗手段は既に 2 つ入っている:

| 手段 | 現在値 | 効き方 |
|---|---|---|
| `ki` | **10**（`config/main_hand.yaml`） | **まさにこの役割。** 動かない側でだけ積分が育ち、静止摩擦を超えるまで電流を積む。§3-1 で「左右の非対称性に自動で追従する」として入れた項 |
| `velocity_ff` | **1.0**（`motion`） | 参照速度に比例した電流を**誤差が出る前に**乗せるので、止まっている時間そのものを短くする |

**それでも足りなければ静摩擦補償**（参照速度の符号に応じた定数電流を足す）を検討する。
**今回は入れていない。** 理由は 3 つ:

- **単位が counts** で、`motion` 節が持つ人間の単位（mm/s・mm/s²）と混ざる。
  同じ節に置くと「片方だけ人間の単位でない値」になり、`scale` を変えた日に
  黙って意味が変わる
- **必要性がまだ推測でしかない。** 上のとおり未観測であり、要らない機構を
  先に足すと「入っているのに効いているか分からない項」が増える
- **`ki` が部分的に代替している。** 静摩擦補償を足すなら `ki` との役割分担を
  決めてからでないと、両方が同じずれを埋めに行って押し合う

入れると決めたときは、**`ki` を下げることとセットで**評価すること。

### 決まったら

1. **値を config へ書き戻す** —— `config/main_hand_positions.yaml` の
   `axes.y_axis.motion`（3 値）と `config/main_hand.yaml` の `pid`。
   **`velocity_ff` と `kd` が同値であることを最後にもう一度確かめる**
2. `axes.y_axis.timeout_s`（4.0s）を実所要時間 + 余裕へ寄せる。
   速度を絞りすぎた設定は起動時に拒否されるが、**緩すぎる `timeout_s` は誰も咎めない**
3. ベンチ側（`config/bench/y_axis_tuning/`）の `output_limit` を 800 へ戻す
   —— 次に誰かが狭い可動範囲で回すときの歯止めである
4. **この節と §3-1 の「まだやっていないこと」、`docs/impl_plan.md` の未解決課題表を
   実測値で書き換える。** 「机上の計算値」という但し書きが残っていると、次の人が
   もう一度同じ測定をする

## 3-3. 2026-09-03 の机上ベンチ実測 —— プロファイルを入れて測った結果

**§3-2 の手順を机上ベンチで一度なぞった記録である。** 決まった値は
`config/bench/main_hand/`（測定当時のディレクトリ名は `m3508_edulite/`）に入れてあり、
**本番 `config/main_hand*.yaml` には持ってきていない**。

### 測定条件 —— この値をそのまま本番へ写してはならない

| | |
|---|---|
| 構成 | `config/bench/main_hand/`（測定時点は M3508 ×2 + EDULITE 05 ×2 のみ） |
| **機構** | **付いていない。左右の M3508 は直結しておらず、空回しである** |

**直結していないので、左右が押し合うことも連れ回すこともない。** §3-1 で見た

したがって**ゲインも加速度も、機構が付いたら測り直しになる**。ここで確かめたのは

### 決まった値

| 対象 | 変更 |
|---|---|
| `motors.y_axis_*.pid.kp` | 10.00 → **32.0**（左右とも） |
| `motors.y_axis_*.pid.ki` / `kd` | **3.57 / 1.35** で据え置き |
| `motors.y_axis_*.pid.integral_limit` | **200**（`output_limit` 1000 の 20%。`ki` がある以上必須） |
| `motors.y_axis_*.pid.output_limit` | **1000** で据え置き |
| `axes.y_axis.motion` | **新設。`max_velocity` 50.0 / `max_acceleration` 600.0 / `velocity_ff` 1.35** |

**`velocity_ff` は本番の 1.0 ではなく 1.35。** この config の `kd` が 1.35 だからで、
`velocity_ff = kd` の対応は config ごとに閉じている（本番から数値を写すと黙って崩れる）。

### `kp` 10 → 32（振幅 5mm、プロファイルあり、各 2 往復）

| | kp=10 | kp=32 |
|---|---|---|
| 整定 | **一度もしない** | 全 8 ステップで整定（0.23〜0.32s） |
| 定常偏差 | ±0.16〜0.40mm | ±0.002〜0.094mm |
| 行き過ぎ | 0.0% | 0.0〜0.7% |
| 飽和 | 0% | 0% |
| ずれ平均 | 0.154mm | 0.129mm |

**`kp` を 3.2 倍にしても飽和は 0% のままだった。** 飽和を恐れて上げられなかった
`kp` が、プロファイルによって上げられるようになった。

**`kp` が定常偏差に効いた本当の理由は摩擦である。** この軸の静止摩擦は実測
**900 counts 相当**（実電流 901 counts が流れているのに動かない周期があった）で、
それとつり合う偏差 `900 / kp / 55.0131` の内側ならどこでも静止できる：

```
kp=10 → 900 / 10 / 55.0131 = 1.64mm   ← この幅のどこでも止まれる
kp=32 → 900 / 32 / 55.0131 = 0.51mm
```

### `max_acceleration`（振幅 5mm、kp=32）

| a_max | 整定 | ずれ最大 | 飽和 | 行き過ぎ |
|---|---|---|---|---|
| 300 | 0.229s | 0.151mm | 0% | 0% |
| **600** | **0.176〜0.197s** | 0.138〜0.228mm | 1〜2% | 0% |
| 800 | 0.192s | 0.292mm | 3% | — |
| 1000 | **整定せず** | 0.345mm | 4% | 5.8〜6.1% |
| 1200 | 1.155s | 0.260mm | 4% | 9.0〜9.9% |

**800 にしても速くならず（0.192s vs 0.197s）、ずれだけ悪化する。**
1000 以上は飽和が増えた瞬間に行き過ぎが出て、整定はむしろ悪化する
——**速くしようとして遅くなる**。**制約は `output_limit` 1000 counts。**

**`max_velocity` は 5mm の移動では効かない。** 巡航に入る前に減速へ移る三角
プロファイルになり、ピーク速度は `sqrt(600 * 5)` = 54.8mm/s。
**短い移動で速度を決めているのは `max_acceleration` の方である。**

### プロファイルの有無（振幅 15mm、kp=32、同一機体での対照）

| | なし | あり |
|---|---|---|
| **左右ずれ 最大** | **1.342mm** | **0.223mm** |
| 左右ずれ 平均 | 1.224mm | 0.170mm |
| 行き過ぎ | 3.0〜7.4% | 0.7〜1.2% |
| 飽和 | 8% | 0〜2% |
| 実電流 | **1334 counts**（`output_limit` 1000 を超える） | 866 counts |
| 整定 | 0.286s | 0.337〜0.344s |

**最も重要な発見: 左右ずれが 6 倍違う。** 飽和中は左右ともフル電流で突っ走るので、
わずかな負荷差がそのままずれとして開く。**測定当時の本番の `sync_tolerance` は 2.0mm**
だったので、プロファイルなしの 1.342mm は当時の閾値では既に **67%** に達しており、
**直結した実機で負荷差が乗れば全体緊急停止が掛かる水準**だった。ここで発報しなかった
のは、ベンチの `sync_tolerance` が 10.0mm と緩かったからにすぎない。**現在は本番も
10.0mm へ緩めてあるため、同じ 1.342mm は 13.4% にとどまる** —— ただし機構が本番相当の
負荷・拘束を持つ以上、飽和で左右ずれが 6 倍に開くこと自体は変わらない。

整定だけはプロファイルなしが 0.06s 速いが、代償が「ずれ 6 倍・行き過ぎ 6 倍・
電流が上限超過」なので割に合わない。

### 効かなかったもの —— 次に測る人が同じ道を歩かないために

- **`integral_limit` を 200 → 500 へ上げても改善しなかった**（右の復路で定常偏差
  −0.194 → −0.444mm）。**ただしこの差は判断材料にならない。**
- **この機体は測定ごとのばらつきが大きい。** 同一条件の 4 ステップで定常偏差が
  **+0.170 / −0.005 / −0.194 / −0.240mm** とばらついた。200 と 500 の差はこの
  範囲内で、区別できない。**1 回の測定で判断してはならない。**
- ばらつきの原因は上の摩擦支配の性質そのもの（`900 / kp / 55.0131` の幅の
  どこでも静止できる）。**摩擦の効きを縮めたのは `ki` ではなく `kp` だった。**

### 残る制約と、未検証のもの

- **上限を決めているのは `output_limit` 1000 counts である。** `max_acceleration`
  600 が最良なのはこの上限の下での話で、**本番は 2000 なのでさらに上げられる余地が
  ある**。ただし**機構が付くと負荷が変わるので、必ず測り直すこと**（効く制約は
  制御側ではなく機構強度とワーク保持力へ移る。§3-2 手順 2 の中止条件）
- **`ki` は `kp`=10 時代の 3.57 のまま。`kp`=32 に合わせた再調整はしていない。**
  上のばらつきのせいで、1 回の測定では効いたかどうかを読めない
- **直結していない空回しでの値である。** 左右が押し合う条件も、片方が他方を
  連れ回す条件も、この測定には含まれていない（§3-1 の機構の性質は再現しない）
- **`sync_kp` は書いていない（既定の 0.0）。** 揃うべき前提が無い 2 台へ「平均へ
  引き戻す」補正を掛けても意味がないので、ベンチ側は 0.0 のままが正しい。
  したがって上の「左右ずれ」はすべて**補正なしの素の追従差**である（§3-1）

## 3-4. 2026-09-04 の実機実測 —— 実運用ストロークで 3.6 倍速くした

**§3-2 の手順を、機構が付いた実機で実運用ストローク（150mm）まで通した記録である。**
決まった値は `config/main_hand.yaml` と `config/main_hand_positions.yaml` に入っている。

### きっかけと、最初に外した前提

「遅すぎる、4 倍ほど速くしてほしい」という要求から始めた。**最初は振幅 15mm で測って
いたが、これは位置定数が 0〜15mm の仮値だったからで、実運用の移動距離ではない。**
実際は **150mm 以上が主で、15mm 前後も走る**。この違いで結論が変わる:

| 振幅 | 巡航が行程に占める割合（v=200 / a=1200） | 所要時間を決めるつまみ |
|---|---|---|
| 15mm | 0%（巡航に入らない三角プロファイル） | **`max_acceleration`** |
| 150mm | 94% | **`max_velocity`** |

**実運用はその両方を走るので、両方上げる必要がある。**

### 測定条件

| | |
|---|---|
| 構成 | 機構が付いた実機（左右の M3508 が直結） |
| ツール | `scripts/tune_y_axis.py`（今回 `--output-limit` を追加した） |
| 振幅 | 2 / 5 / 10 / 15 / 30 / 60 / **150** mm |
| `sync_tolerance` | 2.0mm（測定当時の本番値。本節の測定の直後に 10.0mm へ緩めた） |

`--amplitude` は `manual` の可動範囲でしか動かせないので、150mm を測るには
**`manual` を一時的に広げた位置定数を別ファイルに作って `--positions` へ渡した**
（本番 config は書き換えていない）。150mm が動くことは実機で確認済みだが、
**ストローク全長は測っていない**（§0 の可動範囲の実測は未了のまま）。

### 手順 1. 現状確認（変更前の基準値）

| 振幅 | 整定 | ずれ最大 | 飽和 | 行き過ぎ |
|---|---|---|---|---|
| 15mm | 0.420s | 0.166mm | 0% | 0.1〜0.6% |
| **150mm** | **3.023s** | 0.236mm | 0% | 0.1% |

**150mm で 3.023s は `timeout_s` 4.0 に対して余裕が 1 秒しかない。** これが
「遅すぎる」の実体だった。

### 手順 2〜3. 律速は `output_limit` だった

15mm で `max_acceleration` を上げると、a≥1200 で**指令が 2000counts に張り付いた**
（行き過ぎ 8→13%、飽和 2%）。`output_limit` を上げると飽和は消える:

| `output_limit` | 飽和 | 行き過ぎ | 整定 |
|---|---|---|---|
| 2000 | 2% | 10.8% | 0.177s |
| 4000 | 0% | 10.4% | 0.182s |
| 8000 | 0% | 10.9% | 0.166s |

**飽和は 4000 で消えるが、行き過ぎ 10% は `output_limit` を上げても変わらない。**
これは加速度ではなく PID 側の問題（§3-2 手順 4）で、`kd` と `velocity_ff` の対を
2.0 へ揃えると 10.7% → 5.1% に半減した。ただし立ち上がりが遅くなり整定は悪化するので、
**最終的には kd=vff=1.0 を採った。**

### 手順 4. `max_velocity` が長距離を決める（150mm）

| v | 整定 | 倍率 | ずれ最大 | 飽和 |
|---|---|---|---|---|
| 50 | 2.943s | 1.03x | 0.399mm | 0% |
| 100 | 1.478s | 2.04x | 0.603mm | 0% |
| **200** | **0.754s** | **4.01x** | 0.602mm | 0% |

**v=200 で目標の 4 倍にちょうど届いた。** モータ軸 1834rpm（出力軸 95.5rpm）で、
M3508 の定格 469rpm に対して 20% なので回転数側の余裕は大きい。

### 手順 5. `max_acceleration` は速さではなく滑らかさで決めた

「ガッと動いて振動する」ことを避けたいという要求があり、**加速度を落としても長距離の
損失は小さい**ことが実測で分かったので、滑らかさを優先した:

| a | 150mm | 15mm | ずれ最大（150mm） | 加速に掛かる時間 |
|---|---|---|---|---|
| 600 | 0.978s (3.09x) | 0.274s (1.53x) | 0.519mm | 0.333s |
| **1200** | **0.837s (3.61x)** | **0.243s (1.73x)** | 0.554mm | **0.167s** |
| 2400 | 0.779s (3.88x) | 0.191s (2.20x) | 0.691mm | 0.083s |
| 4800 | 0.755s (4.01x) | 0.160s (2.63x) | 0.690mm | 0.042s |

**4800 → 1200 で 150mm の所要時間は 1 割しか延びないのに、加速に掛ける時間は 4 倍に
なる。しかも左右ずれは減る。** 短い移動だけは素直に遅くなる（15mm で 0.160→0.243s）
ので、**短距離を優先したくなったらここを上げ直すこと**。

> **台形プロファイルは加速度がステップ状に変わる（ジャークが無限大）ので、
> `max_acceleration` を下げる以外に「ガッと」を消す手段が現状は無い。**
> 加速度を保ったまま滑らかにしたければ S 字（ジャーク制限）プロファイルが要るが、
> `lib/control/trajectory.py` の拡張になるので今回は入れていない。

### 手順 6. `sync_kp` は振幅で最適値が変わる

**§3-1 で決めた 8.0 は、150mm では最悪値だった。**

| `sync_kp` | ずれ最大 | ずれ平均 |
|---|---|---|
| 8 | 1.042mm（別の回では **1.899mm**。測定時点の `sync_tolerance` 2.0mm では 95%、現在の 10.0mm では 19%） | 0.680mm |
| **16** | **0.637mm** | **0.578mm** |
| 24 | 1.125mm | 0.682mm |

2 回の測定とも 16 が最良で再現した。**振幅 1.5mm で決めた値をそのまま長距離へ
持ち込んではならない**という実例である。

### `output_limit` は 5000 —— 余裕ではなく実測値

a=1200 まで落とすと指令ピークも下がるので、上限も取り直した:

| `output_limit` | 飽和 | ずれ最大 |
|---|---|---|
| 4000 | 1% | 0.693mm |
| **5000** | **0%** | **0.633mm** |
| 6000 | 1% | 1.925mm |

**必要以上に上げてはならない** —— 機構端に当たったときに押し込む力がそのまま増える。
`integral_limit`（20%）と `sync_limit`（25%）は比率で追従させて 1000 / 1250 にした。

### 決まった値と、最終確認（本番 config そのまま）

| 対象 | 変更 |
|---|---|
| `motors.y_axis_*.pid.output_limit` | 2000 → **5000** |
| `motors.y_axis_*.pid.integral_limit` | 400 → **1000** |
| `motors.y_axis_*.pid.kp` / `ki` / `kd` | **32 / 10 / 1.0 で据え置き** |
| `axes.y_axis.sync_kp` / `sync_limit` | 8.0 / 500 → **16.0 / 1250** |
| `axes.y_axis.motion.max_velocity` | 50.0 → **200.0** |
| `axes.y_axis.motion.max_acceleration` | 300.0 → **1200.0** |
| `axes.y_axis.motion.velocity_ff` | **1.0 で据え置き**（`kd` と同値） |

| 振幅 | 変更前 | 変更後 | 倍率 | 行き過ぎ | ずれ最大 | 飽和 |
|---|---|---|---|---|---|---|
| 15mm | 0.420s | **0.244s** | 1.72x | 3.4% | 0.225mm | 0% |
| **150mm** | **3.023s** | **0.838s** | **3.61x** | 0.4% | 0.706mm | 0〜1% |

モータ温度は一連の測定を通して 27→28℃ で、発熱側の余裕は大きい。

### 残っている未検証のもの

- ~~**ストローク全長を測っていない。** 150mm が動くことは確かめたが、`manual`
  （−2.0〜20.0mm）と `positions`（0〜15mm）は**仮値のまま**である。実運用の移動距離が
  150mm 以上なら、この 2 つは実態と食い違っている。§0 と §3-2 準備 1〜2 が未了~~ →
  **解消。** `manual` は 0.0〜650.0mm、`positions` は実測値（home 0.0 / work_1 120.0 /
  work_2 320.0 / work_3 520.0 / work_shared 650.0mm）へ更新済み（§1）
