## 何をしたいときにどれを読むか

| やること | まず読む |
|---|---|
| 画面にパネルを足す・並べ替える | `screens.md` → `pitfalls.md`（grid と flex） |
| 色・チップ・アイコン・ラベルを変える | `design.md` → `pitfalls.md`（daisyUI の対） |
| ボタン・ホットキーを足す | `design.md`（確認の取り方・EMG STOP の配置） |
| サーバーの配信を増やす・変える | `data_flow.md`（契約の再生成と両方向の突き合わせ） |
| 新しい状態表示を足す | `screens.md`（既に描かれていないか）→ `data_flow.md`（判定の置き場所） |
| 部品を新設する | `screens.md`（6 バケツのどこか）→ `design.md`（記号の衝突） |
| 接続先・開発サーバーの設定を触る（`?ws=` / `VITE_ALLOWED_HOSTS` / `DEV_WS_TARGET`） | `data_flow.md`（接続先の解決） |
| テストが落ちた・増やした | `pitfalls.md` |
| **試合当日に画面がおかしい** | **`docs/venue_recovery.md`（会場カード）** |

## 前提

すべての判断がここから出ている:

- 操縦者は**機体を見ている**。画面へ視線を戻すのは一瞬しかない
- 操縦者 2 名 + Monitor が**別ブラウザ・別 PC** で繋がる（正はサーバーが持つ）
- 機材は 1366×768 級のノート PC から 1920×1080 まで幅がある
- 会場にネットワークがある保証はない
- **機体が動くのは操縦者がボタンを押したときだけ。** UI は可否を決めず、送る前に理由を説明する

## 変更したら

**コードと文書は同じコミットで揃える。** ここに書いたパス・シンボル・数値が実在しなくなったら、
仕様書として信用されない。現況はこの束、理由は `docs/invariants.md` §8、経緯は `docs/history/` へ。

検証は `cd web && pnpm check`（ビルドまで含む）。配色とレイアウトはそれだけでは足りないので
`pnpm dev` で実描画も見る。**実描画がどう見えるかは `images/screens/`**（全 15 画面・1366×768・
`--dry-run`）。ASCII 図と食い違ったらどちらかが古い。
